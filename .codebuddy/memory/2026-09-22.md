## Git 安全边界（已向用户说明）
- 已 commit 的内容：对象进 `.git/objects`，后续删除/修改都不影响历史版本，可用 `git log -- <path>` / `git checkout HEAD~1 -- <path>` 取回
- 残余风险点（必须在常识上提醒）：本地未 push 时仓库物理损坏；`--force push` 或删远程分支；悬空对象（只 add 未 commit）会被 `git gc/prune` 在默认 90 天后回收；`.git` 被 rm
- 真正高危的始终是：**从未 add/add 后被 reset 出来的未跟踪文件**，`git clean -fd` 一次清空且无回收站

## 表盘开发可行性分析文档（docs/表盘开发可行性分析（讨论稿）.md）
- 用户提出 5 个问题：仓库位置、表盘开发能力、数据通讯、标准/高级版对接、屏幕兼容。
- 核心结论：
  1) **仓库**：建议独立仓库 —— 表盘 `.bin` 与快应用 `.rpk` 在技术形态/工具链/发布节奏三方面都不同；用文档共享「数据契约」而非共用仓库（契约基准 = `docs/import-export-json-format-analysis.md` 的格式 A：storage 键 `allCourses_N`，按 day 分组，time 为 `"HH:MM - HH:MM"`）
  2) **表盘能力**：能开发但受限。官方路径（小米运动健康表盘市场）门槛高；社区路径 = 米坛「表盘自定义工具」（包名 `tech.pingx.watchface`，支持手环 7~9Pro / 手表 S3/S4 / 红米手表 4/5），配置式 DIY（选底包 + 拖元素 → 生成 `.bin`），含"课程表小程序"；**官方未开放第三方表盘 SDK**；制作需米坛账号，安装需手表开发者模式授权码
  3) **通讯（最大风险）**：快应用侧有 `@system.storage` / `system.interconnect` / `$emit` / `@system.file`；但表盘是表盘引擎渲染的 `.bin`、与快应用沙箱隔离，**未检索到官方"表盘读快应用数据"能力** → 必须 PoC；三条候选路径 P1 表盘侧独立小程序 / P2 手机中转载入（AstroBox 有插件 SDK 通信描述）/ P3 表盘直读快应用存储（把握最低）
  4) **授权对接**：建议 S3「分发层区分」—— 表盘作为高级版专属下载物，表盘内部不做授权判断（避免依赖通讯）；后续再考虑 S1/S2
  5) **屏幕兼容**：快应用是"一包内部 `@media(shape:)` 自适应"（已验证 capsule 192×490 / rect 336×480 / circle）；**表盘大概率需按屏型分底包分别出包**（底包与机型绑定），需实测工具能否一工程多机型

## 表盘联动性与仓库结构深度分析（docs/表盘联动性与仓库结构深度分析.md）

## 独立课程表盘能力边界分析（docs/独立课程表盘能力边界分析.md）

- 边界澄清：表盘可"静态显示"课程，**绝不可**输入/编辑/删除/存储/实时同步；"要能输入能编辑的课程应用" = 快应用，不是表盘

## 表盘数据固化机制解析（docs/表盘数据固化机制解析.md）
- 用户追问 P1 的本质结构：表盘有没有存储？能不能显示自己的内容？

- 待实测：①工具能否添加自定义静态文字 ②是否支持多页/点击切换 ③"课程表小程序"是否即烤入文字的表盘 ④能否用 Mi-Create 等外部工具直接生成含自定义文本的 `.bin`（若可则 P1 可自动化，不必手工录课）

## 表盘能力修正：可按星期自动切换显示（已更新 docs/表盘数据固化机制解析.md）

- 做法：准备 7 组课程内容（周一~周日），绑定"星期"数据源 → 引擎按当天星期**自动选中对应那组** → "抬手即见今日课程，且每天自动变"

- 关键前提：底包/格式须支持"星期 → 自定义内容组"映射（课程表底包通常已内置；不支持则只能静态一页）→ **仍需实测**
- 本次改动：`docs/表盘数据固化机制解析.md` 新增「四·补、表盘其实可以"动态"」章节 + 能力矩阵加入 L1.5 层 + 修正零节结论表 / 第六节限制表 / 第七节边界
- 口径修正：从"表盘只能静态显示"→"**表盘 = 预设内容 + 可按星期/时间自动切换**"；限制仍在"内容不能自己变（无自定义数据源）"与"改课要重做"
