# 表盘数据固化机制解析 —— 表盘"能存吗、能显示自己的内容吗"

> 承接 `docs/独立课程表盘能力边界分析.md` 的 P1 路径（只读课程表盘）。
> 本文专门澄清一个核心概念：**P1 到底是什么结构？表盘有没有存储？能不能显示自己的内容？**
>
> 结论预告：**你的推测基本正确** —— 表盘**没有存储**，它是把课程"**写进文件**"里；表盘**能显示自己的内容**，但只能是**打包时写死的静态内容**。

---

## 零、直接回答（先给答案）

| 你的说法 | 判定 | 精确表述 |
|---|---|---|
| "这个表盘有文件格式" | ✅ 对 | 表盘是 `.bin` 资源包，有固定格式 |
| "先在手机里把表盘写到文件里" | ✅ 对 | 在手机侧工具里编辑 → 生成 `.bin` 文件 |
| "把自己的课程像什么课一样显示在表盘上" | ✅ 对 | 课程作为**文字/图片元素**被"烤"进表盘资源 |
| "它并没有什么存储，只是在文件里存入了它自己的课程" | ✅ **准确** | 这叫「**编译期固化（烤入）**」，**不是运行时存储** |
| "改课要重做" | ✅ 对 | 内容在文件里，手环上改不了 → 必须重新打包 + 重新安装 |
| "能结合日期/星期动态显示课程吧？" | ✅ **可以** | 预置 7 组内容 + 绑定"星期"数据源自动切换（详见第四节补充） |

**一句话**：**表盘像"印好的纸质课表"，快应用像"可擦写的白板"。** 前者一印定终身，后者随时可改。

## 一、P1 的完整结构（数据流）

```
        手机侧                                  手环侧
┌──────────────────────────┐            ┌──────────────────────────┐
│  表盘自定义工具（App）      │            │  表盘引擎                  │
│   ① 选底包（模板）         │            │   ① 读取 .bin 资源         │
│   ② 录入课程文字           │            │   ② 渲染图像 + 文字元素     │
│   ③ 拖拽/调整元素位置      │  蓝牙推送   │   ③ 显示（**只读**）        │
│   ④ 生成 .bin 文件 ────────┼───────────▶│                          │
└──────────────────────────┘            └──────────────────────────┘
            ▲                                        │
            │                                        │
            └──── 改课 = 回到①②重新做 + 重新安装 ──────┘
                   （手环上没有任何编辑入口）
```

**三个要点：**
1. **编辑只发生在手机侧**，手环侧只负责"显示"。
2. **数据在生成 `.bin` 时就固定了**，之后不会再变。
3. **改任何内容都要重走全流程**（重新生成 + 重新推送安装）。

## 二、`.bin` 表盘文件里到底有什么

表盘文件大致由以下部分组成（示意，具体字段以工具/格式文档为准）：

```
.bin 表盘文件
├── 元信息       机型、屏幕尺寸、预览图、版本
├── 图像资源     背景图、图标、字体图集（图片素材）
├── 布局定义     每个元素的坐标、大小、层级、样式（颜色/字体）
├── 静态文本元素  写死的字符串 ← ★ 课程就"烤"在这里
└── 数据源绑定    指向引擎白名单数据源（时间/步数/心率/天气…）
```

**关键**：课程内容落在「**静态文本元素**」（或干脆被做成图片）。它不是"数据槽"，而是"**排版素材**"——和背景图、图标是同级别的东西。这就是为什么手环改不了：**改文字等于改素材，只能重新生成文件。**

## 三、"没有存储"到底是什么意思

| 概念 | 定义 | 表盘 | 快应用 |
|---|---|---|---|
| **存储** | 运行时能**读写的容器**，应用自己可以改 | ❌ 无 | ✅ `@system.storage` |
| **固化（烤入）** | 打包时就确定的**常量**，装到设备上就固定 | ✅ 是这种 | — |
| 能否被 App 修改 | — | ❌ 不能 | ✅ 能 |
| 修改方式 | — | 重新打包 + 重新安装 | 应用内直接改 |

**所以你的理解是对的**：表盘不是"存"了课程，而是"**课程被固化在文件里**"。
"存储"意味着可读写、可变化；表盘的课程是**不可变的静态资源**。

## 四、表盘能显示"自己的内容"到什么程度（能力矩阵）

| 层级 | 能力 | 表盘是否支持 | 说明 |
|---|---|---|---|
| L1 | **静态文字/图片**（自定义内容） | ✅ **支持** | 课程名、时间、教室都可以当文字/图片放上去 |
| **L1.5** | **数据源映射：按"星期/时间"切换显示不同预设内容** | ✅ **支持** | ⭐ "按星期自动显示今日课程"就靠这一层，详见第四节补充 |
| L2 | **绑定系统数据源**（显示当前值） | ✅ 支持 | 时间/日期/步数/心率/电量/天气等（白名单） |
| L3 | **绑定自定义业务数据**（课程） | ❌ 不支持 | `sources.json` 白名单里没有课程这类字段 |
| L4 | **运行时读写自己的存储** | ❌ 不支持 | 无存储容器 |
| L5 | **实时更新 / 与外部同步** | ❌ 不支持 | 只能重新打包重装 |

**所以对"能不能展示自己的内容"的回答是：**

> **能展示"自己预设的内容"（L1）；能"按星期/时间自动切换"显示预设内容（L1.5）；不能展示"会随课程数据自己变化的内容"（L3~L5）。**

也就是说：**内容要你提前做好，但"每天自动翻到对应那一份"是引擎自带的。**

## 四·补、表盘其实可以"动态"—— 按星期显示课程可行吗？

**结论：可以。** 这是对前面"静态"结论的重要补充：表盘的内容是**预设**的，但"**显示哪一组预设内容**"可以是**动态的**。

### 原理：数据源映射（社区说的"切图"机制）

表盘的显示逻辑，本质是「**数据源 → 内容组**」的索引：

```
        数据源（引擎提供）            显示的内容
      ┌──────────────┐        ┌────────────────────┐
时钟   │ 当前"分钟"值   │ ─────▶ │ 0~9 数字图集        │
星期   │ 当前"星期"值   │ ─────▶ │ 周一~周日 星期图/文字 │
天气   │ 当前"天气"状态 │ ─────▶ │ 晴 / 阴 / 雨 图标    │
      └──────────────┘        └────────────────────┘
```

时钟和星期之所以能"变化"，就是因为格式支持"**用数据源的值去索引一组预设内容**"。社区表盘常被形容为"切图较多、表盘文件大于 3M"，说的正是这种图集机制。

### 课程怎么接上去

**复用"星期"这个已有数据源，把课程做成"按星期索引的内容组"：**

```
星期数据源 = 星期二
        │（索引）
        ▼
内容组[2] = "今日课程：数学 / 英语 / 物理"
        │
        ▼
表盘显示周二的课
```

**做法**：
1. 在表盘工具里准备 **7 组课程内容**（周一到周日各一组，做成文字或图片）；
2. 把它们**绑定到"星期"数据源**，每组对应一个星期值；
3. 表盘运行时，引擎按当天星期**自动选中对应那组**。

效果就是"**抬手一看是今天的课表，而且每天自动变**" —— 正如你所设想的。

### 前提与限制

| 项 | 说明 |
|---|---|
| **关键前提** | 底包/格式必须支持"**星期 → 自定义内容组**"的映射。若是"课程表底包"通常已内置；若不支持，就只能做静态一页 |
| 内容仍是预设的 | 7 组内容是**提前做好的**，"动态"只体现在**选中哪一组** |
| 改课仍需重做 | 改了课 = 重做那一组内容 + 重新安装（**不会自动同步**） |
| 容量有限 | 一天内容要塞进一屏（如 192×490），通常几行；放不下就得分页 |
| 可扩展 | 同理可用"时间"数据源做"上午/下午切换"、"工作日/周末切换" |

### 一句话

> **表盘不是"死"的，它是"7 张牌摊在那儿，每天自动翻一张"。**
> 牌面要你提前印好，但**翻牌这件事是自动的**。

## 五、关键旁证："电子书表盘"

社区有一个广为流传的玩法：**把 TXT 文本同步进自定义表盘，手环上就能翻页阅读**。公开描述里有一个非常准确的说法：

> "它**并不是 App**，而是一个**内置文字载体的特制表盘**，这也正是它能够在系统限制下运行的原因。"

这段话印证了本文的全部判断：

- 表盘**可以被当作"文字载体"**（L1 能力的极致应用）；
- 它**伪装成表盘**才能在系统限制下运行（说明表盘引擎不允许真正的应用逻辑）；
- 内容来自**打包时写入的文本**，而不是运行时读取。

**推论**：所谓"课程表小程序"，本质就是**把课表文字烤进表盘**的一种特制表盘，与"电子书表盘"是同一套路子。

## 六、这样做的真实体验与限制

| 维度 | 现实情况 |
|---|---|
| 改课 | **必须回手机重新制作 + 重新安装**，改一节自习课也一样 |
| 数据来源 | 只能在表盘工具里**再录一遍**，与 Ev课程表**不互通** |
| 显示空间 | 表盘尺寸有限（如手环 9 为 192×490），一周课表大概率放不下 → 用"**按星期自动切换**"（每天只显示当天）最合理 |
| 翻页/多页 | 是否有"点击切换页面"能力**需实测**（社区表盘有分页先例，但需确认工具支持度） |
| 自动跟随日期 | ✅ **可以**：预置 7 组 + 绑定"星期"数据源即可（见第四节补充） |
| 与快应用联动 | ❌ 无通道（详见联动性分析文档） |
| 授权控制 | 只能在**分发层**控制（谁能下载表盘），表盘内部无法判断授权 |

## 七、最终边界（能做什么 / 不能做什么）

**✅ 能做的**：
- 做一个表盘，显示"今日课程"，并**按星期自动切换**（预置 7 组内容 + 数据源映射）
- 用表盘工具在**手机侧录入**课程内容（7 天各录一份）
- 把它作为**高级版专属装饰**分发

**❌ 不能做的**：
- 在手环上**输入 / 编辑 / 删除**课程
- 让表盘**存储**课程并在以后读取
- 让表盘**内容自动更新**（课程改了，表盘不会跟着变，必须回手机重做）
- 让表盘读取 **Ev课程表** 的数据

**一句话**：**"把 7 天课程印在表盘上、每天自动翻页"可以；"让表盘管理课程"不行。**

## 八、待验证（建议实测）

1. **表盘工具能否添加自定义静态文字**（而非只能绑定数据源）—— 决定 L1 是否成立。
2. **是否支持多页 / 点击切换**—— 决定一张表盘能放多少课程。
3. **"课程表小程序"是否就是"烤入文字的表盘"** —— 验证它与"电子书表盘"是否同源。
4. **能否用外部工具（Mi-Create 等）直接生成含自定义文本的 `.bin`** —— 若有，则 P1 可自动化，不必手工在做工具里录课。
