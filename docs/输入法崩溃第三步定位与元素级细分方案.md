# 第 3 步崩溃 —— 定位结论、元素级细分方案与二维码信息收集

> 日期：2026-09-25
> 实测结果：**第 1 步（并发写 ×5）通过、第 2 步（并发读 ×7）通过、第 3 步（建键盘，不加载词典）崩溃**
> 本文回答三件事：①这条结果排除了什么、锁定了什么；②下一步怎么把范围缩到"具体哪种 UI 元素"；③底部二维码要不要加、加哪些字段、怎么控长度。

## 一、这条结果把范围缩到了很小

### 1.1 被排除的假设

| 假设 | 判定 | 依据 |
|---|:---:|---|
| **W3 并发 storage I/O** | ❌ **排除** | 第 1 步（5 次并发写）、第 2 步（7 次并发读）**全部通过**，存储层没问题 |
| **W4 词典内存 OOM** | ❌ **排除** | 第 3 步传的是 `dictlazy=true`，**根本没有加载词典**就崩了 |
| **W1 单帧阻塞（看门狗）** | ❌ **排除** | 词典分片修复在本次包内，且第 3 步不加载词典；崩的是纯 UI 渲染 |
| **W2 `progress type="arc"`** | ⚠️ **基本排除** | 诊断页是在移除 arc 之后构建的（`975f2b0` 早于 `faaff14`），**移除 arc 后第 3 步仍然崩** → arc 不是（唯一）元凶 |

### 1.2 锁定范围

> **真凶 = 胶囊（pill-shaped）分支「键盘 UI 的渲染本身」，与存储、词典都无关。**

这是本次分析最重要的收获：**之前三个方向全错了**，问题一直在"渲染键盘 UI"这一层。

### 1.3 pill 分支里到底有什么

第 3 步渲染的 `src/components/InputMethod/InputMethod.ux:234+`（pill 分支）构成如下：

| 元素 | 数量 | 关键样式/属性 |
|---|:---:|---|
| `<text class="calbtn66">` 按键 | **26 个**（10+9+7） | `width/height:60px`、`border-radius:30px`、`border:3px solid rgba(255,255,255,0.06)`、`font-size:32px`、`font-weight:bold`、背景 `#262626` |
| `<img>` 键盘区 | 1 张（`arc/space.png`） | 60×60 |
| `<img>` 候选/功能区 | **6~7 张**（`search.png` / `{{lang}}.png` / `back2.png` / `123.png` / `bigA.png` / `a.png` / `del.png`） | 42~186px 不等 |
| `<scroll scroll-x>` | **2 个**（`keyboard66` 键盘区 + `cvalWaiting` 候选区） | 横向滚动，带 `padding-left/right: (screenWidth-192)/2` |
| 容器 | 3 层 | `width:100%;height:305px` + 内层 `position:absolute` |

### 1.4 嫌疑排序（第二轮要验的就是这几条）

| 编号 | 嫌疑 | 理由 |
|:---:|---|---|
| **S1** | 26 个 **带圆角 + 3px 描边**的 `<text>` | Vela 对 `border-radius` + `border` 组合在 text 上的渲染支持历来可疑；26 个同屏渲染，成本与兼容性风险都最高 |
| **S2** | **7~8 张 PNG 图片** | 图片解码/显存占用；`docs/inputmethod-png-lab-page-analysis.md` 早已提示过 PNG 键盘的资源开销 |
| **S3** | **2 个嵌套的 `scroll-x`** | 横向滚动容器在窄屏上的虚拟化布局风险 |
| **S4** | 大量 `position:absolute` 堆叠 | 与 S3 叠加时容易算错可视区 |
| **S5** | 固定 `height:305px` | 在 490 高屏上本就紧张（次要） |

## 二、第二轮：元素级细分（一次装机继续榨）

不再依赖 `InputMethod` 组件，而是**在诊断页内直接构造 DOM**，逐个隔离上面 5 条嫌疑：

| # | 构造内容 | 隔离目标 | 崩了说明什么 |
|:---:|---|---|---|
| **A** | 26 个**纯 `<text>`**（只有 `font-size`，无尺寸/边框/圆角/背景） | 纯文本节点数量 | 节点数量本身超限 |
| **B** | 26 个 `<text>` + `60×60 尺寸 + border 3px + border-radius 30px + 背景色`（复刻 `.calbtn66`） | **S1 圆角描边样式** | **样式是元凶** |
| **C** | 1 个 `<scroll scroll-x>`，内含 3 排纯文本 | **S3 横向滚动容器** | scroll 是元凶 |
| **D** | 只放 8 张 `arc/` 下的 `<img>` | **S2 图片** | PNG 是元凶 |
| **E** | 复刻 pill 键盘的**绝对定位堆叠**（无 PNG、无 scroll、无圆角） | **S4 绝对定位** | 定位方式是元凶 |
| **F** | 完整 pill 键盘（现状，作对照） | 组合确认 | 用于确认"去掉某元素后确实不崩" |

**执行方式**：同样保留"一键跑全部（A→F）"+ 单步按钮 + 崩溃点落盘。每步之间留 800ms。

**为什么这样设计能一次定案**：A 不崩而 B 崩 → 就是圆角描边；A/B 不崩而 D 崩 → 就是 PNG；以此类推。理论上**一次装机、一次崩溃**就能拿到答案。

## 三、二维码：建议加，但必须做"精简 + 分层"

### 3.1 结论：要加，理由是省掉反复追问

用户在真机上，开发者看不到设备。一次崩溃后，只要用户**用手机扫一下、把地址栏 URL 发过来**（或截图），开发者就能同时拿到：设备标识、装机版本、屏型、崩溃在第几步、已通过哪些 —— 省掉至少 3 轮沟通。

### 3.2 但现有激活 URL 有两个问题

1. **信息不够**：只有设备与版本，没有"崩溃/通过"这类诊断结果；
2. **长度受限**：二维码要显示在小屏上，密度太高手机扫不出来（激活页已有 `>200 字符` 就降级的逻辑）。

### 3.3 字段设计（新增只用 1 个字母，避免与现有冲突）

现有参数：`m` model · `p` product · `o` osVersionCode · `v` platformVersionCode · `t` deviceType · `s` screenShape · `w`/`h` 宽高 · `a` APILevel · `l` language · `r` versionName · `c` channel

**新增：**

| 参数 | 含义 | 示例 | 长度 |
|:---:|---|:---:|:---:|
| `dg` | 诊断结果：**崩在第几步 . 已通过步骤** | `dg=3.12`（崩第 3 步，通过 1、2） | ~8 字符 |
| `kb` | 键盘渲染分支（p=pill / r=rect / c=circle） | `kb=p` | ~4 字符 |

`dg` 是本次最有价值的补充 —— 它把"用户口述的现象"变成"结构化结论"。

### 3.4 长度控制：分两档

| 档位 | 内容 | 预估长度 | 用途 |
|:---:|---|:---:|:---:|
| **完整版** | 现有全部参数 + `dg` + `kb` | ~210 字符 | 信息全，但二维码密，小屏可能难扫 |
| **精简版（推荐默认）** | `deviceId` + `r`(版本) + `s`(屏型) + `w`/`h` + `dg` + `c`(渠道) | **~110 字符** | 密度低、192px 屏也能稳定扫出 |

精简版示例：

```
https://app-auth.gudq.com/activate.html?deviceId=uuid-e45fc19c01bdbb38270eaad9b3a61fb5&r=1.6.105&s=pill-shaped&w=192&h=490&dg=3.12&c=t-9p-d
```

**取舍说明**：精简版砍掉的是 `m`（恒为 `ap`，无信息量）、`p`（设备名最长但可从 deviceId/s/h 反推）、`o`/`v`/`a`/`t`（同一机型基本一致，优先级低于"崩在哪一步"）。保留的 5 项是定位问题的最小充分集：
- `deviceId` → 哪台设备
- `r` → **装机版本**（上一轮就是栽在分不清版本上，性价比最高）
- `s` + `w`/`h` → 屏型与分辨率（本次问题与屏型强相关）
- `dg` → **崩溃步骤 + 已通过**（结论本身）
- `c` → 渠道

### 3.5 其它注意

- 二维码用 Vela 原生 `<qrcode>` 组件（项目已在激活页/二维码生成器中使用，无需第三方库）；
- 二维码**只在有诊断结果时显示**（`dg` 非空才渲染），避免空白二维码干扰；
- 同时在二维码下方**以纯文本显示同一串参数**，万一扫不出还能手抄/口述；
- 服务端无需新增页面：沿用 `/activate.html` 域名即可，未识别参数会被忽略，开发者从地址栏取 URL 自行解析。

## 四、判读与修复预案

| 第二轮结果 | 结论 | 修复方向 |
|---|---|---|
| A 崩 | 节点数量超限 | 减少同屏节点（分页/虚拟化） |
| **B 崩（A 不崩）** | **圆角描边样式** | 去掉 `border`/`border-radius`，改用纯色块或图片背景 |
| **C 崩** | **横向 scroll 容器** | 改为非滚动分行布局，或去掉嵌套 scroll |
| **D 崩** | **PNG 图片** | 精简/复用图片，或改为纯文字键盘 |
| **E 崩** | **绝对定位堆叠** | 改为 flex 流式布局 |
| 只有 F 崩 | 组合因素 | 按 6.2 结构性重构：pill 分支改为 flex 相对布局 + 高度自适应 |

> 补充：`docs/inputmethod-png-lab-page-analysis.md` 早已给出"建议优先使用纯文字版输入法"的结论；若 D 命中，这正好是该结论的实证支持。

## 六、直接修复：胶囊屏键盘改为极简实现（已应用）

考虑到用户测试机会有限，不再走"再测一轮再修"的循环 —— **一次性把第 3 步里所有可疑元素全部去掉**，让这一版大概率直接修好。

### 6.1 改了什么（pill-shaped 分支整段重写）

| 原实现 | 新实现 |
|---|---|
| 7~8 张 `arc/` PNG（含**带变量的路径** `{{lang}}.png`） | **全部移除**，功能键改为纯文字（中/En、123、空格、删除） |
| 26 个 `.calbtn66`：`60×60` + `border:3px` + `border-radius:30px` | 纯色块 `<text>`：`40×44`，**无描边、无圆角** |
| **2 个** `scroll-x`（键盘区 + 候选区） | **只留 1 个**（键盘区）；候选行改为固定 4 个横排，不用 scroll |
| 3 层 `position:absolute` 堆叠 + `static` 标记 | 纯 flex 流式布局 |
| 固定 `height:305px` | **自适应**，实测约 **254px**（原 305 + 28 拼音行 = 333） |

### 6.2 顺带解决的老问题

高度从 333px 降到约 254px，**之前分析的"竖直空间不足"也一并解决了**（手环 9 可用高度约 292px，现在有富余）。

### 6.3 保留的能力

打字、候选选择、删除、空格、数字/符号切换、中英切换 —— 功能不减。
英文大小写切换按钮因 192px 宽度放不下而省略，默认小写输入（如需可后续补在第二行）。

### 6.4 唯一保留的可疑项

**1 个 `scroll-x`**：QWERTY 三排在 192px 宽屏上必须横向滚动才能保住可点键宽（40px）。
`scroll` 是全项目最通用的组件（首页、设置页等大量使用），且第一轮第 1、2 步证明页面基础渲染正常，故判定风险最低、予以保留。

### 6.5 如果这一版仍然崩

说明元凶就是 `scroll-x` 或更底层的布局能力，届时方案是：**改为 T9 九宫格布局**（3 列 × 4 行，每键约 60×48，192px 宽完全可以静态排布，**彻底不用 scroll**）—— 组件已有 `keys.t9` 数据与 `keyboardtype="T9"` 支持，只需放开 `onSelect` 中"胶囊屏不走 T9"的限制。这条已记为下一步预案。
