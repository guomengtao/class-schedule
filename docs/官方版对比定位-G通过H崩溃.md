## 三、首要嫌疑：`$watch("screentype", "adjustScreenWidth")`

官方版 `onInit` **只有 3 个 watch**：

```javascript
    this.$watch("hide", "watchHidePropsChange");
    this.$watch("maxlength", "watchMaxLengthPropsChange");
    this.$watch("keyboardtype", "watchKeyboardTypePropsChange");
```

我们**多加了第 4 个**：

```javascript
    this.$watch("screentype", "adjustScreenWidth");   // ← 官方没有这一行
```

### 3.1 为什么它能致崩（机制解释）

1. `onInit` 里**已经**有一次 `adjustScreenWidth()`（`if (screentype === 'rect' || 'pill-shaped')` 分支）→ 第 1 次 `device.getInfo`；
2. 紧接着注册 `$watch("screentype", "adjustScreenWidth")` —— **若框架在注册时用当前值立即回调一次**，就会**再触发一次** `adjustScreenWidth()` → **第 2 次 `device.getInfo`**；
3. `adjustScreenWidth` 的 `success` 回调里修改 `self.screenWidth` 与 `self.l66DownPanelWidth` → **data 变更**；
4. 这一变更发生在**组件首次渲染 pill 键盘（26 个描边圆角按键 + 8 张图片）的同时** → **渲染重入 / 竞态** → 表现为**"卡很久 → 看门狗复位"**。

### 3.2 为什么它"看起来无害"

- 它只是一行 watch 注册，静态阅读完全看不出问题；
- 官方用 `watchHidePropsChange` 这类**专门的、轻量的** watch 回调；而 `adjustScreenWidth` 是**会发起异步设备调用并修改 data 的业务方法**，把它直接当 watch 回调用，是**用法上的越界**。

## 四、修复方案

### 方案 A（最小改动，推荐先做）：删掉那一行

```javascript
    this.$watch("screentype", "adjustScreenWidth");   // 删除
```

**理由**：
- 官方本就没有它 → 删除 = **回到官方行为**，零副作用；
- 屏型变化时的重新适配，`onInit` 里那一次 `adjustScreenWidth()` 已覆盖（`chinese-input.ux` 的 `screenType` 是异步回填的，组件收到新值时会**重新走 `onInit` 的判定路径**或由页面侧重新渲染，不需要额外 watch）。
- 改动仅 1 行，**不影响外观、不影响其它屏型**。

### 方案 B（兜底，百分百有效）：正式组件直接换成官方版

**G 已经在真机验证通过**，因此这条路是**确定可行**的。代价是会把官方的原始特征带回来：
- pill 的 `progress type="arc"` 弧线（视觉上多一条进度弧）
- 下展面板（更多候选项能力）
- 与我们定制的少量差异

### 执行顺序建议

1. **先做方案 A**（删一行）→ 让用户测 **F 项**；
   - F 通过 → 找到真凶，收工（改动最小、外观不变）；
   - F 仍崩 → 说明还有第二个致崩点，**立即切方案 B**（换官方版，已验证可行）。
2. 两种情况下都建议顺带回归：设置 → 昵称 → 真实输入页。
