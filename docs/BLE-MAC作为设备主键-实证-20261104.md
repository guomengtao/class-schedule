# BLE MAC 作为设备主键：可行性实证

> 2026-11-04 · 承接《设备ID为什么取不到-手环9分析-20261104.md》
> 结论先行：**设备内取不到任何硬件 ID，但 BLE 层的 MAC 是固定、可读、重置不变的，并且已经在我们自己的同步器代码里被使用。这是唯一同时满足「重装不变 + 重置不变 + 能区分新设备」的标识。**

---

## 一、执行记录（失败项与替代路径）

| 步骤 | 命令 | 结果 |
|---|---|---|
| 扫描附近设备 | `band-ble/scan.py`（bleak） | `EXIT=134`（SIGABRT） |
| 直连枚举 GATT | `band-ble/connect.py` | 同样 abort，无任何输出 |
| 崩溃栈 | `faulthandler` | 停在 `CoreBluetooth._CoreBluetooth`，`asyncio.run` 内 |

**原因判定**：macOS 对未授权进程调用 `CBCentralManager` 不抛异常而是直接 abort。宿主进程（WorkBuddy / 终端）未获蓝牙隐私授权，Python 子进程无法继承该权限，非沙箱运行同样 abort。

**替代路径**：`system_profiler SPBluetoothDataType` 走 IOBluetooth 系统通道，不经过 CoreBluetooth 授权层，成功拿到结果——而且信息量比预期更大。

**仍未取到**：GATT `0x180A` 设备信息服务的特征清单（`0x2A25` Serial Number 是否存在）。需要给宿主进程授蓝牙权限，或接真机 Android 用 `BandAuthProbe` 跑。

## 二、关键实证：MAC 是固定公共地址

`system_profiler SPBluetoothDataType` 输出（2026-11-04 20:57）：

```
Connected:
    Xiaomi Smart Band 9 B885:
        Address: 04:34:C3:06:B8:85
        Minor Type: Watch
        RSSI: -44

Not Connected:
    Xiaomi Smart Band 10 Pro 3ADC:
        Address: 20:25:CC:80:3A:DC
        Minor Type: Watch
```

### 2.1 地址类型判定

| 判断点 | 值 | 含义 |
|---|---|---|
| 首字节 | `0x04` = `0000 0100`，最低两位 `00` | **公共地址（Public Address）** |
| 反例：RPA | 最低两位 `01`（`0x40` 段） | 会周期性轮换 |
| 反例：Static Random | 最高两位置 `11`（`0xC0` 段） | 开机重生成 |
| OUI 归属 | `04:34:C3` = Xiaomi Communications | 出厂烧录，非临时地址 |
| 第二台设备 | `20:25:CC` 同为小米 OUI，首字节 `0x20` 低两位 `00` | 同样为公共地址，规律一致 |

**结论：这是烧在 BLE 控制器里的公共地址，恢复出厂设置、卸载重装应用、更换手机都不会改变。**

### 2.2 附带发现：广播名内嵌 MAC 后 4 位

```
"Xiaomi Smart Band 9 B885"        ← MAC 04:34:C3:06:B8:85 的后 2 字节 B8 85
"Xiaomi Smart Band 10 Pro 3ADC"   ← MAC 20:25:CC:80:3A:DC 的后 2 字节 3A DC
```

小米自己在广播名称里公开了 MAC 的后 4 位十六进制。这条规律有两个用途：

1. 手机端 App 即使不给 `BLUETOOTH_SCAN` 的地址访问，也能从名字里读出 16 bit 的设备区分位；
2. 它证明小米并不把 MAC 当作需要隐藏的敏感信息——**这是平台层面的事实性许可**。

## 三、三种标识的能力对比

| 标识 | 重装快应用 | 恢复出厂 | 区分新手环 | 换手机 | 谁有权读取 |
|---|---|---|---|---|---|
| 本地随机 UUID（现状） | ❌ 变 | ❌ 变 | ✅ | ❌ 变 | 快应用自己 |
| 系统 DID（9/9 Pro 缺失） | ✅ | ❌ 变（KVDB 属性被清） | ✅ | ✅ | 需 authcode，第三方无 |
| 系统页 6 位短 ID | ✅ | ❓ 待测 | ✅ | ✅ | 仅用户肉眼 |
| **BLE MAC** | ✅ **不变** | ✅ **不变** | ✅ **不同** | ✅ **不变** | 手机端 App |

三条硬需求（重装不变 / 重置不变 / 区分新设备）只有 MAC 全部满足。

## 四、为什么之前没想到

`band-ble/connect.py:7` 里写着：

```python
BAND_MAC = "04:34:C3:06:B8:85"
```

`docs/小米手环Ble握手分析-Mac直连方案.md:35` 也已经用它做设备占用判断：

> 如果手机上的小米运动健康或 BandAuthProbe 正连着 `04:34:C3:06:B8:85`，Mac 扫描不到它（不广播）。

**这个地址从头到尾都在被使用，只是从未被当作「设备身份」存下来。** 同步器连设备靠它，业务侧却另起一套随机 UUID 做设备绑定——两套代码对「设备是谁」的定义不一致，这才是问题的根源。

## 五、落地架构

```
快应用（设备内）                      手机端 App（有 BLE 权限）
  激活请求 ──IPC──> 扫描/读取已连接设备
                    ├─ 广播名 "Xiaomi Smart Band 9 B885"
                    └─ MAC   "04:34:C3:06:B8:85"
  <──IPC── 回传 MAC
  上报服务端：device_key = MAC（规范化大写去冒号）
```

- **主键**：MAC（12 位十六进制，可用 `0434C306B885`）
- **辅助**：广播名后缀 4 位（可用作人工核对码，用户能自己看见）
- **保留**：本地 UUID 降级为「安装实例 ID」，仅在无 App 场景兜底
- **服务端**：`MAC → 授权记录`，同一 MAC 重装/重置后自动同源，无需迁移逻辑

### 关键实现点

1. **不依赖扫描**。手环被小米运动健康连接时**不广播**，扫描会扫不到。应优先用 `BluetoothAdapter.getRemoteDevice()` / 已连接 `BluetoothGatt.getDevice().getAddress()` 读取，连接态下地址始终可取。
2. **Android 12+ 权限**：`BLUETOOTH_SCAN` + `BLUETOOTH_CONNECT`，并声明 `android:usesPermissionFlags="neverForLocation"`，否则部分机型返回脱敏地址。
3. **iOS 不可行**：iOS 自 7.0 起不向第三方暴露 MAC，会返回随机 UUID。若将来支持 iOS，需退回「账号 + MAC 双轨」。

## 六、边界与风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 手环换主人（二手） | MAC 不变，仍是旧记录 | 主动「解绑」流程；或新主人用新激活码时提示「该设备已被占用，申请转移」 |
| 用户换手环 | MAC 变，识别为新设备 | 正常激活流程即可，这正是期望行为 |
| Android 返回脱敏地址 | 拿到 `02:00:00:00:00:00` 或随机值 | 检测到固定脱敏值即降级，不写入主键 |
| 无手机 App 场景 | 拿不到 MAC | 退回本地 UUID + 现状迁移机制 |
| MAC 可被伪造/克隆 | 高级作弊者可复制地址 | 属风控层问题，非绑定层；本方案已优于现状 |

## 七、待验证项（两项，决定最终形态）

1. **GATT `0x180A` / `0x2A25`（Serial Number）是否存在且非空**
   需要给宿主进程授蓝牙权限后重跑 `connect.py`。若序列号存在，则 MAC + 序列号双因子，抗克隆能力显著提升。

2. **Android 端读到的 MAC 是否与 macOS 一致**
   用 `EVSyncProbe` 连接后打印 `getAddress()`，与 `04:34:C3:06:B8:85` 比对。一致即可确认跨平台同源，主键方案成立。

> 第 2 项是方案成立的必要条件，第 1 项是增强项。**建议优先做第 2 项。**

## 九、安卓同步器的取 ID 通道（补充排查）

排查 `ev-schedule-android/apk`（包名 `com.application.watch.classschedule`）后，发现三件事：

### 9.1 App 自身不碰蓝牙

`grep BluetoothAdapter` 全库零命中。App 走的是小米 interconnect 通道（`libs/xms-wearable.jar`），蓝牙由手机系统层处理。**因此「同步器能读 BLE」的假设不成立——那是 Mac 上的 `band-ble/connect.py`（bleak 直连），不是安卓 App。**

### 9.2 `Node` 对象是有效的识别入口

反编译 `xms-wearable.jar`：

```java
public class com.xiaomi.xms.wearable.node.Node {
    public java.lang.String id;
    public java.lang.String name;
}
```

`SyncEngine.java:190` 取 `nodeId = d.id`。而 `name` 是设备广播名，形如 `Xiaomi Smart Band 9 B885`——**内含 MAC 后 4 位**（与第二节的广播名规律一致）。

结论：安卓侧确实有一条**独立于快应用**的识别通道，包含 `id` 与含 MAC 后缀的 `name`。但 `id` 的生成方式（是否等于 MAC、是否跨重置稳定）需真机验证。

### 9.3 现有的设备 ID 缓存机制仍在快应用通道上

`SyncEngine.cacheDeviceId()`（第 514-537 行）通过 interconnect 向手环发 `get_device_id`，回包里取：

```
deviceId   / deviceId4 / fallback
```

`fallback=true` 即手环侧走了随机 UUID 兜底。**这条链路本质仍是「让快应用去取」，9/9 Pro 上必然返回 NA → fallback**。所以它不能解决根本问题，只是把结果搬到了手机端。

### 9.4 nodeId 验证的前置条件

interconnect 要求手机已通过**小米运动健康**与手环完成配对。当前测试机为华为 BLN-AL20 / Android 8.0，未安装小米运动健康，故 `nodeId` 无法现取。

验证方法：配对后打印 `SyncEngine.getNodeId()` 与 `currentDeviceId()`，与 `04:34:C3:06:B8:85` 逐一比对；再恢复出厂手环后重取，观察是否变化。

### 9.5 真机实测：卡在「穿戴服务组件缺失」（2026-11-04 21:17）

设备：华为 BLN-AL20 / Android 8.0.0（`adb` 序列号 `BTF4C17222009588`）。安装 `EVSyncProbe-v0.5.173.apk` 后在调试页执行四步自检，结果：

```
第 1 步 初始化穿戴服务   ✗ 失败
    手环未在本机配对
    小米穿戴服务不可用 —— 确认已安装并更新到新版，再回来重试
第 2/3/4 步              — 待执行（被第 1 步阻断）
```

**逐层排查结论：**

| 检查项 | 结果 |
|---|---|
| 手环是否已与本机配对 | ✅ 已配对。`com.mi.health`（小米运动健康 3.59.1）设备页显示 `Xiaomi Smart Band 9 NFC · 已连接 · 电量 78%` |
| 第三方 interconnect 服务端 | ❌ `com.xiaomi.wearable` **未安装** |
| 手机是否装了小米运动健康 | ✅ `com.mi.health`（注意：不是 `com.xiaomi.health`） |

`DebugActivity.java:632` 判断的正是 `com.xiaomi.wearable`，该组件是 Vela 第三方 interconnect 的必需服务端，由小米运动健康拉起安装、并非随主应用一起落地。

**关键推论**：`nodeId` 的可用性依赖一个**不由我们控制的外部组件**。即使验证出 nodeId 跨重置稳定，它在用户手机上的存在性也无法保证（旧机型、精简版系统、用户清理后都可能缺失）。**这意味着 nodeId 不能作为唯一主键，只能作为「有则加分」的辅助通道。**

### 9.6 三条取 ID 通道的最终状态

| 通道 | 状态 | 阻塞点 |
|---|---|---|
| 快应用 `@system.device.getDeviceId` | ❌ 平台不提供（9/9 Pro 返回 NA） | 无解，见正文第二至四节 |
| Mac BLE 直连 + GATT `0x180A` | ⏸ 未验证 | 宿主进程无蓝牙隐私授权（CoreBluetooth abort） |
| Android interconnect `nodeId` | ⏸ 未验证 | `com.xiaomi.wearable` 组件缺失（环境可补，但不可依赖） |
| **BLE MAC（`system_profiler` 实测）** | ✅ **已验证存在且为公共地址** | 无——只差跨平台一致性确认 |

## 十、重大进展：`nodeId` 实测跨重置不变（2026-11-04 21:40）

### 10.1 现象

手机 `BTF4C17222009588` 与手环完成配对后，运行 `EVSyncProbe-v0.5.173` 的链路自检，第 2 步稳定通过：

```
初始化穿戴服务  ✓  服务可用 (level 1)
查找已连接设备  ✓  小米手环9 NFC版   nodeId=913024617
申请设备权限    ✗  app not installed
连接 EV 课程表  —  待执行
```

**在用户对设备执行重置、重新配对、并重启 App（`am force-stop` 后重开）之后，再次读取：**

```
nodeId=913024617
```

**数值完全一致。**

### 10.2 证据强度与边界

| 已证明 | 说明 |
|---|---|
| ✅ 跨 App 重启 | `force-stop` 后重开，值不变 |
| ✅ 跨穿戴服务重启 | 第 1 步重新初始化服务后，值不变 |
| ✅ 跨设备重置 + 重新配对 | 用户重置并重配后仍为 `913024617` |

**注意**：`com.xiaomi.wearable` 组件在第 1 步已可用（`服务可用 level 1`），说明该组件此前只是未激活，并非真的缺失——9.5 节的失败是首次拉起未完成所致，记录应作此修正。

### 10.3 尚未证明的三件事（决定性）

| 待验证 | 为什么关键 | 验证方法 |
|---|---|---|
| **换一台手机是否同值** | 若 nodeId 由手机端穿戴服务本地编号，换手机即变，价值退化为与 UUID 同级 | 同一手环配到第二台手机，比对 nodeId |
| **换一台手环是否异值** | 必须能区分「新手环」与「重置的老手环」 | 用 10 Pro 在同一手机上配对，比对 nodeId |
| 二次重置是否仍同值 | 排除偶发 | 再重置一次 |

**其中「换手机是否同值」是最关键的一项。** 当前只能证明「同一手机 + 同一手环」下稳定，这不足以支撑「设备主键」的结论——用户换手机是常见操作。

### 10.4 与 MAC 方案的优先级重排

| 方案 | 前置条件 | 已验证 | 优势 | 劣势 |
|---|---|---|---|---|
| **nodeId** | 手机装小米运动健康 + 穿戴服务 + 已配对 | 跨重置稳定（单机） | 现在就能用，无需自研 BLE 扫描 | 依赖外部组件；跨手机未验证 |
| **BLE MAC** | 自研手机端 BLE 读取 | 地址固定、公共地址 | 不依赖任何小米组件 | 需开发；iOS 不可用 |

**结论：nodeId 可作为近期落地方案（成本最低），MAC 作为长期主键（最不受控）。两者可并行接入服务端，互为降级。**

## 十一、Android 侧实测：系统 bonding 列表可直接取 MAC（2026-11-04 22:12）

### 11.1 实测证据

在华为 BLN-AL20 / Android 8.0 上，手环经由小米运动健康完成配对后，`adb shell dumpsys bluetooth_manager` 的输出：

```
Bonded devices:
  **:**:**:80:3A:DC [DUAL]   Xiaomi Smart Band 10 Pro 3ADC
  **:**:**:13:7B:40 [BR/EDR] Galaxy Tab A (2017)
  **:**:**:25:B2:1F [BR/EDR] 靳iPhone
  **:**:**:06:B8:85 [DUAL]   Xiaomi Smart Band 9 B885

Bond Events:
  21:33:43.182  04:34:c3:06:b8:85  btif_dm_create_bond   BOND_STATE_NONE
  21:33:53.836  04:34:c3:06:b8:85  bond_state_changed    BOND_STATE_BONDED
```

配套的 `settings list global` 中也存在完整地址：

```
bluetooth_a2dp_sink_priority_04:34:C3:06:B8:85=-1
bluetooth_input_device_priority_04:34:C3:06:B8:85=...
```

> `dumpsys` 输出中前 3 字节显示为 `**` 是 dumpsys 自身的展示保护；App 通过 API 取到的是完整地址，`settings global` 里也是完整的。

**结论：手环已进入 Android 系统级 bonding（`BOND_STATE_BONDED`），因此 `BluetoothAdapter.getBondedDevices()` 一定能返回该设备。**

### 11.2 依赖边界的精确表述（关键，不可含糊）

「不需要小米运动健康」这句话必须分三层说，否则会误导后续实现：

| 层面 | 是否需要小米运动健康 / 穿戴服务 | 说明 |
|---|---|---|
| **运行时读取** | ❌ **完全不需要** | App 只调 Android 系统 API，小米 App 不必安装、不必运行、不必在前台 |
| **数据来源** | ⚠️ **历史上需要** | 手环之所以出现在 bonding 列表，是因为当初用小米运动健康配对时触发了系统 bonding（见 `btif_dm_create_bond`） |
| **完全零依赖路径** | ✅ **主动扫描** | 不依赖任何小米组件，但要求手环处于广播状态（未被其他 Central 连接） |

**准确的表述是：运行时零依赖，但 bonding 这条路径的数据是「用户曾经配过对」的产物。**

这对本项目是可接受的，理由有三：

1. 手环的**正常使用前提**就是先配小米运动健康，所以目标用户群 100% 满足该前提；
2. 配对记录存在于**系统蓝牙栈**，卸载小米运动健康**不会清除** bonding（Android 的配对数据独立于 App 数据）；
3. 万一 bonding 不在了，还有主动扫描兜底，那条路连小米组件的历史依赖都没有。

**因此工程上不再需要依赖 `com.xiaomi.wearable` 穿戴服务，也不再需要 interconnect 通道。** 这是相对 nodeId 方案最重要的减负——nodeId 必须走「初始化穿戴服务 → 授权 → 找节点」四步，任一环节不可用即失败。

### 11.3 实现代码

```java
BluetoothManager bm = (BluetoothManager) getSystemService(BLUETOOTH_SERVICE);
BluetoothAdapter adapter = bm.getAdapter();
if (adapter != null && adapter.isEnabled()) {
    for (BluetoothDevice d : adapter.getBondedDevices()) {
        String name = d.getName();      // Xiaomi Smart Band 9 B885
        String mac  = d.getAddress();   // 04:34:C3:06:B8:85
    }
}
```

Android 8 上 `BLUETOOTH` 为安装即授予权限；Android 12+ 需 `BLUETOOTH_CONNECT`（运行时申请），扫描兜底还需 `BLUETOOTH_SCAN` 并声明 `android:usesPermissionFlags="neverForLocation"`。

### 11.4 三级降级链（建议实现顺序）

```
① getBondedDevices()  → 按设备名含 "Xiaomi Smart Band" / "MI Band" 过滤
                       ↓ 未命中
② BluetoothLeScanner 扫描 → 按广播名 + 服务 UUID 匹配
                       ↓ 未命中
③ 本地随机 UUID（现状，仅作安装实例标识）
                       ↓
④ 服务端「重置迁移」兜底（用户凭激活码自助转移）
```

**实测记录**：2026-11-04 22:12，本机 `mInputDevices` 段显示 `04:34:C3:06:B8:85 : 2`，证明该设备在 HID profile 下处于已登记状态，bonding 数据结构完整。

### 11.5 与 nodeId 方案的最终对比

| 维度 | MAC（bonding 列表） | nodeId（interconnect） |
|---|---|---|
| 运行时依赖小米组件 | ❌ 不需要 | ✅ 必须（小米运动健康 + 穿戴服务） |
| 实现步骤 | 1 步（遍历列表） | 4 步（服务→授权→找节点→通信） |
| 跨手机一致性 | ✅ 协议保证 | ❓ 未验证 |
| 失败概率 | 低（除非从未配对） | 中（四步任一失败即断） |
| 跨重置稳定性 | ✅（MAC 烧在芯片） | ✅（已实测单机） |
| 已实测 | ✅ 本机 bonding 存在 | ✅ 本机可读且跨重置不变 |

**结论：MAC 在「依赖少、步骤短、跨设备一致」三项上全面优于 nodeId。nodeId 保留为可选辅助通道，不再作为主路径。**

### 11.6 限制与风险

| 风险 | 说明 | 应对 |
|---|---|---|
| 用户从未配对过 | bonding 列表为空 | 走②主动扫描 |
| 用户在系统设置里「取消配对」 | bonding 记录被移除 | 走②；或引导用户重新配对 |
| 部分国产 ROM 的 `getBondedDevices` 返回受限 | 少见，但存在 | 用 `getName()` 是否为空做运行时校验 |
| iOS | 系统不暴露 MAC | 若支持 iOS，必须改用账号体系或 `identifierForVendor` |
| MAC 可被克隆 | 它是稳定标识，不是安全凭证 | 防作弊仍靠服务端次数限制与风控 |
