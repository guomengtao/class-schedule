# 切换课程表无效问题分析

## 问题描述

在课程表管理页面（`schedule-manager.ux`）中，点击某个课程表项后，虽然执行了切换操作并返回了主页，但主页显示的课程内容并未更新为对应课程表的数据，即切换课程表功能无效。

## 涉及文件

| 文件 | 路径 | 作用 |
|------|------|------|
| schedule-manager.ux | `src/pages/schedule-manager/schedule-manager.ux` | 课程表管理页面，提供切换/增删/重命名课程表功能 |
| index.ux | `src/pages/index/index.ux` | 主页面，展示当前课程表的内容 |
| database.js | `src/data/database.js` | 数据库模块，管理课程数据的持久化存储 |
| store.js | `src/data/store.js` | 存储模块，管理课程表名称列表和当前索引 |

## 完整调用链路分析

### 1. 用户点击切换课程表

在 `schedule-manager.ux` 中，`selectSchedule` 函数被调用：

```javascript
// schedule-manager.ux 第 ~366 行
selectSchedule(index) {
    if (this.editingIndex >= 0) {
      return
    }
    if (index === this.currentIndex) {
      router.back()
      return
    }
    var self = this
    database.setScheduleIndex(index, function() {
      store.setCurrentScheduleIndex(index, function() {
        self.currentIndex = index
        router.back()
      })
    })
  },
```

执行流程：
1. `database.setScheduleIndex(index)` → 设置 `currentScheduleIndex = index`（内存），并写入 storage
2. `store.setCurrentScheduleIndex(index)` → 再次写入同一个 storage key
3. `router.back()` → 返回主页面

### 2. `database.setScheduleIndex` 的实现

```javascript
// database.js 第 765 行
setScheduleIndex: function(index, callback) {
    currentScheduleIndex = index    // ① 更新内存中的值
    storage.set({
      key: "currentScheduleIndex",
      value: String(index),
      success: function() {
        if (callback) callback()
      },
      fail: function() {
        if (callback) callback()    // ② 即使失败也调用回调
      }
    })
  },
```

### 3. 主页面 `onShow()` 重新加载数据

```javascript
// index.ux 第 ~230 行
onShow() {
    ...
    database.getAllCourses(function(schedule) {
      self.schedule = schedule
      self.loadDayClasses()
      ...
    })
  },
```

### 4. `getAllCourses` 内部调用 `loadScheduleIndex`

```javascript
// database.js 第 713 行
getAllCourses: function(callback) {
    ensureReady(function() {
      loadScheduleIndex(function() {    // ③ 重新从 storage 读取！
        if (useSqlite) {
          getAllCoursesSqlite(callback)
        } else {
          getAllCoursesStorage(callback)
        }
      })
    })
  },
```

### 5. `loadScheduleIndex` 覆盖内存值

```javascript
// database.js 第 68 行
function loadScheduleIndex(callback) {
  storage.get({
    key: "currentScheduleIndex",
    success: function(data) {
      var idx = parseInt(data)
      if (isNaN(idx) || idx < 0) { idx = 0 }
      currentScheduleIndex = idx    // ④ 覆盖了步骤①设置的值！
      ...
    },
    fail: function() {
      currentScheduleIndex = 0      // ⑤ 读取失败则重置为 0
      ...
    }
  })
}
```

## 根因分析

### 核心问题：`loadScheduleIndex` 覆盖了 `setScheduleIndex` 设置的内存值

**问题链条：**

```
selectSchedule(index)
  └→ database.setScheduleIndex(index)
       └→ currentScheduleIndex = index  ← 内存中设置为新值
       └→ storage.set("currentScheduleIndex", index)  ← 持久化

  └→ router.back()
       └→ index.ux onShow()
            └→ database.getAllCourses()
                 └→ loadScheduleIndex()
                      └→ storage.get("currentScheduleIndex")  ← 从 storage 读取
                      └→ currentScheduleIndex = 读取到的值  ← 覆盖内存值！
```

**关键矛盾**：`setScheduleIndex` 已经在内存中正确设置了 `currentScheduleIndex`，但 `getAllCourses` 每次都调用 `loadScheduleIndex` 从 storage 重新读取并覆盖。这个设计假设 storage 的读写是完美同步的，但在实际环境中存在以下风险：

### 风险场景

#### 场景 A：storage 缓存延迟

某些 QuickApp 平台的 `@system.storage` 实现可能有内部缓存。`storage.set` 写入后，立即 `storage.get` 可能返回缓存中的旧值，而不是刚刚写入的新值。

- **结果**：`loadScheduleIndex` 读取到旧的 index（如 0），覆盖了 `setScheduleIndex` 设置的 index（如 1），导致切换无效。

#### 场景 B：storage 读取失败

```javascript
// loadScheduleIndex 的 fail 回调
fail: function() {
    currentScheduleIndex = 0    // 直接重置为 0！
}
```

如果 `storage.get` 失败（例如权限问题、存储空间不足等），`currentScheduleIndex` 会被重置为 0，导致无论切换到哪个课程表，最终都显示第 0 个课程表的内容。

#### 场景 C：异步竞态

`setScheduleIndex` 的 `storage.set` 是异步的。虽然在回调中才执行 `router.back()`，理论上写入已完成。但如果在某些平台上 `storage.set` 的回调在写入实际落盘之前就触发了，那么 `loadScheduleIndex` 的 `storage.get` 可能读取到旧值。

### 次要问题

#### 问题 1：冗余的 storage 写入

`selectSchedule` 中 `database.setScheduleIndex` 和 `store.setCurrentScheduleIndex` 都向同一个 storage key `"currentScheduleIndex"` 写入相同的值。这是不必要的重复操作，增加了出错概率。

#### 问题 2：`loadScheduleIndex` 被不必要地反复调用

`getAllCourses`、`insertCourse`、`updateCourse`、`deleteCourse` 等方法每次调用都会执行 `loadScheduleIndex`，从 storage 重新读取 `currentScheduleIndex`。但 `setScheduleIndex` 已经维护了内存中的正确值，这个反复读取是不必要的，且引入了覆盖正确值的风险。

#### 问题 3：`getAllCourses` 和 `store.getCurrentScheduleIndex` 并行读取

在 `index.ux` 的 `onShow()` 中，`database.getAllCourses()` 和 `store.getCurrentScheduleIndex()` 是并行调用的，两者都读取同一个 storage key。虽然通常不会出问题，但缺乏协调。

## 修复建议

### 方案一：移除 `getAllCourses` 中的 `loadScheduleIndex` 调用（推荐）

当前 `getAllCourses` 中调用 `loadScheduleIndex` 是多余的，因为 `setScheduleIndex` 已经正确维护了 `currentScheduleIndex` 的内存值。

```javascript
// 修改前
getAllCourses: function(callback) {
    ensureReady(function() {
      loadScheduleIndex(function() {    // ← 删除此行
        if (useSqlite) {
          getAllCoursesSqlite(callback)
        } else {
          getAllCoursesStorage(callback)
        }
      })                                // ← 删除此行
    })
  },

// 修改后
getAllCourses: function(callback) {
    ensureReady(function() {
      if (useSqlite) {
        getAllCoursesSqlite(callback)
      } else {
        getAllCoursesStorage(callback)
      }
    })
  },
```

同样修改 `insertCourse`、`updateCourse`、`deleteCourse` 中的 `loadScheduleIndex` 调用。

**优点**：
- 彻底消除覆盖风险
- 减少不必要的 storage 读取
- `setScheduleIndex` 设置的值直接生效

**注意**：`loadScheduleIndex` 应保留在 `initSqlite` 和 `fallbackToStorage` 中，确保初始化时正确读取。

### 方案二：在 `selectSchedule` 中只调用一次 storage 写入

移除冗余的 `store.setCurrentScheduleIndex` 调用，只保留 `database.setScheduleIndex`：

```javascript
selectSchedule(index) {
    if (this.editingIndex >= 0) return
    if (index === this.currentIndex) {
      router.back()
      return
    }
    var self = this
    database.setScheduleIndex(index, function() {
      self.currentIndex = index
      router.back()
    })
  },
```

### 方案三：增加错误处理和日志

在 `loadScheduleIndex` 的 `fail` 回调中，不要直接重置为 0，而是保留当前内存值：

```javascript
function loadScheduleIndex(callback) {
  storage.get({
    key: "currentScheduleIndex",
    success: function(data) {
      var idx = parseInt(data)
      if (isNaN(idx) || idx < 0) { idx = 0 }
      currentScheduleIndex = idx
      if (callback) callback()
    },
    fail: function() {
      // 不要重置为 0，保留当前内存值
      logErr("loadScheduleIndex failed, keeping current value: " + currentScheduleIndex)
      if (callback) callback()
    }
  })
}
```

## 总结

切换课程表无效的根本原因是 **`database.getAllCourses()` 内部调用 `loadScheduleIndex()` 从 storage 重新读取 `currentScheduleIndex`，覆盖了 `database.setScheduleIndex()` 刚刚在内存中设置的正确值**。当 storage 存在缓存延迟、读取失败或异步竞态时，`loadScheduleIndex` 读取到旧值或默认值 0，导致课程数据加载错误。

**推荐采用方案一**，移除 `getAllCourses` 等数据操作方法中多余的 `loadScheduleIndex` 调用，让 `setScheduleIndex` 设置的内存值直接生效。同时保留 `loadScheduleIndex` 在初始化流程中的调用，确保应用启动时正确加载索引。
