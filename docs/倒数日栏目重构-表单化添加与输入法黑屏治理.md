## 〇、结论摘要（先看这里）

1. **添加倒数日的现状是「三次跳转 + 三次回填」**：列表 → 全屏输入页（输名称）→ 全屏日期页（选日期）→ 回列表才算保存成功。中途任何一步返回，数据全丢，用户看到的是「什么也没发生」。
2. **改为「进入即表单」**：新增 `countdown-edit` 单页，`mode=add|edit` 双模式。名称 + 日期 + 保存**全部在一屏内完成**，0 次跳转，0 次页面栈切换。名字输入改为**页内就地弹键盘**（不跳 `chinese-input`）。
3. **几何上完全可行**（关键量化，屏 192×490）：

   | 组成 | 高度 |
   |---|---|
   | 头部（返回+标题） | 34 + 8 = 42 |
   | 「名称」标签 | 22 |
   | 名称行（整行热区） | 44 |
   | 「日期」标签 | 22 |
   | 年/月/日 三列步进器 | 96 |
   | 保存按钮 | 48 |
   | **合计** | **274** |

   剩余 **216px** 冗余 → 表单 + 步进器 + 按钮一屏放得下，**不需要滚动**。
   键盘升起时：42 + 50 + 305（pill-shaped 键盘实测高度） = **397 < 490**，同样放得下。
4. **上游输入法核查结论（已实证，非推测）**：上游是 `NEORUAA/Vela_input_method`，**最新提交 `67338b1e`（2026-09-18），此后 33 天零提交**。官方**没有**发布任何针对「点按钮黑屏」的新修复。另一个常被引用的 `DengAiden/Vela-IME` 最后提交是 2024-08-12，已停更两年，不可用。
5. **但有个被旧文档写错的事实必须纠正**：正式 `InputMethod.ux` **已经是最新架构**（`createDictionaryLoader` + 外置 `assets/dictionary/*.txt`），词典不再内联进页面。所以——
   - 旧铁律「多页引用会让 rpk 显著增大（每页复制 185KB 词典）」**已不成立**；
   - 实测 `chinese-input.jsc` 仅 **93,914 字节**，词典 460KB 全包只存一份；
   - 「同步加载词典 → 看门狗复位 → 进页即黑屏」这条根因**已被官方架构性消除**。
6. **因此黑屏只能靠我们自己做工程防线，不能等上游**。方案给出 5 类根因 + 对应 6 道防线（§四），并指出用户观察到的「安装后打字不黑屏」最可能指向**资源版本指纹不一致**，必须用对照组实验确认，而不是继续盲改 CSS。

## 一、现状诊断（为什么必须改）

### 1.1 添加一条倒数日要经几个页面

```
countdown-manage  ──startAdd()──►  写 5 个 storage 键
      │                                  │
      │                                  ▼
      │                          /pages/chinese-input   （全屏输入名称）
      │                                  │ 点「完成」→ 写 countdown_name_result
      │                                  ▼ router.back()
      ├──────── onShow → drainName() ────┘
      │                │ 拿到名称 → openDatePage()
      │                ▼
      │          /pages/countdown-date   （全屏年月日 picker）
      │                │ 点「确定」→ 写 countdown_date_result
      │                ▼ router.back()
      └──────── onShow → drainDate() ────┘
                       │
                       ▼ finalizeFlow() → 才真正落盘
```

**代码定位**：

| 环节 | 位置 |
|---|---|
| 写 5 个参数键 + 跳输入页 | `countdown-manage.ux:203-217` |
| 回填名称（`flowStep==='await_name'`） | `countdown-manage.ux:164-182` |
| 回填日期（`flowStep==='await_date'`） | `countdown-manage.ux:184-201` |
| 二次跳日期页 | `countdown-manage.ux:237-247` |
| 最终落盘 | `countdown-manage.ux:249-264` |

### 1.2 三条硬伤

| # | 问题 | 后果 |
|---|---|---|
| H1 | **用 `flowStep` 状态机跨页面接力**（`idle/await_name/await_date`），状态存在页面实例内存里 | 任意一步 `router.back()`，`flowStep` 归 `idle`，已输入的名称被静默丢弃，用户感知为「点了没反应」 |
| H2 | **日期要跳到第三个页面**，且该页是 3 个 `picker`（年月日独立拨盘） | 胶囊屏 192 宽上三个拨盘横向极挤，选一个日期要拨 3 次，是当前最重的一步 |
| H3 | **`toggleItem` / `deleteItem` 用数组下标定位**（`countdown-manage.ux:316-337`） | `persistList` 后 `loadList` 会重排（`sortForDisplay` 按剩余天数），3 秒二次确认窗口内索引已漂移 → **可能删错条目** |

> H3 是本次顺带要修的既有缺陷，与栏目重构同批处理（改用 `id` 定位）。

### 1.3 页面承载能力已到极限

`countdown-manage.ux` 现在 **788 行**（模板 93 行 + 脚本 342 行 + 样式 350 行），同时承担：列表、排序、清空、二次确认、详情遮罩、添加流程状态机、编辑流程状态机。继续在此页加「表单」只会让它更不可维护 —— **必须拆独立页**。

## 二、重新规划：栏目结构与职责

### 2.0 规划总图

```
倒数日栏目
├── 列表页  countdown-manage（改版：只读+导航，不再承载表单）
│     ├─ 显示：按剩余天数分组的卡片列表
│     ├─ 操作：点击整行进编辑页 / 长按无（胶囊屏去掉长按）
│     └─ 底部：＋ 添加倒数日（整行按钮，168×44）
│
├── 表单页  countdown-edit（★ 新增，本次核心）
│     ├─ mode=add ：进入即空表单，默认聚焦「名称」行
│     └─ mode=edit：进入即回填，底部多一个「删除」
│
└── 展示位
      ├─ 首页 index 的倒计时模块（只读，读 countdown.js 数据）
      └─ 表盘 schedule-panel-countdown（只读，已有页）
```

**`countdown-date` 全屏日期页的去向**：改版后表单页内嵌步进器，该页**不再被倒数日流程调用**。但 `date-picker-demo` / 其它栏目若仍引用，保留文件不动，仅在 `manifest.json` 保持注册，标记为「遗留」，下一轮清理时统一评估。

**`chinese-input` 的去向**：仍是**全项目唯一中文输入页**（`docs/input-method-spec.md` 铁律）。本次改动是**新增一个「页内就地输入」宿主**，而非取消该铁律 —— 详见 §四 4.5 的方案对比与推荐。

### 2.1 表单页线框（192×490 胶囊屏）

**默认形态（进入即此形态，无键盘，无跳转）**

```
┌────────────────────────────┐ 192
│ [←]   添加倒数日            │ 34px  header
├────────────────────────────┤
│ 名称                        │ 16px 标签
│ ┌────────────────────────┐ │
│ │ 点此输入名称        ›  │ │ 44px  整行热区 → 就地弹键盘
│ └────────────────────────┘ │
│ 日期                        │ 16px 标签
│ ┌────────────────────────┐ │
│ │  2026  │  10  │  21    │ │ 22px  三列数值

│ │  [＋]   │ [＋] │ [＋]   │ │ 36px
│ └────────────────────────┘ │

**就地输入形态（点名称行后）**

```

│ └────────────────────────┘ │

**形态切换规则（关键，避免"表单和键盘抢空间"）**：

| 状态 | 显示 | 触发 |
|---|---|---|
`mode: form` | 完整表单（名称行 + 步进器 + 保存） | 进页默认 / 点键盘「完成」后
`mode: typing` | 只留名称显示条 + 键盘 | 点名称行

用**两个 `<div if="{{mode==='form'}}">` / `if="{{mode==='typing'}}">` 平级切换**，不做同一容器内的显隐 —— 避免 `show` 让两套节点同时存在于 VDOM（`InputMethod.ux` 顶部注释已记录过这个坑）。

### 2.2 保存逻辑（取代三段式状态机）

```
点「保存」
 ├─ 校验：title.trim() 非空 && date 合法
 │    └─ 不通过 → 按钮置灰 + 行内红字提示（不用 toast）
 └─ 通过 → countdown.load() → 内存变更 → countdown.save()
      └─ mode=add ：push 新条目
      └─ mode=edit：按 id 找到并更新（★ 不用下标）
      └─ router.back()（不是 replace：回列表页会让列表 onShow 刷新）
```

**为什么用 `back()` 而不是 `replace()`**：已有规划文档写的是 `replace`，但 `replace` 会销毁列表页实例 → 列表页 `onInit` 重跑 → 冷启般的重载卡顿。`back()` 保留列表实例，只走 `onShow` 增量刷新，胶囊屏上体验差异明显。

### 2.3 列表页改版要点

| 项 | 现状 | 改为 |
|---|---|---|
| 添加入口 | 列表底部 `+ 添加倒数日`（`countdown-manage.ux:59-61`） | 保留（头部禁放按钮，见胶囊屏规范） |
| 点击行为 | 点击卡片 → 弹详情遮罩（`openDetail`） | 点击整行 → **直接进编辑页**（少一层遮罩，遮罩内又是编辑/删除/开关三排按钮，小屏极挤） |
| 开关 ON/OFF | 卡片内 52×28 小开关 | 移入编辑页（列表只读，避免误触） |
| 排序 / 清空 | header 下方 toolbar 一行 | 保留，但仅在 ≥2 条时显示 |
| 删除 | 卡片内二次确认按钮 | 移入编辑页，页内二次确认 5 秒 |
| 详情弧环 `progress` | 遮罩内 120×120 | 移入编辑页顶部（作为编辑页的视觉锚点），或整体删除 |

> 详情遮罩（`countdown-manage.ux:64-92`）是当前页面复杂度的主要来源之一（3 个定时器 + 5 个状态位），移除后列表页可减约 120 行。

## 三、数据层调整

### 3.1 保持 v2 schema，不新增版本

```js
{ version: 2, items: [{ id, title, date, enabled, createdAt }] }
```

**不加 `note` / `category` / `color` 字段**。理由：胶囊屏上输入备注的成本远高于收益，且每加一个字段就要在表单里加一行（一屏预算只有 490px）。若将来要做，单独提 v3 迁移。

### 3.2 需要补的两个纯函数（`src/data/countdown.js`）

| 函数 | 用途 | 必要性 |
|---|---|---|
| `findIndexById(items, id)` | 取代所有下标定位，修 H3 | 必须 |
| `upsert(items, item)` | 按 id 存在则更新、不存在则追加，返回新数组 | 必须 |

### 3.3 `sortForDisplay` 的既有缺陷（顺带修）

`countdown.js:71-87` 的 `recent` 模式在**组内**用 `Math.abs(daysLeft)`：
- 已结束组（`daysLeft<0`）按 `-daysLeft` 升序 = 越久远越靠后 ✅ 符合预期
- 但**进行中组**里 `daysLeft` 最小者为「最近」，正确 ✅

结论：排序逻辑本身正确，**不需要改**。但 `sortForDisplay` 直接原地 `list.sort`，而列表页 `toggleSort` 传的是 `slice()` 副本 —— 排序后 `countdownList` 整体替换，`deleteConfirmIndex` 之类的下标态必然失效。这是 H3 的另一个入口，改 id 定位后自动消失。

## 四、输入法点按钮黑屏 —— 专项治理

### 4.1 先分清是哪种"黑屏"

用户观察：「**安装后打字不黑屏**，点按钮黑屏」。这句话本身是**最有价值的线索**，它把问题从「渲染坏了」推向「某个特定交互路径崩了」。必须先把现象分成三类，分别取证，禁止混为一谈：

| 类型 | 现象 | 判据 |
|---|---|---|
| **T1 进页即黑** | 进入输入界面，什么都看不到 | 键盘子树未创建 / 宿主无定位上下文 |
| **T2 打字不黑、点键黑** | 能看见键盘和光标，按下某个键瞬间黑屏 | 事件回调抛异常 / 看门狗复位 |
| **T3 装完不黑、热更后黑** | 干净安装正常，增量更新/模拟器复现 | 资源版本指纹 / 缓存不一致 |

用户描述的正是 **T2**，若「安装后」是重装 APK 则同时命中 **T3** 的可能。**两种都要验，且必须先验 T3**（成本最低：重装一次即可排除）。

### 4.2 上游核查：结论是"没有新修复"

用 GitHub API 实证（`GET /repos/NEORUAA/Vela_input_method/commits`）：

**FACT-1：截至 2026-10-21，上游 HEAD 仍是 `67338b1e`（09-18），此后 33 天零提交。**

→ **不能指望"上游最近更新解决了黑屏"。这个期待在事实上不成立。**

### 4.3 但我们已经吃到了上游架构红利（旧文档写错了）

旧文档《input-method-spec.md》称「每个页面内嵌 InputMethod 会重复引入键盘资源，使 rpk 体积显著增大」，并据此立下「全项目只有一个中文输入页」的铁律。**这条在旧架构下成立，现在不成立了**：

| 证据 | 实测值 |
|---|---|
| 正式组件已用新架构 | `InputMethod.ux:335` `import { createDictionaryLoader } from "./assets/dictionaryLoader.js"`
| 词典外置为 txt | `src/components/InputMethod/assets/dictionary/*.txt`（cn / jp / words-a~x） |
| 词典物理体积 | `assets/` 共 **460K**，全包只存一份 |
| 页面 bundle 实测 | `build/pages/chinese-input/chinese-input.jsc` = **93,914 字节**（不含词典） |
| 全包体量 | `build/` 2.9M / 52 页 |

**推论**：再让一个页面引用 `InputMethod`，代价 ≈ +94KB（页面代码），**不是 +185KB 词典复制**。这使「表单页内嵌键盘」从"体积上不可接受"变成"可接受，需设门禁"。

> ⚠️ 但「资源文件（assets/*.png、*.txt）在多页引用时是否重复打包」**尚未实测**。这是 §4.5 选型的**唯一未决变量**，必须在 P0 阶段用构建产物实测（见 §六 阶段 0）。

### 4.4 黑屏剩余根因（已排除的划掉）

| # | 根因 | 现状 | 防线 |
|---|---|---|---|
| **R1** | ~~同步加载 185KB 词典 → 单帧超预算 → 看门狗复位~~ | ✅ **已消除**（词典外置 + 输入驱动按需加载 + 失败重试） | — |
| **R2** | 宿主容器缺定位上下文 / 宽度塌缩 → 键盘渲染为 0 尺寸 = 黑底 | 现存风险（`chinese-input.ux:38-48` 已修，新页会重新引入） | **D1** 宿主规则模板化 |
| **R3** | `@media screen and` 触发 Vela 引擎崩（10-03 已修 40 页） | 现存风险（新页 CSS 若照抄老写法会复发） | **D2** 断点写法禁令 |
| **R4** | 键盘事件回调（`onCharacter`/`onRsSelect`/`onBtnClick`）抛异常 → 整页白/黑 | **最可能命中 T2**，当前**零 try-catch** | **D3** 事件边界 |
| **R5** | 页面栈堆积 / 定时器泄漏 → 内存耗尽的延迟黑屏 | 现存（列表页 3 个 timer） | **D4** 生命周期清理 |
| **R6** | 资源版本指纹不一致（装完正常、热更黑屏） | **最可能命中 T3，未验证** | **D5** 指纹自检 |
| **R7** | 键盘子树进页即建 200+ 节点 → 进页卡顿 | 已在组件内用 `keyboardCreated` 懒建解决 | 保持 |

### 4.5 三种输入方案的取舍（决定表单页怎么写名字）

| 方案 | 做法 | 跳转 | 体积 | 黑屏面 | 结论 |
|---|---|---|---|---|---|
| **A 现状** | 表单页 → 跳 `chinese-input` 全屏 → 回填 | 2 次 | 0（不新增引用） | 键盘只在 1 个页面，崩溃面最小 | 违背"进入即表单"诉求 |
| **B 就地输入** | 表单页内嵌 `InputMethod`，两态切换 | **0 次** | +~94KB/页（待实测） | 键盘在 2 个页面，任一处崩即崩 | **推荐**，但需 D1/D3 到位 |
| **C 混合** | 默认 B；若 §阶段0 实测体积超门禁，则降级为 A | 0 或 2 | 可控 | 可控 | **保底方案** |

**推荐 B（就地输入）**，理由：
1. 用户明确要求"添加倒数日默认先显示一个表单" —— 跳走再回来本质上仍是"表单被输入页打断"，且回填链路（storage + onShow）正是当前丢数据的根源；
2. 几何已算清（397/490，余 93px），不会挤；
3. 词典外置后体积代价可控；
4. 键盘代码只有一份（`src/components/InputMethod/`），两个页面引用同一份代码，**不存在"两套输入法"的维护分叉**。

**门禁（硬性）**：`阶段 0` 实测 `build/pages/countdown-edit/countdown-edit.jsc` 与 rpk 总增量 —— **增量 > 150KB 则降级方案 C**。

### 4.6 六道防线（可直接抄进代码）

| 编号 | 防线 | 具体做法 | 对应根因 |
|---|---|---|---|
| **D1** | 键盘宿主规则模板 | 宿主必须 `flex:1 + flex-direction:column + width:100%`，**禁止用 `<scroll>` 包裹键盘**，禁止 `position:absolute` 直接放键盘而父级无 `position:relative` | R2 |
| **D2** | 断点写法禁令 | 全页禁用 `@media screen and (...)`；只用 `@media (shape: pill-shaped)` / `@media (shape: rect)`；base 以手环 9 为基准，大屏只做增量 | R3 |
| **D3** | 键盘事件边界 | 在表单页对三个回调全部包 `try/catch`，catch 内只做两件事：① 记一行 `console`；② `this.mode='form'` 退回表单态（**保证用户永远有一条出路**） | R4 |
| **D4** | 生命周期对称清理 | `onDestroy` 里清掉所有 `setTimeout`；`mode` 切回 `form` 时若键盘子树已建，保持保活不重建（防止反复建/销毁触发引擎内部状态错乱） | R5 |
| **D5** | 资源指纹自检 | 输入法页 `onInit` 比对 `manifest` 版本号与 storage 里上次记录值，不一致时打一条日志（真机可用 `hilog`），用于区分「装完正常/热更黑屏」 | R6 |
| **D6** | 冒烟脚本门禁 | 用 `tools/vela-loop.py` 增加 `--tap x,y` 能力，脚本化：进页 → 点 3 个不同键（字母/退格/完成）→ 每步截图 → 校验「非纯黑」+ md5 去重 | 全部 |

**D6 的必要性**（这是最容易跳过、又最该做的一条）：当前输入法**零自动化测试**，每次改动只能靠真机手点，这是"18 天修 10 次还在复发"的方法论根因。冒烟脚本把"能否点键"变成可回归的断言。

**D6 判据（可直接实现）**：
```
截图非空：mean(pixel) 在全黑阈值之上
非重复：连续两帧 md5 不同（防"三张图同一帧"假验证）
非白屏：存在 ≥2 种主色（防只剩背景色的假正常）
```

## 十一、阶段 0 实测记录（2026-10-21 10:07）

### 11.1 体积门禁：✅ 通过

同模式对比（均为 debug 产物 `.js`，`aiot build` 一次生成）：

| 产物 | 字节 |
|---|---|
| `build/pages/countdown-edit/countdown-edit.js` | 737,922 |
| `build/pages/chinese-input/chinese-input.js` | 667,960 |
| **差值** | **69,962（≈68KB）** |

**关键旁证**：
- `build/components/InputMethod/` 作为**独立共享目录**存在 → 组件只打一份，未被复制到两个页面；
- 未引用键盘的 `build/pages/index/index.js` 已达 **523,502** → 700KB 量级来自公共运行时，不是键盘；
- 若组件真被复制，该页应为 ≈1.4MB（667K + 68K + 700K），实测 737K 直接证伪。

**结论：内嵌键盘的真实代价 ≈ 68KB（本页自身代码），远低于 150KB 门禁。维持方案 B。**

> ⚠️ 注意：`.jsc` 与 `.js` 不可混比。`aiot build`（debug）产 `.js`，`aiot release --enable-jsc` 产 `.jsc`；此前记录的 `chinese-input.jsc=93,914` 是 release 态，与本表不同模式。

### 11.2 运行时验证：❌ 未通过（阻塞于设备，非页面）

两次完整尝试均以「连续 3 次冷启未出画」告终：

| 设备 | 冷启耗时 | vapp 进程数变化 |
|---|---|---|
| `emulator-5554` | 48s / 48s / 48s 全超时 | 2 → 4 → 6 |
| `emulator-13000` | 47s / 46s / 47s 全超时 | 8 → 10 → 12 |

**判据与结论**：

1. **进程数单调递增且从不退出** —— 若是页面 JS 崩溃，系统会 kill 该进程，数量不会累积；只有**进程启动后卡死不退**才会出现该模式 → 判定为 **设备级 hang / 资源耗尽**，不是 T1 进页黑屏；
2. `emulator-5554` 后续 `adb shell` **3 分 49 秒无响应**（`ps`/`dumpsys`/`logcat` 全部挂住），设备已不可用；
3. 首次尝试时启动日志提示**当前有 2 台模拟器在线**（`emulator-13000=evc-xiaomi_band-buddy-1`、`emulator-5554=xiaomi_band`）→ 存在与他会话争用的可能，需先确认设备归属。

### 11.3 本次同时做的两处静态加固

| 项 | 改动 | 理由 |
|---|---|---|
| 多类名 | `class="name-value name-placeholder"` → 拆成两个元素各自单类名 | Vela 对多类名支持差，可能静默丢弃或解析异常 |
| 词典路径 | 显式传 `dictionarypath="/components/InputMethod/assets/dictionary/"` | 上游文档记录：官方版需宿主传绝对路径覆盖默认值，否则词典 loader 可能初始化失败 |

### 11.4 复验前置（下一轮开工第一条）

1. **重启模拟器**（`emulator-5554` 已 hang，必须冷重启；`emulator-13000` 有 12 个残留 vapp 进程）；
2. 先用 `vela-loop --page index` 跑一次已知正常页，**确认设备恢复出画能力**（当前无法区分"设备坏"与"页面坏"）；
3. 再跑 `--page countdown-edit`，若 index 正常而本页黑屏 → 才进入页面二分（第一步：临时移除 `<import>` 与 `<input-method>`，验证表单骨架单独出画）；
4. 采集 `logcat` 时**先 `adb logcat -c` 清空**再触发，避免被历史噪声淹没。
