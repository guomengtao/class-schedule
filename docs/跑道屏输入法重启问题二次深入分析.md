## 一、先核对一件事：你测的可能不是修复版 ⭐

`r` 参数的来源是有据可查的：

```316:316:src/pages/activation/activation.ux
    self.versionText = version.versionName
```

```461:463:src/pages/activation/activation.ux
      if (self.versionText) {
        qr = qr + '&r=' + encodeURIComponent(self.versionText)
      }
```

即 **`r` = 安装包里的 `versionName`**。对照结果：

| 项目 | 值 |
|---|---|
| 本次真机 URL | `r=1.6.100` |
| 仓库 `src/data/version.js` | `versionName: "1.6.103"` |

→ **结论：`r=1.6.100` 说明手环上跑的是修复之前的包。** 上一轮的三处修复（词典分片 / 键盘错峰展开 / 移除 arc 进度条）压根没有被装进去，所以"不管用"是必然结果，而不是"方向错了"。

## 二、如果装上新版本仍然重启 —— 上一轮的修复为什么覆盖不到

上一轮针对的是"单帧阻塞触发看门狗"。有两类成因，它是**结构上管不了**的：

### W3：并发 storage I/O（RTOS 上的老大难）⭐⭐⭐⭐⭐

"点击昵称"的完整调用链是这样的 —— 注意**在跳转之前就有 5 次并发写**：

```351:360:src/pages/settings/settings.ux
  openNicknameEdit() {
    var storage = require("@system.storage")
    storage.set({ key: "chinese_input_title", value: "编辑昵称", success: function() {} })
    storage.set({ key: "chinese_input_placeholder", value: "输入昵称", success: function() {} })
    storage.set({ key: "chinese_input_value", value: this.nickname, success: function() {} })
    storage.set({ key: "chinese_input_maxlen", value: "12", success: function() {} })
    storage.set({ key: "chinese_input_return_key", value: "chinese_input_nickname_result", success: function() {
      router.push({ uri: "/pages/chinese-input" })
    }})
  },
```

进入页面后又是**一整片并发读**（`loadParams` 5 个 + `onInit` 里 `getTheme` / `getThemeName` 2 个 = **7 次**）：

```97:117:src/pages/chinese-input/chinese-input.ux
  loadParams() {
    var self = this
    var storage = require("@system.storage")
    storage.get({ key: "chinese_input_title", success: function(data) { ... } })
    storage.get({ key: "chinese_input_placeholder", success: function(data) { ... } })
    storage.get({ key: "chinese_input_value", success: function(data) { ... } })
    storage.get({ key: "chinese_input_maxlen", success: function(data) { ... } })
    storage.get({ key: "chinese_input_return_key", success: function(data) { ... } })
  },
```

→ **5 次并发写 + 7 次并发读**，全部集中在几十毫秒内发出。

**这不是凭空猜测，本项目早有先例**：`docs/settings-xiaomi-band9pro-analysis.md` 对"手环 9 Pro 设置页打不开"给出的头号怀疑原文是 ——

> **并发存储读取限制**：RTOS 的存储 I/O 可能不支持高并发异步读取，多个并发的 `storage.get()` 可能导致某些请求被丢弃或超时。

手环 9 与 9 Pro 是同代 RTOS 设备，机制高度相似。而且它与本次症状的**时序吻合**：重启发生在"点击"这个动作附近，而上一轮修复改的是"键盘展开之后"的词典初始化 —— 时间点对不上。

### W4：内存总量 OOM（分片解决不了）⭐⭐⭐⭐

上一轮把"一次建齐 6 张表"改成"分 ~10 个 tick 建"，**分摊的是时间，不是总量**。最终驻留内存一点没少：

| 对象 | 量级 |
|---|---|
| `py2hz` | 6763 条 |
| `py2hz2` | 首字母索引 |
| `syllableSet` | ~6763 项 Set |
| `words` | ~3000 条 |
| `initialsIndex` + `forwardIndex` | 3000 词倒排 ×2 |
| `romaji2kanji` | 日文表 |
| PNG 资源 | 61 张 |
| 键盘节点 | 200+ |

如果手环 9 的 RTOS 堆预算只有几 MB，这套东西**建完就爆** —— 分不分片都会爆。这也能解释为什么"键盘延后一帧展开"没用：内存峰值只是被挪到了后面几帧。

**判据**：如果重启发生在**键盘已经画出来之后**（先看到键盘，再重启），OOM 嫌疑最大。

### W5：`router.push` 叠加页面栈 ⭐⭐⭐

从设置页 push 到输入页 → **两个页面同时在栈上** + 输入法组件（自带 61 张 PNG 与整本词典）→ 内存接近翻倍。可对比"冷启动直接进输入法"是否更稳，以判断是否为叠加效应。

## 三、最小复现二分法（请严格按顺序做）

**前置**：先让手环上的版本号可见（设置页或输入页加一行 `versionText`），确认装机版本。

| 编号 | 操作 | 判读 |
|:---:|---|---|
| **T0** | 确认手环上 `versionName` = 1.6.103 | 不是 → **先装机**，别往下做 |
| **T1** | 把 `openNicknameEdit` 的跳转目标临时改成一个**空白页**（`storage.set` 那 5 行不动） | 仍重启 → 崩在**跳转前的 5 个并发 set** 或路由本身；不重启 → 崩在页面内 |
| **T2** | 空白页里只放 **1 次** `storage.get` | 崩 → 存储层问题；不崩 → 逐个加到 5 次，找到临界值 |
| **T3** | 空白页里放 `InputMethod`，但**临时屏蔽 `_ensureDictInit()` 的调用** | 崩 → 崩在**键盘 UI / PNG / 节点**（内存或渲染）；不崩 → 崩在词典 |
| **T4** | 去掉外层 `<scroll>`，把组件放进固定高度 `div` | 崩 → 与 scroll 无关，是组件本身 |
| **T5** | `adb logcat` 抓重启前最后 10 秒 | 有崩溃栈 → 直接定案 |

**同时请记录时序**（这一条最省力也最关键）：点击后是
- **立刻黑屏重启**（没看到输入页）→ 指向 **W3**（并发 storage / 路由）
- **先闪出输入页或键盘，再重启** → 指向 **W4**（内存）

## 四、对应修复方案（等 T1~T5 定案后选一条）

### 若 T1 / T2 命中 W3（并发 storage）

1. **合并成一个 key**：把 `title / placeholder / value / maxlen / returnKey` 打包成一个 JSON 字符串，1 次 `set` + 1 次 `get`（并发 4→1、5→1）。改动面小、收益最大。
2. **串行化**：用回调链逐个 `set`，不要并行发。
3. **`loadParams` 改串行**：先取 `returnKey`，再依次取其它。

### 若 T3 命中 W4（内存 / PNG）

1. **裁剪词典**：按常用度裁剪（单字 6763→3000、词 3000→1500），或改为按需加载。
2. **词典再延后**：现在仍是"键盘一展开就建"，可推迟到**第一次按键**。
3. **移除 `getDictJp()`**：纯中文应用不需要日文表。
4. **PNG 精简 / 复用**，或改用纯文字键盘 —— `docs/inputmethod-png-lab-page-analysis.md` 已有"建议优先使用纯文字版输入法"的结论。

### 若 T5 命中 W5（页面栈叠加）

- 输入页改用单实例 `launchMode`，或跳转前清理栈，避免两个重页面同时驻留。

## 六、诚实的小结

上一轮我把"进页面即重启"归因为**单帧阻塞（看门狗）**，并据此做了三处修复。现在回看，有两个问题：

1. **真机很可能根本没装上新版本**（`r=1.6.100` vs 仓库 `1.6.103`），所以那一轮结论尚未被真机检验过。
2. **即使装上，那三处修复也只覆盖"阻塞"这一种成因**，结构上覆盖不到：
   - **并发 storage I/O**（W3）—— 发生在点击瞬间，早于我改动的时机；
   - **内存总量 OOM**（W4）—— 分片只摊平时间，不减少总量，内存峰值照旧。

所以"没改对"这个判断是对的。下一步请先按 **T0 → T1 → T2** 走一遍（都是几分钟的改动），拿到"崩在跳转前还是页面内"这个定性结论，再决定是改存储并发还是砍内存。

## 七、一次性诊断方案（新增诊断页，专为"测试机会极少"设计）

### 7.1 为什么需要它

前面的 T0~T5 每一条都要**改代码 + 重新出包 + 重新安装**，而测试机在用户手上、每次崩溃体验极差、机会有限。因此改为：**一次装机，页面内完成全部排查。**

新建页面 `src/pages/input-crash-diag/input-crash-diag.ux`，入口：**工具 → 输入法崩溃诊断**。

### 7.2 核心机制：崩溃点落盘

复用项目已有的成熟模式（`src/pages/device-id-diagnosis/device-id-diagnosis.ux` 的"落盘进度 → 延时 → 执行 → 完成清空"）：

| storage key | 含义 |
|---|---|
| `input_diag_step` | 正在执行的步骤号。测试前写入、测试完成清空 —— **若中途重启，它会保留下来** |
| `input_diag_passed` | 已通过的步骤列表（如 `1,2,3`） |

**重新打开页面时，顶部会直接显示「上次崩在第 N 步：XXX」和「已通过：1,2,3」。** 也就是说：**用户点一次，崩了，再打开页面就已经拿到结论了**，不需要重新出包，也不需要第二次复现。

### 7.3 五个测试项（每项都能独立定案）

| # | 测试 | 复刻/隔离的内容 | 崩在这一步说明什么 |
|:---:|---|---|---|
| 1 | 并发写 ×5 | 复刻 `settings.ux` 点击昵称先发的 5 个 `storage.set` | **并发写**是元凶（W3） |
| 2 | 并发读 ×7 | 复刻进输入页的 5 个 `get` + 主题/主题名共 7 次并发读 | **并发读**是元凶（W3） |
| 3 | 建键盘（不加载词典） | `dictlazy=true`，只渲染键盘 UI 与 PNG，跳过词典 | 元凶是**键盘 UI / 图片 / 节点** |
| 4 | 加载词典 | 重建组件并加载整本词典 | 元凶是**词典内存**（W4） |
| 5 | 跳转真实输入页 | 端到端 | 前 4 步之外的**组合因素**（如页面栈叠加 W5） |

**第 3 步与第 4 步的分离是这套方案的关键**：为此给 `InputMethod` 组件新增了一个诊断用 prop `dictlazy`（默认 `false`，不影响线上行为；为 `true` 时跳过 `initDict`）。3 崩 4 也崩 = UI/图片问题；3 不崩 4 崩 = 词典内存问题。

### 7.4 用户怎么用（一句话）

> 打开「工具 → 输入法崩溃诊断」，**先点「★ 一键跑全部」**，然后不用管；如果手环重启了，重新打开应用进这个页面，看顶部红字。

- 「一键跑全部」会自动串行跑 1→5，每步之间留 800ms 给落盘与渲染；
- 每个测试也可以单独点（用于精细复现）；
- 「清空记录」用于换一轮测试前重置。

### 7.5 结果判读速查

| 页面顶部显示 | 结论 |
|---|---|
| 崩在第 1 步 | → 并发写（W3），按第四章"合并成一个 key + 串行化"修 |
| 崩在第 2 步 | → 并发读（W3），同上 |
| 崩在第 3 步 | → 键盘 UI / PNG，需精简图片或改纯文字键盘 |
| 崩在第 4 步 | → 词典内存（W4），需裁剪词典或延后到首次按键 |
| 崩在第 5 步 且 1~4 全通过 | → 组合因素（页面栈叠加 W5 等） |
| 五步全过、第 5 步跳转后崩 | → 崩在真实输入页内部，需在 `chinese-input.ux` 内再做细分埋点 |

### 7.6 需要注意

- **出包前请 bump 版本号**（当前 `1.6.105`）。上一轮的教训就是分不清装机版本 —— 请保证真机上看到的版本号**大于**包含本诊断页的这一版，否则测的还是旧包。
- 诊断页**进页面不自动执行任何测试**，只有点了按钮才跑，避免"一进页面就崩"白费一次机会。
- 第 3 / 4 步的键盘宿主区用 `if` 控制，默认不挂载，页面本身保持轻量。
