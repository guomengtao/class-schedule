# 设备ID诊断实测结果与替代方案分析

> 前置文档：[手环9胶囊屏设备ID为NA分析.md](./手环9胶囊屏设备ID为NA分析.md)（诊断前的方案设计）
> 本文档基于**真机实测结果**，给出结论与后续可行方案。

## 一、实测结果

在小米手环（Vela）上，依次点击工具 → 设备ID诊断页的 7 个按钮，结果如下：

| # | 项目 | 结果 | 说明 |
|:-:|------|:--:|------|
| 1 | 本地 UUID | ✅ 绿 | storage 里生成并持久化的 UUID（**软件生成，非硬件**） |
| 2 | getInfo | ❌ 红 | API **调用成功**，但返回里没有 `deviceId`/`serialNumber`/`udid` 等标识字段 |
| 3 | getUA | ❌ 红 | API 不存在或调用失败 |
| 4 | getDeviceId | ❌ 红 | 返回 `NA` / 空 |
| 5 | getSerial | ❌ 红 | 返回空 / `NA` |
| 6 | getMac | ❌ 红 | API 不存在或调用失败 |
| 7 | getId | ❌ 红 | API 不存在或调用失败 |

**一句话结论：所有硬件级设备标识（deviceId / serial / mac / id）在这台设备上全部拿不到；唯一"绿"的本地 UUID 是我们自己生成的软件值。**

---

## 二、先澄清一个容易被误读的点

**「红色」并不都等于「API 坏了」**，要分三类看：

| 现象 | 实际含义 | 举例 |
|------|---------|------|
| API 成功，但**没有标识字段** | 接口本身工作正常，只是 Vela 不暴露硬件 ID | `getInfo`（能拿到型号/屏幕/OS，但无 deviceId） |
| API 成功，但**值无效** | 接口存在，底层没填/被抹掉 | `getDeviceId` 返回 `NA`、`getSerial` 返回空 |
| API **不存在 / 调用失败** | 该接口在 Vela band 上未实现 | `getMac` / `getId` / `getUA` |

所以对 `getInfo` 不要下"坏了"的结论——它其实**能正常工作**（设备的型号、固件、屏幕等信息都能读），只是**里面没有能当唯一 ID 用的字段**。

---

## 三、本地 UUID 到底能不能用？

本地 UUID 的实现是：首次调用时 `generateUUID()` 生成一个随机 UUID，写进 `storage`（key `diag_uuid_v1`），之后每次读同一个值。

要判断能不能当"设备唯一标识"，必须同时满足四个维度：

| 维度 | 是否满足 | 说明 |
|------|:--:|------|
| **能拿到** | ✅ | 一定拿得到（自己生成的） |
| **唯一** | ❌ | 只能区分"这台设备的这个安装实例"，无法区分硬件；且可被清除/重置 |
| **稳定** | ✅ | 同一安装实例内、重启后不变 |
| **持久** | ❌ | **卸载重装 / 清除应用数据即变**；OTA 也可能丢 |

> **结论：不能用。**
> 它是"软件生成 + 可被抹除"的值，不是硬件身份。把它当设备 ID 用，等价于"让用户自己给自己发身份证"——同一台设备重装一次就能拿到新 ID，设备绑定形同虚设。

它正确的定位是：**「本机安装实例标识」**，用于记录"这一次安装"的状态，而不是"这台设备"的身份。

---

## 四、为什么硬件标识全拿不到

与前置文档的推断一致，根因在 Vela / 设备侧，不在我们的代码：

1. **权限收紧**：Vela 对第三方快应用读取硬件标识符（deviceId / serial / mac）持续收紧，band 类设备的身份体系本身就不完整；
2. **provisioning 缺失**：手环不像手表有 eSIM / 支付等强身份需求，出厂未必写入唯一硬件 ID，`getDeviceId` 于是返回 `NA`；
3. **API Level 2 限制**：当前平台较低，部分接口（getMac / getId / getUA）尚未实现；
4. **这不是我们的 bug**：测试页各项都已独立 try/catch 且正确区分了"拿到/空/NA/不存在/失败"。

**所以"再想办法加一个硬件标识"这条路，在系统层面是堵死的**——我们无法凭空获得系统不提供的硬件 ID。

---

## 五、可行的替代方案

既然拿不到硬件 ID，就得换"设备绑定"的模型。可选方案如下：

### 方案 A：弱指纹（软指纹）
把 `getInfo` 能拿到的**稳定字段**拼起来当成一个"弱指纹"：

```
product(型号) + osVersionCode(固件) + platformVersionCode + screenWidth×screenHeight + APILevel
```

- ✅ 实现简单、纯客户端
- ⚠️ **不唯一**：同型号同固件的手环指纹完全一样；也无法区分"重装"
- 定位：只能**提高作弊成本**，不能真正绑定

### 方案 B：本地 UUID + 服务端首次绑定
首次激活时把"本机安装 UUID"上报服务端，服务端记录 `UUID ↔ 激活码 ↔ 首次激活时间`。

- ✅ 能防"一个码无限刷"（服务端可限次）
- ✅ 能记录激活时间、做风控
- ⚠️ 重装应用会生成新 UUID → 需要重新激活（**这是可以接受的**，因为重装是低频操作）
- ⚠️ 无法阻止"同一个人反复重装绕过次数限制"（但这属于风控层，不是设备绑定层）

### 方案 C：激活码不绑设备，改为「次数 + 限速 + 风控」
激活码本身携带/关联"可用次数"，由服务端控制：

- 每个激活码 / 万能码有使用次数上限
- 服务端按 IP / 时间窗口限速
- 异常模式（同一码短时间大量激活）告警

### 方案 D：账号绑定
若有账号体系（微信 / 手机号 / 小米账号），直接绑账号，与设备无关。

- ✅ 最彻底
- ❌ 本项目目前**没有账号体系**，落地成本最高

### 方案对比

| 方案 | 防"换设备" | 防"重装刷" | 实现成本 | 用户体验 |
|------|:--:|:--:|:--:|:--:|
| A 弱指纹 | 弱 | ❌ | 低 | 好 |
| B 本地UUID+服务端 | 弱 | 中（服务端限次） | 中 | 好 |
| C 次数+限速+风控 | 弱 | 中 | 中 | 好 |
| D 账号绑定 | 强 | 强 | 高（需账号体系） | 中 |

## 六、推荐方案

**推荐 B + C 组合**（在没有账号体系的前提下性价比最高）：

1. **用本地 UUID 作为「设备安装实例 ID」**（明确它不是硬件 ID）；
2. **服务端记录** `UUID → 激活码 / 首次激活时间 / 本次安装的激活次数`；
3. **激活码 + 万能码加次数上限 + 服务端限速 + 异常告警**；
4. **诚实接受**"重装可重置 UUID"这一现实——通过服务端风控把成本抬高，而不是追求不可能做到的"硬件级强绑定"。

> 这比"用 `product + version` 拼一个假 ID"更可维护：假 ID 会给人"能绑定设备"的错觉，实际同型号全撞号，反而更糟。

### 取值降级链（客户端 + 服务端）

```javascript
// 客户端：优先硬件 ID，全拿不到时退到"弱指纹 + 本地 UUID"
function resolveLocalId(info, localUUID) {
  if (info.serial && info.serial !== 'NA') return info.serial
  if (info.deviceId && info.deviceId !== 'NA') return info.deviceId
  // 硬件 ID 都拿不到 → 弱指纹 + 本机安装 UUID
  var fp = [info.product, info.osVersionCode, info.platformVersionCode,
            info.screenWidth + 'x' + info.screenHeight].join('-')
  return fp + '#' + localUUID
}
```

```javascript
// 服务端：把上报的 id 归一化后再做限次/风控
function resolveDeviceId(params) {
  if (params.serial && params.serial !== 'NA') return params.serial
  if (params.deviceId && params.deviceId !== 'NA') return params.deviceId
  return params.fingerprint + '#' + params.installUUID   // 弱标识，仅用于限次/风控
}
```

## 七、实施建议

| 优先级 | 事项 |
|:--:|------|
| P0 | 激活流程 `activation.ux` 的 `deviceId` 改为取值降级链，**不要再让 `NA` 直接进 URL**（`NA` 是 truthy，会绕过 fallback） |
| P0 | 明确产品文案：激活绑定的是"当前设备 + 当前安装"，重装需重新激活 |
| P1 | 服务端加：激活码次数上限、IP/时间窗限速、`deviceId=NA`/`fingerprint#` 上报监控 |
| P1 | 弱指纹字段固化（型号 / 固件 / 平台版本 / 分辨率 / API Level），并在服务端留版本位，便于日后调整 |
| P2 | 若日后引入账号体系，升级为方案 D |

---

## 八、结论

| 问题 | 结论 |
|------|------|
| 本地 UUID 能用吗？ | **不能**当设备唯一标识（软件生成、可清除、不唯一） |
| 能再加一个硬件标识吗？ | **不能**——系统不提供，客户端拿不到 |
| 那怎么办？ | 改用「本地安装 UUID + 弱指纹 + 服务端次数/风控」模型（方案 B+C） |
| getInfo 红色是坏了吗？ | 不是，接口正常，只是返回里没有标识字段 |
| 其他全红说明什么？ | Vela 在该设备上不暴露任何硬件级唯一标识（与系统权限收紧一致） |
