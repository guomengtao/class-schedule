## 一、代码证据：手环端主动发送已完整实现

### 1.1 核心发送函数

所有发送最终都走 `connect.send()`，位置在 [src/app.ux](file:///Users/Banner/Documents/guomengtao/ev/class-schedule/src/app.ux)：

```js
function syncReply(connect, payload) {
  try {
    connect.send({ data: payload })   // ← 这就是发送
  } catch (e) { ... }
}
```

### 1.2 手环主动发送的三种场景

| 场景 | 入口 | 发送内容 | 说明 |
|---|---|---|---|
| **聊天消息**（手环主动说话） | `chatBridge.send(text)` | `{action:"chat", id, text, ts}` | 留言板页面输入文字后点发送，手环**主动**把消息推给手机 |
| **工具箱指令**（遥控手机） | `chatBridge.sendCmd(type, params)` | `{action:"cmd", type, ...}` | 如"查找手机"、"静音"、"倒计时"——手环**主动**遥控手机 |
| **所有应答回包** | `syncReply()` | `{ok:true, action:"ping"\|"export"\|...}` | 手机问、手环答——虽是被动触发，但走的也是 `send` |

实现文件：[src/data/chat-bridge.js](file:///Users/Banner/Documents/guomengtao/ev/class-schedule/src/data/chat-bridge.js)

### 1.3 跨文件副本问题已解决

由于 aiot 打包会把 `chat-bridge.js` **分别打进** `app.js` 和页面文件（两份互不相干的副本），之前存在"app.ux 注册了 connect，但留言板页面拿不到"的 bug。

现已通过**三级取用机制**解决（见 [chat-bridge.js](file:///Users/Banner/Documents/guomengtao/ev/class-schedule/src/data/chat-bridge.js#L38-L73)）：

```
① 本文件内 register() 注入的 connect
② 全局桥 globalThis.__evSyncConnect（app.ux 注册时顺手挂一份）
③ 自己 require @system.interconnect 取实例（兜底）
```

这意味着任意页面都能获取到 connect 并发消息。

## 三、历史疑点：S1′ 实验的"0 条"结论

### 3.1 当时的实验

`docs/EV课程表主动发送测试消息到插件.md` 记录了早期的一次反向通道测试（S1′）：

- **已知**：插件能拉起 EV（手环立即打开），插件 register/send 返回 Ok
- **问题**：ping/export 回包**从未到达插件**（0 条 InterconnectMessage）
- **实验设计**：在手环 EV 上添加测试按钮，让 EV **主动**调用 `connect.send()` 发消息
- **目的**：一刀劈开是"插件→EV 方向"问题还是"宿主派发"问题

### 3.2 实验预期结论

| 实验结果 | 结论 |
|---|---|
| EV 主动发的消息被插件收到 ✅ | 插件订阅 + 宿主派发正常 → 问题在插件→EV 方向 |
| EV 主动发的消息也收不到 ❌ | **插件订阅或宿主派发有问题** → 与 EV 业务逻辑无关 |

### 3.3 当时的状态

该文档在背景中写道：

> 当前状态：**插件已确认能拉起 EV**（手环上 EV 课程表能立即打开），但 `ping`/`export` 回包从未到达插件。

这说明在文档写作时，**反向通道（手环 → 插件）被怀疑不通**。

## 五、需要确认的关键问题

### 5.1 最核心的问题

> **S1′ 实验的最终结果是什么？**
>
> - 如果结果是"收到了" → 反向通道通，手环可以主动给同步器发消息 ✅
> - 如果结果是"收不到" → 问题在 Vela 宿主层（路由/派发），不在 EV 代码 ❌

### 5.2 当前代码的证据

从代码角度看，手环端已经完全准备好了：

1. `connect.send()` 调用路径完整且正确
2. 跨文件副本问题已通过全局桥解决
3. 协议格式与插件侧约定一致（`{data: object}` 而非字符串）
4. 后台常驻确保通道不因应用切后台而断

### 5.3 如果反向通道仍然不通

可能的根因（按优先级）：

| 可能性 | 说明 | 验证方式 |
|---|---|---|
| **Vela 宿主层路由问题** | `connect.send()` 调了，但宿主没有把消息通过 BLE 路由回手机 | 看插件日志是否有 InterconnectMessage 事件 |
| **interconnect 通道未真正建立** | `onopen` 回调可能没触发，或连接状态不是 ready | 检查 `getReadyState` 返回值 |
| **AstroBox 宿主侧 `register_interconnect_recv` 订阅问题** | 插件注册了接收，但宿主没有正确派发 | 检查插件日志 + 插件注册代码 |
| **BLE 协议层单向** | 某些 Vela/BLE 版本可能只支持手机→手环方向 | 查阅 Vela 官方文档 |

## 六、验证方案

### 6.1 最快的验证方法

在手环留言板页面发一条消息，同时观察插件日志：

```
手环端：留言板 → 输入文字 → 发送（走 chatBridge.send，即 connect.send）
插件端：查看日志是否出现 EventType::InterconnectMessage，payload 含 action:"chat"
```

如果插件收到了，说明反向通道完全正常。

### 6.2 替代验证（不改代码）

任何会触发 `syncReply` 的操作都能验证：
- 插件发 ping → 手环回 pong
- 插件发 export → 手环回课表数据
- 插件发 import → 手环回 ok

**如果这些回包插件能收到，就说明反向通道是通的。**
