# 跑道屏设备「输入法打不开」差异分析（手环 9 / 手环 11 vs 手环 10 Pro）

> 日期：2026-09-25
> 代码基线：v1.6.103（`src/manifest.json` versionName）
> 现象：真机测试中，**小米手环 11、小米手环 9（跑道屏）**进入中文输入页后键盘出不来（用户描述为"输入法打不开"）；**小米手环 10 Pro（方形屏）**同版本正常。
> 文档性质：代码静态分析 + 可执行的真机判定步骤。凡标注「待真机确认」的，需用第 5 章的步骤取到真机日志后定案，不要在没取证前改代码。

---

## 〇、先说结论

**键盘能不能出来，只由一条链条决定：**

```
device.getInfo().screenShape
        ↓  （chinese-input.ux 做一次值转换）
screenType（传给 <input-method> 的 screentype）
        ↓  （InputMethod.ux 三个 if 严格等值匹配）
命中 circle / rect / pill-shaped 之一 → 该分支的键盘渲染
一个都没命中                          → 键盘区完全空白 = "打不开"
```

10 Pro 之所以没事：它的 `screenShape` 是标准的 **`rect`**，命中方屏分支，而**方屏分支是三套实现里唯一的纯 flex 相对布局**（`width:100%` + `justify-content:center`），既不用固定像素坐标，也不依赖 `screenWidth` 算居中。

9 / 11 之所以打不开：跑道屏走的是**胶囊分支**，而它是三套实现里最脆的一套 —— **唯一使用「固定 305px 高度 + 绝对定位 + `(screenWidth - 192) / 2` 算居中」** 的分支。链条上任何一环取值异常（屏型值不认识、`screenWidth` 拿错、竖直空间不够），结果都是"键盘不渲染"或"键盘被推出可视区"。

**换句话说：这不是"输入法在跑道屏上坏了"，而是"跑道屏分支的取值链条没有兜底"。**

### 结论一：R1「屏型值未命中三分支」被实测排除 ✅

两台设备的 `screenShape` 都是 **`pill-shaped`**（不是 `capsule`，也不是空值）。

→ `src/pages/chinese-input/chinese-input.ux:83-87` 会把它原样传给组件 → 组件 `screentype==='pill-shaped'` 分支**必定命中**。
→ **"屏型不命中导致三分支全空"不再成立，R1 划掉。**

### 结论二：R2 的「居中量算错」被排除，但首帧偏移仍需确认

实测代入 `(screenWidth - 192) / 2`：

- 手环 9：`(192 - 192) / 2 = 0` ✅
- 手环 11：`(212 - 192) / 2 = 10` ✅

居中量完全正确。而且激活页能取到全部字段，说明 `@system.device` 在两台设备上都正常。
→ R2 的"`getInfo` 失败 → 兜底 336 → 偏移 72px"分支概率大幅下调。
→ 仅保留小尾巴：`src/components/InputMethod/InputMethod.ux:358` 的初始值 `screenWidth: 336` 会让**首帧**产生 `(336-192)/2 = 72px` 的偏移，是否存在可见的错位闪烁需真机确认（低优先级）。

### 结论三：R4「vibrator 顶层导入」被间接排除 ✅

`src/components/InputMethod/InputMethod.ux:293` 是顶层 `import vibrator from "@system.vibrator";`。若该模块在设备上不可用会导致模块解析失败，那么**用同样方式导入的 `src/pages/activation/activation.ux:246` 也会崩** —— 而这两台设备刚刚成功跑完激活页并生成了带全部字段的 URL。

→ **R4 降级，不再是首要怀疑。**

### 结论四：唯一能同时解释「两台跑道屏都失败」的因素 —— 竖直高度不够 ⭐

胶囊分支是全仓**唯一固定高度 305px** 的键盘分支；且键盘上方还有一条 `if="{{screentype !== 'circle'}}"` **常驻**的 28px 拼音小字行（`src/components/InputMethod/InputMethod.ux:12`）。两者合计 **333px**。

| `.header` | `height 48 + margin-bottom 8` | 56 |
| `.input-display` | `min-height 44 + padding 16 + border 4 + margin-bottom 6` | 70 |
| `.done-row` | `done-btn height 38 + margin-bottom 4` | 42 |
| **固定占用合计** | | **198** |

### 结论五：`scroll` 包住"绝对定位根节点"是结构性放大项

组件根节点 `.page` 是 `position: absolute; left: 0; bottom: 0`：

```760:765:src/components/InputMethod/InputMethod.ux
.page {
	width:100%;
	position:absolute;
	left:0;
	bottom:0
}
```

却被挂在 `src/pages/chinese-input/chinese-input.ux:33` 的 `<scroll class="keyboard-scroll" scroll-y="true">` 里。绝对定位元素不参与 scroll 的内容高度计算 —— 一旦键盘所需高度超过 scroll 可视高度，`bottom: 0` 的贴底行为会把溢出部分推到可视区**上方**（而不是下方），用户不主动滑动就看不到 → 表现得像"键盘没出来"。

→ 与结论四叠加，这也是建议**优先改结构**的原因。

### 结论六：新暴露的两个独立问题（与本次现象无关，但要记台账）

1. **`w = 212` 是项目首次出现的胶囊宽度。** 全项目胶囊规范（字号阶梯、`week-view` 列宽 `160 ÷ cellWidth`、192px 居中算法）都按 **192** 定标。212 比基准宽 **10.4%**，需单独评估。本次输入法恰好因为 `(212-192)/2 = 10px` 而无恙，其它页面不保证。
2. **`t = band`，而 `src/manifest.json:8-10` 的 `deviceTypeList` 只有 `["watch"]`。** 两台设备都自报 `band`。该字段主要影响"寻址/筛选"，实测不阻断安装与运行；但设备类型与声明不符是否会在运行时触发能力限制，暂无证据，列为待验证项（历史上曾因"手环 11 装不上"加过 `band`，属推测性方案）。
3. 手环 11 的 `o = 0`（`osVersionCode` 未返回），说明新机型 ROM 字段完整度与手环 9 不同 —— 后续"按字段判断能力"的代码不能假设字段一定存在。

## 补充二：症状修正 —— 手环 9 是「进页面即重启」（2026-09-25 二次追加）⭐

### 症状修正（这一条推翻前文的整个方向）

测试同学补充：**手环 9 上的真实症状是「点进输入法页面就直接导致手环重启」，不是「进得去但看不见键盘」，是根本进不去。**

这条修正的影响是根本性的：

| 之前的假设 | 为什么现在不成立 |
|---|---|
| R3 竖直高度不足 | 布局溢出只会"显示不全/被裁"，**不可能让整机重启** |
| R2 居中量偏移 | 同上，纯视觉问题 |
| 全部布局类根因 | 症状是**系统级复位（崩溃）**，必须找"能打崩系统"的东西：主线程长时间阻塞触发看门狗、或内存耗尽 OOM、或渲染引擎崩溃 |

**手环重启的三种典型成因**：① 主线程阻塞超看门狗阈值；② 内存峰值耗尽堆；③ 渲染引擎非法输入直接崩。下面两条假设分别对应 ①② 和 ③。

### 新首要假设 W1：进页面即「同步全量初始化」，注释与实现已漂移 ⭐⭐⭐⭐⭐

`dicUtil.js` 的文件末尾写着这样的设计说明：

```490:491:src/components/InputMethod/assets/dicUtil.js
// 注意：initDict 不再于模块加载时同步执行。
// 由 InputMethod.ux 在 onInit 中 setTimeout 延迟到首帧渲染后调用，避免模块加载阻塞首屏。
```

**但实现不是这样。** `InputMethod.ux` 的实际代码是**同步直调**，没有 `setTimeout`：

```399:426:src/components/InputMethod/InputMethod.ux

    var ml = parseInt(this.maxlength);
    ...
    if (!this.hide) {
      // 挂载即展开的用法：键盘子树直接创建并保活
      this.keyboardCreated = true
      this._ensureDictInit();
    }
```

```699:703:src/components/InputMethod/InputMethod.ux
  _ensureDictInit() {
    if (this.__dictInitStarted) return
    this.__dictInitStarted = true
    SimpleInputMethod.initDict()
  },
```

而调用方 `chinese-input.ux` 传的是 **`hide="{{ false }}"`**：

```34:42:src/pages/chinese-input/chinese-input.ux
      <input-method
        hide="{{ false }}"
        keyboardtype="QWERTY"
        maxlength="{{ maxlen }}"
        vibratemode="short"
        screentype="{{ screenType }}"
        oncomplete="onCharacter"
        ondelete="onDeleteChar"
      ></input-method>
```

→ `hide=false` 使 `onInit` 里 `if (!this.hide)` **必定成立** → **一进页面就同步跑完整词典初始化**。注释里承诺的"延迟到首帧渲染后、避免阻塞首屏"**在这个页面上完全失效**。

`initDict()` 的同步工作量（`dicUtil.js:23-49`）：

| 步骤 | 内容 | 是否分片 |
|---|---|:---:|
| `getDict()` → `py2hz` | 建 **6763** 条拼音→单字对象 | ❌ 同步 |
| `getDictJp()` → `romaji2kanji` | 建日文罗马字表 | ❌ 同步 |
| `new Set(syllables)` + `for key in py2hz` | 建 **~6763 项** 音节 Set，并逐键写入 `py2hz2` | ❌ 同步 |
| `getWords()` → `words` | 建 **~3000** 条词对象 | ❌ 同步 |
| `getInitialsIndex()` | 建简拼倒排索引（815 行数据） | ❌ 同步 |
| `_buildForwardIndex()` | 建前向索引 | ✅ 唯一分片（200 词/片） |

**只有最后一项是分片的**，前五项全部在进页面的那一刻同步完成。叠加同一时刻模板首次构建的 **200+ 节点 / 60+ PNG**（组件注释自证），在 RTOS 手环上极易造成主线程长时间阻塞（看门狗复位）或堆内存峰值（OOM 复位）。

这条假设同时命中了两个关键差异：
- **为什么是"点页面就重启"**：因为重活在 `onInit` 里就做完了，用户根本没机会操作。
- **为什么 10 Pro 正常**：方屏设备的 RAM / CPU 余量更大，同样的峰值扛得住。

### 新次要假设 W2：胶囊分支独有的 `progress type="arc"` + 非法负角度 ⭐⭐⭐⭐

```229:231:src/components/InputMethod/InputMethod.ux
      <div if="{{screentype==='pill-shaped'}}" style="width: 100%;height: 305px">
        <div static style="position:absolute;left:0px;top:34px;width:100%;height:276px;">
          <progress percent="{{30+percent66}}" type="arc" style="start-angle:204deg;total-angle:-48deg;width:188px;height:188px;top:82px;left:2px;position:absolute;color:#ffffff;stroke-width:6px;layer-color:#262626;margin-left: {{(screenWidth - 192)/2}}px;"></progress>
```

- **全仓只有胶囊分支用 `type="arc"`**：方屏分支是普通线性 progress（无 `type`），圆屏分支干脆没有 progress。
- 而且 `total-angle: -48deg` 是**负数**，属于非标准用法。渲染引擎若对负角度处理不当（除零、绘制循环无法收敛），可能直接崩掉渲染进程并触发系统复位。

这条的吸引力在于：**它严格只影响跑道屏**，与"9/11 挂、10 Pro 好"的现象完全吻合。但它是渲染层的猜测，需实测（V2）验证。

### 修复建议（对应 W1 / W2）

1. **兑现注释里的设计意图**：`_ensureDictInit()` 改为异步 + 分片：

```javascript
// 建议写法：先让出一帧，再把大表构建拆成片
_ensureDictInit() {
  if (this.__dictInitStarted) return
  this.__dictInitStarted = true
  setTimeout(function () { SimpleInputMethod.initDict() }, 0)
}
```

## 二、代码事实（可核对）

### 2.1 组件只认三个值，第四个值会让键盘整个不渲染

`InputMethod.ux` 的 `screentype` prop 默认 `"circle"`，模板里三个键盘分支是并列的严格等值判断：

```326:328:src/components/InputMethod/InputMethod.ux
    screentype: {
      default: "circle",
    },
```

```16:16:src/components/InputMethod/InputMethod.ux
      <div if="{{screentype==='circle'}}" style="width: 480px;height: 321px;">
```

```146:146:src/components/InputMethod/InputMethod.ux
      <div if="{{screentype==='rect'}}" style="width: 100%;height: 255px;flex-direction: column">
```

```229:229:src/components/InputMethod/InputMethod.ux
      <div if="{{screentype==='pill-shaped'}}" style="width: 100%;height: 305px">
```

**关键点：这三行没有 `else` 兜底。** 只要 `screentype` 是第四个值（例如 `"pill"`、`"band"`、`"capsule"` 本身、空串以外任意非预期字符串），三个分支全部为 false → 键盘一个像素都不渲染 → 用户看到的就是"输入法打不开"（页面只剩 header、输入框、"完成"按钮）。

### 2.2 页面侧的屏型映射不完整，且没有失败兜底

```81:89:src/pages/chinese-input/chinese-input.ux
    device.getInfo({
      success: function(data) {
        var shape = data.screenShape || "circle"
        if (shape === "capsule") {
          shape = "pill-shaped"
        }
        self.screenType = shape
      }
    })
```

这段代码有三个洞：

1. **只转换 `"capsule"` 一种别名**。若设备返回的是其它字面值，会被**原样**传给组件 → 命中 2.1 的"三分支全空"。
2. **`|| "circle"` 的兜底帮了倒忙**。跑道屏上若 `screenShape` 为空/缺失，会落到 `"circle"`，而 circle 分支是**写死 480×321 的圆表键盘** —— 在 192px 宽的跑道屏上只能显示左上角一小块，视觉上和"打不开"很难区分。
3. **没有 `fail` 回调**。`device.getInfo` 失败时 `screenType` 保持初始值；这里初始值恰好是 `"pill-shaped"`，算是不幸中的万幸，但这属于巧合而非设计。

### 2.3 三套屏型判定口径互相矛盾

同一个 `screenShape`，项目里至少存在三种解释：

| 位置 | 判定写法 | 是否认识 `capsule` |
|------|---------|:---:|
| `src/pages/chinese-input/chinese-input.ux:84` | `capsule → pill-shaped` | ✅ |
| `src/pages/index/index.ux:232` | `capsule \|\| pill-shaped` | ✅ |
| `src/pages/week-view/week-view.ux:316` | `capsule \|\| pill-shaped` | ✅ |
| `src/pages/device-info/device-info.ux:41-45` | 只映射 `rect` / `circle` / `pill-shaped` | ❌（`capsule` 会原样显示） |

多处页面同时写 `capsule || pill-shaped`，反证了**真机上确实见过 `capsule` 这个返回值**。而 `device-info` 页（我们准备用来取真机数据的那一页）偏偏不认识 `capsule` —— 取证时看到英文原文不要误判为异常。

### 2.4 胶囊分支是全仓最脆的一段布局

```229:232:src/components/InputMethod/InputMethod.ux
      <div if="{{screentype==='pill-shaped'}}" style="width: 100%;height: 305px">
        <div static style="position:absolute;left:0px;top:34px;width:100%;height:276px;">
          <progress percent="{{30+percent66}}" type="arc" style="start-angle:204deg;total-angle:-48deg;width:188px;height:188px;top:82px;left:2px;position:absolute;color:#ffffff;stroke-width:6px;layer-color:#262626;margin-left: {{(screenWidth - 192)/2}}px;"></progress>
          <scroll id="keyboard66" scroll-x="{{true}}" onscroll="handelScroll" style="padding-left: {{(screenWidth - 192)/2}}px;padding-right: {{(screenWidth - 192)/2}}px;">
```

```269:269:src/components/InputMethod/InputMethod.ux
        <div static style="position: absolute;left: {{(screenWidth - 192)/2}}px;top: 0px;width: 192px;height: 110px;">
```

- 键盘高度**硬编码 305px**，另外键盘外上方还有一条 `height: 28px` 的拼音小字行（`.cvalrow-wrap`，见 `InputMethod.ux:852-856`），实际占用 **≈333px**。
- 水平居中量 = `(screenWidth - 192) / 2`，**完全依赖 `screenWidth` 的取值正确**。

### 2.5 `screenWidth` 的取值链有三处风险

```358:358:src/components/InputMethod/InputMethod.ux
    screenWidth: 336,
```

```409:411:src/components/InputMethod/InputMethod.ux
    if (this.screentype === "rect" || this.screentype === "pill-shaped") {
      this.adjustScreenWidth();
    }
```

```742:755:src/components/InputMethod/InputMethod.ux
  adjustScreenWidth(){
    var self = this;
    device.getInfo({
      success: function(data) {
        self.screenWidth = data.screenWidth;
        // 胶囊屏更多候选面板：宽度适配视口，保证左右各留 6px 边距
        self.l66DownPanelWidth = Math.min(Math.max(data.screenWidth - 12, 120), 192);
      },
      fail: function() {
        self.screenWidth = 336;
        self.l66DownPanelWidth = 192;
      }
    })
  }
```

| 风险 | 后果 |
|------|------|
| 初始值 `screenWidth: 336` 是**方屏基准**，首帧先按 336 渲染 → 胶囊屏首帧 padding = `(336-192)/2 = 72px` | 键盘首帧被右推 72px |
| `fail` 兜底同样写死 **336**（方屏基准） | 一旦 `getInfo` 失败，胶囊屏**永久**右推 72px；192px 宽的屏上 192px 键盘 + 72px 左偏移 → 右半部分被切出屏幕 |
| `self.screenWidth = data.screenWidth` **不做任何校验**（不判空、不判断是逻辑像素还是物理像素） | 若返回 `undefined` → `(undefined-192)/2 = NaN` → `padding-left: NaNpx` 无效；若返回物理像素（如 390/432）→ padding 变成 99~120px，键盘被整体推出可视区 |

**这一条是"10 Pro 正常、9/11 打不开"最干净的解释**：方屏分支（`rect`）压根不使用 `screenWidth`，所以这三个风险对它全部免疫。

### 2.6 组件根节点是绝对定位，却放在外层 `<scroll>` 里

```2:2:src/components/InputMethod/InputMethod.ux
  <div class="page" style="flex-direction: column; height: {{hide ? '0px' : 'auto'}}; overflow: {{hide ? 'hidden' : 'visible'}};">
```

```760:765:src/components/InputMethod/InputMethod.ux
.page {
	width:100%;
	position:absolute;
	left:0;
	bottom:0
}
```

而调用侧把组件塞进了一个纵向 `scroll`：

```32:43:src/pages/chinese-input/chinese-input.ux
    <!-- 键盘区：下展面板已移除，不再存在「scroll 套 list」的嵌套滚动冲突，恢复原有 scroll 包裹 -->
    <scroll class="keyboard-scroll" scroll-y="true">
      <input-method
        hide="{{ false }}"
        keyboardtype="QWERTY"
        maxlength="{{ maxlen }}"
        vibratemode="short"
        screentype="{{ screenType }}"
        oncomplete="onCharacter"
        ondelete="onDeleteChar"
      ></input-method>
    </scroll>
```

`.page` 是 `position:absolute; bottom:0`，**绝对定位元素不参与父级 scroll 的内容高度计算**。在方屏上键盘只有 255px、余量充足，问题被掩盖；在跑道屏上键盘高 333px、可视余量本来就紧张（见 2.7），`bottom:0` 的贴底行为就可能把键盘推到可视区之外，只留下一条黑边 —— 同样表现为"打不开"。

### 2.7 跑道屏的竖直空间本来就比方屏紧

`chinese-input.ux` 的纵向结构是：`header 48px + 输入框 ≈44px + 完成按钮 38px + 键盘 ≈333px`，再加上 `.page` 的 `padding-top: 30px`，正常需要 **≈500px** 以上的可用高度。

方屏键盘只有 255px，余量宽裕；跑道屏键盘是 305px（+28px 拼音行），**余量最小**。因此"竖直方向被裁"这个问题也只会在跑道屏暴露。

## 六、修复建议

### 6.1 最小改动（先让 9/11 能用）

1. **给 `screenShape` 一个统一的归一化函数，并增加未知值兜底**。建议新建 `src/data/screen.js` 集中维护，替换掉当前散落在各页的判定：

```javascript
// 归一化屏型：所有页面统一调用，杜绝"某页认识 capsule、某页不认识"
function normalizeScreenShape(shape, screenWidth) {
  if (shape === "capsule" || shape === "pill-shaped" || shape === "pill") return "pill-shaped"
  if (shape === "rect") return "rect"
  if (shape === "circle") return "circle"
  // 未知/空值不猜屏型，改用宽度判断（跑道屏为 192）
  return (screenWidth && screenWidth <= 240) ? "pill-shaped" : "rect"
}
```

2. **组件三分支加兜底**，杜绝"一个都不命中"：

```html
<!-- 思路：显式列出合法的 pill 值，其余非 circle/rect 的输入一律按 pill 渲染 -->
<div if="{{screentype !== 'circle' && screentype !== 'rect'}}" style="width: 100%;height: 305px">
```

3. **`screenWidth` 加校验与正确兜底**：拿不到或数值明显不合理（≠192 量级）时，不要退回方屏基准 336，而应按屏型分别设默认值（胶囊 192 / 方屏 336）。

4. **居中量对 NaN 免疫**：把 `{{(screenWidth - 192)/2}}` 换成脚本里预先算好的字段（`pillPadX`），在 `adjustScreenWidth` 里统一 `Math.max(0, Math.round(...))` 并处理 `NaN`。

5. **`device.getInfo` 补 `fail` 回调**（`chinese-input.ux` 当前完全没有），失败时按上一帧屏型或宽度兜底，并打日志。

### 6.2 结构性改动（建议排期）

1. **取消组件根节点的 `position:absolute; bottom:0`**，改为普通流式布局（`width:100%`），让它能参与外层 scroll 的高度计算。
2. **让键盘高度自适应**：胶囊分支不要写死 `305px`，改为由 `screenHeight - 已占用高度` 计算，最低保证 3 行按键（≥ 210px）可点。
3. **拼音小字行（28px）改为不占高度**（叠加显示），为窄屏省出竖直余量。
4. **把屏型判定收敛到唯一入口**，并顺手把 `device-info` 的 `screenShapeMap` 补上 `capsule`，避免取证时误判。

## 八、结论

1. **直接原因**：跑道屏设备走的胶囊分支，是全仓唯一"严格等值匹配 + 固定高度 + 依赖 `screenWidth` 算居中 + 组件根绝对定位"的布局路径，链条上没有任一层兜底；任何一环取值异常，结果都是键盘不渲染或被推出可视区。
2. **为什么 10 Pro 正常**：方屏分支不吃这三类风险（相对布局、不依赖 `screenWidth`、竖直余量宽裕）。**它的正常不能反证胶囊分支无问题。**
