## 1. 背景：router.push() 和 router.back() 是什么

### router.push()

```js
router.push({ uri: "/pages/settings" })
```

**含义**：在当前页面**之上**创建一个新页面实例，压入页面栈。旧页面**不销毁**，只是被遮住。

```
push 之前:  [ 首页 ]
push 之后:  [ 首页, 设置页 ]   ← 首页还活着，还在内存里
```

### router.back()

```js
router.back()
```

**含义**：从页面栈**弹出**最顶层的页面，该页面被**销毁**（触发 `onDestroy`），露出下面一层。

```
back 之前:  [ 首页, 设置页, 详情页 ]
back 之后:  [ 首页, 设置页 ]       ← 详情页被销毁
```

### router.replace()

```js
router.replace({ uri: "/pages/index" })
```

**含义**：用新页面**替换**当前页面，当前页面被销毁，**栈深度不变**。

```
replace 之前:  [ Welcome页 ]
replace 之后:  [ 首页 ]           ← Welcome页被销毁，栈深度 = 1
```

### 类比：一叠纸

| 操作 | 比喻 |
|------|------|
| `router.push()` | 往纸堆上**放一张新纸**，旧纸还在下面 |
| `router.back()` | 从纸堆上**拿走最上面那张**，扔进垃圾桶 |
| `router.replace()` | 把当前这张纸**抽出来换一张新的**，纸堆高度不变 |

### 为什么 push 会造成问题？

**穿戴设备内存极小**（~64MB）。每个页面实例占用约 1-3MB（DOM 树 + 数据绑定 + 定时器闭包 + 缓存）。

如果一个用户点一条路径：
```
首页 → 设置 → 课表管理 → 周视图 → 课程详情 → 编辑课程 → back → back → back → back → back
```

在这个路径中，页面栈最多达到 **6 层**。6 × 2MB = **12MB**，占可用内存的 ~30%。

更糟的是：**每个被遮住的页面还在跑定时器**——状态条每 60 秒刷新一次，课程进度条每 60 秒刷新一次，自定义内容轮播每 3 秒切换一次。页面越多，定时器越多，CPU 越忙。

## 2. 黑屏的完整因果链

```
第 1 步：用户正常使用，router.push() 层层叠加
        页面栈：首页 → 设置 → 课表管理 → 周视图 → 详情（5层）

第 2 步：每个页面创建 setInterval 定时器
        首页：  status-bar(60s) + class-list(60s) + custom-content(3s) = 3个定时器
        设置页：无定时器但占用 DOM 内存
        课表管理：无定时器但占用 DOM 内存
        周视图： 无定时器但占用 DOM 内存
        详情页： 无定时器但占用 DOM 内存

第 3 步：所有页面的 onDestroy() 都不被调用（因为页面还在栈里）
        定时器持续运行，即使页面被遮住、用户看不到

第 4 步：如果用户又打开了 message-inbox（聊天页）
        message-inbox 加了一个 setInterval(pollPeerTyping, 1000)
        每秒轮询一次！在所有定时器里这是最慢的杀手

第 5 步：CPU 被打满
        同时运行中的定时器：status-bar + class-list + custom-content + typing-poll
        = 至少 4 个 interval 在并发运行
        UI 主线程被定时器回调抢占 → 用户点击响应变慢 → "越来越卡"

第 6 步：内存持续增长
        每个定时器回调都持有页面实例的闭包引用
        → 页面实例无法被 GC 回收
        → database.js 的 _cache 也在累积
        → 可用内存越来越少

第 7 步：内存耗尽
        穿戴设备只有 ~64MB 内存
        系统检测到内存不足 → 杀掉应用
        或：GPU 无法分配帧缓冲 → 渲染管线断裂

第 8 步：黑屏
        用户看到的是：卡 → 更卡 → 黑屏 → 应用重启
```

### 实际测量数据

| 指标 | 数值 |
|------|------|
| `router.push()` 总调用次数 | **84** |
| `router.back()` 总调用次数 | **66** |
| `router.replace()` 总调用次数 | **1** |
| push/back 比率 | **1.27 : 1**（push 多于 back，栈会越来越大） |
| 无 `onDestroy` 页面数 | **43 / 64**（67% 的页面无法释放资源） |
| 有定时器但无清理 | **2** 个页面 |
| 最高危定时器 | message-inbox 每秒轮询 |
| 模块级单例泄漏 | custom-content.js、database.js |

## 3. 修复方案（按优先级排列）

### 修复 P0-1：所有页面在 onHide 时停止定时器，onShow 时恢复

**为什么这是最重要的**：页面的 `onDestroy` 只有 `router.back()` 时才会触发，而 push 出去的页面只触发 `onHide`。在 `onHide` 停止定时器，在 `onShow` 恢复，这样被遮住的页面就不会消耗 CPU。

**改法（以首页 index.ux 为例）**：

```js
// ===== 新增 onHide =====
onHide() {
  // 被遮住时停止所有定时器，释放 CPU
  if (this.loadTimeout) {
    clearTimeout(this.loadTimeout)
    this.loadTimeout = null
  }
  if (this.stopStatusTimer && typeof this.stopStatusTimer === 'function') {
    this.stopStatusTimer()
  }
  if (this.stopProgressTimer && typeof this.stopProgressTimer === 'function') {
    this.stopProgressTimer()
  }
  if (modules.customContent && modules.customContent.destroy) {
    modules.customContent.destroy()
  }
},

// ===== onShow 中恢复 ====
onShow() {
  var self = this
  if (!self.initialized) return

  // ... 现有的 onShow 逻辑 ...

  // === 新增：恢复定时器 ===
  if (self.startStatusTimer && typeof self.startStatusTimer === 'function') {
    self.startStatusTimer()    // 重新启动状态条定时器
  }
  if (self.startProgressTimer && typeof self.startProgressTimer === 'function') {
    self.startProgressTimer()  // 重新启动进度条定时器
  }
  if (modules.customContent && modules.customContent.refresh) {
    modules.customContent.refresh(self)  // 重新启动轮播
  }
}
```

**受影响的页面清单**（有定时器的生产页面）：

| 文件 | 定时器 | 优先级 |
|------|--------|--------|
| `src/pages/index/index.ux` | statusTimer + progressTimer + rotationTimer | 🔴 P0 |
| `src/pages/message-inbox/message-inbox.ux` | typingTimer (1s 轮询) | 🔴 P0 |
| `src/pages/countdown-manage/countdown-manage.ux` | deleteTimer + clearTimer (setTimeout) | 🟡 P1 |
| `src/pages/detail/detail.ux` | deleteTimer + undoTimer | 🟡 P1 |

### 修复 P0-2：首页 → Settings/课表管理等页面改用 replace 而非 push

**为什么**：用户从首页跳到设置页，通常不需要按"返回"回到之前那个首页实例——首页只是重新渲染一遍。`router.replace` 会销毁旧首页，创建新首页，栈深度不变，内存不会增长。

**改法**：

```js
// ===== 之前（会累积页面栈）=====
openSettings() {
  router.push({ uri: "/pages/settings" })
}

// ===== 之后（栈深度不变）=====
openSettings() {
  router.replace({ uri: "/pages/settings" })
  // replace 会：
  // 1. 销毁当前首页实例（触发 onDestroy → 清理所有定时器）
  // 2. 创建设置页实例
  // 3. 栈深度不变（还是 1 层）
}

// 设置页返回首页也是 replace：
// settings 的 goBack():
goBack() {
  router.replace({ uri: "/pages/index" })
  // 销毁设置页，创建新首页
}
```

**适用 replace 的页面跳转**：

| 起点 | 终点 | 原因 |
|------|------|------|
| 首页 | 设置页 | 不需要回到旧首页实例 |
| 首页 | 课表管理 | 同上 |
| 首页 | 添加课程 | 同上 |
| 首页 | 周视图 | 同上 |
| 设置页 | 首页 | 返回到新首页即可 |
| 课表管理 | 首页 | 同上 |
| 课表管理 | 周视图 | 不需要回到课表管理 |

**不适用 replace 的跳转**（必须用 push/back）：

| 场景 | 原因 |
|------|------|
| 详情页 ← 返回 → 首页 | 用户需要"返回上一页"的体验 |
| 激活/付费弹窗 | 关闭后必须回到触发页 |

### 修复 P1-1：custom-content.js 模块级 _timer 改为实例级

**问题**：`_timer` 是模块级变量，所有页面实例共享同一个。如果同一个页面的多个实例先后调用 `init()`，第二个 `init` 的 `startRotation` 会覆盖第一个的 `_timer`，但第一个页面实例的闭包仍在引用旧的定时器回调。

**改法**：

```js
// ====== 之前 ======
var _timer = null

function init(instance) {
  // ...
  instance._rotationTimer = null
}

function startRotation(instance) {
  stopRotation()
  // ...
  instance._rotationTimer = setInterval(function() { ... }, interval * 1000)
  // 定时器存到实例上，而不是模块级
}

function stopRotation(instance) {
  if (instance._rotationTimer) {
    clearInterval(instance._rotationTimer)
    instance._rotationTimer = null
  }
}

function destroy(instance) {
  stopRotation(instance)
}

// ====== 之后（定时器挂到实例上）======
// 删除模块级 var _timer = null

function init(instance) {
  instance._rotationTimer = null
  // ...
}

function startRotation(instance) {
  stopRotation(instance)   // 传 instance
  // ...
  instance._rotationTimer = setInterval(function() {
    // callback logic
  }, interval * 1000)
}

function stopRotation(instance) {
  if (instance._rotationTimer) {
    clearInterval(instance._rotationTimer)
    instance._rotationTimer = null
  }
}

function destroy(instance) {
  stopRotation(instance)
}
```

**调用方也要改**（index.ux 的 onDestroy）：

```js
onDestroy() {
  // ...
  if (modules.customContent && modules.customContent.destroy) {
    modules.customContent.destroy(this)  // 传入 this
  }
}
```

### 修复 P1-2：message-inbox 1s 轮询优化

**问题**：`setInterval(pollPeerTyping, 1000)` 每秒触发一次，即使手机端没有在打字也在轮询。

**改法**：用 `globalThis` 事件驱动代替轮询。

```js
// ====== 之前 ======
startTypingPoll() {
  this.stopTypingPoll()
  this.typingTimer = setInterval(function () {
    self.pollPeerTyping()
  }, 1000)
}

// ====== 之后（事件驱动）======

// 在 app.ux 的 syncHandleChatIncoming 中设置钩子：
// 当收到 typing 消息时，直接触发页面刷新

// message-inbox.ux
startTypingPoll() {
  this.stopTypingPoll()
  // 改为 5 秒兜底轮询 + 事件驱动
  this._pendingTypingRefresh = false
  this._onTypingChange = function() {
    if (!this._pendingTypingRefresh) {
      this._pendingTypingRefresh = true
      var self = this
      setTimeout(function() {
        self.pollPeerTyping()
        self._pendingTypingRefresh = false
      }, 200)  // 防抖 200ms
    }
  }.bind(this)

  // 兜底轮询降到 5s（而不是 1s）
  this.typingTimer = setInterval(function() {
    self.pollPeerTyping()
  }, 5000)

  // 注册 globalThis 监听
  globalThis.__evTypingNotify = this._onTypingChange
}

stopTypingPoll() {
  if (this.typingTimer) {
    clearInterval(this.typingTimer)
    this.typingTimer = null
  }
  if (this._onTypingChange) {
    delete globalThis.__evTypingNotify
    this._onTypingChange = null
  }
}
```

兜底 5 秒轮询保证了即使事件丢失也不会"卡住显示正在输入"。

### 修复 P2-2：database.js 缓存加淘汰策略

**问题**：`_cache` 对象按索引存课表数据，在多课表场景下会无上限增长。但当前场景通常会限制课表数量（最多 ~10 套），影响有限。

**改法**（如果将来课表数量可能很多）：

```js
var _cache = {}
var _cacheOrder = []   // LRU 队列
var MAX_CACHE = 5      // 最多保留 5 套课表的缓存

function setCache(index, data) {
  if (_cacheOrder.length >= MAX_CACHE) {
    var oldest = _cacheOrder.shift()
    delete _cache[oldest]
    delete _cacheDirty[oldest]
  }
  _cache[index] = data
  _cacheDirty[index] = false
  _cacheOrder.push(index)
}
```

## 5. 定时器用途说明

### 为什么会有定时器？

课表应用需要"根据时间变化来更新 UI"。系统不会主动通知"过了午夜"或"下一节课开始了"，所以必须用 `setInterval` 轮询。

### 现有定时器清单

| # | 位置 | 代码 | 间隔 | 用途 |
|---|------|------|------|------|
| ① | `status-bar.js` | `setInterval(updateStatus, 60000)` | **60 秒** | 检测是否过了午夜、星期几变了，更新状态条文案 |
| ② | `class-list.js` | `setInterval(updateClassProgress, 60000)` | **60 秒** | 根据当前时间更新每节课进度状态（还没上/进行中/已结束），卡片变色 |
| ③ | `custom-content.js` | `setInterval(rotate, N*1000)` | **3~10 秒** | 首页下方轮播励志语录/小贴士，用户可配置间隔 |
| ④ | `message-inbox.ux` | `setInterval(pollPeerTyping, 1000)` | **1 秒** ⚠️ | 轮询手机端是否正在打字，显示"正在输入…" |

### 定时器不是问题，问题是"页面被遮住了还在跑"

打个比方：

> 你离开房间时，灯还开着，电视还开着，空调还开着。
> 去第二个房间，又开一套灯+电视+空调。
> 去第五个房间，总电闸跳了——**黑屏**。

定时器 ①②③④ 本身合理。只要确保 `onHide` 时关掉（停止定时器），`onShow` 时再开回来，就不会有累积效应。

## 6. 内存使用统计（PerfMonitor）

### 6.1 能做什么、不能做什么

QuickApp 框架**没有直接的内存 API**（没有 `system.getMemoryInfo()`），无法获取精确的 MB 数值。但可以通过 **3 个间接指标**推算健康度：

| 指标 | 含义 | 健康阈值 |
|------|------|----------|
| **页面栈深度** | 当前有多少个页面在栈里 | ≤ 3 绿色，4-5 黄色，≥ 6 红色 |
| **活跃定时器数** | 当前有多少个 setInterval 在跑 | ≤ 3 绿色，4-5 黄色，≥ 6 红色 |
| **帧间隔时间** | 每一帧渲染花了多少毫秒 | < 50ms 正常，50-200ms 黄色，> 200ms 红色（卡顿） |

### 6.2 模块：`src/data/perf-monitor.js`

已创建专用性能监控模块，API 如下：

```js
var monitor = require("./data/perf-monitor.js")

// --- 接入 app.ux 路由钩子 ---
// 每次 router.push 时调用:
monitor.onPush("/pages/settings")

// 每次 router.back 时调用:
monitor.onBack()

// 每次 router.replace 时调用:
monitor.onReplace("/pages/index")

// --- 接入每个页面的定时器 ---
// 创建定时器时:
monitor.registerTimer("statusBar", 60000)
self.statusTimer = setInterval(...)

// 销毁定时器时:
monitor.unregisterTimer("statusBar")
clearInterval(self.statusTimer)

// --- 帧率监控 ---
monitor.startFrameCheck()   // app.ux onInit 中启动
monitor.stopFrameCheck()    // app.ux onDestroy 中停止

// --- 随时获取健康报告 ---
var report = monitor.getReport()
console.log(JSON.stringify(report, null, 2))
// 输出:

//   "stackDepth": 3,
```

### 6.3 健康评分算法

```
初始 100 分
  页面栈 ≥ 6 层   → -30
  页面栈 ≥ 4 层   → -10
  活跃定时器 ≥ 6  → -25
  活跃定时器 ≥ 4  → -10
  丢帧 > 10       → -20
  丢帧 > 3        → -5

≥ 80 分 → GREEN  (健康)
50-79分 → YELLOW (注意)
<  50分 → RED    (危险，快黑屏了)
```

### 6.4 接入计划

**第一优先级**：`app.ux` 中接入 `onPush` / `onBack` / `onReplace`，所有页面自动统计栈深度。

**第二优先级**：index 首页的 3 个定时器 + message-inbox 的 1 个定时器接入 `registerTimer` / `unregisterTimer`。

**第三优先级**：调试模式下在页面角落显示健康灯（绿/黄/红小圆点），方便测试时一眼判断。
