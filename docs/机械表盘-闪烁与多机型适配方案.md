| # | 现象 | 定位 | 影响面 |
|---|------|------|--------|
| 1 | 每秒整页闪一下 | 渲染管线：每秒 6 次 setData 触发全树重绘 | 所有机型 |

## 二、问题一：每秒整页闪

### 2.1 现象还原

`tick()` 每秒被 `setInterval` 调一次，内部连续写 6 个数据字段：

```js
tick() {
  this.timeText = pad2(...) + ":" + pad2(...)   // ①
  this.dateText = ...                            // ②
  this.dayText  = pad2(...)                      // ③
  this.syncHands()                               // ④⑤⑥ 三个 cls
}
```

### 2.2 根因推断

Vela（`minPlatformVersion 1050`）的 setData 走的是**「一次赋值 = 一次脏标记 = 一轮 diff + 一次整屏重绘」**，旧管线**不会把同一帧内的多次赋值合并**。

于是每秒发生：

| 字段 | 真实变化频率 | 当前实际写入频率 | 浪费倍数 |
|------|--------------|------------------|----------|
| `timeText`（时:分） | 1 次 / 60 s | 1 次 / 1 s | **60×** |
| `dateText`（日期+星期） | 1 次 / 天 | 1 次 / 1 s | **86400×** |
| `dayText`（日期窗数字） | 1 次 / 天 | 1 次 / 1 s | **86400×** |
| `hourCls` | 1 次 / 6 min（3°/档） | 1 次 / 1 s | 360× |
| `minuteCls` | 1 次 / 30 s（3°/档） | 1 次 / 1 s | 30× |
| `secondCls` | 1 次 / 1 s | 1 次 / 1 s | 1×（本来就要） |

**每秒 6 轮全树 diff + 6 次整屏重绘**，而页面有约 150 个绝对定位节点。手表 SoC 上单轮重绘就要 100 ms 量级，6 轮挤在 1 秒内 → 视觉上就是「整页一直在闪」。

侧证：上一版 EV 指针表盘（423 行）每秒只改 3 个 cls，没有收到闪烁反馈；机械表盘多了 3 个**文本**字段（文本节点重建成本高于纯 class 切换），闪烁变可见。

### 2.3 修复三档（按性价比排序）

**P0 · 脏值判断（必做，改动 15 行）**

```js
tick() {
  const now = new Date()
  const t = pad2(now.getHours()) + ":" + pad2(now.getMinutes())
  if (t !== this.timeText) this.timeText = t          // 每分钟 1 次
  const d = pad2(now.getMonth() + 1) + "-" + pad2(now.getDate()) + " " + FULL_DAY[now.getDay()]
  if (d !== this.dateText) this.dateText = d           // 每天 1 次
  const day = pad2(now.getDate())
  if (day !== this.dayText) this.dayText = day          // 每天 1 次
  this.syncHands()                                      // 内部同样加脏判断
}
```

稳态下每秒只剩 `secondCls` 一次写入（且秒针 cls 本就是 1/秒）。**6 次 → 1 次**。

**P1 · 秒针降频（可选，看 P0 效果）**
秒针改成 2 秒一跳（`s % 2`），真机械表是扫秒，2 跳/秒已经没有"秒针"的精度语义损失（手表屏本来也不是秒表）。setData 降到 0.5 次/秒。

**P2 · 合并写入（兜底，需先验证 API）**
若 P0 后仍有轻微闪动，把三针的字符合并成一次「档位组合」写入 —— 但那样就要回到动态 class 串（历史结论：整串动态 `class="{{cls}}"` 会让应用启动即退），**不可行**。备选是自定义组件封装秒针（隔离重绘范围），但 Vela 组件隔离效果未验证，成本高，留作最后手段。

### 2.4 验收方法

连拍 12 帧（间隔 0.4 s），对每帧算**全屏平均亮度**，看抖动幅度：

- 修复前：帧间亮度标准差明显（整屏重绘导致亮度台阶）
- 修复后：帧间亮度仅随秒针位置微变（0.2 以内）
- 兜底：真机录屏看肉感，用户确认"不闪了"

## 三、问题二：10 Pro 偏左、不居中、不放大

### 3.1 事实

| 机型 | AVD | 分辨率 | 短边 | 相对 192 基准 | 当前表现 |
|------|-----|--------|------|---------------|----------|
| 手环 9 标准 | `xiaomi_band` | 192×490 | 192 | 1.00 | ✅ 正常（设计基准） |
| 手环 10 | `xiaomi_band_10` | 212×520 | 212 | 1.10 | 偏小、右侧留 20px |
| 9 Pro / **10 Pro** | `xiaomi_band_pro` | **336×480** | 336 | **1.75** | ❌ **靠左，右侧空 144px** |
| REDMI Watch 6 | `redmi_watch` | 432×514 | 432 | 2.25 | ❌ 更明显 |
| Watch S4 | `xiaomi_s4` | 466×466 | 466 | 2.43 | ❌ 更明显 |

`manifest.json` 里 `config.designWidth = "device-width"` —— 含义是「按设备实际宽度算设计宽度」，即 **1px = 1 物理像素，引擎不做任何缩放**。而页面里 150 个节点的 left/top/width 全是对着 192×490 的截图手调出来的像素值。

结论：**不是布局 bug，是"没做适配"** —— 内容天生只有 192 宽，放在 336 宽屏里当然靠左。

### 3.2 目标

```
表盘直径 = 短边 × 0.875        （192 基准下 168/192 = 0.875，保持不变）
表盘水平居中                    （左右留白相等）
表盘垂直位置 = 屏高 × 0.42 中心  （略偏上，给底部时间/日期让位）
品牌字、底部信息 = 随表盘等比，但不参与"整页缩放"（否则方屏会溢出）
```

用户诉求「自适应加大」= 让表盘在 336×480 上直径约 294px（168×1.75），而不是现在的 168px 硬塞在左边。

### 3.3 三条候选路线

#### 方案 A：vw 单位（首选，若引擎支持）

把 192 基准的 `Npx` 全局换算成 `N × (100/192) vw = N × 0.5208vw`。

- 优点：**无需机型判断**，任意屏宽（含未来机型）自动铺满；水平天然居中（因为父容器本来就是 100% 宽）；代码量 = 一次全局正则替换。
- 缺点：垂直方向用 vw 也会等比放大，490 基准在 480 高的方屏上会溢出 830/490 = 1.75 倍 → **页面上半部分（表盘）必须与下半部分（信息）解耦**，信息区用固定 px 或 vh。
- **待验证**：Vela 引擎是否支持 `vw` 单位（快应用规范以 px/% 为主，vw 属实现相关）。

#### 方案 B：transform: scale 档位（次选）

按短边算 `k = min(W,H)/192`，向下取档（1.0 / 1.1 / 1.75 / 2.25 / 2.4），给"表盘舞台"容器套 `transform: scale(k)`。

- 优点：复用本项目已验证的「字面量 transform + 静态 class 档位」套路；只改容器不动 150 个内部坐标。
- 优点：**已知引擎轴心 = 元素顶部中点**（2026-10-19 四色标定结论），所以只要把舞台水平居中，缩放会以中点为中心向两侧膨胀 → **水平居中自动成立**，垂直位置可按公式写进档位 class。
- 缺点：档位离散，非标机型落在档间会有 ±8% 误差（可接受）。
- **待验证**：`scale()` 是否生效、轴心是否同样在顶部中点（rotate 和 scale 可能走不同分支）。

#### 方案 C：多套坐标表（兜底，不推荐）

按机型准备 192 / 336 两套 left/top。成本 = 再写一遍 150 个坐标，且每加一个元素都要改两处。**否决**。

### 3.4 决策：先标定，再选 A 或 B

写一个一次性标定页 `pages/scale-lab`，同屏放 4 个 40×40 色块：

| 块 | 写法 | 验证点 |
|----|------|--------|
| 1 | `left: 20vw; top: 20px` | vw 是否生效（是否落在 20% 屏宽处） |
| 2 | `transform: scale(2)`，left/top 固定 | scale 是否生效 |
| 3 | 同上 + 中心打点 | 缩放轴心（顶部中点 / 元素中心 / 左上） |
| 4 | `transform: scale(1.5) rotate(20deg)` | scale 与 rotate 是否叠加冲突（走针要用 rotate） |

实拍 10 Pro + 9 标准两台，读像素位置即可判定。**标定页用完即删，不进提交**。

### 3.5 布局改造（A/B 通用）

不管走 A 还是 B，页面都要从「单一直角坐标系」拆成两个区：

```
┌─────────────────────────┐
│                         │
│   ┌───────────────┐     │  ← 表盘区（等比缩放，水平居中）
│   │  MECHANICAL   │     │
│   │  ╭─────────╮  │     │
│   │  │ 168 表盘 │  │     │
│   │  ╰─────────╯  │     │
│   └───────────────┘     │
│                         │
│      10-19 周日         │  ← 信息区（独立定位，贴底）
│        17:24            │
│       轻触返回           │
└─────────────────────────┘
```

- **表盘区** `.stage`：内含品牌两行 + 上下表耳 + `.dial-wrap`，内部坐标从原 192 坐标系整体上移 50px（因为品牌字 top 50 是最上元素），得到 stage 本地坐标 `〔0, 250〕`。
- **信息区** `.info`：`date-line` / `time-line` / `back`，用档位 class 分别定位到屏底，字号随 k 微调（`font-size` 也走档位，不靠 scale 放大文字，避免位图虚化）。
- **三针的 `.rN` 120 档完全不动** —— 它们作用在针元素上，舞台 scale 作用在祖先容器上，两层 transform 不冲突（前提：针元素自身不能再套 scale）。

### 3.6 档位表（若走方案 B）

`k = 短边 / 192`，取 5 档：

| 档 | k | 短边 | 机型 | 表盘直径 | 舞台 left（W−192k)/2 | 舞台 top |
|----|---|------|------|----------|----------------------|----------|
| `.g1` | 1.00 | 192 | 手环 9 | 168 | 0 | 118（现状） |
| `.g2` | 1.10 | 212 | 手环 10 | 185 | 9 | 0.42×520 − 84×1.10 = 126 |
| `.g3` | 1.75 | 336 | 9 Pro / 10 Pro | 294 | 0 | 0.42×480 − 84×1.75 = 55 |
| `.g4` | 2.25 | 432 | REDMI Watch 6 | 378 | 0 | 0.42×514 − 84×2.25 = 27 |
| `.g5` | 2.40 | 466 | S4 | 403 | (466−461)/2 = 2 | 0.42×466 − 84×2.40 = −6 |

> 注：`left` 必须让**未缩放**的舞台先水平居中，缩放才会围绕屏心对称膨胀。`top` 是未缩放时舞台顶部，因为轴在顶部中点，垂直方向不位移。

机型判定用 `device.getInfo().screenWidth/screenHeight`（项目里 `week-view`、`device-info` 等页已在用这个 API），取短边落档。

## 六、实测标定结果（2026-10-19 17:2x，10 Pro 336×480）

在真机模拟器上做了三组标定，结论推翻了方案初稿的两条假设：

| # | 测试项 | 写法 | 实测结果 | 判定 |
|---|--------|------|----------|------|
| 1 | `scale()` 是否生效 | `.back` 加 `transform: scale(2)` + 红底 | 红块宽度由 192 变 384、文字同步放大 | ✅ **生效** |
| 2 | scale 的轴心 | 同上（元素 left=0，中点在 x=96） | 左边缘仍在 x=0 不动，向右溢出 → 轴在**左上角** | ✅ 轴 = 元素左上角（与 rotate 的"顶部中点"**不同**） |
| 3 | `vw` 是否生效 | `.vw-lab { left:25vw; width:50vw }` | 实测落在 x=25 宽 50 → vw 被当成 px | ❌ **不支持** |

**方案 A（vw）当场否决**，只能走方案 B 方向。

### 6.1 致命发现：祖先 scale + 子孙 rotate 会让应用启动即退

把 `.stage` 套 `transform: scale(1.75)` 包住表盘（内部 9 根针 + 60 个刻度都有 `rotate`）后：

- 构建正常（15s 无 error）
- **应用启动即退出**，`ps` 查不到 vapp 进程，连拍全黑
- 摘掉 scale 后同一结构**立刻恢复**（冷启出画 14.0s）
- 在无 rotate 子孙的元素上单独用 scale（测试 1）则完全正常

→ 这是继「旋转父元素里嵌子 div」之后发现的**第二条嵌套 transform 雷区**：
**祖先带 transform、子孙又带 transform，会导致 JSC 层崩溃**。表盘不能用整块 scale 放大。

### 6.2 可用的替代路径（已验证不崩）

| 能力 | 可行性 | 证据 |
|------|--------|------|
| 动态内联 `style="left:{{x}}px;width:{{w}}px"` | ✅ 可用 | `.stage` 尺寸/位置改为动态绑定，冷启出画 14.1s |
| 百分比定位 `left: 6.25%` / `width: 87.5%` | ✅ 可用 | `.dial-wrap` 改百分比后正常，表盘随容器等比变化 |
| 容器嵌套多一层（page > stage > dial-wrap） | ✅ 安全 | 三容器结构本身不导致崩溃 |
| 动态 class 绑在容器上 | ✅ 安全 | `class="stage {{stageCls}}"` 正常 |

→ **适配的正确路线是「动态尺寸 + 百分比坐标」，不是 scale。**

### 6.3 当前落地进度

已完成并上线：

- 闪烁修复（脏值判断），`watch-face-gold.ux` 877 行，构建 16.9s，10 Pro 实拍出画正常。
- 三个容器拆分（`.brandbox` / `.stage` / `.info`）+ 5 档位表 + `device.getInfo` 选档逻辑已写好并验证不崩（保存在 `/tmp/fit-wip-2.ux`，未提交）。

未完成（下一轮必须做）：

- 表盘内部约 100 个元素的 left/top/width/height 仍是 **168 基准 px**，需要全部换算成相对 `.dial-wrap` 的百分比（`value / 168 * 100`），否则外壳放大而刻度针不动。
- 13 个 `text` 的 `font-size` 需要改成按 k 计算的动态绑定。
- 完成后在 192×490 / 336×480 / 466×466 三机型实拍验收。

> 换算脚本要点：只改 `.dial-wrap` 子树内的样式（8 层表壳、刻度、时标、三针、日期窗、螺钉、盘心），
> `.rN` 的 rotate 角度与针的 left/top 基准**不要动**（角度与尺寸无关，位置除以 168 即可）。

## 七、结论

- **闪烁**：根因是每秒 6 次无意义 setData，P0 脏值判断即可解决 90%，改动 15 行，风险极低。**建议直接做。**
- **10 Pro 适配**：完全可行，但**必须先标定 vw / scale 是否可用**（历史教训：这台引擎的 transform 行为与标准 CSS 有偏差，凭猜测写必翻车）。标定 1 次构建 + 1 次实拍就能定方案，之后改造只动容器与信息区，150 个内部坐标零改动。
