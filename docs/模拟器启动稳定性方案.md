# Vela 模拟器启动稳定性方案

> 目标：**简单、保留（不破坏数据）、稳定、快速**地启动模拟器；清理残留；杜绝多实例并存。
> 依据：2026-09-29 故障实例 + `docs/qa-reports` 历史记录 + `.codebuddy/memory` 沉淀。

## 二、深层机制分析（为什么会僵死 / 崩溃 / 慢）

### 2.1 为什么 guest adb 会僵死
- guest 的 adbd 跑在 NuttX 上，**部署用 `adb shell unzip` 长命令**；宿主 adb 客户端被杀（或 IDE 断开）时，guest 侧 shell 会话可能没有干净回收，adfd 进入不再接受新连接的状态。
- 表现即"控制台通、shell 不通"——此时**重试部署只会继续挂**，唯一出路是重启实例。

### 2.2 为什么会崩溃 / 变慢
- **多实例并存**是主因：每个 qemu 实例约 1–2GB 内存 + 持续 CPU；3 个并存时 IDE 的部署/日志通道还要区分 serial，很容易把命令发到错误实例后干等超时。
- **端口约定**：console 端口 = adb serial 数字部分（5554），gRPC = console + 3000（8554）。多实例时端口分配靠 qemu 自增，上一次异常退出留下的**半开端口/锁**会让新实例漂移到 5556/5558，进一步放大"打错实例"的概率。
- **渲染通道**：`-qt-hide-window` 无头模式省资源但用户不可见；带窗模式偶尔与 macOS 窗口合成器冲突造成白/黑窗，`1373B 纯黑 PNG` 是判空判据（见第五节）。

### 2.3 为什么 IDE 表现为"没反应"
IDE 的运行链路是串行的：构建 → adb 推包（unzip）→ `vapp` 启动。第 2 环卡死时，IDE 不报错只转圈，用户看到的就是"点了没反应"。**所以先查 `adb shell unzip` 残留进程，再看实例本身。**

## 三、稳定启动方案（规则 + 脚本）

### 3.1 五条铁律
1. **单实例**：启动前先 `status`，同 AVD 已在跑就**复用**，绝不并启第二个。
2. **先探活再部署**：`shell echo alive` 通了才推包；不通 → 重启实例，不要重试部署。
3. **只用启动器**：一律通过 `~/.vela/sdk/emulator/darwin-aarch64/emulator` 拉起，**禁止直接跑 qemu-system-armel**（dyld 必挂）。
4. **带窗口**：日常启动**不加** `-qt-hide-window`；无头只用于 CI/巡航取证。
5. **日志落盘**：启动日志写 `/tmp/vela_emu_<avd>.log`，出问题先看日志再猜。

### 3.2 脚本用法（`scripts/emu-start.sh`）

```bash
bash scripts/emu-start.sh status          # 看在跑实例、探活、端口
bash scripts/emu-start.sh start xiaomi_band   # 单实例启动（已跑则复用）
bash scripts/emu-start.sh stop  xiaomi_band   # 停一个
bash scripts/emu-start.sh stop  all           # 全停
bash scripts/emu-start.sh clean               # 清残留（卡死 adb 客户端、孤儿 crashpad、死实例锁）
```

脚本行为约定：
- `start`：已有同 AVD 存活 → 直接打印 serial 退出（**不启第二个**）；发现 guest 僵死的旧实例 → 自动 `stop` 后重启；启动后轮询 `shell echo alive`（约 40s 超时），通了才报成功。
- `stop`：只杀对应 qemu 与其 crashpad；**绝不碰应用数据目录**（`/data/quickapp/app/<pkg>/` 在 AVD 磁盘镜像里，进程级停止不损伤）。
- `clean`：只清三类安全目标——①命令行含 `unzip -o /data/quickapp` 的卡死 adb **客户端**；②父进程已死的 crashpad 孤儿；③**确认无 qemu 在跑时**才把 AVD 目录的 `*.lock` 移入 `/tmp/trash/<时间戳>/`（用 `mv`，全程零 `rm -rf`）。

### 3.3 IDE 侧配合
- 在 IDE 点运行**之前**先跑 `status` 确认目标实例 guest 活着；IDE 卡转圈超过 30s 时，先 `clean` 再 `stop` + `start`，**不要连点运行**。
- 同时只保留一个 AVD 的窗口；xiaomi_band_pro / band_10 用完即 `stop`。

## 四、残留清理清单

| 目标 | 判定 | 动作 |
|---|---|---|
| 卡死部署进程 | 命令行含 `adb … shell unzip -o /data/quickapp` | `kill <pid>`（客户端，安全） |
| guest 僵死实例 | `emu avd name` 通 + `shell echo` 不通 | `stop` 后 `start` |
| 孤儿 crashpad | 父 qemu 已不在 | `kill <pid>` |
| AVD 锁残留 | **无任何 qemu 进程**时存在 `*.lock` | `mv` 到 `/tmp/trash/<ts>/`（禁 rm -rf） |
| 黑窗实例 | gRPC 截图恒为 1373B 且 `vapp` 拉不起 | `stop` 重启 |

## 五、快速排障决策表

| 症状 | 第一查 | 判据 | 处置 |
|---|---|---|---|
| IDE 点运行没反应 | `ps aux \| grep "shell unzip"` | 有残留部署进程 | `clean` → `status` → 重试 |
| 模拟器窗口不见了 | qemu 进程在不在 | 进程在但无窗口 | 上次用了 `-qt-hide-window`，`stop` 后 `start`（带窗） |
| 部署一直转圈 | 探活两步法 | `emu avd name` 通、`shell echo` 不通 | guest 僵死：`stop` + `start` |
| 画面纯黑 | gRPC 截图字节数 | 恒 1373B | 应用没起：`vapp app/<pkg> &`；拉不起则重启实例 |
| 直接跑 qemu 报 dyld | 启动方式 | 缺 `libandroid-emu-tracing.dylib` | 改用 SDK 启动器（铁律 3） |

**探活两步法**（本项目标准判据）：
```bash
ADB=<项目>/node_modules/@aiot-toolkit/emulator/node_modules/@miwt/adb/bin/mac/adb
$ADB -s emulator-5554 emu avd name      # 通 = 宿主侧 qemu 活着
$ADB -s emulator-5554 shell echo alive  # 通 = guest adb 活着（可部署）
```

## 六、已知限制与后续

- 本脚本未做 IDE 集成；IDE 内部拉起实例的逻辑不可控，只能靠「启动前 status」规避打错实例。
- 若后续要支持多机型并行联调（pro + band 同时跑），需把 `start` 改为按 AVD → serial 映射管理，并给 `deploy` 命令显式带 `-s <serial>`；当前版本刻意只保单实例。
- 2026-09-29 会话的执行通道输出异常（同一命令两次结果矛盾），本文档证据均取自交叉验证过的输出；脚本运行时行为请以实测为准，发现问题直接改本文件附 PR。
