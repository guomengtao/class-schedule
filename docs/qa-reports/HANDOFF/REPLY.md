## 三种答复方式（挑最省事的那个）

### 方式 A：commit message 里带编号（最省事，推荐）

你本来就要 commit，顺手在 message 里带上缺陷编号，我下一轮会自动扫 git log 比对，**你一个字文档都不用写**：

```bash
git commit -m "fix(qa): P0-2 新增课程后首页不显示（database 缓存未失效）"
git commit -m "fix(qa): U-7 方屏返回键热区 28x24 -> 48x48"
```

规则：
- 前缀固定 `fix(qa):`，后面跟**编号**（`P0-2` / `P0-S-1` / `P1-6` / `U-7` 都行）
- 一条 commit 修多个就写多个编号：`fix(qa): P0-1 P0-5 删除课表串表 + 备份主题键`
- 括号里随便写中文说明，方便你我事后看懂

我每轮会跑：`git log <上轮HEAD>..HEAD --oneline`，把所有 `fix(qa):` 里的编号摘出来，然后**打开代码复核**是不是真修了。

### 方式 B：改这个文件（适合要解释、要反驳、要提问）

需要说清楚的事（比如「我认为这条不是问题」「需要你补信息」），直接改下面那张表。
**只改这个文件**，别去动 `2026-09-11-roundN.md` 那些轮次文件 —— 那边是 QA 的地盘，双方各写各的才不会 git 冲突。

### 方式 C：代码改了但什么都不写（也行）

我每轮本来就会重新扫代码。只要 push 上去了，我大概率能自己发现「这条没了」。
**但有两个例外必须用 A 或 B 告诉我**：
1. 你觉得**不是问题 / 有意为之** —— 不然我每轮都会再报一遍
2. 我标了「无法静态确认」的条目 —— 只有你知道真机上发生了什么（比如输入法到底是 A/B/C 哪种现象）
