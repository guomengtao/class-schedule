# 一套 CSS 自适应方案分析

> 目的：回答「能否用一套 CSS 自适应覆盖所有手环屏幕，还是要按屏幕分套处理」。
> 结论先行：**纯一套「零分屏」不可行**。正确结构是 **「base CSS = 手环 9 基准 + 宽度断点增量 + 圆屏特例」**——彻底抛弃 `@media (shape: pill-shaped)` 这类黑屏高危写法，用宽度断点替代所有 shape 查询（只留 circle 因为圆方不同构）。本文是 [手环9黑屏根因定位](./手环9黑屏根因定位-pill-shaped分支已验证-编辑页修复.md) 讨论后的深化方案。

---

## 一、真实的屏宽跨度

| 屏 | shape | 物理分辨率 | 内容区宽 | 相对 9 |
|----|------|-----------|:---:|:---:|
| 小米手环 9 | pill-shaped | 192×490 | **160px** | 1×（基准） |
| 小米手环 10 / 10 Pro | capsule | 212×520 | 180px | 1.13× |
| REDMI Watch 6 | rect | 432×514 | ~400px | 2.5× |
| 圆形表盘（Watch S 等） | circle | ~466×466 | ~430px | 2.7× |

> 宽度来源：`src/pages/width-detect/width-detect.ux` 实测。跨度最大 2.7×。这是本文所有讨论的物理基准。

---

## 二、推荐结构（改进版）

```
base CSS（无 media query）
  → 为手环 9 设计（160px 内容区基准）
  → 字号：9 能放得下的最大值
  → 按钮 ≥ 48px 起，间距紧凑但不拥挤
  → 弹性 flex + % 撑满，不写死 px 宽
  → 手环 9 默认命中，无需任何 media query

    ├── @media (width >= 200px)
    │     手环 10 / 胶囊屏大号
    │     只调「多出来的空间」：字号略大、间距略松

    ├── @media (width >= 400px)
    │     Watch 6 / 方屏
    │     字体再大一级、可多列、留白更多

    └── @media (shape: circle)
          圆形表盘（唯一保留的 shape 查询）
          圆屏需要放射/居中布局，不是宽度能区分的
```

### 为什么这个结构更好

| 要点 | 说明 |
|------|------|
| **手环 9 零风险** | base CSS 就是为它写的，不需要任何 media query 命中就能正常渲染。没有 `(shape: pill-shaped)` 就不会触发黑屏 |
| **宽度断点比 shape 查询更稳定** | 宽度是物理现实，不会因厂商改 shape 名而失效。`@media (width >= 100px)` 已实测在手环 9 上匹配正常 |
| **大屏「增量」而非「覆盖」** | 大屏在 base 基础上只调多出来的空间怎么用，不改 base 已有的值。base 始终是安全兜底，大屏分支出错也只是「不够好看」，不会崩 |
| **圆屏单独保留 shape:circle 是必要的** | 圆形和方形是排版哲学差异——466px 的圆屏和 432px 的方屏宽度差不多，但布局完全不同。这一点无法用宽度断点替代 |

## 三、和旧方案的关键区别

| | 旧方案（已废弃） | 改进方案（推荐） |
|---|---|---|
| base CSS 的设计目标 | 「各屏都凑合能用的通用值」 | **专门为手环 9 设计**（最小屏基准） |
| 分屏机制 | 宽度断点 or 逗号组合（含 shape） | **只用宽度断点**，彻底不用 shape 查询（除 circle） |
| shape 查询 | 保留 rect / circle | **只保留 circle**（圆方不同构），rect 也用宽度断点 |
| 大屏适配 | 覆盖 base | 在 base 之上 **「加量」**（增量） |
| 手环 9 安全 | 靠绕坑（逗号让 9 忽略分支） | **零依赖**（base 本身就为 9 写，不依赖任何媒体查询命中） |

## 四、手环 9 媒体查询踩坑速查（写进决策依据）

> 详见 `docs/media-query逗号不兼容手环9.md` 与 `docs/手环9黑屏根因定位*.md`。

| 写法 | 手环 9 结果 | 安全性 |
|------|:---:|:---:|
| `@media (shape: pill-shaped)` 独立大块 | 🟢 命中 → **已实锤会黑屏重启** | ☠️ 禁止 |
| `@media (shape: capsule), (shape: pill-shaped)` 逗号 | 🔴 整条失效 → 跳分支走 base | ⚠️ 临时止血可用，不推荐长期依赖 |
| `@media (width >= 100px)` | 🟢 已实测可匹配 | ✅ 推荐 |
| `@media (shape: circle)` | 9 不命中 → 无害 | ✅ 安全（圆屏专用） |
| `@media (shape: rect)` | 9 不命中 → 无害 | 改为宽度断点更优 |

## 五、「一套 base 弹性」的优点

弹性布局（flex 撑满 + 百分比 + min-width + margin:auto），能自动覆盖大约 80~90% 的屏差异：

| 可自适应 | 说明 | 例子 |
|------|------|------|
| 元素宽度 | `width:100%`、`flex:1`、`min-width:0` | 卡片、按钮行、输入框随屏宽自动满宽或均分 |
| 元素排列 | `flex-direction` / `flex-wrap` 窄屏自动换行竖排 | 表单在 160px 自动竖排，宽屏自动横排 |
| 间距与留白 | `%`、flex gap、`margin:0 auto` | 宽屏间距自动宽松、窄屏自动收紧 |
| 文案安全 | `min-width:0` + 允许换行，不写死单行截断 | 避免窄屏把标题挤出屏幕 |

**项目现状佐证**：全仓 55 个页面里已有 436 处使用百分比 `%`，弹性 base 的地基已经存在。

## 六、一套 CSS 做不到的（硬局限，非写法问题）

### 1. 字号无法随屏自动缩放（最大硬伤）
- 固定 px 字号（如 24px）在 160px 内容区只能放 ~3 字，在 430px 屏能放 ~8 字。
- `vw` 相对单位在手环快应用中未验证。
- 结论：字号必须用宽度断点分级调整，一套值无法兼顾。

### 2. 物理可点目标（48px）的数量上限差异
- 160px 宽一排最多放 3 个 48px 按钮，430px 屏能放 8 个。
- 弹性只能「均分」不能「按屏变数量」——160px 屏放 4 个按钮会压到 44px（合规红线）。

### 3. 圆屏 vs 方屏是排版哲学差异
- 圆形表盘要留安全区、放射/居中分布；方屏/胶囊是上下堆叠卡片流。
- 不是缩放能转换的——所以 circle 保留独立分支。

### 4. 不同屏的信息密度层级
- 大屏可以「一屏多列、信息丰富」，小屏只能「一条一条、极简」。
- 弹性只能同构缩放，无法自动重排成另一个信息层级。

## 七、难以实现的效果（明确清单）

以下效果用一套 CSS 极难达成、必须通过宽度断点（或圆屏分支）处理：

1. **字号分级随屏缩放**——标题/正文在大屏更大、小屏更小且各自可读
2. **大屏多列 / 小屏单列的层级重排**——弹性只能缩放，不能改变列数
3. **圆形放射式 / 环形布局**——与方屏卡片流完全不同构
4. **按钮数量按宽度自动增减**——触控目标上限是写死的物理值
5. **各屏差异化留白气质**——相对间距只能做到一致的松紧比例
6. **每行文案期望长度**——大屏想展示 8 字、小屏只要 3 字，受固定 px 字号限制

## 八、落地路径

```
Phase 1：detail 样板重构
  ① 读懂 detail 当前的 base CSS（无 media query 部分）
  ② 把它重新调整为「手环 9 基准」——字号/间距/按钮以 160px 为准
  ③ 把原 pill-shaped 分支的有效值归类：弹性能解决的归 base，物理必须区分的用宽度断点
  ④ 删除独立的 @media (shape: pill-shaped) 大块

Phase 2：三屏复测
  复测 9 / 10Pro / 圆形，各屏截图，对照眼睛核对清单逐项过

Phase 3：推广
  schedule-manager → 其余有独立 pill-shaped 分支的页面

Phase 4：沉淀规范
  后续新页面按此书写，从源头避免独立 shape 大分支
```

## 九、备选思路：JS 驱动动态缩放（暂不推荐）

如果在 JS 里能可靠读到屏幕宽度（`$device` 或类似 API），可以算一个缩放系数，CSS 全部用动态 px，零 media query。

| 优点 | 缺点 |
|------|------|
| 真正的「一套」，永远不崩 | 需要确认快应用 JS API 能否拿到可靠宽度 |
| 所有尺寸按比例自动缩放 | 性能开销（每次渲染都要算） |
| | CSS 失去静态分析能力 |

**对当前项目判断：过度设计**。宽度断点方案已经够用且稳定，引入 JS 动态计算增加运行时风险面，不值得。
