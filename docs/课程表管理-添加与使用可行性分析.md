## 〇、直接回答你的两个问题

### Q1：课程表可以添加吗？

**官方入口不行，实际可以。**

| 路径 | 未解锁用户 | 已解锁用户 |
|---|---|---|
| 点「+ 新增课程表」 | ❌ **弹「解锁高级版」弹窗**，加不了 | ✅ 能加 |
| 点课表 → 「复制」 | ✅ **能加，且不加任何限制** | ✅ 能加 |

第二条就是漏洞。`copySchedule()` 与 `addSchedule()` 走的是**两套完全不同的门禁**：

```js
// schedule-manager.ux:569  ← 真门禁（异步查本地解锁状态）
addSchedule() {
  store.isPremiumUnlocked(function(unlocked) {
    if (unlocked) { self.doAddSchedule() }
    else          { self.showDialog = true }   // 弹解锁弹窗
  })
}

// schedule-manager.ux:157  ← 假门禁（写死）
checkProAccess() {
  return true
}

// schedule-manager.ux:391  ← 用了假门禁
copySchedule(index) {
  if (!this.checkProAccess()) return     // 恒为 true，永远不拦
  ...
  names.push(newName)                    // 同样是在新增一条课表
  store.setScheduleNames(names, ...)
}
```

**`checkProAccess()` 是一个空壳**——函数体只有 `return true`。它被 5 个操作调用，
所以这 5 个操作**对未解锁用户全部开放**：

| 行号 | 方法 | 对应按钮 | 门禁是否生效 |
|---|---|---|---|
| 324 | `startRename` | 重命名 | ❌ 失效 |
| 392 | `copySchedule` | **复制** | ❌ 失效（**可绕过付费墙新增课表**） |
| 466 | `openQrPopup` | 导出（二维码） | ❌ 失效 |
| 481 | `openWeekView` | 总览 | ❌ 失效 |
| 496 | `openScheduleStats` | 统计 | ❌ 失效 |
| 569 | `addSchedule` | **+ 新增课程表** | ✅ **唯一生效的** |

结论很反直觉：**付费墙只挡住了「新增」这一个按钮，而「复制」同样能增加课表数量却没人管。**
弹窗文案写着「✓ 多课表管理」是高级版权益，实际多课表管理基本是白送的。

## 一、解锁到底怎么判定的

`store.isPremiumUnlocked()`（`src/data/store.js:818`）两选一，**满足其一即解锁**：

1. 本地 storage `premium_unlocked === "true"`（一次性解锁标记）
2. `authStore.getAuthData()` 里 `isActivated || isPermanent`（激活码 / 永久授权）

所以「能不能添加」在真机上的答案取决于这个用户有没有激活过。**代码层面没有任何阻止**，
只要 `premium_unlocked` 被写成 `"true"` 就永久开放（包括新增）。

## 二、顺手发现的三个体验/一致性问题

| # | 问题 | 依据 | 建议 |
|---|---|---|---|
| 1 | **未解锁用户一进页面就被弹窗糊脸** | `checkAndShowOverlay()` 在 `onReady`(154) 和 `onShow`(168) **都调用一次**，只要未解锁就 `showDialog = true` | 弹窗应只在**点了新增**时出现；进页就弹 = 强制劝退，也让「看看有哪些课表」这个基础功能不可用 |
| 2 | **付费墙只挡一个按钮，形同虚设** | 见上文 5 处失效门禁 | 要么把 5 处都接上 `isPremiumUnlocked`，要么干脆把多课表免费化、只保留真正的高级权益 |
| 3 | **新增课表的名字是随机串** | `doAddSchedule()` 生成 `课程表 + 3位随机字母数字`（如 `课程表X7k`） | 手环上没输入法，随机名是无奈之举，但可以直接进重命名流程，省一步 |

另外 `logPageWidth()`（178 行）是取证用的临时代码，注释里自己写了「验证通过后本方法可安全删除」，还留在页面里每次 `onShow` 跑一次 500ms 定时器。

### 两个测起来有点意思的点

**① 怎么测随机命名？**
`doAddSchedule` 用 `Math.random` 生成 3 位后缀，直接测不可预测。
测试里临时把 `Math.random` 钉成 `() => 0` → 后缀恒为 `"AAA"`，于是：

- 第一次：得到 `课程表AAA`（断言精确等于）
- 第二次：列表里已有 `课程表AAA` → 100 次尝试全撞 → 走 `Date.now().toString(36)` 兜底 → 断言不重名

用一行 stub 把随机逻辑变成确定性用例，顺带把兜底分支也测了。

**② 删除后的索引修正**
删掉一条课表后 `currentIndex` 怎么变，是最容易出静默 bug 的地方。三种情况分别建用例：

| 场景 | 起始 | 删谁 | 结果 |
|---|---|---|---|
| 删当前 | `[A,B,C]`, current=1 | B | `[A,C]`, current=**0** |
| 删当前之前 | `[A,B,C]`, current=1 | A | `[B,C]`, current=**0** |
| 删当前之后 | `[A,B,C]`, current=1 | C | `[A,B]`, current=**1**（不变） |

三条全对，源码逻辑正确。

## 四、建议（按优先级）

| 级别 | 动作 | 理由 |
|---|---|---|
| **P0** | 修付费墙绕过：`copySchedule` 要么接真门禁，要么承认多课表免费 | 现在的状态是「卖的权益没守住」，比干脆免费更糟 |
| **P1** | 停掉进页即弹的解锁弹窗，改为只在点「新增」时弹 | 现在未解锁用户连"看一眼课表列表"都做不到 |
| **P1** | 统一门禁：`checkProAccess()` 改接 `store.isPremiumUnlocked()`（异步），或整函数删掉 | 一个恒 true 的门禁函数比没有门禁更误导后人 |
| **P2** | 删 `logPageWidth()` | 作者自己标注了可删 |
| **P2** | 新增课表后直接进重命名 | 随机名 `课程表X7k` 对用户毫无意义 |
