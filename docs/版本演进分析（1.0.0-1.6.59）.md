## 一、总体结论（先给答案）

**1. 每个版本都有进步吗？—— 有，但进步的"性质"在变。**

- 1.0 → 1.4：**功能扩张型进步**（新页面、新体系、新商业模式），代码量持续暴涨。
- 1.5 → 1.6：**一致性收敛型进步**（跨屏型统一、体验打磨、数据完整性），代码量回落但质量提升。
- 增量峰值出现在 **1.4 段**（单段 +34,361 行），此后 1.5 段回落到 +14,966 行，呈典型"开发曲线收敛"。

**2. 是否已经是成熟产品，不再需要太多开发与维护？**

- **"不需要太多开发"——基本成立。** 提交密度从 1.3 段的约 48 次/天降到 1.6 段的约 9 次/天；新增功能占比下降，提交以修复、打磨、构建、文档为主。
- **"不需要维护"——不成立。** 真机适配问题仍在持续出现（手环 11 兼容、方屏 padding、二维码显示等），依赖小米/华为渠道平台，且假期数据等业务数据需按年更新。维护成本下降，但不为零。

## 三、逐版本详解

### 3.1 v1.0.0 —— 诞生（单次初始提交）

- 一次提交落地：课程表手环应用的基础框架（7 个文件、约 1000 行）。
- 能力边界：课程展示（"今天有什么课"）。
- **进步判定**：这是从 0 到 1，属基线，无版本内对比。

### 3.2 v1.1.0 —— 从"能看"到"能管"（+1000 行）

- 新增**周总览（week overview）**：从单日视图扩展到整周视图。
- 新增**状态栏（status bar）**：当前/下一节课的实时提示。
- 课程管理页（schedule-manager）改进。
- 集成**中文输入法**（自绘键盘），解决手环上输入课程名的痛点。
- **进步判定**：有，且是"可用性跃迁"——第一次让应用具备完整的信息闭环（看 + 管 + 输入）。

### 3.3 v1.2.x —— 从"能用"到"好用 + 好看"（+7404 → +19464 行）

- **1.2.0**：快速添加课程预设、今/明导航、主题感知进度条、状态栏仅当天显示。
- **1.2.33 / 1.2.34**：移除滑动删除（手势在手表上不可靠）、新增"恢复默认数据"、删除图标替换为 PNG、警告图标改 CSS 三角形、修复闪屏。
- **1.2.37**：首页时钟居中防抖、走马灯状态提醒、课程总览今日用"今"字圆形标记。
- **1.2.70**：Logo 虚线与多主题优化；**集中新增多个实验室页面**——设备信息、震动实验室、后台运行、二维码生成、弹窗演示。
- **进步判定**：有，且是"体验 + 体系化"双重进步。此时"多主题 + 功能实验室"两大体系成型，为后续高级版功能分层埋下伏笔。

### 3.4 v1.3.x —— 从"作品"到"产品"（+13284 / +25190 行，239 次提交）

这是**商业属性诞生**的阶段，也是提交最密集的阶段。

- **授权体系上线**（1.3.0）：引入激活码。
- **激活码演进**：18 位纯数字编码 → 6 列界面 → 纯 JS 加密库（修复 webpack 构建）→ 99 个月永久激活。
- **商业模式定稿**：方案 B「永久基础可用 + 增值一次性买断」，并落地为**标准版 / 高级版**两档。
- **弹窗遮罩模块 premium-overlay**：统一高级功能的解锁提示（数据备份、首页设置、课程表进入等）。
- **首页组件化重构**：抽出 `utils.js`、`status.js` 等模块，为后续维护减负。
- **多课程表索引加载**：支持多张课表。
- 大量白屏排查（debug step1~14 的二分定位法）。
- **进步判定**：**大幅进步**。项目性质发生质变——从"个人作品"变成"可售卖的产品"。

### 3.5 v1.4.x —— 多屏适配 + 工程化（+34361 行，代码增量峰值）

这是**代码量与工程体系同时爆发**的阶段。

- **输入法**：T9 九键输入法实现后被判定不合适并删除（一次有价值的技术验证），字体统一。
- **激活链路**：激活码二维码携带设备信息参数、单字母参数缩写、扫码传参。
- **工程化**：构建改为正式版 `aiot release --enable-jsc`；**RPK 体积从 2.0MB 压到 737KB，再压到 538KB**。
- **多屏型适配攻坚**：手环 9 Pro 方屏黑屏问题系统性排查（V1~V6 系列版本对比），最终定位到 `width/height:100%` 与不支持的 CSS 属性（如 `box-sizing`）。
- **胶囊屏 UI 规范 v2.0.0** 建立（按钮/开关/输入框/步进器/弹窗/分隔线/滚动容器/颜色变量）。
- **添加课程 V2**：单页布局 + 课程网格 + 横向滑动选择，重塑核心流程。
- **全页面胶囊屏适配**：index-full / settings / week-view / add-course / schedule-manager / activation 等页统一字号 ≥20px、补齐 line-height、padding 120px。
- 新增 404 页、Icon 收集页；Header 样式全局统一。
- **进步判定**：**进步最快的一站**。解决了"能不能在多种手表上正常跑"的生存问题，并建立了可复用的规范与构建体系。

### 3.6 v1.5.x —— 胶囊屏标准化 + 发布流水线（+14966 行）

- **v1.5.0**：胶囊屏首页优化（总按钮默认显示、自定义/快速添加默认关闭、课程名与时间教室同行、状态栏秒数隐藏）。
- **架构精简**：删除欢迎页与"默认首页"概念，应用入口统一为 `index-full`。
- **胶囊屏 UI 规范 v2.0.0 全面落地**：确立字号阶梯 **H1=28 / Body=24 / Caption=22 / Small=20**。
- 全页面按新规范对齐：倒数日、震动实验室、数据备份、添加课程等。
- **性能优化**：删除全部 `console.log`、禁用模块跳过初始化。
- **14 渠道构建流水线 + GitHub Release**：一条命令产出多平台包并自动发布。
- **进步判定**：有，是"可维护性 + 可发布性"的进步——从"手动出包"升级为"流水线出包"。

### 3.7 v1.6.x —— 一致性打磨 + 数据完整性（当前，+21591 行含文档）

- **平台兼容**：小米手环 11 兼容、CSS 方案验证、14 渠道包全部构建完成。
- **视觉统一**：header 按钮统一 48px、首页圆形导航、icon 图标体系、胶囊屏全页面适配、**方屏顶部 padding 统一为 6px（覆盖 22 个页面）**。
- **模板体系**：总课表新增极简 / 清爽（minimal-clean）/ 紧凑模板，方屏宽度撑满 99%。
- **数据完整性**：接入 **2026 官方假期（放假 + 调休）数据**，启动自动补齐、节假日页支持一键恢复；新增节假日规则与来源说明、今年调休清单。
- **交互重构**：中文输入法候选下展统一为组件化方案，并最终收敛为"只保留默认候选行"的极简实现。
- **细节**：打赏页胶囊屏二维码改为 100% 全屏、字号显示与设置页布局修复。
- **进步判定**：有，但性质已变——从"功能进步"转为"体验一致性 + 数据正确性"进步，属于成熟期特征。

## 五、成熟度评估

### 5.1 支持"已成熟"的证据

1. **质量体系已建立**：存在 100 分制综合评分与"守护手册"（防回退清单），有 15 轮 QA 报告台账。
2. **发布自动化**：14 渠道构建流水线 + GitHub Release，出包不再是瓶颈。
3. **规范完备**：三屏型（胶囊 / 方屏 / 圆屏）适配规范、胶囊屏 UI 规范 v2.0.0、字号阶梯均已固化。
4. **开发节奏收敛**：提交密度从 48 次/天降到 9 次/天；feat 占比仅约 12%，fix/docs/构建类占多数。
5. **近期变更性质**：v1.6.57/1.6.58 均为"默认开关调整""padding 统一"等微调，无颠覆性改动。

### 5.2 说明"仍需维护"的证据

1. **真机适配仍在持续暴露问题**：手环 11 兼容、方屏 padding、二维码、黑屏/白屏等，属于长尾且依赖具体机型。
2. **依赖外部平台**：小米/华为渠道的包规范、系统能力（如 `system.resident`）会变化。
3. **业务数据需周期性更新**：假期/调休数据按年度变化，需持续接入与校验。
4. **QA 仍能滚动发现问题**：说明"已满分"不等于"零缺陷"，回归测试是常态成本。
5. **仓库仍有未 push 提交**：本地领先远端，存在丢失风险，需建立提交/推送纪律。

## 六、后续建议

1. **降低开发频率，提高发布门槛**：从"小步快跑"转为"里程碑发版"，例如以 0.1 为粒度攒批发布。
2. **维护重心转向两件事**：
   - **防回退**：以守护手册 100 分红线为每次改动的自检清单。
   - **真机回归**：建立覆盖胶囊/方屏/圆屏 + 手环 11/9 Pro 的最小回归用例集。
3. **年度性维护任务清单化**：假期数据更新、渠道包规范跟进、系统能力（resident）适配。
4. **治理文档债**：`docs/` 已达 270+ 篇，存在 `capsule-donate-spec.md` 等与当前实现脱节的历史文档，建议标注"已废弃"或归档，避免误导维护者。
5. **建立提交与推送纪律**：AI 或人工改动后尽快 `git add -A && git commit`，定期 `push`，避免未入库文件因误操作丢失。
6. **判断"何时可以真正停止投入"**：当连续 3~4 个发版周期内 `fix` 提交趋近于零、且无新增真机适配问题时，方可认为进入"仅年度维护"状态——**目前尚未到达**。
