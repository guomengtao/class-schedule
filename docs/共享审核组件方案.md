# 共享审核组件方案（多项目 / 多手环型号通用）

> 目标：把 pages.html 的审核能力（审核标注 / 换最新版 / 删除 / 记录历史 / 昵称 / 撤销）抽离为**单一来源的共享组件**，任何新项目、新手环型号的截图档案页**只调用、不复制**，数据库共享，功能同步更新。
> 关联：`docs/pages-html审核结果功能规划.md`（一期，已上线）
> 后端：Vercel serverless + Upstash Redis（`api/admin/review.js`）

---

## 一、核心原则

1. **单一来源**：审核逻辑只有一份（`/js/review-widget.js` + `/api/admin/review`），所有档案页 `<script src>` 引用。组件升级 = 改一个文件，所有接入方立即同步。
2. **调用方零逻辑**：接入方只做两件事——① 引组件；② 按**约定结构**渲染截图（约定见 §3）。不允许接入方 fork/修改组件。
3. **数据库共享，按项目隔离**：Redis key 加入 `projectId` 维度，一套库服务 N 个项目。
4. **可逆操作**：删除=动态隐藏（数据保留），换版=标记待重采，全部可撤销。

## 二、后端扩展（已具备 90%）

现有 `api/admin/review.js` 的 field 是 `pageId|shotFile`。扩展：

```
field: <projectId>|<pageId>|<shotFile>
```

- `projectId` 约定：`ev-schedule-watch9`（现网默认，兼容旧数据自动迁移）、未来如 `ev-schedule-band10`、`其他项目名`
- `GET /api/admin/review?projectId=xxx`：按项目过滤
- `POST`：body 带 projectId，写入对应 field
- **兼容**：无 projectId 的旧数据归入 `ev-schedule-watch9`
- AI 读取：`web_fetch /api/admin/review?projectId=新项目ID&action=pending`

工作量：review.js 约 20 行改动。

## 三、前端组件化（核心工作）

### 3.1 抽离 `review-widget.js`（单一来源，放 app-auth 仓库 `/js/` 下）

从 pages.html 迁出以下能力，封装为一个对象：

| 能力 | 对外 API |
|---|---|
| 工具条渲染 | `ReviewWidget.mount(container, { projectId, pageId, shotFile, imgSelector })` |
| 拖框标注（多框） | 组件内部，坐标归一化（cover 裁剪换算内置） |
| 问题多选 chips | 组件内部（9 类预设，可扩展传入） |
| 快捷标记+撤销 | `quickMark(action)` / 再点撤销，按钮状态机内置 |
| 历史记录折叠区 | `toggleHistory()`，数据来自 GET 回填 |
| 随机昵称 | localStorage 记住、可改，组件内部 |
| 删除隐藏/恢复 | 组件内部（动态 display，可逆） |
| 角标/状态回填 | `ReviewWidget.refresh()`（组件自动 GET 并回填全部已挂载实例） |

### 3.2 接入方约定（新项目档案页只需 3 步）

```html
<!-- 1. 引组件（单一来源，自动同步更新） -->
<script src="https://app-auth.gudq.com/js/review-widget.js"></script>

<!-- 2. 截图按约定结构渲染 -->
<div class="shot-unit" data-project="my-new-project" data-page="home" data-file="shots/home-1.png">
  <div class="device"><img src="/images/my-new-project/home-1.png"></div>
</div>

<!-- 3. 初始化 -->
<script>ReviewWidget.autoMount({ projectId: "my-new-project" });</script>
```

- 组件自动扫描页面内所有 `[data-project]` 的 `.shot-unit` 并挂载工具条
- **约定优于配置**：只要 HTML 结构符合 `shot-unit / device / img` 三层，无需其他代码
- 样式由组件注入（组件内嵌 CSS，避免接入方漏样式）

### 3.3 与现有 pages.html 的关系

- pages.html 改为**第一个接入方**：删除内联审核代码，引用 review-widget.js，`data-project="ev-schedule-watch9"`
- 行为与现在完全一致（历史数据无缝，projectId 迁移自动归入）

## 四、新项目 / 新手环型号接入流程（标准流程）

以「发布一个新的方屏手环（如 10 Pro）」为例：

```
1. 建档
   - 新建 pages-<project>.html（或复用 pages.html 模板），projectId = ev-schedule-10pro
   - 逐页截图采集（emulator-eye + start-page 直达，同现有流程）
   - 图片传 /images/<project>/ 下

2. 挂审核
   - 页面引 review-widget.js，shot-unit 带 data-project="ev-schedule-10pro"
   - 刷新即具备：审核标注 / 多框 / 批注 / 换最新版 / 删除 / 记录 / 昵称

3. 审核闭环（与现有完全一致）
   - 用户框选标注 → 提交
   - AI web_fetch /api/admin/review?projectId=ev-schedule-10pro&action=pending
   - 按 box 归一化坐标 × 该型号分辨率（如 336×480）还原像素 → 修复
   - 修复后回写 resolved → 档案绿框

4. 归档
   - 全部 resolved 后该轮采集完成，截图档案即该型号的"体检报告"
```

**不同手环型号的特殊性只在分辨率**：box 已归一化（0~1），AI 修复时乘以对应型号分辨率即可，组件与后端零改动。

## 五、数据库结构（共享 + 隔离）

```
Redis HASH review:pages
  field: <projectId>|<pageId>|<shotFile>
  value: {
    projectId, pageId, shotFile,
    issues[], boxes[], note, action, nickname, reviewer,
    updated_at, status, count,
    history[]        // 全量保留，含昵称/时间
  }
```

- 同库不同 projectId 天然隔离
- 跨项目统计（如"本周各项目审核量"）可后续加聚合端点

## 八、风险与对策

| 风险 | 对策 |
|---|---|
| 组件升级破坏已接入方 | 组件版本号 + GET 返回 version；接入方无感更新（同源引用） |
| 公开 POST 被刷 | 已有限频；后续可加轻量 token |
| 旧数据迁移遗漏 | 迁移函数幂等，无 projectId 自动归类默认项目 |
| 多项目数据混淆 | field 首段强制 projectId；GET 必带过滤 |
