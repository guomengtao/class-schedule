# 激活入口顺序调整方案（兑换码优先）

- 日期：2026-11-04
- 涉及项目：`ev/class-schedule`（快应用）、`ev/app-auth`（网页与爱发电私信）
- 目标：把「兑换码激活」扶正为**默认重点方式**，安卓扫码同步器降为可选项
- 定序依据：**稳定性**（不是路径长短）。安卓路径依赖 `同步器 → 小米运动健康 → 手环 SPP 会话` 三段同时在线，经常卡住；手工路径只依赖一个网页

---

## 一、结论先说

这次改动不是三处各改一句文案，而是**一次入口定序**。

**定序依据不是路径长短，而是可靠性。**

> 安卓路径真正的问题不是"步骤少所以显得快"，而是**依赖链太长**：
> `同步器 → 小米运动健康 → 手环 SPP 会话` 三段必须同时在线，任一段断掉，激活就失败。
> 而手工路径只依赖一个网页。

| | 安卓扫码激活（A） | 兑换码激活（B） |
|---|---|---|
| 运行时依赖 | 同步器 App + 小米运动健康 + 蓝牙 SPP 会话 + 手环 | 一个浏览器 |
| 失败表现 | 卡住、转圈、无响应，**且用户无法自救** | 明确报"兑换码无效/设备ID不对"，可立即换手重来 |
| 平台 | 仅安卓 | 全平台（含 iOS、Mac） |
| 用户可理解度 | 低（"连接失败"到底是什么失败？） | 高（输入错了就是输入错了） |

**A 路径的"短"是假短**：短在用户点击次数，长在依赖链。一旦中段卡住，用户面对的是一个转圈界面，既不知道卡在哪，也没有替代方案——同步器排查不了，小米运动健康的连接状态普通用户看不懂。

**B 路径的价值是确定性**：不碰蓝牙、不碰 App、不碰账号，只需要 4 位码和一个浏览器。输错了立刻知道。

所以 A 只能作为**可选补充**（对安卓用户，装好同步器后确实一键完成），不能作为默认推荐。

**但它现在还不成立**：B 路径的首步仍然是"扫码取激活码"，仍要另一台设备。所以必须先补手输设备ID（P1），入口才能真的翻上来（P0）。**P0 与 P1 必须同批上线**，否则就是把用户从"能自动成功但不稳"推到"还要扫码且要输 18 位"。

## 二、现状实测

### 2.1 快应用入口页 `src/pages/activation/activation.ux`

| 行号 | 现状 |
|---|---|
| 20-22 | 「购买兑换码」按钮，亮底（cardLight），是唯一主操作 |
| 25-31 | **A 路径卡**：编号 `A` + 标题「扫码激活」+ 副标「安卓 2 步」，编号用 `theme.accent` 高亮 = **当前重点推荐** |
| 33-39 | **B 路径卡**：编号 `B` + 标题「手工激活」+ 副标「全平台 3 步」，编号用 `textSecondary` = 次选 |

两条路径的实际内容：

- **A（`path-a-sync.ux`）**：标题「安卓」→「第1步 共2步」→「扫码安装同步器」→ 二维码 → 终态「自动激活 / 无需输兑换码」。**需要装 APK，仅安卓，iOS 和 Mac 用户走不通。**
- **B（`path-b-redeem.ux`）**：标题「激活码」→「第2步 共3步」→「扫码取激活码」→ 显示 `ID ••XXXX` → 二维码 → 按钮「去输入激活码」→ `activation-code.ux` 手输 18 位（3 行 × 6 格）。

### 2.2 18 位激活码的构成

`docs/activation-code-validation-rules.md` 定义：

```
产品ID(2) + 兑换码(4) + 月份数(2) + 设备ID(4)   →  加密后得到 18 位
```

其中那个 **4 位兑换码**，就是爱发电赞助后发给买家的东西。它一次性、由服务端生成、存在服务端记录里。

### 2.3 爱发电私信 `ev/app-auth/lib/afdian-dm.js`

第 36-50 行，三条私信。第 1 条是信息量最大的一条：

```
🎉 感谢您赞助 Ev课程表 永久高级版！

您的激活链接（点开自动激活）：{activate_url}

若链接点不开：打开 App → 高级版 → 输入兑换码 {code} → 一键激活
```

问题在于：**4 位兑换码被放在"若链接点不开"的兜底位置**，主语是链接。而且这句话里"输入兑换码 → 一键激活"跟快应用的实际流程对不上——手环里要输的是 18 位，不是 4 位。

### 2.4 网页激活页 `ev/app-auth/activate.html`

第 249-290 行，现状：

- 标题「设备激活」，副标「输入兑换码获取激活码」
- 步骤 4 条：确认设备ID → 输入 4 位兑换码 → 得到 18 位激活码 → 输入到手环
- 表单：设备ID（**readonly，灰色不可编辑**）+ 兑换码（4 位）+「立即激活」

第 585 行是关键约束：

```js
showResult('error', '请通过手环/手表上的二维码打开本页面，直接浏览器打开无法激活');
```

**设备ID 只能从 URL 参数带进来，不支持手输。** 这就是"必须先扫码"的技术根源。

### 2.5 安卓路径为什么不稳定（本次定序的核心依据）

A 路径不是"一条命令直达手环"，中间串了四段，每段都能断：

```
① 扫码装同步器  →  ② 同步器拉小米运动健康  →  ③ 小米健康建 SPP 会话  →  ④ 会话下发到快应用
```

各段的现实故障：

- **②③ 段：手环的 SPP 服务只维护一份认证会话，是独占的。** 这一点在 2026-11-04 上午已被实测证实：Mac 上的 AstroBox 与手机上的 Mi Fitness 抢同一份会话，抢占方之外的那一侧表现就是 `RFCOMM open channel → 等 12 秒 → Channel 1 open timed out`，连认证包都没能发出。
- **小米运动健康有后台保活，会主动把连接抢回去。** 所以即使 ③ 段一度通了，用户切个 App、来条通知，会话就可能被夺走，同步器侧表现为"卡住不动"。
- **④ 段：快应用侧互联通道有 1.5s 的兜底超时**（`src/app.ux:490` `setTimeout(finish, 1500)`）。链路稍有延迟就会走到兜底分支，用户看到的是"点了没反应"。
- **用户侧不可诊断**：上述任一失败，用户看到的都只是"连接失败"，无法区分是没装同步器、蓝牙没开、小米健康没连上手环、还是手环被别的设备占着。

对比 B 路径：只有 `网页计算` 一段，无状态、无会话、无独占，天然可重试。

**这才是把 A 降级的真正理由。** 不是"B 更短"，而是"B 不会卡，卡了也能自己重来"。

## 三、真正的技术约束（决定了方案边界）

### 3.1 手环端不能联网换码

查 `class-schedule/src/manifest.json`，features 列表：

```
system.router / storage / prompt / device / vibrator / request
system.app / resident / interconnect / clipboard / file / battery
```

**没有 `system.fetch`**，整个 `ev/` 生态里也搜不到任何 `@system.fetch` 用法。`system.request` 是下载管理器（download/upload），不是通用 HTTP 客户端。

结论：**手环端无法自己把 4 位码发给服务端换 18 位码。** 4→18 的换算必须在网页端完成，因为密钥在服务端（本地能算就等于能伪造）。

### 3.2 所以"快捷"只能快在"去掉扫码"上

唯一能砍掉的环节是**设备ID 的传递方式**。现在的链路是：

```
手环出二维码 → 用户拿另一台设备扫 → URL 带 deviceId 进网页 → 输 4 位码 → 出 18 位 → 回手环输
```

可以砍成：

```
手环显示设备ID（4 位，大字） → 用户在任何浏览器打开网页 → 手输设备ID + 4 位兑换码 → 出 18 位 → 回手环输
```

省掉相机、省掉手机必须和手环配对、iOS 也能用。

### 3.3 为什么不干脆用手环↔手机互联通道

`system.interconnect` 在项目里已有实际使用（`src/data/chat-bridge.js`、`evbox/src/data/sync-channel.js`），理论上可以让手环把 4 位码交给手机 App 代发请求、再把 18 位回传。

但这条路的成本是：**要求用户装配套手机 App**，正好违背"不装东西"的初衷。所以本方案不采用，仅作为远期选项记录在第七节。

| 行号 | 改前 | 改后 |

### 5.3 爱发电私信改写 `ev/app-auth/lib/afdian-dm.js` 第 36-50 行

**先说一个必须纠正的现状**：私信第一条现在把「点开自动激活」的链接放在首句，而这个链接是

```
https://app-auth.gudq.com/deep-link-test.html?code={兑换码}&u=..&o=..&c=..&g=activate
```

（`lib/afdian-processor.js:313-318`）

**走的是深链 → 同步器通道，也就是 2.5 节说的那条最不稳定的链路。** 等于把用户第一眼就推向最容易卡住的那条路，而且卡住之后私信里没有任何替代指引——兑换码只出现在"若链接点不开"的次要从句里，用户很容易忽略。

改前的结构是「感谢 → 链接 → 兜底给码」。改成「感谢 → **码直接给** → 操作步骤 → 链接作为替代」：

```
🎉 感谢您赞助 Ev课程表 永久高级版！

您的兑换码：XXXX

激活方法（3 步，稳定，不用装任何东西）：
1. 打开手环 → 高级版 → 兑换码激活，记下屏幕上的 4 位设备ID
2. 浏览器打开 https://<domain>/activate ，输入设备ID + 上面的兑换码
3. 网页会给出 18 位激活码，回手环输进去即可

安卓手机也可以点这个链接自动激活（需装同步器；若卡住请用上面的手工方式）：
{activate_url}

有任何问题直接回复这条消息。
```

要点：

- **兑换码出现在第一段**，不再藏在"若链接点不开"里
- 卖点写「3 步、稳定」——**稳定性是主卖点，"不用装东西"是手段**
- 链接保留但降为备选，并如实标注"需装同步器"
- **必须给一句失败退路**：「若卡住请用上面的手工方式」。这句话是本次改动的关键之一——现在用户卡住后无处可去，只能来问客服
- 删掉原来那句「输入兑换码 → 一键激活」，它与快应用实际流程不符（手环要输的是 18 位）

**`code` 字段已核实为 4 位兑换码，文案可直接前置。** 证据链：

- `lib/afdian-processor.js:203-216` → `crypto.generateRedeemCode()`，冲突时重试 3 次
- `lib/crypto.js:192-198` → 循环 4 次取字符
- `lib/crypto.js:4` → `CHARSET = "0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZ"`

即 `{code}` 就是 4 位大写字母/数字，与 `lib/validate.js:1` 的 `^[A-Z0-9]{4}$` 完全对齐。**私信里的 `{code}` 不需要任何生成逻辑改动。**

## 六、P1：去掉扫码依赖（同批上线）

### 6.1 `activate.html` 支持手输设备ID

改动点：

1. 删除第 585 行的强制拦截：
   ```js
   // 改前
   showResult('error', '请通过手环/手表上的二维码打开本页面，直接浏览器打开无法激活');
   ```
   改为：URL 无 `deviceId` 时，不报错，把设备ID 输入框解除 `readonly`，并在步骤里高亮"请输入手环上显示的 4 位设备ID"。

2. 校验规则：4 位、字符集 `A-Z a-z 0-9`（与 `activation-code-validation-rules.md` 的设备ID 定义一致）。格式不对就地提示，不发请求。

3. URL 带 `deviceId` 时保持原有自动填充行为（扫码进来的老用户路径不受影响）。

### 6.2 服务端 `api/activate.js`：已核实，只需改一处大小写

核过代码，结论比预想的好：

`api/activate.js:768` 的 POST 主流程对 `deviceId` **只做格式校验，不查库**：

```js
var deviceCheck = validateDeviceId(deviceId);   // lib/validate.js:52
// → 非空 + 不在 NA 类黑名单 + 剥离非字母数字后长度 ≥ 4
// → 返回 normalizeDeviceId(deviceId) 的末 4 位
```

也就是说，**手输设备ID 走的是与扫码带入完全相同的分支，服务端无需为"手输"新增任何逻辑**，只有 `activate.html` 前端那一道拦截要放开。

安全性不受影响：单有设备ID 无法激活，真正的一次性凭据是兑换码（`auth:redeem:<code>` 用后即删）。所以**第 5.2 节把设备ID 从掩码改成明码是安全的**。

### 6.3 ⚠️ 必须先处理的隐患：设备段大小写敏感

这是本次核查发现的真问题，直接决定"手输"能不能做。

三端各自实现，且**大小写处理不一致**：

| 端 | 位置 | 行为 |
|---|---|---|
| 服务端归一化 | `lib/crypto.js:86` `normalizeDeviceIdSegment` | 保留原样大小写，取末 4 位 |
| 服务端编码 | `lib/crypto.js:200` `generateActivationCode` | 设备段按 `charToBase62` 逐字符编码，**区分大小写** |
| 手环端比对 | `src/app.ux:516-520` | `s.substring(len-4) !== decrypted.deviceId` **严格字符串相等** |

实测验证（`node` 直调）：

```
normalizeDeviceIdSegment('A1B2') = 'A1B2'
normalizeDeviceIdSegment('a1b2') = 'a1b2'     ← 不相同
generateActivationCode(...,'A1B2',...) = 001854518811443512
generateActivationCode(...,'a1b2',...) = 001854518817641652   ← 结果不同
```

后果：手环屏幕显示的是 `raw.slice(-6)`，用户手抄末 4 位时若大小写输错，网页会**照常返回一个格式完全合法、但设备段对不上的 18 位码**，手环上报「设备ID不匹配」，用户完全无法自查。

**修法（向后兼容，不打乱已发出的码）**：

1. `lib/crypto.js:86` `normalizeDeviceIdSegment` 返回前 `.toUpperCase()`
2. `activate.html` 设备ID 输入框 `toUpperCase()` + 自动去掉易混字符
3. `src/app.ux:520` 比对改成大小写不敏感：
   ```js
   if (!s || !decrypted.deviceId ||
       String(decrypted.deviceId).toUpperCase() !== last4.toUpperCase()) { ... }
   ```

第 3 步是关键：它让**已发出的旧码（设备段可能含小写）继续可用**，新码则一律大写。三端都改才自洽，缺一不可。

> 另一个潜在坑：手环端用 `substring(len-4)`，服务端用"剥离非字母数字后取末 4 位"。两者只在设备ID 全是字母数字时一致。当前设备ID 形态下没暴露问题，但若将来 deviceId 带 `-` 或 `/`，两端会算出不同的段。本次不改，记录备查。

### 6.4 快应用 `path-b-redeem.ux` 与 `activation-code.ux` 文案同步

- `path-b-redeem.ux` 的说明文案改成「记下这 4 位设备ID，在网页输入」
- `path-b-redeem.ux` 显示值必须是 `deviceId.slice(-4)`（**不是现在 `activation-info.ux` 用的 `slice(-6)`**），否则用户抄 6 位会多抄
- `activation-code.ux` 的输入页标题保持「激活码」，但上方加一行小字「18 位，从网页获取」，避免用户把 4 位兑换码往 18 格里塞

## 七、远期选项（本次不做）

若后续确实想做到「手环上输 4 位码，一键激活」，唯一路径是 `system.interconnect`：手环把 4 位码 + 设备ID 交给手机侧 App，由 App 代发 HTTP 请求拿回 18 位码，再回传手环自动填入。

代价与前提：

- 用户必须装配套手机 App（`ev-android` / `ev-schedule-android`）
- 手机 App 需常驻并能响应互联请求
- 平台需支持 `system.fetch` 或 App 侧代发

这三条任一不成立就退化成现在的方案。**不建议在本次改动中尝试。**

## 九、风险

按"已核实"和"仍需观察"分开，避免把已排除的担心继续挂在方案里。

### 已排除（核查后确认无风险）

| 原担心 | 核查结论 |
|---|---|
| 私信里的 `code` 可能是 18 位整码 | **是 4 位兑换码**。`generateRedeemCode()` 生成，字符集 `0-9A-Z` |
| 服务端只信任扫码来源，手输会开伪造入口 | **不存在这个分支**。`validateDeviceId` 只校验格式，不查库；手输与扫码同一分支 |
| 设备ID 明码展示可被冒用 | **不足以激活**。一次性凭据是兑换码，设备ID 只是段的载体 |
| 手输要新增服务端校验逻辑 | **不用**。服务端零改动（除大小写归一化） |

### 仍需处理

1. **顺序调整先于能力上线** —— 最大风险。用户被从"能自动成功但不稳的链路"推到"还要扫码且要输 18 位"，两头都不占优。P0 与 P1 必须同批发布。
2. **设备段大小写敏感**（6.3）—— 已定位、有确定修法，但**三端必须一起改**。只改网页不改手环，会让旧码集体失效；只改手环不改网页，用户输错仍是静默失败。这类"静默失败"正是要把用户从 A 路径拉走的同类问题，不能在新路径上重演。
3. **手环端 `substring(len-4)` 与服务端"剥离非字母数字后取末 4 位"语义不等价** —— 当前不触发，将来 deviceId 形态变化会踩。本次不改，记入坑库。
4. **`path-b-redeem.ux` 首屏设备ID 需从 `slice(-6)` 改 `slice(-4)`** —— 现在 `activation-info.ux` 用 6 位，两处不一致，实施时容易抄错。
5. **手环屏幕高度** —— `activation.ux` 此前多次因加一行文案就溢出，验收第 3 项必须真机实测。
6. **A 路径不能真的删掉** —— 对已经装好同步器、链路正常的安卓用户，它确实是"点一下就好"。本次只降权重、不加贬低，保留即可。若将来同步器侧修好了连接稳定性，可以再评估提回。
7. **私信改版后存量订单** —— `afdian-dm.js` 的文案是运行时拼的，改完只影响新订单；已发出的老私信不会变。若担心老用户卡住，考虑在群公告或 `user-guide.html` 里补一段手工激活说明。
