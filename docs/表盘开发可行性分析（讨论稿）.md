# Ev课程表 表盘开发可行性分析（讨论稿）

> 讨论目标：评估「为 Ev课程表开发配套小米手环表盘」的可行性，重点回答五个问题——仓库位置、开发能力、数据通讯、标准/高级版对接、屏幕兼容性。
> 立场说明：本文**区分「已核实事实」与「待实测推断」**，凡未经真机/工具验证的，均明确标注，不写成结论。

---

## 零、结论速览

| # | 问题 | 初步结论 | 把握度 |
|---|---|---|---|
| 1 | 仓库放哪 | **建议独立仓库**（表盘是二进制资源包，与 rpk 代码仓、同步器仓都不同类）；若要复用数据契约，用「共享 JSON 格式 + 文档约定」，而非共用仓库 | 高 |
| 2 | 能否开发表盘 | **能，但受限**：主流路径是米坛「表盘自定义工具」的**配置式 DIY**（选底包 + 拖元素 + 生成 `.bin`），**不是自由写代码**；官方未开放第三方表盘 SDK | 中高 |
| 3 | 表盘与快应用通讯 | **最大风险点**。快应用有 `@system.storage` / `system.interconnect`，但**表盘是 `.bin` 资源包、与快应用隔离**，未发现官方开放"表盘读快应用数据"的能力 | 中（需 PoC） |
| 4 | 标准版 / 高级版对接 | 运行时读授权困难（受制于通讯）；**建议改为「分发层区分」**——表盘作为高级版专属下载物，而非表盘内部判断授权 | 中 |
| 5 | 屏幕兼容性 | 快应用是「一包内部适配」（已验证）；**表盘大概率需按屏型分别制作底包/出包**，与快应用模式不同 | 中（需实测工具） |

**一句话**：**表盘"做出来"不难，"和快应用联动"很难。** 建议先用最小成本做一次技术验证（PoC），再决定投入规模。

---

## 一、背景：三类产物的形态差异

要回答"仓库放哪""能不能联动"，先要把三个东西分清——它们**不是同一种技术产物**：

| 产物 | 技术形态 | 交付格式 | 构建工具 | 运行环境 |
|---|---|---|---|---|
| **Ev课程表** | Vela 快应用（JS + UX 模板） | `.rpk` | aiot-toolkit | Vela 应用运行时（隔离沙箱） |
| **EV 同步器** | 电脑/手机侧数据导入工具（对接 JSON） | 可执行程序/插件 | 各自技术栈 | 手机/PC 侧 |
| **手环表盘** | 表盘资源包（底包 + 元素配置） | `.bin` | 米坛「表盘自定义工具」 | 表盘引擎（Vela 表盘层） |

**关键认知**：`.rpk`（快应用）与 `.bin`（表盘）在 Vela 上属于**两条不同的技术链路**，由不同的引擎渲染、有不同的分发方式。这一点直接决定了后四个问题的答案。

**数据侧已有基础**：本仓库已有 `docs/import-export-json-format-analysis.md`，明确了课程数据的 **格式 A**（存储键 `allCourses_N`，按 `day` 分组，`time` 为 `"HH:MM - HH:MM"` 合一字符串）。这份格式可作为表盘与快应用之间的**数据契约基准**。

## 二、Q1：代码仓库的存放位置

### 2.1 三种方案对比

| 方案 | 做法 | 优点 | 缺点 | 评价 |
|---|---|---|---|---|
| A. 并入 Ev课程表仓库 | 在本仓库加 `watchface/` 子目录 | 数据格式、文档、版本可以一起管 | ①构建工具链完全不同（aiot vs 表盘工具），脚本混杂<br>②表盘多为二进制资源，会撑大仓库、污染 git 历史<br>③发布节奏不同（表盘受工具/机型限制）<br>④`git clean` 类事故风险面扩大 | 不推荐 |
| B. 并入 EV 同步器仓库 | 放进同步器 | 都能"传递数据" | 同步器是侧端工具，表盘是设备端资源，**产物不同类**；同步器开发者可能非同一人 | 不推荐 |
| C. **独立仓库** | 新建 `ev-watchface` 之类 | ①职责单一、工具链干净<br>②发布独立、互不影响<br>③可单独开源/闭源 | 需要显式维护"数据契约"与文档同步 | **推荐** |

### 2.2 推荐做法

1. **独立仓库**承载表盘产物与制作工程。
2. 用**文档 + JSON 契约**与主仓解耦：把 `import-export-json-format-analysis.md` 的格式 A 抽成一份**稳定契约文档**（版本号 + 字段表），主仓与表盘仓都引用它。
3. 若表盘未来能用 JS 实现（见 Q2），再评估是否改为 monorepo（主仓 + 表盘子包）；**在可行性未验证前，不建议合并**。

> 判断依据：**代码仓库应按「技术形态 + 发布节奏」划分，而不是按「产品名字」划分。** 表盘与快应用在这两点上都不同。

## 三、Q2：表盘开发能力

### 3.1 两条路径

| 路径 | 说明 | 对个人开发者的可行性 |
|---|---|---|
| **官方路径** | 小米运动健康 App「表盘市场」上架官方表盘；部分型号支持上传图片做表盘 | 上架需与小米官方/商务对接，门槛高；仅"图片自定义"不满足课程表需求 |
| **社区路径** | 米坛「表盘自定义工具」（包名 `tech.pingx.watchface`）制作 `.bin` 表盘，Zepp Life / 小米运动健康同步安装 | **个人可行**，社区事实标准；支持小米手环 7~9 Pro、小米手表 S3/S4、红米手表 4/5 |

### 3.2 社区路径的实际能力（已核实）

- **制作方式**：选「底包」→ 编辑元素（时间/日期/步数/心率/背景/字体/位置）→「提交制作」→ 生成安装包 → 同步到设备。
- **支持形态**：官方资料显示该工具除表盘外，还支持「**课程表小程序**」「电子书小程序」「环间图库小程序」等。
- **免编程**：主打**可视化拖拽 + 参数调节**，无需编程基础。

### 3.3 硬性规定与限制（关键）

| 项目 | 说明 |
|---|---|
| 产物格式 | `.bin` 表盘资源包（**不是 rpk**），与快应用技术栈不同 |
| 开发自由度 | **"配置式"**而非"代码式"：可以换元素、换布局、换底包，但**不能自由写业务逻辑** |
| 需要什么 ID | 表盘打包本身不以"应用包名"标识（这点与 rpk 的 `package` 不同）；但**制作/上传需要米坛账号**；安装需在手表开启**开发者模式**（小米运动健康 → 设备 → 关于 → 连续点击开启）以获取授权码 |
| 是否需要签名 | 未发现表盘需要应用签名/包名认证；**以工具实际流程为准** |
| 依赖第三方工具 | 是的。**官方未开放第三方表盘 SDK**，社区工具是事实路径，存在工具停更/设备不支持的风险 |

### 3.4 结论

**"能不能开发？"——能。** 但要澄清预期：

- ✅ 可以做：一个**课程表风格的表盘**（显示今日课程名、节次、时间等**静态或半静态**信息）。
- ❓ 待验证：这些信息**能否动态读到手环上快应用的数据**（见 Q3）。如果不能，表盘只能显示"预先写死/由手机侧推送"的数据。
- ❌ 不能做：把表盘当成"第二个快应用"自由实现交互逻辑。

## 四、Q3：数据通讯（最需要先验证的一环）

### 4.1 快应用侧已具备的能力（已核实）

| 能力 | API | 用途 |
|---|---|---|
| 本地键值存储 | `@system.storage` | 本项目课程数据就存在这里（`allCourses_N`） |
| 跨设备传输 | `system.interconnect` | 手表 ↔ Android 手机双向通道（官方样例：分片传输图片，`header → data → end`） |
| 应用内通信 | `$on` / `$emit` / `$off` | 模块/组件间通信 |
| 文件存储 | `@system.file` | 落盘缓存 |

### 4.2 表盘侧的现状（问题所在）

- 表盘是**表盘引擎**渲染的 `.bin` 资源包；快应用运行在**隔离沙箱**中（Vela 官方强调"三重隔离机制"保障安全）。
- **未检索到任何官方资料说明"表盘可读取快应用数据"**，Vela 官方样例列表中也没有表盘相关样例。
- 因此存在两种可能，**必须实测**：
  - **可能 A（乐观）**：表盘工具提供的"课程表小程序"是**独立打包的小程序**，可在表盘/设备侧独立运行并读数据 → 那么"联动"其实是"在表盘侧重做一个轻量课程程序"，而非"表盘读快应用"。
  - **可能 B（现实）**：表盘与快应用**完全隔离**，课程数据只能通过**手机侧中转**（同步器/App 写入手表）后由表盘显示。

### 4.3 三条可能的技术路径（按可行性排序）

| 路径 | 说明 | 依赖 | 风险 |
|---|---|---|---|
| **P1. 表盘侧独立小程序** | 用表盘工具的"课程表小程序"能力，在表盘侧自带一份课程数据 | 表盘工具支持度 | 数据需重复维护，与快应用不同源 |
| **P2. 手机中转载入** | 快应用/同步器先经手机把课程写入手环 → 表盘读取（借助米坛工具/AstroBox 插件等） | `system.interconnect` + 第三方工具协议 | 需第三方工具配合，稳定性存疑；AstroBox 有"插件 SDK 可实现应用数据通信"的公开描述，可调研 |
| **P3. 表盘直读快应用存储** | 表盘直接读 `@system.storage` | **需官方开放** | 目前**无公开证据**，把握最低 |

### 4.4 结论

**"表盘与快应用数据通讯"是整个项目最大的不确定性**，不能想当然。建议：

1. 先做 **PoC**：用米坛表盘工具做一个"读课程数据"的最小表盘，验证数据从哪来、怎么来。
2. PoC 未通过前，**不要承诺"表盘显示实时课程"**。
3. 若 P3 不通，退守 P1/P2：**把表盘定位为"课程速览"，而不是"实时同步"**。

## 五、Q4：标准版与高级版的对接

### 5.1 难点

本项目已有标准版/高级版分层（激活码 → `premium_unlocked` 等状态存于快应用存储）。若要"表盘里享受高级版功能"，需要让**表盘知道当前用户的授权状态**——而这同样卡在 Q3 的通讯问题上。

### 5.2 三种方案

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| S1. 运行时读授权 | 表盘读取快应用的授权状态，决定显示内容 | 体验最自然 | **依赖 Q3 通讯能力**，风险最高 |
| S2. 手机中转授权 | 授权状态经手机写入设备，表盘读取 | 可行性略高于 S1 | 链路长、易失效 |
| **S3. 分发层区分（推荐）** | **表盘本身就是高级版权益**：标准版用户不提供表盘，或只提供基础表盘；高级版用户可下载"课程表表盘" | 实现简单、可靠、无需通讯 | 无法做"表盘内功能解锁"，是粗粒度区分 |

### 5.3 结论

**建议先用 S3（分发层区分）落地**：
- 把表盘作为**高级版专属下载物**（在高级版页面/激活后可获取表盘下载引导）。
- 表盘内部**不做授权判断**，只做"有数据就显示"。
- 待 Q3 通讯可行性验证通过后，再考虑升级到 S1/S2 做细粒度区分。

> 理由：**授权判定放在"你能否拿到表盘"这一步，比放在"表盘内部判断"更简单、更可控**，且完全不受表盘沙箱限制。

## 六、Q5：屏幕兼容性 —— 一个包适配，还是分屏出包？

### 6.1 快应用的模式（本项目现状）

**一个 rpk 内部适配全部屏型**，通过 `@media (shape:)` 媒体查询：

| shape 值 | 设备 | 典型分辨率 |
|---|---|---|
| `capsule` / `pill-shaped` | 小米手环 9 / 10 系列 | 192×490（手环 9）、212×520（手环 10） |
| `rect` | 方形屏 | 336×480（手环 9 Pro） |
| `circle` | 圆形屏 | 466×466 等 |

> 本项目已验证可用（见 `docs/胶囊屏UI规范.md`），这是**代码级自适应**，所以"一包兼容"成立。

### 6.2 表盘的模式（关键差异）

- 表盘制作是**"选底包"**起步，而底包与**设备型号/分辨率绑定**（工具按机型列出模板）。
- 这说明表盘**大概率需要针对不同屏型分别制作底包 / 分别出包**，**不具备快应用那样的"代码自适应"能力**。
- **待实测**：米坛表盘工具是否支持"一个工程导出多机型表盘"，还是必须逐机型各做一份。

### 6.3 结论

| 维度 | 快应用 | 表盘（推断） |
|---|---|---|
| 适配方式 | 代码级 `@media(shape:)` | 底包/模板级 |
| 是否一包多适配 | ✅ 是 | ❓ 大概率否，需分屏出包 |
| 维护成本 | 低（改一次全局生效） | 高（每机型各维护一份） |

**建议**：表盘不要一开始就全机型铺开。**先做 1 个主力机型**（建议手环 9 或 10，用户量最大），跑通后再复制到其他屏型。

## 七、风险清单与 PoC 验证项

在正式立项前，建议按以下顺序做验证（每项都是"能不能继续"的前置条件）：

| 编号 | 验证项 | 方法 | 通过标准 |
|---|---|---|---|
| V1 | 表盘工具是否支持手环 9/10（目标机型） | 装米坛表盘工具，看模板列表 | 目标机型在支持列表内 |
| V2 | 能否做出一个"显示文字"的表盘 | 选底包，加文字元素，生成 `.bin` 并安装成功 | 手环上能看到自制表盘 |
| **V3** | **表盘能否读到课程数据** | 尝试 P1/P2/P3 三条路径 | 表盘上能显示真实课程名 |
| V4 | 一个工程能否导出多机型 | 尝试同工程切不同机型底包 | 明确"分屏出包"或"一包多适配" |
| V5 | 数据更新链路 | 改课程后，表盘多久能更新 | 更新延迟可接受（如 ≤1 分钟） |

> **V3 是决定成败的关键**。V3 通过 → 值得投入；V3 不通过 → 表盘只能做"静态课程展示"，需重新评估价值。

## 八、建议的推进路线

### 阶段一：可行性验证（低成本，1~2 天）
- 完成 V1 / V2 / V3 验证，**把 V3 的结论写回本文档**。
- 只做最小可用表盘，不加任何美化。

### 阶段二：单机型 MVP（验证通过后）
- 选定 1 个机型，做一个"今日课程"表盘（课程名 + 时间）。
- 确认数据来源与更新方式，评估维护成本。

### 阶段三：多机型与版本对接
- 按 V4 结论，决定分屏出包方案。
- 按 Q4 的 **S3 方案**，把表盘作为高级版权益接入。
- 仓库独立（Q1 结论），并同步"数据契约文档"。

### 阶段四：分发
- 走米坛社区 + 轻腕 + GitHub（与主应用同一套渠道策略，详见 `docs/渠道发布与宣传分析（个人开发者版）.md`）。

## 九、待办与开放问题（给后续讨论）

1. **米坛表盘工具的"课程表小程序"到底是什么？** 是独立小程序，还是能读快应用数据？—— **最高优先级**。
2. 表盘的"底包"是否允许商用/二次分发？版权与合规边界需确认。
3. 表盘是否需要为不同固件版本分别制作？
4. 若最终无法读取快应用数据，是否接受"由手机侧同步器统一写入课程数据，表盘/快应用都从同一份数据读取"的架构？
5. 高级版权益的表达方式：是"下载表盘"就算权益，还是"表盘内解锁功能"？
