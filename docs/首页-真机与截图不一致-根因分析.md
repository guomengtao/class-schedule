# 首页真机与截图不一致 · 三项异常根因分析

- 日期：2026-11-01
- 范围：`src/pages/index/index.ux`（首页）
- 触发：真机安装 1.9.73 后，顶部时间留白、底部按钮形态与模拟器截图不一致
- **状态：已在模拟器完成对照复现（§0），根因确认**

---

## 0. 对照复现（已完成）

在模拟器（`xiaomi_band`，192×490，AVD 配置 `hw.lcd.shape=pill-shaped`）上把 L1443 的 `@media (shape: capsule), (shape: pill-shaped)` 临时改成 `@media (shape: capsule)`，使胶囊分支**必然不命中**，模拟器立刻呈现出用户真机的全部异常：

| 项目 | A：媒体命中（改前） | B：媒体未命中（改后） | 用户真机描述 |
|---|---|---|---|
| 顶部时间留白 | 5px，紧贴表顶 | 44px，明显下沉 | ✅ "时间空隙还是很大" |
| 底部加号 | 48×48 正圆 | flex:1 宽条约 64×44 | ✅ "第一个加号是宽的" |
| 底部另两枚 | 48 圆 | 48 圆（不变） | ✅ "不是三个圆形" |
| 课表切换条 | 通栏 100% | 通栏 100% | ✅ 本次一并修掉（§7） |

归档图：`ev-twins-weekview/首页-真机复现-对照.png`（两台均带模拟器外壳，符合总纲 §3.24）。

**结论：真机与模拟器跑同一份包，但真机上 `@media (shape: pill-shaped)` 未命中，整页退回基础样式。不是安装问题、不是版本问题、不是屏型判定问题——是设备端 CSS 媒体查询解析差异。**

实验后源码已 `git checkout` 还原，模拟器已重新部署正式包。

---

## 1. 结论摘要

三项异常不是三个 bug，而是**同一个根因的三个投影**：真机上 `@media (shape: ...)` 未命中，首页整页退回 `index.ux` 的**基础样式**（未分屏型的默认值）；而模拟器上媒体查询命中，走的是胶囊屏分支。截图跑的是"胶囊分支"，真机跑的是"基础分支"，所以两者必然不同。

由此同时解释"为什么一直这样、重装不管用"：**包内容相同 → 运行结果必然相同**。这是运行期样式解析问题，与安装/重装动作无关。

## 2. 现象 → 代码 → 数值 三方对照

| # | 真机现象 | 真机实际走的基础样式 | 模拟器截图走的胶囊分支 | 差值 |
|---|---|---|---|---|
| 1 | 顶部时间空隙仍然很大 | `.schedule-page { padding: 44px 8px 8px 8px }`（L854）<br>`.date-row { height: 28px }`（L882）<br>`.header { padding: 5px 4px }`（L867） | `.schedule-page { padding: 5px 16px 14px 16px }`（L1451）<br>`.date-row { height: 20px }`（L1458）<br>`.header { padding: 0 }`（L1454） | **顶部多 39px**<br>（44 vs 5） |
| 2 | 底部第一个加号是宽条、占位过大 | `.add-btn-wrapper { flex: 1; height: 44px; border-radius: 22px; margin-right: 4px }`（L1220–1228） | `.add-btn-wrapper { flex: 0 0 48px; width: 48px; height: 48px; border-radius: 24px }`（L1559–1567） | 宽约 56px×44 变宽条<br>vs 48×48 正圆 |
| 3 | 后两个按钮是圆 | `.set-btn-circle { flex: 0 0 48px; height: 48px; border-radius: 24px }`（L1278）——**该规则不在任何 media 块内，基础样式与胶囊屏一致** | 同左 | 0 |

第 2、3 条合起来是决定性证据：**同一行里两个圆形按钮形态正确、唯独加号变宽条**。原因是 `.set-btn-circle` 只有一份基础定义（不受 media 影响），而 `.add-btn-wrapper` 有基础版（`flex: 1` 宽条）+ 胶囊覆盖版（48 圆）。真机只拿到了基础版 → 一个宽、两个圆。

若真机是 `isCapsule=false`，底部应渲染 `[添加课程 长条] + [设置 长条]` 两枚而**不是三枚**；用户看到三枚 → 说明 **JS 侧 `isCapsule` 判定为 true，模板走胶囊分支，只有 CSS 没跟上**。这排除了"屏型判定错误"，问题被锁死在 CSS 媒体查询这一层。

## 3. 根因

### 3.1 直接根因

`index.ux` 全文有三处屏型媒体查询（L1404 `circle`、L1443 `capsule/pill-shaped`、L1632 `rect`）：

```css
@media (shape: circle) { ... }
@media (shape: capsule), (shape: pill-shaped) { ... }   /* L1443，逗号列表 */
@media (shape: rect) { ... }
```

真机上这三条**一条都没命中**（否则顶部 padding 会是 5 而不是 44）。基础样式即"未适配任何屏型"的默认值。

### 3.2 为什么没命中：两个候选，指向同一处

**候选 A（可信度最高）：逗号分隔的多条件媒体查询不被设备端 CSS 解析器接受。**

- 小米官方 Vela 文档给的并列写法是 **`or`**：`@media (shape: circle) or (shape: pill-shaped) { ... }`；
- 本项目写的是 **CSS Level 3 的逗号列表** `@media (shape: capsule), (shape: pill-shaped)`；
- 逗号列表语法在 Vela 属较新支持项，老 ROM 解析失败时**整条 at-rule 被丢弃**（不是部分生效），表现为该屏型样式全丢；
- 另外 `(shape: capsule)` 并非官方枚举值（官方为 `rect / circle / pill-shaped`）。严格解析器遇到未知枚举值时，同样可能整条丢弃。

**候选 B：真机 ROM 版本对媒体查询特性的支持落后于模拟器 SDK。**

模拟器 AVD 配置 `~/.vela/vvd/xiaomi_band.vvd/config.ini` 明确写着 `hw.lcd.shape=pill-shaped`，SDK 较新 → `@media (shape: pill-shaped)` 命中，所以我们截图是对的。真机 ROM 若解析器更保守，同一份 CSS 结果不同。

两个候选的共同点：**判定权在设备端，本地无法自证**。这也正是历史修复反复失效的原因。

### 3.3 为什么历史修复没解决问题

`docs/fix-capsule-shape-media-query.md`（2026-09-13）记录了同类问题：当时结论是"`screenShape` 返回 `pill-shaped` 而非 `capsule`"，修复动作是给 media 加上 `pill-shaped` 并列值，共改 31 个文件 33 处。

该修复的两个缺口：

1. **仍是双值并列而不是换语法**——若根因是"逗号列表/未知枚举导致整条丢弃"，加一个值并不能救；
2. **`(shape: capsule)` 一直留着**——一个非法枚举陪着合法枚举待在同一个条件里，风险一直在。

结果就是：现象在 9 月出现、10 月修、11 月又出现，每轮都在 media 分支里调数值（padding 44→18→5），而真机压根没进这个分支。

## 4. 为什么"重装不管用"

| 猜测 | 是否成立 | 依据 |
|---|---|---|
| 重装无效＝安装动作没生效 | ❌ | `vela up --rpk` 部署回 rc=0；真机能跑起来说明包体完整 |
| 装的是旧版本包 | ⚠️ **可能，需先排除** | `release/` 目录最新只有 `ev-v1.9.61-*.rpk`（10-30），而新构建在 `dist/…1.9.73.rpk`（11-01）。若真机装的是 `release/` 里的渠道包，则**差 12 个小版本的改动**，顶部紧凑化、三圆都在 1.9.61 之后才进 |
| 重装同一份包结果不变 | ✅ **必然** | 样式在编译期写进 `.jsc`，重装同一 rpk 不会改变设备端 CSS 解析结果 |

所以"重装不管用"是**正常的、预期的**。真正要回答的是：真机跑的是不是 `dist/…1.9.73.rpk`？见 §5 实验 1。

## 5. 三步判定实验（建议按序，总耗时约 10 分钟）

### 实验 1：确认包版本（排除旧包）

真机 → 设置 → 关于/版本，读 `versionName`。

- 显示 **1.9.73** → 排除旧包，直接做实验 2；
- 显示 **≤1.9.61** → 装错了包。改用 `dist/com.application.watch.classschedule.release.1.9.73.rpk` 重装，然后再看现象是否消失。**先做这步，能省掉后面所有分析成本**。

### 实验 2：直接验证媒体查询是否命中（决定性）

在首页顶部临时加三枚色块，分别由不同条件控制，看真机上哪一枚变色：

```html
<!-- 临时探针，验完即删 -->
<div style="height: 6px; background-color: {{ probeBase }}"></div>
<div class="probe-circle"></div>
<div class="probe-pill-comma"></div>
<div class="probe-pill-or"></div>
```

```css
.probe-circle      { height: 6px; background-color: #333; }
.probe-pill-comma  { height: 6px; background-color: #333; }
.probe-pill-or     { height: 6px; background-color: #333; }

@media (shape: circle) { .probe-circle { background-color: #2ecc71 } }
@media (shape: capsule), (shape: pill-shaped) { .probe-pill-comma { background-color: #e74c3c } }
@media (shape: pill-shaped) { .probe-pill-or { background-color: #3498db } }
```

判读：

| 真机看到 | 结论 |
|---|---|
| 只有蓝条变（`or`/单条件版命中） | 根因＝候选 A，逗号列表不被接受 → 按 §6 方案二统一改语法 |
| 红蓝都不变 | 真机完全不支持 `shape` 特性 → 必须走 §6 方案一（内联布局层） |
| 红蓝都变 | 媒体查询正常，问题在别处（回头查 `isCapsule` 异步回填时序） |

### 实验 3：读设备真实上报值（备用）

首页 `onInit` 临时打印：

```js
device.getInfo({ success: d => console.log('SHAPE', d.screenShape, d.screenWidth, d.screenHeight) })
```

用 EvEmuBuddy 抓日志。同时进「设置 → 设备信息」页对照 `screenShape` 显示值。

## 6. 修复方案（三选一）

### 方案一：内联布局层（推荐）

把屏型相关的几何量从 CSS 媒体查询搬到 JS 数据层，模板用内联 `style` 下发。

```js
// data 层
layout: { pagePaddingTop: 5, pagePaddingH: 16, pagePaddingBottom: 14, dateRowH: 20, dateFont: 18, addBtnW: 48, addBtnH: 48, addBtnRadius: 24 }

// 模板
<div class="schedule-page" style="background-color: {{ theme.bg }}; padding: {{ layout.pagePaddingTop }}px {{ layout.pagePaddingH }}px {{ layout.pagePaddingBottom }}px {{ layout.pagePaddingH }}px">
```

- 优点：与 `isCapsule` **同源同判**（底部三枚圆能正确渲染，已证明 JS 判定可靠）；彻底绕开设备端 CSS 解析差异；与 `week-view` 的 `LAYOUT_CONFIGS` 架构一致，后续一处配置管多屏。
- 代价：模板内联 style 变多；三处 media 块需逐条清点迁移（index.ux 内约 40 条规则）；回归面覆盖圆屏/方屏/胶囊屏三档。
- 风险：低。项目已有先例——`dayTitleSize`、`grid-item-name` 的字号本来就是脚本算完内联下发的。

### 方案二：只改媒体查询语法（快，但不彻底）

```css
/* 改前 */
@media (shape: capsule), (shape: pill-shaped) { ... }
/* 改后：去掉非法枚举 capsule，改用官方 or 写法 */
@media (shape: pill-shaped) { ... }
```

- 优点：改动 3 行，10 分钟可验证。
- 缺点：仍需设备端支持 `shape: pill-shaped`；若实验 2 显示红蓝都不变，此方案无效。**建议仅在实验 2 显示"蓝条命中"时采用。**

### 方案三：根节点 class 切换 —— 不推荐

`class="schedule-page {{ screenClass }}"` + `.capsule .xxx` 选择器。构建日志已明确告警 `Selector type unsupport Descendant Selector`，后代选择器在 Vela 不可靠，等于换一种不确定。

### 推荐路径

§0 已复现"未命中 → 三项异常"，但**"真机为何未命中"仍需一次真机取证**（实验 1 + 实验 2，约 10 分钟）。

- 若实验 1 发现装的是 ≤1.9.61 旧包 → 换 `dist/…1.9.73.rpk` 重装，现象应直接消失，本轮不改码；
- 若实验 2 显示"蓝条命中、红条不命中" → 方案二可快速止血（改 3 行）；
- 若实验 2 显示红蓝都不变 → **直接上方案一**，不必再在 media 分支里调数值。

从工程稳定性看，方案一是唯一能终结该问题反复出现的选择：真机与模拟器的媒体查询解析能力不可控，而 JS 侧 `isCapsule` 已被底部三圆渲染事实证明可靠。

## 7. 附：第三项需求（底部课表按钮居中、不 100% 宽）— **已实施**

改动前（L1308–1316）：`.schedule-indicator` 是 `.schedule-page`（flex column）的直接子项，默认 `stretch` 拉满整行，`cardLight` 底色铺成通栏。

**改法（wrapper 包裹，规避 Vela 不支持 `align-self` 的限制）**：

```html
<div class="schedule-indicator-row">
  <div class="schedule-indicator" onclick="openScheduleManager" style="background-color: {{ theme.cardLight }}">
    ...
  </div>
</div>
```

```css
.schedule-indicator-row {
  flex-direction: row;
  justify-content: center;
  align-items: center;
  flex-shrink: 0;
  margin-bottom: 4px;
}
.schedule-indicator {
  flex-direction: row;
  align-items: center;
  justify-content: center;
  padding: 6px 16px;      /* 左右内距加大，宽度由文字自然决定 */
  border-radius: 18px;
  margin-bottom: 0;        /* 下距交给 wrapper，避免叠加 */
  flex-shrink: 0;
}
```

注意：不要用 `margin: 0 auto` / `align-self: center` —— 前者在 Vela flex 容器里行为不确定，后者运行时直接告警 `Unknown style - alignSelf`（index.ux L1503 有历史注释佐证）。

**本轮已实施并验证**：模拟器 192×490 截图确认——条已居中、宽度＝内容宽（约 96px，左右各留约 32px 背景），不再通栏。点击热区未变（整条仍可点进课表管理）。

注意该改动在真机上还需复核一次：**真机若确实媒体查询全失效，`.schedule-indicator` 用的是基础样式（本轮已同步更新基础样式），行为一致，不需要额外适配**——这是把规则写进基础样式的额外收益。

## 9. 一句话总结

真机跑的是"未命中任何媒体查询"的基础样式，模拟器跑的是胶囊分支，所以截图和真机永远对不上；重装不解决问题，因为问题不在安装，在**屏型适配全部押在设备端 CSS 媒体查询上**这一架构选择。要根治，把几何量交回 JS（方案一），让"判屏型"和"用屏型"用同一个来源。
