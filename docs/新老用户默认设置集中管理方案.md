# 新用户 / 老用户默认设置集中管理方案

> 目标：把所有"默认开关、默认风格、默认行为"从散落各处收敛为**一张配置表**，
> 并区分三种生效场景：**新用户安装**、**老用户升级（软升级/不动）**、**老用户强制重置**。
>
> 示例诉求（来自用户）：
> - 首页设置里「快速添加」栏目默认是否打开
> - 默认主题风格
> - 假期模式默认开启；新建课程表时默认开启
>
> 结论先行：**"强制重置老用户"可以实现，且风险可控**——前提是必须能判定"老用户"、
> 必须能知道"用户是否亲手动过这一项"、必须保证重置只执行一次。

---

## 1. 现状盘点：默认值到底散落在几处

以「首页设置」为例，同一个 `homepage_settings` 对象，默认值分布在 **4 个地方**，且互相矛盾：

| 位置 | `showTime` | `showPinnedBar` | `showQuickAdd` |
|---|---|---|---|
| `src/data/store.js:702-714`（读不到时的兜底对象） | `false` | `false` | `true` |
| `src/pages/index/index.ux:301-305`（页面 private 初值） | `true` | `true` | `true` |
| `src/pages/index/index.ux:577-582`（`settings.showTime !== false`） | undefined 视为 `true` | 同 | 同 |
| `src/pages/homepage-settings/homepage-settings.ux:172-178`（另一份 private 初值） | `true` | `true` | `true` |
| `src/data/storage-tables.js:81-85`（文档性列清单） | 无默认值 | 无默认值 | 无默认值 |

**同一个开关有 3 种语义**，最终生效的是哪一个取决于"storage 里有没有值、值里有没有这个字段、用户从哪个页面读"。这就是本方案要根治的问题。

### 1.1 更隐蔽的病：老用户永远拿不到新默认值

`store.getHomepageSettings()` 读到数据后是**直接 `callback(settings)`，不做字段补齐**：

```js
// store.js:717-726
success: function(data) {
  if (data) {
    var settings = JSON.parse(data)
    callback(settings)          // ← 缺字段就缺着，补齐交给各个页面自己兜底
  }
}
```

后果：老用户的 storage 里只要存在 `homepage_settings` 这个对象（哪怕只有一个字段），
后面新增的开关 **永远读不到"默认值"**，只能靠各页面的 `!== false` 之类的临时兜底兜着。
**改默认值 = 只对新用户有效，对老用户无效** —— 这正是用户想解决的痛点。

### 1.2 已有的正确范式（可以直接推广）

`src/data/holiday-preset.js` 已经实现了一套完整可用的模型，本方案直接沿用它的范式：

| 机制 | 实现位置 | 做法 |
|---|---|---|
| 数据版本号 | `holiday-preset.js:8-9` | `VERSION_KEY = "holiday_preset_version"` |
| 幂等守卫 | `holiday-preset.js:100-115` | 版本号一致直接 return |
| 增量补齐 | `holiday-preset.js:117-156` | **只补缺失项，不覆盖用户改过的** |
| 手动恢复 | `holiday-preset.js:159-188` | `restoreDefault()` 覆盖内置项、保留用户自定义 |

把它从"节假日数据"泛化为"所有默认设置"，就是本方案。

### 1.3 缺失的三块地基

| 缺口 | 现状 | 后果 |
|---|---|---|
| **首次启动标记** | `app.ux` 的 `onCreate()` 里没有 | 无法区分"全新安装"与"老版本升级" |
| **用户显式修改记录** | 完全没有 | 不敢改默认值，怕覆盖用户的个性化选择 |
| **迁移幂等** | `app.ux:639` 的 `migrateFontScale()` 每次启动都跑一遍 | 无法表达"一次性强制重置" |

补充证据：`app.ux:631-644` 的 `onCreate()` 目前只做了 `database.init()` / `authStore.initAuth()` /
字号兜底 / `migrateFontScale()` / `migrateBuiltinHolidays()`。**这里就是新机制的挂载点。**

---

## 2. 设计目标

1. **一处定义**：所有默认值写在一张表里，页面与 `store.js` 都从表取，不许再硬编码。
2. **三种场景**：新用户安装 / 老用户升级（软升级）/ 老用户强制重置，各自语义明确。
3. **尊重用户**：用户亲手改过的项，默认**不动**（除非明确标为强制）。
4. **只跑一次**：每个默认值变更都由版本号保证**恰好执行一次**，绝不每次启动都重置。
5. **失败安全**：迁移失败不能阻断启动；宁可这一轮不迁移，也不能丢用户数据。
6. **可观测**：能查出"这台机器是第几版默认值、哪些项被强改过"。

---

## 3. 核心设计

### 3.1 一张配置表：`src/data/app-defaults.js`

以**字段级**（不是 key 级）为粒度，因为 `homepage_settings` 是一个大对象，需要逐字段控制。

- `policy: "keep"` 的项占大多数。**主题、字号、昵称、钉首页、自定义文案这些用户主观数据永远不碰**，这是本方案的安全底线。
- `dynamic: true` 表示"默认值是随机/动态生成的"，**不参与新旧值比较**，只在"值不存在时生成一次并固化"。否则每次启动都可能变一个昵称。
- `dynamicKey: true` 表示 key 形如 `holidayReminderEnabled_{i}`，按当前课程表数量展开处理。

### 3.2 状态记录：`app_state`

```js
// storage key: app_state
{
  "installedAt": 1758768000000,      // 首次安装时间戳
  "isFreshInstall": true,            // 是否为全新安装（诊断用）
  "defaultsVersion": 1,              // 已应用到第几版默认值
  "lastApplyAt": 1758768000000,      // 上次执行时间
  "forcedKeys": ["holiday.perSchedule"],  // 被强制覆盖过的条目（可审计、可向用户解释）
  "userSet": {}                      // 用户亲手设置过的字段路径集合，如 {"homepage.showTime":true}
}
```

`userSet` 是本方案能实现"软升级"的关键：**没有它，就无法区分"用户主动关掉了时钟"和"用户从没动过时钟"**。

### 3.3 三种场景的判定与处理矩阵

```
                    读 app_state
                    ┌─── 存在 ──→ 场景 B：老用户（常规升级）
  app.ux onCreate ──┤
                    └─── 不存在
                          │
                          ├── 探测业务数据（串行，命中即停）
                          │     scheduleNames / allCourses_0 / homepage_settings /
                          │     appTheme / baseFontSize / userNickname
                          │
                          ├── 命中任一 → 场景 B'：老版本升级上来的老用户
                          │               （补写 app_state，isFreshInstall=false）
                          │               *** 这里绝不能当成新用户 ***
                          │
                          └── 全未命中 → 场景 A：全新安装
```

| 场景 | 判定 | 处理 |
|---|---|---|
| **A 新用户（全新安装）** | 无 `app_state` 且无任何业务 key | 全部条目按 `value` 落盘；写 `app_state`，`defaultsVersion = CURRENT_VERSION`，`isFreshInstall = true` |
| **B 老用户（已有 `app_state`）** | `app_state` 存在 | 逐条比较 `since > app_state.defaultsVersion` 的条目，按 policy 处理；更新 `defaultsVersion` |
| **B' 老用户（老版本升级，无 `app_state`）** | 无 `app_state` 但探测到业务数据 | **按老用户处理**；先补写 `app_state`（`isFreshInstall = false`），再走 B 的流程 |
| **C 强制重置** | 条目的 `policy === "force"` 且 `since > defaultsVersion` | 无条件写入 `value`，并把 `id` 追加进 `forcedKeys` |

**场景 B 内部，按 policy 分三路：**

| policy | 用户没改过（不在 `userSet`） | 用户改过（在 `userSet`） |
|---|---|---|
| `keep` | 不动 | 不动 |
| `soft` | **写入新默认值** | 保留用户值 |
| `force` | **写入新默认值** | **仍写入新默认值（覆盖）** |

一句话总结：**keep 永不碰，soft 只碰没被碰过的，force 谁都碰。**

### 3.4 "用户改过没有"怎么记：写入侧统一登记

规则只有一条：

> **迁移引擎不走 `store.js` 的 setter，直接操作 storage；
> `store.js` 的所有 setter 一律视为"用户行为"，自动登记 `userSet`。**

这样零侵入、零遗漏：

```js
// store.js 内新增（供所有 setter 调用）
function markUserSet(path) {
  _pendingUserSet[path] = true      // 内存累积
  scheduleFlushUserSet()            // 合并成一次 storage 写（低频、串行）
}

// 例：setHomepageSettings 内部，逐字段登记
setHomepageSettings: function(settings, callback) {
  delete _cache.homepageSettings
  storage.set({ key: "homepage_settings", value: JSON.stringify(settings), ... })
  markUserSet("homepage.showQuickAdd")   // 只登记本次实际变更的字段最优，
  markUserSet("homepage.showTime")       // 简化做法：整对象涉及字段全登记
  ...
}
```

**为什么必须集中登记**：如果让每个页面自己记，迟早漏。项目里已经有过"注释承诺与实现漂移"的教训（`dicUtil.js:490-491`），凡是靠人守的约定都会漂。

**写入侧的性能约束**（项目已知红线）：手环 RTOS 存储 I/O **不支持高并发**。
`userSet` 必须**内存累积 + 合并写**，绝不能每次点开关都立刻写一次 `app_state`。
建议：内存里攒，`onHide` / 定时 2s / 累积超过 8 条时合并写一次；写用串行队列。

### 3.5 幂等与"只跑一次"

延续 `holiday-preset.js` 的做法：

```js
function run(callback) {
  readState(function(state, kind) {
    if (kind === "existing" && state.defaultsVersion >= CURRENT_VERSION) {
      return callback(0)          // 版本一致 → 直接返回，零开销
    }
    var todo = pickItems(state.defaultsVersion)   // 只挑 since 落后的条目
    applySerial(todo, state, callback)            // 串行应用
  })
}
```

- 版本一致时，代价只有 **1 次 `storage.get`**，不影响启动速度。
- 每条条目应用完才处理下一条（串行）。
- 全部成功后才写回 `defaultsVersion`；中途失败 → 保留旧版本号，下次启动重试幂等。

### 3.6 挂载点：`app.ux`

```js
// app.ux onCreate()
onCreate() {
  database.init()
  authStore.initAuth()
  store.getBaseFontSize(function(size) { if (!size) store.setBaseFontSize(48) })
  migrateFontScale()          // 保留，后续可并入新机制
  migrateBuiltinHolidays()
  defaultsEngine.run(function(applied) {     // ← 新增，放在页面创建前
    if (applied > 0) store.clearCache()      // 让 store 的 _cache 失效（关键！）
  })
  startResident()
  initSyncReceiver()
}
```

**`store.clearCache()` 是必须的**：`store.js` 有 `_cache`（主题、字号、首页设置等），
如果迁移写了 storage 而缓存还是旧值，页面会继续显示旧设置，看起来"迁移没生效"。

## 4. 针对用户举例的落地清单

| 用户诉求 | 对应配置项 | 现值 | 建议值 | policy | 说明 |
|---|---|---|---|---|---|
| 首页「快速添加（快速发帖）栏目」默认打开 | `homepage.showQuickAdd` | `true` | `true` | `soft` | 现值已一致，纳入表内统一管理即可 |
| 默认风格 | `appTheme` | `"blue"` | `"blue"` | **`keep`** | 主题是用户主观选择，**禁止重置** |
| 假期模式默认开启 | `holidayReminderEnabled_{i}` | **实际为 `false`** | **`true`** | `soft` | 见下方 4.1，这是本次要修的真实 bug |
| 新建课程表默认开启 | 同上（`dynamicKey`） | `false` | `true` | `soft` | 新建课程表时读不到值，天然走默认值 |
| 首页时钟/钉首页栏 | `homepage.showTime` / `showPinnedBar` | **三处冲突** | 统一 `true` | `soft` | 见第 1 节，靠统一表消除矛盾 |

### 4.1 「假期模式默认开启」现在为什么是关的

```js
// store.js:936-946
getHolidayReminderEnabled: function(scheduleIndex, callback) {
  storage.get({
    key: "holidayReminderEnabled_" + scheduleIndex,
    success: function(data) {
      callback(data === "1")        // ← 无值（undefined）时得到 false
    },
    fail: function() {
      callback(true)                // ← 只有读失败才返回 true，语义完全反了
    }
  })
}
```

`storage.get` 在"key 不存在"时走的是 `fail` 还是 `success(undefined)`，取决于实现；
但**只要走 `success`，新用户/新建课程表就是"关闭"**。
把默认值收到配置表后，这个函数应改为：

```js
getHolidayReminderEnabled: function(scheduleIndex, callback) {
  var d = defaults.get("holiday.perSchedule")     // true
  storage.get({
    key: "holidayReminderEnabled_" + scheduleIndex,
    success: function(data) { callback(data === "" || data === undefined ? d : data === "1") },
    fail: function() { callback(d) }               // 语义一致：读不到就用默认值
  })
}
```

注意 `fail` 分支原本返回 `true` 与 `success` 分支返回 `false` 是**自相矛盾**的，
统一后必须两个分支都用同一个默认值来源。

## 5. 风险、红线与防护

| # | 风险 | 防护措施 |
|---|---|---|
| 1 | **把老用户误判成新用户 → 清空全部设置** | 场景 B'：`app_state` 不存在时**必须先串行探测业务数据**，命中任一即按老用户处理。这条是最高优先级红线 |
| 2 | `force` 每次启动都重置，用户改了又被改回去 | 用 `since` + `defaultsVersion` 保证**恰好执行一次**；执行后把 `id` 记进 `forcedKeys` |
| 3 | 迁移覆盖用户个性化数据 | 昵称、钉首页、自定义文案、主题、字号一律 `policy: "keep"`；`dynamic` 项不参与比较 |
| 4 | storage 并发写导致设备异常（项目已知红线） | 全部串行；`userSet` 内存累积合并写；不使用 `Promise.all` 式并行 |
| 5 | 迁移失败导致启动异常 | 整个流程 `try/catch`；单条失败跳过并继续；失败不写回版本号，下次重试 |
| 6 | 写了 storage 但页面显示旧值 | 迁移后必须 `store.clearCache()` |
| 7 | 整对象替换导致丢字段（项目已有此约定） | 一律**读 → 改 → 写**，逐字段合并，禁止整对象 `set` 覆盖 |
| 8 | 用户/插件同时改同一字段 | AstroBox 同步的 `update_settings` 也视为"用户行为"，同样登记 `userSet` |
| 9 | 备份恢复后又被迁移覆盖 | 恢复流程视为用户行为 → 登记 `userSet`，其中 `soft` 项不再被后续升级覆盖 |
| 10 | 表与文档脱节 | 改动默认值时必须同步更新 `storage-tables.js` 的 `columns` 描述 |

## 6. 分阶段落地（每阶段可独立上线、可单独回滚）

### 阶段 1：只建机制，不改行为（零用户可见变化）

- 新建 `src/data/app-defaults.js`（**所有条目 policy 先统一写 `keep`**）
- 新建 `src/data/defaults-engine.js`（`app_state` 判定 + 幂等执行 + 串行应用）
- `app.ux` 的 `onCreate()` 接入 `defaultsEngine.run()`
- `store.js` 加 `markUserSet()` 并在各 setter 内调用
- `storage-tables.js` 登记 `app_state`

此阶段**行为与现在完全一致**（因为全是 `keep`），但地基已就位：新用户/老用户能被正确识别，`userSet` 开始积累。

### 阶段 2：消除默认值矛盾（仍不改老用户体验）

- 把 `store.js` 里各处硬编码默认值改为 `defaults.get(...)`
- 把 `index.ux` / `homepage-settings.ux` 的 private 初值与 `!== false` 兜底统一改为从表取
- 修 `getHolidayReminderEnabled` 的 `fail` 分支语义矛盾（改为同源默认值）

此时老用户行为不变（他们的 storage 里已有值），但**新装用户从此拿到一致、可预期的默认值**。

### 阶段 3：需要"静默升级"的项切 `soft`

- 例如 `homepage.showTime`、`homepage.showPinnedBar` 统一切 `soft`，`since` +1
- 效果：**从没动过这两个开关的老用户**，升级后自动变成新默认值；**动过的**保持原样
- 这是风险最可控的"老用户升级默认设置"方式

### 阶段 4：需要"强制重置"的项切 `force`

- 例如某个版本发现"假期提醒默认关闭"是 bug、要统一打开：`holiday.perSchedule` 切 `force`，`since` +1
- 效果：所有老用户的假期提醒都会被打开一次；用户之后手动关掉不会被再改
- **建议配套**：变更说明 / 首次进入时的 Toast 告知，并把 `id` 记入 `forcedKeys` 备查

## 7. 可观测性与验收

### 7.1 可观测

- `app_state` 里直接能读：`defaultsVersion` / `forcedKeys` / `lastApplyAt` / `isFreshInstall`
- `console.log("[defaults] v" + N + " applied: " + ids.join(","))`，便于抓 logcat
- 建议在 `tools.ux` 加一行"默认值迁移审计"入口，显示当前版本与强制项清单（诊断用）

### 7.2 验收清单

| # | 场景 | 操作 | 期望 |
|---|---|---|---|
| 1 | 全新安装 | 清数据后首次启动 | 全部项 = 表内 `value`；`app_state.isFreshInstall = true` |
| 2 | 老用户软升级（未改过） | 造一个"有数据、无 `app_state`、`userSet` 无该项"的环境，升到新版本 | 该项变为新默认值，其余保持 |
| 3 | 老用户软升级（改过） | 同上，但先手动改过该项 | **保持用户值不变** |
| 4 | 强制重置 | `policy: force` 的项 +1 版本 | 无条件变为新默认值，且 `forcedKeys` 记录到 |
| 5 | 强制只跑一次 | 重启两次 | 第二次不再改动；用户改过之后也不会被改回 |
| 6 | 幂等 | 版本一致时反复启动 | 除 1 次 `storage.get` 外无任何写入 |
| 7 | 失败安全 | 人为让某次 `storage.set` 失败 | 启动正常；版本号不推进；下次启动重试 |
| 8 | 缓存一致 | 迁移后立刻进首页 | 显示的是迁移后的新值（验证 `clearCache` 生效） |
| 9 | 个性化数据安全 | 老用户设置过昵称/钉首页/主题 | 任何 policy 下都**绝不被改动** |
| 10 | 新建课程表 | 老用户新建一张课程表 | 假期提醒默认开启（验证 `dynamicKey` 条目） |

## 8. 回答用户的两个疑问

**问：某些功能强制对老用户重置，不确定是否可以实现？**

可以实现，本方案用 `policy: "force"` + `since` 版本号实现，并且解决了"强制"最容易踩的三个坑：

1. **不会每次都重置** —— 版本号保证只执行一次
2. **不会反复覆盖用户** —— 用户在被强制之后的手动修改会被 `userSet` 记录下来，后续不再被动
3. **有据可查、可解释** —— `forcedKeys` 留下审计记录，客服/用户问起时能说清"哪一版改了什么"

**问：新用户和老用户的默认设置怎么区分？**

靠 **`app_state` 标记 + 业务数据探测** 双重判定。
最关键的防护是：**`app_state` 不存在时不能默认当成新用户** —— 那会把所有从旧版本升级上来的老用户设置一次性清空。
必须先串行探测几个业务 key，命中任一即按老用户处理。这条必须写进守护手册的红线清单。

## 10. 一句话总结

**建一张表（`app-defaults.js`）说清"每个设置的默认值和它的脾气"，
用一个标记（`app_state`）记住"这台机器走到哪一步了"，
用一个集合（`userSet`）记住"用户亲手动过什么"，
再用一个版本号（`since` / `defaultsVersion`）保证每一步都恰好只走一次。**
