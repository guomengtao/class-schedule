# 第三轮反馈：「卡了很久 → 重启」；重启后显示 E / F —— 根因收敛到「渲染负载」

> 日期：2026-09-25
> 用户原话：**"点的时候，卡了很久，后面又重启了，然后显示个E"**、**"重启之后就显示F"**
> 前序文档：[第二轮结果-F项卡住分析.md](file:///Users/Banner/Documents/guomengtao/tom/class/class/docs/第二轮结果-F项卡住分析.md)
> 结论性质：本轮把根因从「组件机制/定位」修正为「**渲染负载（单帧总量 + 累积量）**」，并给出**不改外观**的修复方案。

---

## 一、新反馈怎么读

| 用户描述 | 技术含义 |
|---|---|
| **"卡了很久"** | **主线程长时间阻塞**——这是看门狗复位（watchdog reset）的典型特征，**不是**某个 API 瞬时崩溃 |
| "后面又重启了" | 阻塞超时 → 系统复位 |
| "然后显示个 E" | `input_diag2_step` 残留为 `5`（E 是第 5 项）→ **卡在 E 项时被复位** |
| "重启之后就显示 F" | 再次执行时越过了 E，**卡在 F 项**（`step=6`） |
| "没修改好，不管用" | 改法 B（定位切换）**未解决问题** |

---

## 二、两个关键推论

### 推论 1：改法 B 无效 → R1「绝对定位根 + scroll 父级」排除

上一轮把组件根在跑道屏上改成 `position: relative`（`aaa067d`），本次现象不变 → **定位方式不是主因**。

至此，轮到我修正自己的判断：R1 只解释了"溢出方向"，解释不了"**卡很久**"。

### 推论 2 ⭐：同一项 E，单独跑通过、连续跑却挂 —— 差异不在 E 本身

对比两次测试方式：

| 轮次 | 测试方式 | 结果 |
|---|---|---|
| 第二轮 | **逐项点** | A ✅ B ✅ C ✅ D ✅ E ✅ **F ❌** |
| 第三轮 | **一键连续跑** | …**E ❌**（未走到 F）→ 再跑 **F ❌** |

同一项 E，**单独跑没事、连在前面跑了 A~D 之后就跑不过**。

→ **问题不在 E（或 F）这个元素本身，而在"它之前已经渲染并销毁过多少东西"。**

**结论：每次 `if` 切换都会创建/销毁大量节点，而渲染资源与内存没有被及时回收，形成累积**；累积到某一项时越过临界点 → 单帧构建/绘制耗时暴增 → 主线程阻塞 → 看门狗复位。

---

## 三、修订后的根因：R2「渲染负载」升为首因

把所有证据排在一起看：

| 证据 | 说明 |
|---|---|
| A~E **单独**跑全部通过 | 每一小块的渲染成本是**可接受的** |
| F **一次性渲染全部** → 卡死重启 | 全部叠加后，**单帧负载**超出设备承受 |
| 连续跑时 **E 也挂** | 前面节点未及时回收 → **累积负载** |
| 真实输入页**一进就重启** | 它本身就是"一次性渲染全部"，等价于 F |
| **"卡了很久"** | 主线程阻塞（**耗时**问题），不是瞬时崩溃 |
| 10 Pro 正常 | 更强的 CPU/GPU，同样的负载扛得住 |

> **一句话：问题出在「同一帧内需要构建与绘制的元素总量」，与具体是哪个元素、用什么定位方式无关。**

pill 键盘的规模量级（回滚后的原版）：

| 元素 | 数量 |
|---|:---:|
| `<text class="calbtn66">`（含 `border:3px` + `border-radius:30px`） | **26** |
| `<img>` PNG | **7~8** |
| `<scroll>` | **2** |
| 绝对定位层 | **3** |
| 候选行 / 功能键 / `cvalrow-wrap` | 若干 |

**合计 200+ 节点、8 张图片、26 个带圆角描边的文本，全部在同一帧内完成布局与绘制。**

---

## 四、修复方案：分帧挂载（**不改任何外观**）

### 4.1 核心逻辑

既然 **A~E 每块单独渲染都被实测证明安全**，那就把整块键盘**拆成多帧挂载**，让每一帧的负载都不超过"已被证明安全"的量级。

这是本次最有说服力的思路：它不是猜测，而是**以实测数据（A~E 全过）为依据**的工程推导。

### 4.2 实现设计（pill 分支，仅跑道屏生效）

1. 组件新增状态 `pillStage`（初始 0），`onInit` 后用 `setTimeout` 逐级递增：
   - `0 → 1`（约 0ms）：先挂**候选行 + 功能键行**（轻量）
   - `1 → 2`（约 60ms）：挂**键盘 scroll 的前两排按键**
   - `2 → 3`（约 120ms）：挂**第三排按键 + 空格图片**
   - 可选 `3 → 4`：挂剩余图片
2. 模板用 `if="{{pillStage >= N}}"` 分段挂载。
3. **外观、尺寸、图片、圆角、滚动全部保持不变** —— 只是"分几次画出来"，总耗时约 150~200ms，用户几乎无感。

**预期效果**：单帧节点数从 200+ 降到约 70，与已验证安全的 A~E 量级相当。

### 4.3 为什么这比"改外观"更可取

- 满足你的要求：**不影响所有跑道屏用户的界面**；
- 只影响**渲染时机**，不改变**渲染结果**；
- 若无效，说明是"总量"而非"单帧"问题（内存层面），此时再考虑减法方案（见第五章），判断依据明确。

## 八、结论

1. **改法 B 无效**（定位不是主因）—— 记录在案，避免以后重复走这条路；
2. 新证据（**卡很久**、**E 在连续跑时也挂**）把根因锁定为「**渲染负载：单帧总量 + 节点累积**」；
3. **最有依据的修复 = 分帧挂载**：A~E 已实测证明"每小块安全"，把整块拆成多帧即可，**且完全不改外观**；
4. 这条路线同时满足你的两个约束：**不影响所有跑道屏用户**、**尽可能一次改对**。

## 九、已实施：独立的「分帧版」组件（H 项）

> 说明：第六章草案里的编号（G=连续跑两遍、H=分段挂载）在实际实施时被重新分配 ——
> **实际编号：G = 官方原版 A/B 对照；H = 分帧挂载版**。以本条为准。

用户提出：**不要直接改现有组件，而是单独加一份独立的、临时并存** —— 若验证有效再切换。这样用户测试最简单（点一下即可），我们稍麻烦一点但风险最低。已按此实施。

### 9.1 新增组件：`src/components/InputMethod/InputMethodStaged.ux`

- **来源**：复制当前 `InputMethod.ux`，**外观、尺寸、图片、圆角、滚动位置全部不变**；
- **唯一改动**：pill 分支的键盘子树改为 **3 帧依次挂载**：

| 帧 | 内容 | 时机 |
|:---:|---|---|
| 1 | 顶部条（候选行 + `search` / `lang` / `123` / `bigA` / `a` / `del` / `back2` 图片） | `pillStage = 1`（立即） |
| 2 | 键盘第 1、2 排按键 | `pillStage = 2`（约 60ms 后） |
| 3 | 键盘第 3 排 + 空格键图片 | `pillStage = 3`（约 150ms 后） |

- 实现要点：
  - 新增 data `pillStage: 0`；
  - 新增方法 `advancePill()`（**仅 `screentype==='pill-shaped'` 生效**，其它屏型直接 return）；
  - 触发点：`onInit`（`hide=false`）、`watchHidePropsChange`（`hide→false`）、`adjustScreenWidth`（屏型变化时）；
  - 模板里原带 `static` 的排节点改为带 `if="{{pillStage >= N}}"`（`static` 与 `if` 不宜并用，故移除 `static`）；
  - **单帧节点数从 200+ 降到约 70**，与"已验证安全的单元素测试（A~E）"量级相当。

### 9.2 诊断页新增 H 项（F vs H 是最干净的对照）

`input-crash-diag2` 现为 **A~H**：

| 项 | 内容 | 条件 |
|:---:|---|---|
| F | 当前组件 | `dictlazy=true` |
| G | 官方原版（A/B 对照） | 无 `dictlazy` |
| **H** | **分帧挂载版** | `dictlazy=true`，**与 F 唯一差异 = 是否分帧** ✅ |

### 9.3 包体空间（"够不够并列"）

| 项 | 数值 |
|---|---|
| `InputMethod.ux` / `InputMethodOfficial.ux` / `InputMethodStaged.ux` | 49 / 52 / 49 KB |
| `assets`（**三者共用，不重复打包**） | 436 KB |
| 现有 `dist/` 总量 | 1.8 MB（含多份渠道包） |

→ 新增一份仅 **+49KB 源码**（jsc 编译后更小），**assets 完全复用**，**空间充足** ✅

### 9.4 三个组件的定位（线上零变化）

| 组件 | 定位 | 参与线上 |
|---|---|:---:|
| `InputMethod.ux` | **线上正式版**（`chinese-input` 使用） | ✅ 是 |
| `InputMethodOfficial.ux` | A/B 对照（官方原版） | ❌ 仅诊断页 G |
| `InputMethodStaged.ux` | 候选修复（分帧） | ❌ 仅诊断页 H |

### 9.5 判读与后续切换

1. 用户**单点 H**（不要一键跑全部，避免 A~G 累积干扰）；
2. **H 通过** → 切换（二选一）：
   - **方式一（推荐）**：把分帧逻辑合并回 `InputMethod.ux`，删除 `InputMethodStaged.ux`；
   - **方式二（零风险）**：把 `chinese-input.ux` 的 import 与标签指向 `InputMethodStaged`，观察后再合并。
3. **H 也不通过** → "单帧总量"假设不成立（是累积/内存层面）→ 回到 F1~F5 细分，或考虑 B3（去圆角描边）。
