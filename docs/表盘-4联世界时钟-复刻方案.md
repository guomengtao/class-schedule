# 表盘复刻方案 · 4 联世界时钟（World Clock 4-up）

> 选题依据：桌面截图（2026-10-26 21:48）中的苹果时钟 App 表盘选择器共 8 款，其中 3 款尚未落地
> —— 4 联世界时钟、CUP 数字盘、纯刻度盘。选 **4 联世界时钟**，理由有三：
> ① 结构上是唯一的多盘布局（现有 17 款全是单盘），能真正扩展能力边界而非换皮；
> ② 已有基准图 `docs/reference/apple-clock-widget/widget-worldclock-4up-dark.png`，可直接进 EVX 验收；
> ③ 它与今天发现的「字号 px 硬编码 + 跨机型倍率不匹配」缺陷正面碰撞，能倒逼适配机制收敛。
>
> 参考图已归档：`docs/reference/apple-clock-widget/worldclock-4up-desktop-20261026.png`（695×335 物理 / 347×167 逻辑）

---

## 1. 原版规格量测

从桌面截图（Retina 2x）逐项量测，换算为逻辑像素：

| 元素 | 规格 | 备注 |
|---|---|---|
| 面板 | 347 × 167，圆角 ≈ 28 | 横向长条，非正方形 |
| 面板背景 | 径向渐变深蓝，中心 ≈ `#2b3a8c`，边缘 ≈ `#1b2060` | 中心偏左上，非纯色 |
| 小盘数量 | 4，横向等分 | Cupertino / Tokyo / Sydney / Paris |
| 单盘直径 | **68** | 无外圈圆环，仅 12 个阿拉伯数字 |
| 盘内数字 | 1–12，白色，字号 ≈ 11 | 沿半径 ≈ 28 的圆周排布 |
| 中心点 | 白色实心圆，直径 ≈ 3 | 四盘各一个 |
| 时针 | 白，长约 18，宽 ≈ 3，圆头 | 无秒针 |
| 分针 | 白，长约 27，宽 ≈ 3，圆头 | 与时针同宽（非典型「分针更细」） |
| 城市名 | 粗体白，字号 ≈ 14 | 单行居中，位于盘下 ≈ 46 处 |
| 日期行 | 灰 `#9aa0c8`，字号 ≈ 12 | `Today` / `Tomorrow` |
| 时区行 | 灰 `#9aa0c8`，字号 ≈ 12 | `-15HRS` / `+1HR` / `+3HRS` / `-7HRS` |

关键观察：**原版没有外圈圆环**，也没有刻度线，12 个数字就是全部表盘元素。这比现有 `watch-face-metal`（36 个盘内节点）结构简单得多，但数量上是 4 份。

## 2. 核心矛盾：小屏不可读（本方案必须正面处理的问题）

4 个盘并排需要的横向空间是刚性的：

| 机型 | 屏宽（逻辑） | 1×4 布局下每盘直径 | 对应数字字号 | 结论 |
|---|---|---|---|---|
| 10Pro | 336 | 68（与原版等比） | 11 | ✅ 与原版一致，可原样复刻 |
| 9 | 192 | **39** | **≈ 6.3** | ❌ 6px 字在 480 高屏上肉眼不可辨 |

字号换算依据：数字沿圆周排布，相邻数字的弦长 = `2·(r−6)·sin15°`。盘径 68 时弦长 14.5，11px 字号刚好填满；盘径 39 时弦长 7.0，字号必须 ≤6 才不重叠。

**这不是参数没调好，是几何约束。** 1×4 布局在 192 屏上无解，必须改布局。

### 三个可选路径

| 方案 | 9 机型做法 | 每盘直径 | 数字字号 | 与原版差异 | 评价 |
|---|---|---|---|---|---|
| **A · 2×2 宫格** | 四盘改为两行两列 | 80 | 13 | 布局不同，元素齐全 | **推荐**：可读性最好，且 192×490 纵向空间充裕（490 高） |
| B · 保留 1×4，去数字 | 仅画刻度线 | 39 | 无 | 丢失数字，信息量下降 | 备选：苹果在极小尺寸（表盘 Complications）确实会这样做，不算错 |
| C · 横向滚动 | 一屏显示 1.5 盘 | 68 | 11 | 需手势，非原版交互 | 不推荐：手表上滑动手势与页面切换冲突 |

**建议 A，并把「布局切换」做成显式分支**，而不是靠 `transform: scale()` 硬套 —— 后者会把文字一起压糊。

## 3. 布局规格（两套，均给到 px）

### 3.1 10Pro（336 × 480）· 还原原版

```
面板: left 8, top 24, width 320, height 160, radius 26
      background: 径向渐变 #2b3a8c → #1b2060

盘 i (i=0..3): cx = 8 + 40 + i*80 = 48 + i*80
              cy = 24 + 22 + 34 = 80
              直径 68（半径 34）

数字 12 个: 角度 θ = i*30°，半径 28
           x = cx + 28·sin θ, y = cy − 28·cos θ
           字号 11，白色，text-align center，需人为减 6 补偿文字盒

城市名: y = 24 + 124 = 148，字号 13 粗体白
日期行: y = 168，字号 11 灰
时区行: y = 186，字号 11 灰
```

### 3.2 9（192 × 490）· 2×2 宫格

```
面板: left 6, top 30, width 180, height 300, radius 22

格 (row, col): cx = 6 + 45 + col*90 = 51 + col*90
              cy = 30 + 52 + row*140 = 82 + row*140
              盘径 72（半径 36）

数字: 半径 29，字号 12
城市名: cy + 52 = 字号 12 粗体
日期行: cy + 68，字号 10
时区行: cy + 84，字号 10
```

纵向核算：2 行 × 140 = 280 + 面板内边距 20 = 300 < 172（499−30−top）的可用高度，**有充足余量**。这是 2×2 在 192 屏成立的关键前提。

## 4. 数据结构

```js
// 一期：静态城市表。偏移单位为小时，正数向东。
const CITIES = [
  { key: "cupertino", city: "Cupertino", tz: -15 },
  { key: "tokyo",     city: "Tokyo",     tz: +1  },
  { key: "sydney",    city: "Sydney",    tz: +3  },
  { key: "paris",     city: "Paris",     tz: -7  }
]
```

渲染：单个 `setInterval(1000)` 驱动 4 盘，**不要开 4 个定时器**（现有 17 款表盘均为单定时器，保持一致；4 个定时器在 Vela 上会叠加唤醒，实测 `watch-face-vibrate` 1218 行已是最重负载）。

时间计算：

```js
// 目标时区时间 = 本机 epoch + 偏移
const d = new Date(Date.now() + tz * 3600 * 1000)
const h = d.getHours() % 12
const m = d.getMinutes()
// 跨日判断用 UTC 日期比较，避免本机时区干扰
const localDay = Math.floor((Date.now() + tz * 3600000) / 86400000)
const todayDay = Math.floor(Date.now() / 86400000)
const dayLabel = localDay > todayDay ? "Tomorrow"
               : localDay < todayDay ? "Yesterday" : "Today"
```

指针角度（沿用 `watch-face-metal` 的 `syncHands`）：

```
时针 = (h + m/60) * 30
分针 = m * 6
```

## 5. 与现有代码的关系

| 事项 | 复用 | 新增 |
|---|---|---|
| 定时器 / 走时 | `watch-face-metal` 的 `startTimer` / `tick`（可直接搬） | — |
| 指针角度 | `syncHands` | — |
| 屏幕适配 | `fitScreen()` 的异步 `getInfo` 模式（含 `screenWidth < 300` 判据） | 布局分支：`screenWidth >= 300` → 1×4，否则 → 2×2 |
| 数字排布 | — | 用 `sin/cos` 生成 12 个节点，**不手写 12 条样式**（48 个节点手写不可维护） |
| 城市 / 日期 / 时区文本 | — | 三段 text + 跨日判定 |

**必须避免的坑**（今天实测得出）：
1. 字号一律写 px 会在 192/336 之间比例失真（现有 17 款表盘的普遍问题：屏宽比 1.75，字号比仅 1.09~1.27）。本表盘 4 个盘横向排布，比例失真会被放大 4 倍，**必须按屏宽算比例字号**，不能照抄现有写法。
2. `onReady` 在 Vela 不可靠，`fitScreen` 必须从 `onInit` 调（`watch-face-metal` 第 135 行已有注释印证）。
3. `require("@system.device")` 必须页内 require，顶部 import 会静默失败。
4. 文字 `width` 必须写 `100%` 而非固定值，否则 `text-align:center` 的中心停在旧屏宽的一半。

## 6. 验收流程（用 EVX）

```bash
# 1) 同刻截图：本机钉死到基准图时刻（基准图约 10:08），两机型各截一张
python3 tools/wf-exact-verify.py \
  --ref docs/reference/apple-clock-widget/worldclock-4up-desktop-20261026.png \
  --mine screenshots/世界时钟-10pro-20261102.png \
  --crop-pct 3,6,96,94 --same-clock 10:08 --name wc-10pro

# 2) 自比自先跑一次，确认工具不产生假差异
python3 tools/wf-exact-verify.py --ref <我方截图> --mine <我方截图> --name wc-self
```

判定门槛（按当前 PASS = SSIM ≥ 0.985 且超阈 ≤ 1.0%）：

| 项 | 期望 |
|---|---|
| 自比自 | SSIM 1.000000 |
| 10Pro vs 原版 | SSIM ≥ 0.95（4 个盘的数字边缘是主要差异来源） |
| 9 机型 vs 原版 | 布局不同（2×2 vs 1×4），**只比单盘内部**：裁任一小盘区域对比 |
| crop 贴合 | 必须 `exit 0`，若 `exit 2` 说明裁剪框切断面板 |

注意：9 机型与原版布局不同，**整图对比无意义**，只能比单盘。这是 2×2 方案的固有代价，需在验收记录里写明。

## 7. 风险与工作量

| 风险 | 影响 | 应对 |
|---|---|---|
| 48 个数字节点渲染压力 | 中。Vela text 节点多会掉帧 | 一期先实现，实测 FPS；若掉帧改为图片化数字（4 个盘共用一张数字底图） |
| 极性与渐变背景叠加 | 低。径向渐变在 Vela 需多层叠加 | 用「底层纯色 + 上层半透明径向」近似 |
| 小屏 2×2 与原版不一致 | 高（视觉验收标准需放宽） | 明确记录为设计决策，而非缺陷；两机型分别出具验收结论 |
| 跨日判定错 | 中（显示 Yesterday/Tomorrow 错误） | 用 epoch/86400000 比较，不依赖本机时区字符串 |

工作量估计：页面骨架 1 份（约 400 行，参考 `watch-face-metal` 560 行），数字生成函数约 20 行，两套布局样式约 120 行。

## 8. 落地顺序建议

1. 先做 10Pro（1×4），可 1:1 对照原版，验证「数字圆周排布 + 指针角度」正确
2. 再做 9 机型 2×2 分支，只改布局容器，盘内逻辑不动
3. 两机型各自截图，跑 EVX 自比自 → 再跑原版对比
4. 把本次的「比例字号」写法沉淀成模板，回头修另外 17 款表盘的字号失真问题（当前屏宽比 1.75、字号比 1.09~1.27，系统性偏差）
