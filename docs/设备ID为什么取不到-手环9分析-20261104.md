# 手环 9 取不到设备 ID：原因分析与三方对照

> 2026-11-04 · 起因：用户在群里反馈「激活页显示的设备 ID 跟设备对不上、我没法识别是哪台」，
> 现场出现两个真实用户分别显示 `4096` 与 `6444`，而手环系统「设置 → 信息」页显示的是 `44c786`。

---

## 〇、先给结论

**不是权限没声明，也不是 API 用错了名字。** 真正的问题有三层，按严重程度排列：

1. **兜底策略在「取不到」的时候凭空造了一个 ID**（`uuid-` + 32 位随机十六进制），还把它持久化到本地存储。
   于是「取不到」这件事在用户界面上不会暴露成失败，反而显示成一个**看起来很正常的 4 位短码**——
   但它跟这台设备没有任何关系，重装应用、清除数据就会变。**这是最致命的一层**，因为它把「不可用」伪装成了「可用」。
2. **展示层只取最后 4 位**（`substring(len - 4)`）。即便真号拿到了，4 位十六进制的取值空间只有 65536，
   用户量一上千就有碰撞风险，而且**无法从 4 位反查整号**，售后只能让用户反复对比。
3. **我们取号的口径与系统「信息」页不是同一个数据源**。用户能自己看到的 `44c786` 是系统层的 6 位短 ID，
   我们显示的 4 位是另一条链路的产物，两者不在同一命名空间，用户拿自己看到的字去核对，必然对不上。

**关于 AstroBox：它其实也没有显示「设备 ID」。** 见第五节实测——它显示的是设备名、连接状态、电量、
充电历史，那些来自 BLE 加密会话的通用设备信息服务，界面上并没有 MAC / 序列号 / 设备 ID 字段。
「AstroBox 能拿到」这个印象，来自它能连上手环并读电量，而不是它展示了 ID。

---

## 一、三条链路的对照

同一台手环，三种「身份」来源，彼此不通：

| 来源 | 通道 | 拿到的字段 | 值的形态 | 用户能否自己看到 |
|---|---|---|---|---|
| **我们的快应用** | 设备内 `@system.device.getDeviceId()` | `deviceId`（或取不到 → 本地随机 UUID） | 正常时未知；兜底时 `uuid-<32 hex>` | 能看到，在兑换码页页脚 |
| **手环系统「设置 → 信息」** | 设备固件自身 | 系统短 ID | 6 位十六进制，如 `44c786` | 能看到，系统原生页面 |
| **AstroBox** | 手机 BLE ↔ 手环，authkey 加密会话 | 设备名、型号、电量、固件、安装记录 | 只显示名称与状态，无 ID 字段 | 能看到名称，看不到 ID |

**关键点：这三者不是同一个值，也不能互相换算。** 用户拿 `44c786` 来核对我们显示的 `4096`，永远对不上。

## 二、我们的取号链路，逐段拆

### 2.1 主动获取（`src/pages/activation/shared/activation-context.js:126`）

```js
function _resolve() {
  var device = require("@system.device")
  if (!device || typeof device.getDeviceId !== "function") { _fallback(); return }
  device.getDeviceId({
    success: function(data) {
      var raw = (data && data.deviceId) || ''
      if (!raw || raw === 'NA' || raw === 'unknown' || raw === 'null') { _fallback(); return }
      _deviceId = raw
      _readInfo()
    },
    fail: function() { _fallback() }
  })
}
```

这段本身写得是对的：已经预料到会返回 `NA` / `unknown` / `null` / 空串，并且做了判定。
**问题在于判定成立之后做的事——`_fallback()`。**

### 2.2 兜底：造一个 ID（`src/utils/device-uuid.js`）

```js
function getLocalDeviceId(cb) {
  storage.get({ key: 'device_uuid_v1',
    success: function(data) {
      if (data) cb(String(data))
      else {
        var id = 'uuid-' + generateUUID32()          // ← 随机生成
        storage.set({ key: 'device_uuid_v1', value: id }, function() { cb(id) })
      }
    },
    fail: function() { cb('uuid-' + generateUUID32()) }  // ← 连存储都失败也现造一个
  })
}
```

后果链：

- 用户 A 的 `@system.device.getDeviceId` 返回 `NA` → 生成 `uuid-9f3c...b4096` → 页脚显示 `4096`
- 用户 A 换一台手环、或清除应用数据 → 生成新 UUID → 页脚变成另一个 4 位
- **同一个人两次报的 ID 不一样**，我们没有任何办法把它和真实设备对应起来
- 服务端把 `uuid-...` 当成 `device_full` 入库，数据库里就留下一批永远无法回连设备的假号

### 2.3 展示：只留 4 位（`path-b-redeem.ux:110`）

```js
formatId(id) {
  if (!id) return '点此重试获取ID'
  return String(id).substring(String(id).length - 4)
}
```

这样设计**当初的理由是合理的**——手环小屏放不下长串，用户也不需要手抄，二维码里带的是全长。
但它带来一个副作用：**「真号后 4 位」和「随机 UUID 后 4 位」在屏幕上长得一模一样。**
用户在群里报 `4096` 的时候，我们无法从这 4 位判断他到底取到了真号还是兜底号。

### 2.4 为什么手环 9 更容易触发

系统镜像（`~/.vela/sdk/system-images/vela-release-4.0/nuttx`）里能扒到这些符号：

```
getDeviceId
requestDeviceIdentity
verify auth propertyKey: getDeviceId, authcode:
```

第三条是关键：**`getDeviceId` 在系统层是一个需要鉴权（authcode）的身份属性读取**，
不是随便读一个静态字段。这意味着它的返回值取决于运行时的认证状态——
手环刚开机、应用刚安装首次启动、系统正在做绑定校验等时机，都可能落到 `fail` 或返回 `NA`。

同时镜像里存在**至少四种不同的「设备 ID」概念**：

```
BindInfoV2_did_tag                       ← 小米账号绑定的 DID
BindLocal_AppVerify_app_device_id_tag    ← 应用校验用的 app_device_id
BT_AD_DEVICE_ID 0x10                     ← 蓝牙广播携带的 ID
did_encode                               ← 编码后的 DID
```

结论：**「设备 ID」在 Vela 生态里不是单一字段**。我们取的那一个，碰巧是鉴权依赖最强、最不稳定的那个。

## 三、四种失败情形与判别方法

| # | 情形 | 用户看到 | 判别方法 |
|---|---|---|---|
| 1 | `getDeviceId` 返回 `NA` / 空 → 走兜底 | `uuid-xxx` 的后 4 位，**每次重装都变** | 让用户清一次应用数据再看：变了就是情形 1 |
| 2 | `getDeviceId` 抛异常 / `fail` → 走兜底 | 同上 | 同上 |
| 3 | 返回正常，但号与系统页不同源 | 固定的 4 位，与系统页 6 位无关 | 重装后 4 位不变 → 取到了真号，只是不同源 |
| 4 | 返回正常且同源 | 4 位应等于系统页 6 位的末 4 位 | 例：系统页 `44c786`，页脚应显示 `c786` |

**现场数据对照**：用户看到 `6444`，系统页是 `44c786` → 末 4 位 `c786` ≠ `6444`。
**说明他落在情形 1 / 2 / 3，不是 4。** 这就是「无法识别」的技术原因。

---

## 四、「用户无法识别」是三重错误叠加

单看每一层都不致命，叠起来就完全失去可追溯性：

1. **兜底造假** → 屏幕上永远有一个值，永远不会出现「获取失败」字样，团队因此长期没有发现这是个问题；
2. **只露 4 位** → 真号和假号外观一致，用户报到群里时我们无法区分；
3. **与系统页不同源** → 用户唯一能自己核对的参照物（设置→信息里的 `44c786`）用不上。

还有一条工程侧的加重因素：**app.ux 里还有一份同样的取号逻辑**（`syncHandleGetDeviceId`，供 APK 通过 IPC 索取），
两份逻辑各写一遍、口径一致但都带兜底。任何一处改动都要同步两处，属于结构性隐患。

## 五、AstroBox 实测：它并没有显示设备 ID

截图：`screenshots/astbox-设备面板-20261104.png`

界面上可见的全部内容：

- 设备卡片：`Xiaomi Smart Band 9 NFC` / `Connected` / `80%` / `Last charge 11 hours ago`
- 侧栏：`Resource Community` / `Explore` / `All Resources` / `Plugins` / `Queue` / `Settings`
- 主区（Queue）：`Installation Queue` / `Download Queue`，历史里是 `Ev 表盘 1.0.31 · Installed successfully` 等安装记录

**没有 MAC、没有序列号、没有设备 ID 字段。**

AstroBox 之所以「看起来能拿到设备」，是因为它做了三件我们没有做的事：

1. 通过 **authkey 建立 BLE 加密会话**（需要用户从小米运动健康里导出 authkey 导入），会话建立后能读协议层的设备信息服务；
2. 读的是**手机侧**能看到的广播与协议字段，不受设备内应用沙箱与权限约束；
3. 它的用途是装包，不需要「唯一设备号」这个概念，所以也从未把它暴露成 ID。

**结论：拿 AstroBox 做对照是错的参照物。** 真正的对照物是手环系统「设置 → 信息」页，
那才是用户能自己看到、且与设备本体绑定的号。

## 六、5 分钟确诊（现场可直接执行）

给用户的三步，按顺序做，每步都能排掉一类情形：

1. **读系统页**：设置 → 信息，记下 `设备 xxxxxx`（本例 `44c786`）。
2. **读我们的页脚**：高级版 → 兑换码激活（或已激活的「历史与设备信息」），记下「设备ID xxxx」。
3. **判等**：页脚 4 位是否等于系统页末 4 位？
   - 相等 → 情形 4，取号正确，问题只在「只有 4 位」；
   - 不等 + 重装后页脚会变 → 情形 1/2，走的是兜底随机 UUID，**该用户从未取到真号**；
   - 不等 + 重装后不变 → 情形 3，取到了另一个命名空间的 ID。

第 3 步「重装后会不会变」是最关键的判据，建议做成固定的客服话术。

## 七、修复方案

### P0（尽快，改动小、收益最大）

**把「兜底随机 UUID」从「静默使用」改为「显式降级」。**

- 取号失败时，页脚不再显示 4 位随机字符，改为显示「ID 获取失败·点此重试」，
  同时把二维码里的 `deviceId` 留空（现有 `_build` 已经是这个语义：空值即表达无号，见 `activation-context.js:178` 注释）；
- 本地 UUID 继续保留，但**只在服务端明确要求时**作为「匿名设备指纹」上报，字段名与 `device_full` 区分开，
  避免继续污染主字段。

理由：今天的问题不是「取不到」，而是「取不到还装作取到了」。先让失败可见，才能统计真实失败率。

### P1（下一版）

**把展示口径统一到系统页那 6 位。**

- 优先尝试取系统同源短 ID（需要先确认 `@system.device` 是否有暴露，或走别的 API）；
- 取不到时，页脚直接引导用户「设置 → 信息 里那 6 位」并允许他手动录入/复制；
- 展示从 4 位扩到 6 位（192 屏 24px 字号仍可容纳，`44c786` 六字符约 72px）。

### P2（结构性）

- **合并两处取号逻辑**：`app.ux:syncHandleGetDeviceId` 与 `activation-context.js:_resolve` 应当共用一个模块，
  现在各写一份，任何改动都要双改，容易漂移；
- **加一条一次性诊断**：把 `getDeviceId` 的原始返回值（含 `NA`/`fail`/异常信息）、`getInfo` 的 model/product、
  以及最终采用的是真号还是兜底，写进二维码的 `i=` 标记（现在只有 `i=f` 一个值），
  服务端就能统计「手环 9 的真号获取成功率」。
