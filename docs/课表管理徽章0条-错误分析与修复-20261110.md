# 课表管理页「两套都是 0 条」错误分析与修复

- 时间：2026-11-10 08:20 +0800
- 影响版本：v1.9.174 ~ v1.9.180（手环端 EV 课程表）
- 报告人：Tom（真机看到「八年级二班 0 / 九年级一班 0」）
- 结论一句话：**数据没有丢，也没有写错格式；是「课表管理」列表的徽章数字首帧被渲染成 0 之后不再重绘**，而抽屉里读的是内存态的真实值，于是同一屏上出现「列表 0 条 / 详情 49 门」的自相矛盾。

---

## 一、现象（三处互相矛盾）

| 观测点 | 显示 | 说明 |
|---|---|---|
| 课表管理列表徽章 | 八年级二班 **0**、九年级一班 **0** | 用户看到的「数据都没了」 |
| 同一行点开的抽屉 | 九年级一班 **49 门课程** | `sheetCount` 读 `self.list[idx].courseCount` |
| 首页（切换到九年级一班后） | 星期二 · 英语 08:00-08:45、物理 09:10-09:55 | 课程真实存在且与真源一致 |

三处都源自同一份内存数据，却给出 0 / 49 / 有课 三种答案 → 只能是**渲染层与状态层不一致**，不是存储层丢数据。

---

## 二、根因

### 2.1 直接原因：首帧「占位 0」后 Vela 不重绘

`src/pages/schedule-manager/schedule-manager.ux` 的 `loadData()` 原实现是两段式：

```js
// 第一段：只拿到名字就先渲染，courseCount 一律填 0
var list = []
for (var i = 0; i < n; i++) list.push({ name: names[i], courseCount: 0, holidayOn: false })
self.list = list          // ← 首帧渲染成 0

// 第二段：异步取每套课程数，再重建行对象整体赋值
database.getAllCoursesWithIndex(idx, function (schedule) { /* draft[idx].courseCount = count */ })
```

第二段的写法本意是历史修复结论「必须重建全新行对象再整体赋值，否则 Vela 判等后不重绘」。但真机实测（v1.9.180，手环 10 Pro）表明：**该修法只在「第二次赋值与第一次不同」时成立，Vela 对同一列表的连续两次赋值只认第一次**，第二次 `self.list = out` 没有触发重绘。

因此：
- 视图停留在第一段的 `courseCount = 0` → 徽章恒为 0；
- state 已经更新成真实值 → 抽屉读取时拿到 49。

**这就是「同一页面，徽章说 0、抽屉说 49」的全部原因。**

### 2.2 为什么之前没发现

1. 抽屉 `sheetCount` 与徽章用**同一个字段**，但读取时机不同（点击时 vs 渲染时），形成「看起来自洽、实际分裂」的假象；
2. 徽章字号小，0 与 45 在低分屏肉眼难辨，历次真机验收只点抽屉、不核对列表数字；
3. 测试（`two-builtin-schedules.test.js`）只断言**存储里写了几套、每套几门**，没有一条断言 **UI 渲染出的数字**——典型「测了数据、没测呈现」。

### 2.3 排除掉的三个错误假设（均已实测否认）

| 假设 | 排除依据 |
|---|---|
| 存储写成了扁平数组（缺 `classes` 包裹） | `builtin.copySchedule()` 返回的确是按天分组结构：本地实测 `days=5 courses=45 / 49`，首元素 `day="星期一"`，`Array.isArray=true`，与 `saveToStorageWithIndex` 完全同口径 |
| `schedule-901.js` 没打进包 | 抽屉显示 49 门、首页周二显示英语/物理，说明模块已加载且有数据 |
| `ensureBuiltinSchedules` 把第二套跳过了 | `scheduleNames` 已写入两套名、抽屉能读到 49 门 |

### 2.4 顺带更正上一轮两个误导性结论

1. **「包是旧构建、第二套没打进去」是错的。** 当时用 `grep` 在 `app.jsc` 里找 `schedule-901`、`九年级一班`，而 jsc 是字节码 + UTF-16LE 常量池，ASCII/UTF-8 匹配根本不适用，属**用错工具得出的错误结论**。正确判据是运行期行为（抽屉 49 门 / 首页课程正确）。
2. **「先 seed 再 flush 就能保证两套」不可靠。** 页面首帧 `getSchedule` 会在 `initStorage` 完成前直接读 storage 并写 slot0，时序无法靠调用顺序保证；已改为「以 `scheduleNames` 为唯一新装判据 + 按槽位幂等补齐」，不可回退。

---

## 三、修复

### 3.1 代码改动（`src/pages/schedule-manager/schedule-manager.ux`）

1. **删除首帧占位渲染**：拿到名字后不再 `self.list = list`（0 徽章），改为 `self.list = []`，数据齐备后**只赋值一次**，让首次渲染就带真实课程数；
2. **flush 幂等**：新增 `flushed` 标志，防止兜底 `setTimeout` 与正常回调重复赋值（重复赋值正是 Vela 不重绘的触发条件）；
3. **兜底超时**：`setTimeout(…, 1200)`，任一异步回调没回来时按已就绪数据渲染一次，避免整页空白。

### 3.2 验收口径（这次必须验「呈现」，不只验「数据」）

| 层级 | 验收项 |
|---|---|
| L0 | `node --check` / 构建通过 |
| L1 | 单元：`builtin.copySchedule(0/1)` 分组结构 45 / 49 |
| L2 | 真机：课表管理徽章显示 **45 / 49**，与抽屉数字一致 |
| L3 | 真机：首页显示当日课程，切换两套后各自课表正确 |

## 四、教训（建议入坑索引）

1. **Vela 列表连续两次赋值只认第一次**：需要「先占位再刷新」的列表，正确做法是**等数据齐备一次性赋值**，不要靠「重建对象」硬刷。
2. **同一字段在两处读取时机不同，会制造自洽假象**：徽章（渲染时）与抽屉（点击时）共用 `courseCount`，导致 0 / 49 并存。
3. **测试要测呈现**：只断言存储条数抓不到「渲染成 0」这类 bug。凡「列表 + 数字徽章」页面，验收必须包含「截图里把数字读出来」。
4. **别用 `grep` 判字节码包内容**：jsc 常量池是 UTF-16LE/字节码，ASCII `grep` 结果不能作为「模块没打进包」的证据。
