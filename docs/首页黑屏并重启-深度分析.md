# 首页安装到手环9胶囊屏 → 黑屏 → 重启 · 深度分析

> **设备**：华为手环 9（胶囊屏，192px × 490px，`screenShape` = `"capsule"` 或 `"pill-shaped"`）  
> **现象**：安装后点击「进入首页」，页面先黑屏，然后手环自动重启（看门狗复位）  
> **版本**：v1.7.17（versionCode 1019）  
> **日期**：2026-10-03

---

## 0. TL;DR

手环 9 胶囊屏**首次安装后进入首页**发生看门狗复位的根因是：

> **首页模块求值 + `onInit` → `database.init` → `getAllCourses` → `initAllModules` 这一整条同步/异步链在胶囊屏上产生了过多的重渲染（`$forceUpdate`）和 storage IPC 调用，主线程被长时间阻塞，触发 RTOS 看门狗（Watchdog）超时重启。**

已有的**探针系统**（`bootStageStamp` 0~10）可通过「设置 → 工具 → 设备信息」读取 `index_boot_stage` 定位死在哪个阶段。对照 `boot_probe_welcome` 可验证 storage 写入是否落盘。

## 2. 关键问题点

### 2.1 模块级副作用：`initScreenShape()`

```javascript
// 位置: src/pages/index/index.ux 第 270-296 行
// 这是「模块级副作用」（全项目唯一一处）：在模块求值阶段就发起异步 IPC 调用 device.getInfo()
function initScreenShape() {
  try {
    device.getInfo({
      success: function(data) {
        var shape = data.screenShape || ""
        var capsule = (shape === "capsule" || shape === "pill-shaped")
        isCapsuleScreen = capsule
        if (indexInstance && indexInstance.isCapsule !== capsule) {
          indexInstance.isCapsule = capsule
          try { indexInstance.applyFontSizes() } catch (e) {}
          // 星期标题缩写 + 课程重新加载
          // ...
        }
      },
      fail: function() {}
    })
  } catch (e) { /* 吞错，防止模块求值失败导致整页不渲染 */ }
}
initScreenShape()   // ← 模块级立即执行
```

**风险**：

- `device.getInfo` 是**异步 IPC**，回调可能晚于首帧渲染
- 胶囊屏首帧会先用 `isCapsuleScreen = false`（默认值）渲染，等回调到达后再改成 `true` → 触发完整的重新计算（`applyFontSizes` + `updateDayDisplay` + `loadDayClasses` + `scheduleRender`）
- 这次「回填」等于一次**完整重渲染**，叠加在首帧路径上

### 2.2 重渲染风暴（已部分修复）

原始问题：首页进页路径上原本有 **5~7 次互不相关的 `$forceUpdate`**（主题/模板/首页设置/课程数据/节假日各一次），每次都重建整棵 DOM 树。

**已修复**：[scheduleRender()](file:///Users/Banner/Documents/guomengtao/ev/class-schedule/src/pages/index/index.ux#L415-L423) 引入渲染合并器（`setTimeout(0)` 批量合并），所有渲染请求合并为同一事件循环中的一次。

**残留问题**：

- `refreshClasses()` 中回调链（`reloadHolidayState` → `loadDayClasses` → `updateStatus`）仍然可能触发多次 scheduleRender
- 胶囊屏回填（`initScreenShape` 成功回调）中的 `scheduleRender()` 与 `onInit` 完成后的 `scheduleRender()` 可能在同一帧内竞争

### 2.3 `applyFontSizes()` 抛错风险

```javascript
// 位置: src/pages/index/index.ux 第 637-646 行
applyFontSizes() {
  var f = this.computeFontSizes(store.getBaseFontSizeSync())  // ← 同步读 storage
  this.displaySize = f.display
  this.metaFontSize = f.meta
  this.dayTitleSize = f.dayTitle
}
```

**风险**：`store.getBaseFontSizeSync()` 在读不到值时可能返回 `undefined`，`computeFontSizes(undefined)` 中 `Math.round(undefined * 32 / 48)` = `NaN`，后续渲染时将 `displaySize: NaN` 传给课程卡片 → 可能导致渲染异常。

**已兜底**：调用处已包裹 `try/catch`（第 482 行）。

### 2.4 8 秒超时 vs 看门狗超时

```javascript
// 位置: src/pages/index/index.ux 第 439-445 行
self.loadTimeout = setTimeout(function() {
  if (self.isLoading) {
    self.loadError = true
    self.isLoading = false
    self.scheduleRender()
  }
}, 8000)
```

- 应用层 8 秒超时：如果异步链超过 8 秒未完成，显示「数据加载失败」
- RTOS 看门狗超时：通常 3~5 秒内主线程无响应即触发
- **差距**：如果异步操作在 3 秒内阻塞主线程（即使只是 storage IPC 队列堆积），看门狗会先于应用层超时触发

### 2.5 胶囊屏 CSS 媒体查询内联覆盖

胶囊屏的 `computeFontSizes()` 将字号收敛到：

- `display`（课程名）≤ 32px
- `meta`（时间/地点）≤ 20px
- `dayTitle`（星期标题）≤ 26px

同时 CSS 媒体查询 `@media screen and (shape: pill-shaped)` 中有独立的内联样式覆盖，如果 `isCapsule` 标志与 CSS 媒体查询不一致（`initScreenShape` 回调尚未到达时），可能出现**样式冲突导致布局异常/无限重排**。

### 2.6 Defer 三帧机制的时序风险

```javascript
// 帧1: 50ms → quickAdd
// 帧2: 50ms+70ms=120ms → statusBar
// 帧3: 120ms+120ms=240ms → customContent + pinnedPages + updateStatus + startStatusTimer
```

- `customContent.init` 内部会再次读取 storage（`customContentList` + `homepage_settings`），可能再触发异步回调
- 如果 `customContentList` 有多条，`startRotation` 会启动 `setInterval` 轮播定时器
- 帧3 末尾的 `bootStageStamp(6)` 是在 `setTimeout` 的最内层执行，此时如果前面的异步 storage 读取还未完成，探针值不代表实际 UI 稳定

## 3. 看门狗复位根因推断（按概率排序）

### 3.1 ⭐⭐⭐⭐⭐ 主线程阻塞：storage IPC 堆积

首页启动链路中至少有 **12+ 次 storage 异步调用**（`getTheme`、`getHomepageSettings`、`getCurrentScheduleIndex`、`getAllCoursesStorage`、`holiday_data`、`customContentList`、`allCourses_dirty` 等），部分还形成链式依赖。

在手环 9 的轻量级 RTOS 上，每个 `storage.get/set` 都是跨进程 IPC（应用进程 → 数据管理服务），大量密集 IPC 会阻塞主线程的消息循环。

**当 IPC 队列在 3~5 秒内未处理完，看门狗（Watchdog）判定应用无响应 → 强制重启。**

### 3.2 ⭐⭐⭐⭐ 胶囊屏回填触发的额外重渲染

`initScreenShape()` 回调到达后：

1. 修改 `isCapsule` 标志
2. 重算字号（`applyFontSizes`）
3. 重新生成星期标题（`updateDayDisplay`）
4. 重新加载课程（`loadDayClasses`）
5. 调用 `scheduleRender` 触发整树重建

如果这个回调与 `onInit` 完成的首帧渲染在相近时间到达，**两轮全量渲染**叠加在 200ms 窗口内 → 布局引擎过载。

### 3.3 ⭐⭐⭐ 首次安装数据初始化

首次安装时：

- `database.init()` 需要执行 `migrateOldData()`（检查/执行 v1 → v2 迁移）
- 如果 `allCourses_0` 不存在，需要从 `schedule.js` 种子数据初始化
- 节假日预设数据（`holiday-preset`）需要首次补齐
- 所有默认设置（`defaults-engine`）需要写入

**首次安装的数据初始化操作在 1~2 秒内密集执行 storage set，占比显著高于后续启动。**

### 3.4 ⭐⭐ CSS 布局循环

胶囊屏 CSS 媒体查询 (`shape: pill-shaped`) 修改了 padding、元素尺寸、flex 属性。如果某次渲染触发了元素的尺寸变化，又反过来触发父级重排 → 可能出现**短时间内多次重排**，在低性能设备上导致 ANR。

### 3.5 ⭐ `require` 依赖树过深

首页 index.ux 的 `require` 依赖链：

```
index.ux
├── store.js → auth-store.js, app-defaults.js, defaults-engine.js
├── database.js → schedule.js
├── modules/quick-add.js
├── modules/day-nav.js
├── modules/status-bar.js
├── modules/custom-content.js
├── modules/pinned-pages.js
├── modules/bottom-buttons.js
├── modules/class-list.js → store.js, @system.prompt
└── modules/holiday.js → store.js, holiday-preset.js
```

在模块求值阶段（`bootStageStamp(0)` → `bootStageStamp(1)` 之间），所有依赖必须同步加载完成。低性能设备上这一步本身就可能接近 1 秒。

## 4. 探针系统使用指南

### 4.1 读取探针数据

在模拟器或真机上：

1. 进入「设置 → 工具 → 设备信息」
2. 查看 `index_boot_stage` 的值
3. 查看 `boot_probe_welcome` 的值（对照组）

### 4.2 探针解读

| 探针值 | 含义                          | 状态          |
| --- | --------------------------- | ----------- |
| 无记录 | 页面脚本压根没开始执行                 | 模块加载阶段就挂了   |
| 0   | 页面脚本开始执行                    | require 阶段  |
| 1   | 依赖加载完成 + device.getInfo 已发出 | 进入 onInit 前 |
| 2   | onInit 同步部分结束               | 异步请求已发出     |
| 3   | database.init 回调到达          | DB 已就绪      |
| 4   | 课程数据回调到达                    | 数据就绪，即将渲染   |
| 5   | initAllModules 完成           | 首帧渲染完成      |
| 6   | defer 三帧全部挂完（约 260ms）       | 所有模块就绪      |
| 7   | 首帧后 1.5s 仍存活                | 应用稳定运行      |
| 8   | 首帧后 5s 仍存活                  | 长期稳定        |
| 9   | 首帧后 15s 仍存活                 | 超长期稳定       |
| 10  | 自定义内容轮播已发生                  | 定时器正常运转     |

**缺少某个探针 → 死在该探针之前。**

### 4.3 对照组

如果 `boot_probe_welcome` 有值但 `index_boot_stage` 无记录：

- 说明 **storage 写入能落盘**
- 说明 **首页模块完全没开始执行**（模块加载阶段就挂了）

如果连 `boot_probe_welcome` 也无记录：

- storage 写入本身没落盘 → 探针方案不适用于该设备
- 需要换用其他取证通道（如日志文件）

## 5. 已实施的修复措施

### 5.1 渲染合并器（§6-R1）

[scheduleRender()](file:///Users/Banner/Documents/guomengtao/ev/class-schedule/src/pages/index/index.ux#L415-L423) 将同一事件循环内的多次 `$forceUpdate` 合并为一次。

### 5.2 Defer 三帧挂载

非关键模块（quickAdd / statusBar / customContent / pinnedPages）延迟到首帧之后分 3 帧挂载（50ms / 120ms / 240ms），避免叠加到首帧渲染上。


### 5.3 日志开关

所有模块的 `DEBUG` 默认设为 `false`，避免真机上日志字符串拼接 + IPC 传输造成主线程额外阻塞。

### 5.4 错误隔离

- `initScreenShape()` 整体 `try/catch` 隔离
- `applyFontSizes()` 调用处 `try/catch` 兜底
- 每个模块 `init` 都有独立的 `try/catch`
- `device.getInfo` 的 `fail` 回调提供兜底

### 5.5 8 秒加载超时

首页有 8 秒超时机制：超过 8 秒数据未返回 → 显示「数据加载失败」+「点击重试」按钮，避免永久停在骨架态。

## 6. 建议的进一步修复

### 6.1 减少首次启动的 storage IPC 调用次数

- **合并读取**：将 `getTheme` + `getHomepageSettings` + `getCurrentScheduleIndex` 等独立读取合并为一次批量读取（通过 `store` 层实现 `getAll` 方法）
- **优先使用同步缓存**：`store` 已有内存缓存（`_cache`），确保首次启动时预热缓存，减少重复 IPC

### 6.2 胶囊屏启动专用优化

- 在 `onInit` 入口处**同步读取一次** storage 中的 `screen_shape` 缓存值，避免完全依赖异步 `device.getInfo`
- 如果缓存中已是 `"capsule"`，立即设置 `isCapsuleScreen = true`，首帧就用正确的胶囊屏布局，避免回填重渲染

### 6.3 降低首帧 DOM 复杂度

- 首帧只渲染 header + 骨架屏，等数据就绪后再渲染课程列表
- 当前骨架屏已经在用（`isLoading` 时显示 skeleton），但骨架屏中的 `for` 循环（3 个 skeleton 卡片）本身也产生 DOM 节点

### 6.4 拆分 storage 依赖

- `holiday-preset.ensurePreset()` 中的首次补齐操作延迟到首帧之后
- `defaults-engine` 的首次落盘延迟到 `onShow` 或 `defer` 帧中

### 6.5 添加 storage 写入监控

在应用层增加一个 `last_storage_write_ts` 探针，记录每次 storage 写入的时间戳。如果某个探针之间出现了异常大的时间差（>2秒），说明 storage IPC 是瓶颈。
