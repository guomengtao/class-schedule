# 首页「进入即黑屏 → 一会儿后重启」深度分析

> 分析日期：2026-10-03
> 目标设备：**小米手环 9 = 跑道屏（`s=pill-shaped`）、192×490、平台 1200 / API 2**（真机激活 URL 实证，见 `docs/手环9跑道屏课程表管理页右侧黑板分析.md` §1）
> 现象（用户原话）：**"首页还是黑屏，并导致重启。进入黑屏一会儿，然后重启。"**
> 影响范围：**只有首页**；欢迎页 / 设置 / 编辑课程等页面正常
> 结论性质：**根因收敛 + 修复方案 + 取证方案**。文中每条结论都标了证据强度；标「假设」的项**必须先用第 8 章取证再动手改**
> 前序：`docs/第三轮反馈-卡顿重启与分帧方案.md`（已把"卡很久→重启"定性为看门狗复位）、`docs/模拟器故障修复经验总结.md`

---

## 0. TL;DR

| 项 | 结论 |
|---|---|
| 现象定性 | **看门狗复位（watchdog reset）**，不是 JS 抛异常秒退、不是某 API 瞬时崩 |
| "黑屏"的含义 | 首页**第一帧内容没画出来**；用户看到的其实是**深色骨架屏/未渲染**（默认主题 `#1a1a2e`，192px 上观感即黑） |
| "一会儿"的含义 | 首屏内容被 **4 级串行 IPC** 卡住 + 数据到达后**多次全树重渲染**，主线程被长时间占用 |
| 首页为什么最特殊 | 全项目**唯一**把首屏内容挂在「4 级串行 storage 回调」之后的页面；`$forceUpdate` 最多（18 处）、模块最多（8 个）、**唯一**在模块级调用 `device.getInfo` |
| 本次已修 | 首页首屏日志量（此前是该路径上唯一的日志密集页）→ commit `7a3df95` |
| 已排除 | capsule/pill 媒体查询、图标缺失、隐式宽度、holiday 预设批量写盘、`getBaseFontSizeSync` 抛错、debug 包、`device.getInfo` 失败、实验性 CSS、模板副作用、定时器过密 |
| 下一步（必做） | 上「**阶段标记**」取证（第 8 章）：把首页启动拆成 6 个阶段写 `storage`，复位重启后回读就知道卡在哪一步（storage 持久，复位不丢） |
| 修复方向 | 合并 `$forceUpdate` + 首屏不等串行 IPC + 内容分帧挂载，**全部零外观改动** |

## 1. 现象判读：为什么定性为"看门狗复位"

| 用户描述 | 技术含义 | 依据 |
|---|---|---|
| **"黑屏"** | 第一帧**完全没画出来**。注意首页根容器绑 `background-color: {{ theme.bg }}`，`theme` 默认 `#1a1a2e`（近黑深蓝）；骨架屏用 `theme.card #16213e` / `theme.borderLight #2a2a5a` —— **这三色在 192px 手环屏上几乎全是黑**。所以"黑屏"= "没渲染"或"只画了深色骨架" | `index.ux:2`、`index.ux:328-338`、`index.ux:83-91` |
| **"一会儿（才重启）"** | 主线程被**持续占用**一段时间后超时复位 —— 这是看门狗复位的典型特征，与"点一下立刻闪退"机制不同 | `docs/第三轮反馈-卡顿重启与分帧方案.md` §一 |
| **"其他页面没事"** | 不是全局性问题（manifest / feature / 包都正常），而是**首页这条路径的负载与时序比别的页高一个量级** | 第 2、5 章量化对比 |

> ⚠️ 必须区分的前提：若重启其实是"**点开首页几乎立刻退回表盘**"，那才是瞬时崩溃，第 4 章排序要重排。
> 用户措辞是"黑屏**一会儿**然后重启"，故本文按**看门狗方向**展开。

## 2. 首页为什么"最重"：量化对比

### 2.1 结构规模

| 指标 | 首页 `index.ux` |
|---|---|
| 文件行数 | **1645 行**（模板 165 + 脚本 590 + 样式 890），全项目最大页面 |
| 模板静态标签 | **98 个**（div 53 / text 35 / image 5 / scroll 2 / input 2 / block 1） |
| `for` 动态列表 | **4 处**（`skeletonCards` / `currentClasses` / `pinnedPages` / `quickAdd.courseNames`） |
| 图片 | 5 张 PNG（`iconTheme` 动态切目录；dark/light 双份均已核存在） |
| 加载模块 | **8 个**（`dayNav`/`holiday`/`classList`/`bottomButtons` + defer 的 `quickAdd`/`statusBar`/`customContent`/`pinnedPages`）→ `index.ux:248-274` |
| 常驻定时器 | **3 个** `setInterval`（进度 60s、状态栏 60s、自定义内容 ≥1s）→ `class-list.js:152`、`status-bar.js:87`、`custom-content.js:98,109` |

### 2.2 渲染调度规模

| 指标 | 数值 |
|---|---|
| `$forceUpdate`（**全树强制重渲染**）调用点 | **18 处** = `index.ux` 15 + `class-list.js` 1 + `day-nav.js` 2 |
| 其中落在"进首页"路径上的 | **约 5~7 次**（见 §3 链），每次都是整棵树重建 |
| 首屏内容的启动等待级数 | **4 级串行**（`database.init` → `migrateOldData` → `getAllCourses` → 渲染） |

### 2.3 storage / IPC 规模

文件内 `storage.get/set/delete` 调用点数：`store.js` **39**、`database.js` **31**、`custom-content.js` 4、`index.ux` 2、其余模块各 1~2。

**"进首页"这一次实际发生的 `storage.get` 约 15~18 次**（清单见 §3.2）。对比各页面页面级调用数：

| 页面 | 页面内 storage 调用 | 用户反馈 |
|---|---:|---|
| `welcome.ux` 欢迎页 | **0** | ✅ 正常 |
| `week-view.ux` | 4 | — |
| `settings.ux` | 7 | ✅ 正常 |
| `detail.ux` 编辑课程 | 10 | ✅ 正常 |
| **`index.ux` 首页** | 2（经 store/database 放大到 **15+**，含 **4 级串行**） | ❌ 黑屏 + 重启 |

> 关键不在"次数"，而在**其中 4 次是串行的、且卡在首屏内容前面**。
> `settings`/`detail` 虽然调用更多，但它们是**用户点进去的**（路由已热、首帧就是最终 UI、不等数据）。

### 2.4 唯一在「模块级」调用 `device.getInfo` 的页面

```225:244:src/pages/index/index.ux
device.getInfo({
  success: function(data) {
    var shape = data.screenShape || ""
    var capsule = (shape === "capsule" || shape === "pill-shaped")
    ...
```

全项目其它 11 处 `device.getInfo` 都写在 `onInit`/方法体里（缩进 4 空格）；**只有首页写在模块作用域**（`index.ux:225`，而 `export default` 在 `:282`）。模块级副作用在**页面模块首次求值时**执行，早于任何生命周期钩子 → 它属于"首帧之前"的执行路径，也让"模块级抛错 → 整页加载失败 → 黑屏"成为一条独立风险通道（本次**未证实**，第 6 章 R-5 顺手加固）。

## 3. 首帧依赖链全图（本问题的核心）

### 3.1 链

```
页面创建
│
├─【模块求值】require ×10（store.js / database.js / @system.device / 8 个 modules）
│    └─ device.getInfo(...)                      ← 模块级副作用（index.ux:225）
│
└─ onInit()                                      ← index.ux:341
     ├─ store.getTheme(cb)                       → storage.get("appTheme")         [IPC 1]
     │    └─ applyHomepageTemplate()
     │         └─ store.getHomepageTemplate(cb)  → storage.get(...)                [IPC 2]
     │              └─ $forceUpdate() ①                                           ← 全树重渲染
     ├─ loadHomepageSettings()
     │    └─ store.getHomepageSettings(cb)       → storage.get(homepage_settings)  [IPC 3]
     ├─ setTimeout(8s)   ← isLoading 降级兜底（index.ux:357）
     ├─ storage.get("allCourses_dirty")                                           [IPC 4]
     └─ database.init(cb)
          └─ ensureReady → initStorage
               ├─ loadScheduleIndex  → storage.get(currentScheduleIndex)          [IPC 5]
               └─ migrateOldData     → storage.get(migration_v2_done)             [IPC 6]
                    └─(仅首次) _doMigrate → storage.get("allCourses") [+可能 set]  [IPC 7]
          └─ getAllCourses(cb)
               └─ getAllCoursesStorageWithIndex → storage.get("allCourses_0")     [IPC 8]
                    └─ ✔ 回调到达后才：schedule=… / initAllModules() / isLoading=false
                       → $forceUpdate() ②                                       ← 全树重渲染
│
├─ onShow()   ← 首次会因 initialized=false 早退（index.ux:394）
│
└─ 数据到达后（resumeRefresh 链）
     └─ loadScheduleData(idx, true)
          ├─ store.getScheduleNames(cb)          → storage.get                   [IPC 9]
          │    └─ $forceUpdate() ③
          └─ database.getAllCoursesWithIndex(idx) → storage.get(allCourses_N)    [IPC 10]
               └─ refreshClasses()
                    └─ reloadHolidayState(dateStr, cb)
                         ├─ ensurePreset   → storage.get(holiday_preset_version)  [IPC 11]
                         └─ readHolidayState → storage.get(holiday_data)+parse    [IPC 12]
                    └─ $forceUpdate() ④（index.ux:624 或 class-list.js:116）
     另有：模块 init 的 storage.get（custom-content ×4、quick-add ×1、pinned ×1）、
           defer 模块在 50ms 后一次性 init
```

**要点**：用户看到的"黑屏"阶段 = 上面 `IPC 1~8` 这段。此期间 `isLoading === true`，页面只画**骨架屏**（深色、对比度极低）；`IPC 8` 回来那一刻 `isLoading` 才转 false，真正的课程列表才开始渲染 —— 而且是**同一帧里连带模块状态一起落地**。

## 5. 为什么"其他页面没事"——差别在哪

| 维度 | 欢迎页（正常） | 设置 / 编辑课程（正常） | **首页（黑屏+重启）** |
|---|---|---|---|
| 首帧是否等异步数据 | **不等** | 不等（首帧即终稿） | **等 4 级串行 IPC 才出内容** |
| 进入方式 | 冷启动入口 | 用户点进去（路由已热） | 冷启动 → `router.replace` 换页到首页 |
| 模块数 | 0 | 0~2 | **8** |
| 进页 `$forceUpdate` 次数 | 0 | 0~1 | **5~7** |
| 常驻定时器 | 无 | 0~1 | **3** |
| storage 调用 | **0** | 7 / 10 | 2（经 store/database 放大到 **15+**，含 4 级串行） |
| `for` 动态列表 | 0 | 0~2 | **4** |
| 模块级 `device.getInfo` | 无 | 无 | **有** |

**一句话**：别的页是"首帧即终稿"；首页是"首帧只是骨架，终稿要等 4 级串行 IPC，拿到后还要整树重渲染 5~7 次"。同一台机器上，只有首页会把主线程压到看门狗阈值。

## 6. 修复方案（按代价从小到大，**全部零外观改动**）

> 原则沿用 `docs/第三轮反馈-卡顿重启与分帧方案.md`：**只改"什么时候画"，不改"画成什么样"**。

### R-1 合并 `$forceUpdate`（代价最小，建议第一优先）

现状：进页路径上 5~7 次互不相关的 `$forceUpdate`（主题 / 模板 / 首页设置 / 课程数据 / 节假日状态各调一次），每次都重建整棵树。

做法：在 `index.ux` 加"渲染合并器"，把同一 tick 内的多次请求合并成一次：

```js
// 同一 tick 内的多次状态变更只触发一次整树重渲染
scheduleRender() {
  var self = this
  if (self._renderPending) return
  self._renderPending = true
  setTimeout(function() {
    self._renderPending = false
    try { self.$forceUpdate() } catch (e) {}
  }, 0)
}
```

把 `index.ux` 那 15 处 `$forceUpdate()` 换成 `scheduleRender()`；回调链上"紧接着又 forceUpdate"的几处自然合并。
**预期**：进页全树重渲染 **5~7 次 → 1~2 次**，收益/风险比最高的一刀。

### R-2 首屏不等串行 IPC（缩短"黑屏"时长）

现状：`isLoading` 直到 `IPC 8`（`allCourses_0`）回来才转 false。二选一：

- **B1（推荐，零外观）**：`onInit` 同步部分结束后立即置 `isLoading=false`，页面先按真实空态渲染，数据到达后再填充 —— 把"骨架→有课"改成"空态→有课"。
- **B2**：保留骨架屏但把 3 张卡降成 1 行提示 —— **属外观改动，需你点头**。

### R-3 模块再分帧（对齐输入法的分帧手法）

现状：4 个 defer 模块在 `setTimeout(50ms)` 里**一次性**全 init（`index.ux:628-641`）。
做法：拆成 2~3 帧（如 50 / 150 / 300ms），每帧 1~2 个模块；`custom-content` 的 4 次 storage 读取单独一帧。**零外观改动**（只改时机）。

### R-4 首屏内容分帧挂载（R-1~R-3 不够时再上）

按 `InputMethodStaged.ux` 的成功先例：给首页加 `bootStage`，用 `if="{{ bootStage >= N }}"` 分帧挂出「状态栏 / 自定义内容 / 钉首页 / 快速添加」等非核心块。**零外观改动**，但改动面较大。

### R-5 顺手加固（低风险，建议随 R-1 一起）

- `index.ux:225` 模块级 `device.getInfo` 包一层 `try/catch`（排除 R3，不改行为）。
- `applyFontSizes()`（内部调 `store.getBaseFontSizeSync()`）在 `database.init` 回调里是**裸调用**，包 try/catch —— 一旦这里抛错，`initialized` 永不置位，页面永久骨架态。

## 7. 与既有结论的关系

| 既有结论（`docs/第三轮反馈-卡顿重启与分帧方案.md`） | 本文对应 |

## 8. 取证方案（**下一步必做**）

真机上拿不到 IDE 日志：手环不走 adb。本次 `adb devices` 里的 `BTF4C17222009588` 经核实是**用户的手机 HONOR BLN-AL20 / Android 8.0**，不是手环。但有**复位也不会丢**的通道：

> **把首页启动拆成阶段，每到一个阶段就往 `@system.storage` 写一个标记。**
> 手环复位后 storage 仍在 → 下次进首页（或进设置页）把标记读出来，就知道**上一次卡在第几阶段**。
> 这就是输入法诊断用过的思路（`input_diag2_step` 残留值判读"A~E"，见引用文档 §一）。

### 8.1 埋点草案（6 个阶段）

| 阶段值 | 写入时机 | "卡在 N" 的判读 |
|---|---|---|
| `1` | 模块求值完成（`export default` 之前代码跑完） | 卡在 1 = 模块级（`device.getInfo` / require 链） |
| `2` | `onInit` 同步部分跑完（4 个异步请求已发出） | 卡在 2 = `store.getTheme` / `getHomepageSettings` 回调没回来 |
| `3` | `database.init` 回调到达 | 卡在 3 = 数据库初始化链（IPC 5~7） |
| `4` | `getAllCourses` 回调到达（**首次内容渲染前**） | 卡在 4 = `allCourses_0` 读取，或"收到后立刻全树渲染"这一步 |
| `5` | `loadScheduleData` + `refreshClasses` 完成（**终稿渲染后**） | 卡在 5 = 渲染完成后的模块 init / 定时器阶段 |
| `6` | 首帧后 1.5s 仍存活（健康基线） | 到 6 = 首屏渲染没问题，问题在其后的负载 |

回读位置：欢迎页/设置页加一行只读展示即可；也可复用既有 `client-event` 上抛通道（见 `docs/EV课程表主动发送测试消息到插件.md`）。

### 8.2 二分法（定位到 4/5 之后用）

阶段标记只能定位"哪一级"。若落在 4/5，还需知道**是哪一块渲染压垮的**：给首页加"分段开关"（`bootStage`），让用户 1→2→3 递进打开（每次只多挂一块），**第一个"打开就复位"的块就是元凶**。这套做法在输入法上已成功过一次（A~E 逐块单独渲染全通过 → 证明小块安全 → 拆帧即修复）。

### 12.4 第一轮探针结果与第二次修正（重要）

**真机回读结果：`无记录` —— 连阶段 1 都没跑到。**

阶段 1 的位置是「`initScreenShape()` 之后」，即**在 `require(store.js)` / `require(database.js)` 之后**。所以"无记录"有两种完全不同的解释，第一版探针分不出来：

| 解释 | 含义 | 修法方向 |
|---|---|---|
| **A. 页面脚本压根没开始执行** | 卡在更外层：`pages/index/index.jsc` 的加载/编译、或页面创建本身 | 查包完整性 / 体积 / 路由，与首页 JS 逻辑无关 |
| **B. 写进去了但复位前没落盘** | 看门狗硬复位丢掉了未 flush 的 kvdb 写入 | 探针方案作废，得换取证通道 |

**因此第二次修正做了两件事：**

1. **探针前移**：`bootStageStamp` 与文本表整体上移到**模块最前面（早于 store/database 的 `require`）**，并新增 **阶段 0 = "页面脚本开始执行（早于 require）"**。随后 `bootStageStamp(1)` 保留在依赖加载之后（1 的含义改为"依赖加载完成 + device.getInfo 已发出"）。
   → 于是：**有 0 无 1** = 死在依赖加载/求值；**连 0 都没有** = 页面脚本一行都没跑（解释 A）。
2. **加对照组**：在**能正常显示**的 `welcome.ux` 里写 `boot_probe_welcome`（模块求值时写一次 + `onInit` 再写一次，确保落盘），并在设备信息页一并显示。
   → 于是：**对照组有值 + `index_boot_stage` 为空 = 写入能落盘、首页脚本真的没跑**（解释 A 坐实）；**对照组也没值 = 写入不落盘**（解释 B 坐实，探针方案要换）。

**体积旁证**（本轮新量）：release 包里 `pages/index/index.jsc` = **95,933 B，是 37 个页面里最大的**，为其余页面均值的 **2.35 倍**（`chinese-input` 94,012 / `detail` 81,572 / 中位数 41,356）。但 `chinese-input` 同样大且可用，所以"体积大"**本身还不构成解释**，只是让解释 A（加载期问题）更值得优先验证。
