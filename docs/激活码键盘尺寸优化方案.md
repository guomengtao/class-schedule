# 激活码输入页：键盘尺寸优化方案

> 对象：`class-schedule/src/pages/activation/activation-code/activation-code.ux`
> 设备基准：Xiaomi Smart Band 9 / 192 × 490 px（header.css 注释内"192×490 实测"为准）
> 日期：2026-11-04

---

## 一、结论先行

**现有布局不是"已经极限",而是"错配"。** 键盘承担 18 次点击,却只拿到页面 33% 的垂直预算;顶部两行纯说明性文字拿走了 21%,还让页面总高溢出屏幕,用户很可能要边滚边点。

三个可量化的结论:

1. **垂直方向有约 240px 可回收**——占屏幕高度 49%。键盘高度可从 40px 提到 66~86px,**面积提升 1.7~2.7 倍**。
2. **水平方向确实到了物理极限**。192px 屏、3 列布局,单键宽度上限 = 192/3 = 64px ≈ **5.0mm**,无论怎么减 padding 都到不了 7mm 舒适线。想突破宽度,**只能改列数**。
3. **用户说的"顶部两行可以去掉"是对的,但不能直接删**——`source-hint` 承担防误输作用(用户手里是 4 位兑换码,页面要 18 位激活码),必须把作用迁移到状态条,而不是消失。

## 二、现状测量

### 2.1 物理换算基准

| 项 | 值 | 说明 |
|---|---|---|
| 对角线 | 1.62 英寸 | Band 9 AMOLED |
| 分辨率 | 192 × 490 px | CSS px = 物理 px |
| 折算比例 | **1px ≈ 0.0782mm** | 15.01mm / 192 |
| 屏幕物理尺寸 | **15.0 × 38.3 mm** | 这就是全部舞台 |

**参照线**:人体工学建议可点触控目标最小 **7mm**;苹果 HIG 44pt ≈ 7mm。当前按键远低于此。

### 2.2 当前垂直预算分配

`.page` padding: `38px 10px 8px 10px` → 内容可用宽 **172px**、可用高约 **444px**。

| 区块 | 计算 | 高度 | 占比 |
|---|---|---:|---:|
| header(返回 + "激活码"标题) | 44 + margin 10 | **54** | 12% |
| source-hint("18位·从网页获取…") | 28 × 2 行 + 6 | **62** | 14% |
| cells-grid(18 格,3 行 × 6) | 3 × (32+4) + 8 | **116** | 26% |
| status-strip(状态条) | 28 + 8 | **36** | 8% |
| keypad(4 行 × 3 列) | 4 × (40+3) + 8 | **180** | 41% |
| verify-btn(验证) | — | **44** | 10% |
| bottom-spacer | — | **8** | 2% |
| **合计** | | **500** | |

> 合计 500px > 可用 444px。**页面实际是溢出状态**,`scroll-y` 让它能滚,代价是键盘底部与验证按钮可能不在首屏。

**关键错配**:键盘占 41% 垂直空间,却承载 100% 的输入操作;顶部两行(header + source-hint)占 26%,承载 0 次点击。

### 2.3 当前按键实际尺寸

| 项 | 计算 | 值 | 物理 |
|---|---|---:|---:|
| 键盘行可用宽 | 172 | 172px | 13.4mm |
| 单键宽 | (172 − 3×2×2) / 3 | **53.3px** | **4.2mm** |
| 单键高 | — | **40px** | **3.1mm** |
| 单键面积 | 53.3 × 40 | **2133 px²** | 13.0 mm² |

**4.2 × 3.1mm,面积约为推荐值的 1/4。** 这解释了"能用但很难点"——不是手感问题,是命中率问题。震动反馈掩盖了失败成本,但每次点偏都要重来。

## 三、根因分析(三层)

### 3.1 第一层:垂直预算错配(可解)

四个非交互或低价值区块,合计 268px,占了 54%:

| 区块 | 高度 | 价值判断 |
|---|---:|---|
| header 标题行 | 54 | 用户已知自己在激活页,**标题冗余**;返回键必须保留 |
| source-hint | 62 | 防误输有效,但**不必常驻** |
| cells-grid | 116 | 18 位回显,但**不需要 3 行 6 格** |
| verify-btn | 44 | 输满 18 位即可自动验证,**独立按钮冗余** |

这四项都可压缩或迁移,不影响任何功能。

### 3.2 第二层:水平物理上限(不可解,只能换形态)

```
单键宽上限 = 屏宽 192 / 列数 3 = 64px = 5.0mm
```

即使把 padding 压到 0、margin 压到 0,**3 列的物理天花板是 5.0mm**,仍低于 7mm。这是硬约束,任何 padding 微调都突破不了。

要真正达标,只有两条路:

| 列数 | 单键宽上限 | 物理 | 是否达标 |
|---:|---:|---:|:---:|
| 3 列 | 64px | 5.0mm | ❌ |
| 2 列 | 96px | 7.5mm | ✅ |

**这是本方案最重要的一个判断**:继续在 3 列布局里抠像素,收益上限只有 +20%;换成 2 列,宽度直接 +47% 并越过舒适线。

补充一个常被忽略的适配论据:**手环戴在腕上,拇指的垂直行程远大于水平行程**。3 列要求左右横移,2 列只需要上下滑动——2 列不仅键更大,也更符合实际的操作轴。

### 3.3 第三层:输入模型本身(产品层)

18 位手输在任何 15mm 宽的屏上都是高成本操作。布局优化只能把单次点击从"难受"降到"可接受",不能改变"要按 18 次"的事实。

真正的结构性解法在交互层,见方案 C。

## 四、可回收空间清单(逐项量化)

| # | 改动 | 释放 | 风险 |
|---|---|---:|---|
| 1 | 删除 `source-hint`,文案并入状态条默认值 | **−62px** | 低(作用迁移,不丢失) |
| 2 | header 标题行删除,返回键改悬浮小圆钮 | **−44px** | 低(标题冗余;或改用边缘右滑手势直接归零) |
| 3 | 18 格 → 单行紧凑回显条(`•••• ••-••••`) | **−84px** | 中(可读性下降,需设计好光标位) |
| 4 | 取消独立"验证"按钮,输满自动验证 | **−44px** | 低(需处理误输满即验) |
| 5 | 状态条 28 → 26,keypad 行距 3 → 2 | **−8px** | 极低 |
| 6 | 页面 padding 10 → 6(仅左右) | 宽度 **+8px** | 低 |
| 7 | 键 margin 2 → 1 | 宽度 **+6px** | 低(过窄会误触相邻) |
| | **合计** | **−242px 高 / +14px 宽** | |

回收后键盘可用高度:**180 + 242 = 422px**(4 行)或 **394px**(含操作行 6 行)。

## 五、三个方案

### 方案 A|压缩式(不删功能,只挤)

保留现有结构,执行清单 #1、#5、#6、#7,以及 cells 行高 32 → 26。

| 项 | 现状 | 改后 | 变化 |
|---|---:|---:|---:|
| 键盘行高 | 40px | **68px** | +70% |
| 键宽 | 53.3px | **57px** | +7% |
| 单键物理 | 4.2×3.1mm | **4.5×5.3mm** | 面积 **×1.72** |
| 页面总高 | 500px | **443px** | 不再溢出 |

- **优点**:改动小、可当天上线、全部功能保留、页面不再需滚动。
- **缺点**:宽度仍只有 4.5mm,用户"宽度太小"的感受**不会消失**。
- **适用**:想先止血、不想冒重构风险。

```css
.source-hint { display: none; }              /* 文案迁入 status 默认值 */
.cell { height: 26px; }                      /* 行高压缩 */
.cells-row { margin-bottom: 3px; }
.status-strip { margin-bottom: 6px; }
.keypad-row { margin-bottom: 2px; }
.keypad-btn { margin: 0 1px; }
.page { padding: 38px 6px 8px 6px; }
```

### 方案 B|重构式(推荐)

执行清单 #1~#7 全部,键盘改 **2 列 × 5 行(0-9)+ 1 行操作栏**。

布局骨架:

```
[悬浮返回 ●]                        ← 12px 视觉区,不占布局流
•••• ••-•••• ••••                   ← 32px 单行回显,当前位高亮
┌──────── status 26px ────────┐    ← 错误提示,固定高度不跳动
├───────────┬─────────────────┤
│     0     │      1          │    ← 每行 66px
├───────────┼─────────────────┤
│     2     │      3          │
├───────────┼─────────────────┤
│     4     │      5          │
├───────────┼─────────────────┤
│     6     │      7          │
├───────────┼─────────────────┤
│     8     │      9          │
├─────┬─────┴─────┬───────────┤
│  C  │     ←      │   验证     │   ← 操作栏 50px
└─────┴───────────┴───────────┘
```

| 项 | 现状 | 方案 B | 变化 |
|---|---:|---:|---:|
| 单键宽 | 53.3px | **88px** | +65% |
| 单键高 | 40px | **66px** | +65% |
| 单键物理 | 4.2×3.1mm | **6.9×5.2mm** | 面积 **×2.75** |
| 最小边 | 3.1mm | **5.2mm** | +68% |
| 点击次数 | 18 + 1 | **18**(自动验证) | −1 |

```css
/* 左右 padding 收到 6,两列 */
.page { padding: 8px 6px 8px 6px; }
.keypad-btn { margin: 0 1px; }               /* 键宽 (180-2)/2 = 89px */
.keypad-row { margin-bottom: 2px; }

/* 单行回显条替代 18 格 */
.code-line {
  height: 32px; font-size: 26px; line-height: 32px;
  letter-spacing: 2px; text-align: center;
}
```

**为什么 2 列优于 3 列**(同为方案 B 预算,两种排法的实测对比):

| 排法 | 键宽 | 键高 | 最小边 | 最小边是否达标 |
|---|---:|---:|---:|:---:|
| 3 列 × 4 行 | 57px / 4.5mm | 95px / 7.4mm | **4.5mm** | ❌ |
| **2 列 × 5 行** | **88px / 6.9mm** | **66px / 5.2mm** | **5.2mm** | 接近 |

3 列方案的键虽然很高,但宽度卡在 4.5mm——**用户抱怨的正是这个维度**。2 列把短板补到了 5.2mm,且单手拇指上下滑动的命中率高于横移。

**代价与缓解**:
- 数字排列不再是熟悉的 3×4 网格 → 缓解:固定左右两列单调递增(左 0-4,右 5-9),形成肌肉记忆;或首屏加一层浅色分隔线。
- 单行回显可读性弱于 18 格 → 缓解:分段显示(`6 位 + 6 位 + 6 位`,段间留 8px),当前编辑位高亮色块;点击回显条可进入"逐位修改"态。

### 方案 C|交互降级(治本,但不在这一版)

布局优化的天花板是"按 18 次但按得舒服"。要真正降低痛苦,只有减少点击次数。按性价比排序:

| 思路 | 效果 | 成本 | 建议 |
|---|---|---|---|
| **主路径改扫码/同步**(path-a-sync 扶正) | 0 次手输 | 中 | **最优先**,已有页面 |
| 输满自动验证 | −1 次点击 | 极低 | 并入方案 B |
| 边缘右滑返回 | 省出 12px + 空间 | 低 | 建议 |
| 码长从 18 缩到 12 | −6 次点击/−33% | 高(需换码窗口) | 与冻结区 `DEVICE_CHARSET` 待办合并考虑 |
| 逐位滚轮选择 | 更慢 | 中 | ❌ 不推荐 |

**核心判断**:18 位码的合理定位是"补救通道",不是"默认通道"。方案 B 让它变得可接受;方案 C 让它变得罕见。两者不冲突,但顺序应是 **B 先上(一周内),C 随后(下个版本)**。

## 六、推荐路线

**立即执行方案 B**,理由:

1. 方案 A 收益上限只到 4.5mm 宽,用户已明确反馈"太小"——**宽度不变等于没解决**。
2. 方案 B 面积提升 2.75 倍,最小边从 3.1mm 到 5.2mm,**是第一个能让用户明显感知到差异的量级**。
3. 全部改动集中在单文件 CSS + 模板结构,无业务逻辑变更,无加解密封动区风险。

分期:

| 期 | 内容 | 验收 |
|---|---|---|
| P0 | 方案 B 布局改造 | 真机截图量按键实际像素;单键 ≥ 88×66px |
| P1 | 输满自动验证 + 边缘右滑返回 | 18 位输完无需额外点击 |
| P2 | path-a-sync 扶正为主入口 | 手输入口点击率下降 |

## 七、风险与验证

### 7.1 技术风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| Vela 不支持 `box-sizing: border-box` | padding 变更会连带压缩内部可用宽 | 改完全量复算一遍,不靠估算 |
| `flex: 1` 在 2 列下的分配 | 需确认 space-between 与 margin 叠加结果 | 真机截图逐像素量 |
| 回显条替代 18 格影响可读 | 用户可能失去"哪一位错了"的定位感 | 保留点击回显条进入逐位修改 |
| 自动验证误触发 | 输满即验,若末位输错直接报错 | 保留 200ms 防抖 + 允许退格后重验 |

### 7.2 验证方法(必须真机)

1. `aiot build` 后装 Band 9,尺子量或截图量单键像素。
2. 连续输 5 次 18 位码,记录误触次数(当前基线需先测)。
3. 检查页面是否还需滚动(方案 B 目标:首屏完整显示键盘 + 回显条)。

### 7.3 真机验证结论(2026-11-05,已推翻 CSS 估算)

用 `vela up xiaomi_band --rpk …1.9.128.rpk`(192×490)在真机上走完整路径截图,两张图已归档:

- `screenshots/激活码键盘-v1现版-真机-20261105.png`(现版)
- `screenshots/激活码键盘-v2对比-真机-20261105.png`(v2 对比版)

**结论一:现版首屏确实溢出,验证按钮在屏外。**

真机截图里屏幕最后一排是 `C 0 ←`,**再往下就没有内容了**,`验证` 按钮完全不在首屏。这印证了 §2.2 的「合计 500px > 可用 444px」,也印证了用户的体感:不是键太小这一个问题,还有「得边滚边点」。

**此前有一版按 CSS 声明累加得出「v1=484px、余量 6px、首屏完整」的结论,是错的** —— 累加漏算了 flex 收缩与 line-height 的实际渲染。教训:这个页面不能靠 CSS 数值推算高度,**必须真机截图复核**。

**结论二:v2 底部操作栏同样被屏底裁切,需要再收 ~8px。**

v2 真机截图里 `验证` 只露出上半截,左侧 `C` 也贴边。按本次实测可用收紧点(任选其一):

| 收紧项 | 省 | 影响 |
|---|---:|---|
| 键盘行间距 2px → 1px | 4px | 几乎无感 |
| 18 格行高 24px → 22px | 4px | 回显略紧 |
| 状态条 28px → 24px | 4px | 提示空间变小 |

建议先做第 1 条 + 第 3 条(共 8px),不动回显可读性。

**结论三:18 格回显在 v2 里仍然折成 2 行,没有按设计压成单行。**

v2 设计意图是单行回显省 60px,真机上是 2 行。这一项没实现,直接导致底部溢出。要么把回显做成真正的单行(18 格 × 约 9px 宽不可行,需改成「前 6 位 + 省略 + 后 6 位」),要么接受 2 行并把省下的空间从别处找。

> 已不再使用 CSS 累加值作为定稿依据。所有高度以真机截图为准。

## 八、明确不做

| 想法 | 为什么不做 |
|---|---|
| 继续在 3 列里抠 padding | 上限 5.0mm,收益 <20%,不值得一次发版 |
| 用位图/自定义字体放大数字 | 数字本身不是矛盾,按键命中区才是 |
| 键盘改滚动容器 | 滚动本身就会造成误触 |
| 加"确认"二次弹窗 | 增加点击次数,方向相反 |
| 缩小字号换空间 | 24px 是手环可读下限,不可让 |

---

## 九、一句话总结

顶部两行能删(约 116px),但**删完还不够**——真正的瓶颈是 3 列布局把键宽锁死在 5.0mm。把垂直省下的 242px 全部投给键盘,并把列数降到 2,才能把单键从 4.2×3.1mm 做到 **6.9×5.2mm**,面积翻近三倍。这是这个页面在 15mm 宽的屏上,能做到的最好结果。
