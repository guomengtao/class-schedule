# BUG：激活成功后提示界面错误（显示"需要4位数"小字，实际已激活）

| 项 | 内容 |
|---|---|
| 发现时间 | 2026-11-04 |
| 发现人 | 用户（真机操作） |
| 影响产品 | EV 课程表（class-schedule） |
| 影响版本 | 1.9.126 (vc1590) 及之前若干版本 |
| 严重级别 | P1 — 功能已成功但界面提示相反，用户会误判为失败并重复输入 |
| 状态 | 待修复（已定位到代码） |

## 一、现象（用户原话）

> 激活的时候，激活成功，提示界面不对，我看到的是**一行小字，说需要4位数之类的**，但是返回看，是激活了的。

关键点：**功能结果正确（已激活、有效期已生效），只有提示界面错误。** 用户当时以为没成功。

## 二、定位结论

问题页面：`src/pages/activation/activation-code/activation-code.ux`

该页成功态由数据项 `verifySuccess` 控制（第 218 行初始 `false`，第 456–459 行 `succeed()` 置 `true`）。成功时隐藏了四块、显示了一块：

| 区域 | 行号 | 成功态 |
|---|---|---|
| `cells-grid`（18 格输入位） | 17 | 隐藏 ✅ |
| `status-strip`（内联状态条，显示"共需18位/已输N位"） | 81 | 隐藏 ✅ |
| `keypad`（数字键盘） | 85 | 隐藏 ✅ |
| `verify-btn`（验证按钮） | 132 | 隐藏 ✅ |
| `done-box`（"已激活"结果块） | 137 | 显示 ✅ |
| **`header`（返回键 + 标题"激活码"）** | 4–11 | **未处理** ⚠️ |
| **`source-hint`（顶部提示小字）** | 14 | **未处理** ⚠️ |

第 14 行的原文是：

```html
<text class="source-hint" style="color: {{ theme.textMuted }}">18位 · 从网页获取，不是4位兑换码</text>
```

**这行字里就含"4位兑换码"，且是全页唯一在成功态仍然显示的小号提示文字（20px，`#555566` 弱化色）。用户描述的"一行小字，说需要4位数之类的"，与它高度吻合。**

## 三、根因（按可能性排序）

### H1 · 成功态漏掉顶部提示行（最可能）

`source-hint` 是给**输入阶段**做防误输的（提醒用户手里是 4 位兑换码，这里要 18 位），但它没有跟随 `verifySuccess` 隐藏。成功页上，输入区、键盘、验证按钮全部退场，唯独这行小字留在最上面，于是"激活成功"的观感变成了"还在提示我要 4 位数"。

### H2 · 滚动位置残留，结果块被推到视口外

页面整体是可滚动容器（第 3 行 `<scroll class="page-scroll" scroll-y="{{true}}">`）。用户输满 18 位时通常已经下滑到"验证"按钮位置；成功后内容高度骤减（键盘、输入格、18 个格子全部隐藏），**但滚动偏移量没有复位**。结果 `done-box` 落在视口之外，用户看到的是残页顶部——也就是那行 `source-hint` 小字。

叠加因素：`.done-box` 用的是固定 `margin-top: 100px`（约第 718 行），不是垂直居中。在 192×490（手环 9）和 336×480（10 Pro）这类矮屏上，100px 的固定偏移占比过大，把"已激活"44px 大字直接顶到了第二屏。

### H3 · 失败态文案残余

`showError()`（第 448–453 行）会把 `hintText` 改成红色短句（如"还差3位""激活码无效"）。成功后 `status-strip` 被隐藏，但 `hintText` 的残余值没有被清理。只要有任何路径让该条重新显示（页面重入、状态未重置、热重载），就会把失败文案带进成功页。

> 说明：H1、H2 都有代码依据；H3 是防御性推断，未观察到实际触发。三者可同时成立，修复时应一并处理。

## 四、修复建议

按行改动，成本很低：

1. **顶部提示跟随隐藏**（治 H1）
   ```html
   <text class="source-hint"
         style="color: {{ theme.textMuted }}; display: {{ verifySuccess ? 'none' : 'flex' }}">
   ```

2. **成功时复位滚动**（治 H2）
   在 `succeed()`（第 456 行）里加 `this.scrollTop = 0`，并给 `<scroll>` 加 `scroll-top="{{ scrollTop }}"` 绑定；或在成功态把 `page-scroll` 换成不可滚动的居中容器。

3. **结果块改垂直居中**（治 H2 的小屏问题）
   `.done-box` 的 `margin-top: 100px` 改为在成功态下用 `flex: 1` + `justify-content: center`，让"已激活 / 有效期 / 完成"三行在任何屏高下都落在首屏中央。

4. **清空残余提示**（治 H3）
   `succeed()` 里补 `this.hintText = '共需18位'`、`this.hintColor = this.theme.textSecondary`。

5. **可选·结构解耦**：把成功态做成独立页面或独立层（与 `scroll` 平级、`position: fixed`），从根本上避免"矮屏 + 残留滚动 + 未隐藏元素"三者叠加。这条改动大一些，前 4 条已能解决用户可见问题。

## 五、验收标准

- 输入正确 18 位码 → **首屏直接看到**「已激活」44px 大字、有效期（如"有效期365天"）、「完成」按钮，**无需滚动**。
- 成功页任何位置**不得出现含"4位"字样的文字**。
- 不留任何红色失败文案。
- 失败路径不受影响：位数不足仍显示"还差N位"、激活码无效仍显示"激活码无效"，位置与样式不变。
- 双分辨率各验证一次：`192×490`（手环 9 标准版）、`336×480`（手环 10 Pro）。

## 六、影响面

- 仅 `class-schedule`。已确认 `ev-face` 无 activation 页面目录，不受影响。
- 课程表内嵌的表盘页（`watch-face-*`）是表盘渲染页，与激活流程无关。
- 后端与激活码校验链路正常——**本次纯前端提示层缺陷，不要动 `auth-store.js` / `markActivated()`**。

## 七、备注

该页此前已做过一轮提示优化（第 506 行注释：`不再报「请输入完整的18位激活码」（11 字，两行且浮层遮挡），只报还差几位`），说明失败态文案已经被收敛过。**这次是成功态漏改**——失败态改好了，成功态没跟着一起过一遍。建议修完后把"成功 / 失败 / 输入中"三种状态放在一起对照检查一次，避免下次再漏第三种状态。

# 【P0】补充：激活码「设备不匹配」——大小写不一致导致同一台设备被判定为他人设备

| 项 | 内容 |
|---|---|
| 发现时间 | 2026-11-04（与上文同一轮） |
| 严重级别 | **P0 — 用户无法激活，且提示"设备不匹配"会让用户以为自己拿错了码** |
| 受影响用户 | 设备号末 4 位含字母（a–f）的用户 |
| 状态 | 已定位，根因确证（有数学验算） |

## 八、现象

某用户持激活码 `003220910257139192`，设备号 `uuid-382d5d14f520c409eb56508ca0136e44`（末 4 位 `6e44`），连续多次激活均提示 **「设备不匹配」**。用户确认界面上显示的设备号自始至终没有变化。

## 九、把这张码拆开看

激活码是 18 位数字，按 `src/lib/crypto.js` 的规则可完整还原出四个字段（productIdIndex / months / redeemCode / deviceId）：

```
combined = 3220910257139192
deviceNum = combined mod 14776336      = 13841928  →  "6E44"
months    = (…/14776336) mod 100       = 99
redeemNum = (…/100) mod 1679616        = 500159
productId = 其余                        = 1
```

**这张码绑定的设备尾 4 位是 `6E44`（大写 E），而用户设备的尾 4 位是 `6e44`（小写 e）。**

同一个字符串在 `DEVICE_CHARSET` 下会编成两个完全不同的数：

| 输入 | 编码值 | 说明 |
|---|---|---|
| `6E44` | 13841928 | 码里实际绑定的 |
| `6e44` | 13941872 | 用户设备真实的 |

## 十、根因（两个缺陷叠加）

### 缺陷 A：`DEVICE_CHARSET` 大小写敏感

```js
// crypto.js:116
const DEVICE_CHARSET = "ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz0123456789";
```

`A` 与 `a` 是 charset 里两个不同的字符（索引 0 与 26）。因此 `6E44` 和 `6e44` 是两个不同的设备身份，**同一个设备的两种写法无法互通**。

### 缺陷 B：两处校验口径不一致

| 位置 | 写法 | 结果 |
|---|---|---|
| `app.ux:521` | `String(decrypted.deviceId).toUpperCase() !== last4.toUpperCase()` | 大小写不敏感 ✅ |
| `activation-code.ux:554` | `if (decrypted.deviceId !== deviceIdLast4)` | **严格比较** ❌ |

`app.ux` 那行是有人踩过同一个坑之后打的补丁，**新写的激活页没有继承这个补丁**。于是同一条激活链路，走 `app.ux` 能过，走 `activation-code.ux` 就报"设备不匹配"。

### 缺陷 C（放大器）：设备号永远是小写

```js
// utils/device-uuid.js:5
var chars = '0123456789abcdef'      // 只生成小写
```

设备端生成的 UUID 全部是小写十六进制，`isLocalUUID` 的校验正则也写死了 `[0-9a-f]`。所以**设备这一侧永远送小写，而码里可能绑着大写**——只要生成端做过一次大写归一化，这台设备就永久激活不了。

这也是为什么中招的是"末 4 位含字母"的用户：纯数字尾号（如 `3921`）大小写没区别，字母尾号（如 `6e44`）才有这个陷阱。

## 十一、修复

### 必要修复（一行，成本极低）

`activation-code.ux:554` 与 `app.ux:521` 对齐：

```js
if (String(decrypted.deviceId).toUpperCase() !== String(deviceIdLast4).toUpperCase()) {
```

### 建议同时做的三件事

1. **编码入口归一化**：`deviceIdToNumber()` 里先 `deviceId = deviceId.toUpperCase()` 再 `indexOf`，让同一个设备只有一个合法编码值，从源头消灭双解。
2. **生成端统一转大写**（或统一转小写），并在 `CRYPTO_SPEC` 里写明"设备尾号大小写不敏感"。
3. **换字符集**：base62 大小写混排本身就容易出错，且 `0/O`、`1/l/I` 肉眼难分。下一版建议改 32 字符集（去 0/1/I/O），顺带把 4 位容量从 1477 万降到 104 万——按当前用户量仍绰绰有余。

### 应急（不改代码，先救这个用户）

同一张码，仅把设备尾号按小写重新编码，其余字段（产品 1 / 99 个月 / 兑换码 500159）完全不变：

```
原码：003220910257139192   → 绑定 6E44（大写，设备永远匹配不上）
新码：003220910257239136   → 绑定 6e44（小写，与设备一致）
```

新码已反解校验通过（product=1 / months=99 / redeem=500159 / device=6e44），可直接发给该用户，**不消耗额外兑换码额度**。

## 十二、验收标准

- 用 `6E44` 编码的旧码 `003220910257139192` 在设备 `…6e44` 上激活**成功**（证明大小写归一化生效）。
- 用新码 `003220910257239136` 同样成功。
- 用尾号纯数字的码回归一次，确保没有影响正常路径。
- `app.ux` 与 `activation-code.ux` 两处校验逻辑一致，建议抽成公共函数 `isSameDevice(codeDeviceId, localDeviceId)`，避免第三处再写一遍。

## 十三、排查提示（写给以后的人）

- 界面上显示的设备号是**末 6 位**（`raw.slice(-6)`），而绑定与校验只用**末 4 位**。看到"ID 没变"不代表编码一致——先确认大小写。
- 遇到"设备不匹配"，第一步不是怀疑用户拿错码，而是**把码拆开算一遍它绑的是哪 4 位**，与设备真实尾 4 位逐字符比对（含大小写）。
- 若两者仅大小写不同 → 本文缺陷；若字符完全不同 → 才是真的绑错设备（用户买错 / 多设备场景）。
