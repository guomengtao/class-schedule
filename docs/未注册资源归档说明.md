# 未注册资源归档说明

> 建立于 2026-09-25。用于说明「排查/测试期间引入的临时页面与组件」如何在**不占包体**的前提下**保留源码**。

## 一、三种处置方式对比

| 方式 | 占包体 | 恢复成本 | 风险 |
|---|:---:|---|---|
| 直接删除 | 不占 | 需 `git show <旧提交>:<路径>` 从历史挖回 | 易忘、路径/版本难找 |
| **归档（本方案）** | **不占** | **加回 manifest 注册即可** | 极低 |
| 留在包里不注册 | **占** | 零 | 白占包体 |

结论：**归档 = 文件保留在源码树 + 从 `manifest.json` 移除注册 + 移除调用入口**。

## 二、实测验证：不注册就不会被打包（关键前提）

本方案的成立前提是「aiot 打包基于**依赖图**，而非扫描 `src/` 全目录」。2026-09-25 做了对照实测：

| 步骤 | 包体（字节） |
|---|---|
| 删除三个文件后构建 | 828,677 |
| **恢复三个文件、manifest 仍不注册** | **828,684** |
| 差值 | **7 字节（即版本号 122→123 的字节差）** |

→ **恢复文件后包体零增长**，证明未注册页面与未被引用组件不进包。方案成立 ✅

## 四、如何启用（恢复使用）

1. **恢复页面注册**：在 `src/manifest.json` 的 `router.pages` 中加回：

```json
      "pages/input-crash-diag2": {
        "component": "input-crash-diag2",
        "group": "实验室工具",
        "name_cn": "输入法诊断2·元素级"
      },
```

2. **恢复分组**：`router._groups` 的 `"实验室工具"` 值末尾加 `, input-crash-diag2`

3. **恢复入口**（可选）：在 `src/pages/tools/tools.ux` 加回按钮与方法

```html
      <div class="item-row" onclick="openInputCrashDiag2">
        <text class="item-label" style="color: {{ theme.accent }}">输入法诊断2·元素级</text>
        <text class="item-hint" style="color: {{ theme.textMuted }}">A→F 定位</text>
      </div>
      <div class="row-divider" style="background-color: {{ theme.border }}"></div>
```

```javascript
  openInputCrashDiag2() {
    router.push({ uri: "/pages/input-crash-diag2" })
  },
```

4. 重新构建即可生效。

> 仅第 1、2 步即可让页面可被 `router.push` 访问；第 3 步只是提供可视化入口。

## 五、注意事项：版本号递增的**真实机制**（2026-09-25 修正版）⚠️

> **重要修正**：本节初版曾写"`npx aiot release` 会自动 +1"，**该结论有误**。经查 `package.json` 与 `scripts/bump-version.js`，真实机制如下。

版本号由**项目自己的脚本** `scripts/bump-version.js` 递增（`patch + 1`、`versionCode + 1`，并**同时写回** `src/manifest.json` 与 `src/data/version.js`），而该脚本**只通过 npm lifecycle 钩子被触发**：

| 命令 | 是否递增版本号 | 原因 |
|---|:---:|---|
| `npm run release` | ✅ 会 | 触发 `prerelease` 钩子 |
| `npm run build` | ✅ 会 | 触发 `prebuild` 钩子 |
| `npm run bump` | ✅ 会 | 显式调用 |
| **`npx aiot release`** | ❌ **不会** | **绕过 npm 钩子，直接调用 CLI** |
| `npm run build:dev`（`aiot build`） | ❌ 不会 | 无对应钩子 |

**实践含义**：用 AIoT-IDE 或 `npm run build` / `npm run release` 构建时，版本号会自动 +1；而直接调 CLI 不会。这就是**同名仓库出现多个不同版本号**的根源。

**由此推出两条重要判断规则**：

1. **"仓库版本号" ≠ "用户设备版本号"**。只要用 IDE / npm 脚本构建过，版本号就会前进；很容易出现"仓库已到 1.6.103、用户装的还是 1.6.100"的情况。
2. **判断"用户测的是不是刚改的包"，必须以下发的 `r` 参数为准**（`r` = 包内 `versionName`，见 `src/pages/activation/activation.ux` 的 `fetchDeviceInfo()`），不能假设仓库版本已上机。

> 这也解释了此前的一次误判：修复提交后仓库版本已 bump，但用户设备回传 `r=1.6.100`（修复前），说明新包**根本没装上**，"改了不起作用"是必然的。

**建议**：给用户发包前，先记录本次构建产生的版本号，并把该号码明确告知用户；用户回传的 `r` 与该号码不一致时，先解决装机问题，不要急着改代码。
