
运行前提：**模拟器已由你自己手动启动**（§3.8e：AI 一律禁止自行起模拟器），脚本只连现成实例。

### 关键参数

| 参数 | 作用 |
|------|------|
| `--page <目录名>` | 目标页（`src/pages/<page>/<page>.ux`），必填 |
| `--build` | 先跑 `aiot release --enable-jsc`（约 14s）；不带则只重推+验收 |
| `--entry` | 临时把设备 manifest 的 `router.entry` 指向该页，**省掉点击导航**；结束自动还原（异常也还原） |
| `--scroll N` | `drag` 次数（默认 4），滚动到底自动停止 |
| `--retry N` | 冷启没出画时的自动重试（默认 2）—— 冷启偶发全黑是常态，脚本自己重来 |
| `--tap x,y` | 截图循环结束后再点一次并补拍（可重复），一轮冷启里顺手验弹层 |
| `--serial / --port` | 默认自动探测（adb devices 首个 `emulator-*`）；模拟器重启后端口常变（13000→13002），写死必打空 |

产出：`/tmp/vela-loop/<page>-long.png`（纵向拼接整页长图）+ 各阶段耗时。

## 2. 为什么「软方式」这么重要（对比手工链路）

| 指标 | 手工链路（§13.6） | `vela-loop.py` |
|------|------------------|----------------|
| 一轮墙钟（含模型↔工具往返） | 8–20 分钟 | **约 1 分钟**（1 次调用 + 1 次读图） |
| 一轮机器时间 | 40–60s / 单屏 | 22–31s / **整页 7 屏** |
| 遗漏风险 | drag 失效时静默漏屏 | 位移检测 + 重试 + 黑帧拦截 |
| 版本误判风险 | 可能截到 `am stop` 旧帧 | baseline 比对，杜绝 |

> 手工链路贵的不是模拟器（打包 14s + 冷启 32s + 截图 3s），而是每一小步都一次
> 模型↔工具的往返：7 次 drag + 7 张截图 + 7 次读图 = 20 来次往返 = 十几分钟墙钟。
> 「软方式」把整条链塞进一个进程，一轮就只剩 **1 次调用 + 1 次读图**。

## 4. 必学硬知识点（踩过的坑）

- **端口三位一体**：`-port 13000` 同时决定 serial 名 `emulator-13000`、console 口 `13000`、adb 监听 `13001`。tap 传 13000，adb 传 `-s emulator-13000`，串了命令"成功但无反应"。
- **冷启 32s，黑屏别急着判死刑**：先 `ps | grep vapp` 确认进程活着；`--build` 后首次冷启全黑 → **原样重跑一次**，别立刻怀疑代码。
- **`am stop` 与 `vapp` 必须留 ≥5s**，否则命令秒回但画面全黑。
- **`nz=0` 全黑会被误判成「画面已稳定」**：判据必须加 `nz >= 3000`，否则验收工具把黑屏当结果，后面全错。
- **应用前台只活约 27 秒**：脚本每帧 `nz < 3000` 判黑，命中即停（不拼黑帧）→ 单轮最多覆盖 4–7 屏，长页分两轮。
- **改 entry 直达可验排版**（§13.4 修正结论）：曾误判"entry 必垮"，真相是页面自己的 `padding: 60px 80px` 的锅，与 entry 无关。但它**没有返回栈**，`router.back()` 无效，验完必须把 manifest 的 entry 还原为 `pages/welcome`。
- **单页 `.jsc` 推送的边界**：`app.jsc`/`common/` 若变化必须连主包一起推，否则新分包配旧主包必崩。
- **长图拼接三坑**：滚动要「位移检测 + 重试」防静默漏屏；固定 header 先测 `hfix`（实测 98 行）再算重叠；单帧 `bs=188160 count=1` 省一半读取时间。
