# 独立「课程表盘」的能力边界分析

> 承接 `docs/表盘开发可行性分析（讨论稿）.md` 与 `docs/表盘联动性与仓库结构深度分析.md`。
> 本轮要回答的是：既然表盘与快应用互相独立，**能不能干脆单独做一个"课程表盘"？它算不算新作品？它到底能做什么、不能做什么？**
>
> 一句话预告：**"独立"成立，"能存能改"不成立**——表盘引擎的数据源是**封闭的**，没有"课程"这一项。

---

## 零、结论速览

| 问题 | 结论 |
|---|---|
| 能否单独做一个课程表盘？ | **能**（用米坛表盘自定义工具做 `.bin`），且完全独立。 |
| 算不算新作品？是否彻底独立？ | **算**，且**彻底独立**：独立仓库、独立分发、独立数据、独立编辑流程。但与 Ev课程表**只有名字相似**，不共享任何代码与数据。 |
| 表盘能存储课程吗？ | **不能**。表盘的动态数据源是**封闭的（时间/健康/设备/环境四类）**，没有"自定义业务数据"入口，也没有运行时业务存储。 |
| 表盘能输入课程吗？ | **不能**。表盘引擎不提供输入组件、没有输入法。你的观察是对的。 |
| 那么"能改课程的课程表"是什么？ | **是快应用（`.rpk`）**。社区里那个"课程表小程序"，附件实为 `com.givemefive.schedule...rpk`。 |
| 显示界面有没有强要求？ | **有，且很受限**：受"底包结构 + 引擎支持组件 + 屏幕尺寸"三重限制，并**按机型分别适配**。 |

---

## 一、决定性证据：表盘的动态数据源是「封闭列表」

开源表盘制作工具 **Mi-Create** 的数据源配置文件 `src/data/sources.json`，公开列出的**全部**动态数据源是：

| 类别 | 可绑定数据 |
|---|---|
| 时间日期 | 小时、分钟、秒、星期、日期、月份 |
| 健康数据 | 步数、心率、卡路里 |
| 设备状态 | 电池电量、连接状态、通知提醒 |
| 环境信息 | 温度、天气状况 |

**这份清单里没有"课程"，也没有任何"第三方可注入的自定义字段"。**

这就是根因：**表盘能显示什么，由表盘引擎的数据源白名单决定，而不是由表盘自己会读什么决定。** 课程属于"自定义业务数据"，不在白名单内 → **表盘无法显示来自 Ev课程表的课程**。

---

## 二、第二个决定性证据：米坛的"课程表小程序"其实是 `.rpk`

米坛社区那篇"小米手环 8 Pro 小程序·课程表"（作者 NEORUAA，米坛首席站长），其帖子内容与附件暴露了真相：

- 附件文件名：**`com.givemefive.schedule.release.1.0.0.rpk`**（29.7 KB）——**标准 Vela 快应用包**，不是 `.bin` 表盘。
- 正文强调"**请使用表盘自定义工具最新版进行修改**"——即在**手机侧工具**里改数据后重新打包安装，**不是在手环上编辑**。

由此可以确认两件事：

1. **社区里真正"能用"的课程表，是以快应用（rpk）形态存在的**，而不是表盘形态。
2. **表盘自定义工具同时充当"第三方 rpk 安装器/打包器"**，既能装 `.bin` 表盘，也能制作/安装 `.rpk` 小程序。

## 三、能力边界对照表（你关心的五项）

| 能力 | 纯表盘 `.bin` | 快应用 / 小程序 `.rpk` | 说明 |
|---|---|---|---|
| **显示课程** | ⚠️ 只能显示**写死的静态文本** | ✅ 可动态渲染 | 表盘无课程数据源，课程只能当"图片/文字"烤进资源 |
| **手环上存储课程** | ❌ 无运行时业务存储 | ✅ `@system.storage` | 表盘只有内嵌资源，没有可读写的课程槽位 |
| **手环上输入课程** | ❌ 无输入组件、无输入法 | ✅（需自绘键盘） | Ev课程表已自研输入法，这是快应用能力 |
| **增 / 改 / 删课程** | ❌ 不可能 | ✅ 完整支持 | 表盘要改课 = **重做表盘 + 重装** |
| **数据同步** | ⚠️ 仅"重新打包后再装" | ✅ 存储读写 + 可与手机通信 | 表盘无实时同步概念 |
| **与 Ev课程表数据互通** | ❌ 不通 | ❌ 不同包也不通 | 数据源封闭 + 应用隔离 |
| **交互能力** | 极弱：多为"点击切主题/切元素" | 完整（列表/滚动/弹窗/输入） | 你观察到的"只有按钮选择"就是表盘交互的上限 |
| **显示布局自由度** | 受**底包结构**限制，只能改元素 | 自由布局（UX 模板） | 表盘不能任意搭版式 |
| **屏幕适配方式** | **按机型分别适配** | 一包内 `@media(shape:)` 自适应 | Mi-Create 用 `preview_sizes.json` 逐机型定义 |

> 表盘设备尺寸举例（Mi-Create `preview_sizes.json`）：小米手环 8 = 122×310、8 Pro = 230×328、手表 S3/S4 = 326×326、红米手表 5 = 432×514。**每个机型一套尺寸**，与"一包多适配"的快应用模式根本不同。

## 四、回答"是否算新作品、是否完全彻底独立"

**从工程与知识产权角度：是，完全独立，算新作品。**

| 维度 | 是否独立 |
|---|---|
| 代码 | ✅ 无共享（表盘无代码，或工具配置） |
| 仓库 | ✅ 独立仓库（前文已论证） |
| 数据 | ✅ 独立（不与快应用互通，需单独维护） |
| 编辑流程 | ✅ 独立（在手机侧工具里编辑，非手环编辑） |
| 分发 | ✅ 独立（表盘渠道与 rpk 渠道不同） |
| 用户认知 | ⚠️ 会被用户当成"Ev课程表的表盘"，形成**心理关联** |

**但"完全独立"是一把双刃剑**：

- 好处：不受快应用沙箱、授权体系、发布节奏的牵制，可以独立立项。
- 代价（必须正视）：
  1. **用户要维护两份课程**——在 Ev课程表里录一遍，在表盘工具里再录一遍；
  2. **手环上不能改课**——改一节自习课就得回手机重做表盘；
  3. **无法复用 Ev课程表已有的能力**（输入法、授权、节假日、模板体系全部用不上）。

> 结论：**"独立作品"这个定位在技术上是成立的，但在产品上是"零复用、高维护"的。** 是否值得，取决于你能否接受"两份数据、两套流程"。

## 五、四条可选路径（含推荐）

| 路径 | 做法 | 独立性 | 用户体验 | 成本 | 评价 |
|---|---|---|---|---|---|
| **P0. 不做独立表盘** | 把精力放在快应用本体的"课程速览"（首页卡片/状态栏提醒，项目已有） | — | 一致 | 最低 | **稳妥** |
| **P1. 做只读课程表盘**（`.bin`） | 手机侧工具里录课 → 打包成表盘 → 安装 | 完全独立 | 改课要重做表盘 | 中 | **可作为"高级版专属装饰"小步试水** |
| **P2. 做轻量课程快应用**（新 `.rpk`） | 只做显示 + 简单切换，不做编辑 | 独立但同形态 | 手环上装两个课程应用，割裂 | 中高 | 重复造轮子，不建议 |
| **P3. 数据中转注入** | 让同步器/工具把 Ev课程表数据导出并注入表盘 | 半独立 | 若成功则体验最好 | 高（需逆向） | **唯一能"联动"的路，风险最高** |

### 推荐

1. **首选 P0**：先认识到"表盘替代不了快应用"，把"课程显示"的体验做在快应用里（这是本项目的强项）。
2. **若要做表盘，只做 P1 的"只读版"**，并明确告知用户"数据需在手机工具里维护、手环上不能改课"，定位为**高级版专属的个性化装饰**，而不是"第二套课程表"。
3. **P3 作为研究项**（不是承诺项）：先验证"表盘是否可能被外部注入数据"，V3 通过才考虑。

## 六、必须澄清的一条边界（避免误解）

**"表盘能显示课程"和"表盘能管理课程"是两件完全不同的事：**

| 说法 | 是否成立 |
|---|---|
| 表盘可以**显示**课程（静态烤入） | ⚠️ 勉强可以，但改课要重做表盘 |
| 表盘可以**输入/编辑/删除**课程 | ❌ 绝不成立（引擎无此能力） |
| 表盘可以**存储**课程并在手环上读取 | ❌ 不成立（无自定义数据源/存储槽） |
| 表盘可以与 **Ev课程表实时同步** | ❌ 不成立（无通道） |
| 想要"能输入能编辑的课程应用" | → **那就是快应用，不是表盘** |

---

## 七、下一步待验证（低成本）

1. **实体体验一次**：装米坛「表盘自定义工具」，走一遍"课程表小程序制作"，亲眼看**数据在哪输入、能否在手环上改**。（这一步能一次性终结所有猜测）
2. **确认表盘是否有"可注入数据槽"**：找 Mi-Create / 表盘工具的资源格式文档，看元素是否只支持白名单数据源。
3. **确认工具能否编辑 rpk 内的课程数据**：若能，说明 P3 有戏；若只是替换图片，说明 P3 不可行。
4. 若以上都不通 → **回到 P0**，把"课程显示"继续做在快应用里。
