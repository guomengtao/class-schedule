# EvEmuBuddy 真机连接可行性分析（AIoT IDE 真机调试机制拆解）

> 2026-10-01 · 背景问题：EvEmuBuddy（菜单栏模拟器保姆）能否加入「真机连接」，像 AIoT IDE 一样填个设备ID就把 rpk 推到真手环上，实现全自动真机测试？

---

## 1. 结论速览（TL;DR）

| 问题 | 答案 |
|---|---|
| 官方真机调试现在能用吗 | **对手环9 不能**。官方文档明说：目前仅支持 **Xiaomi Watch S4**，且仅对「特定合作方」开放，需要联系小米拿专属 OTA 固件 + 测试版运动健康 |
| 本机 IDE 有这个功能吗 | **没有**。本机 AIoT IDE 内置的 vela 扩展是 0.0.5，全文搜不到「真机调试/连接设备/等待IDE连接」任何字样——官方文档对应的是新版 IDE/扩展 |
| Mac 蓝牙需要吗 | **不需要**。蓝牙只在「手环 ↔ 手机（运动健康）」之间；IDE 在电脑上，走的是**局域网（电脑与手机同网段）** |
| 设备ID 和 authKey 一样吗 | **完全两码事**（见 §4）。真机调试只需要 debug-App 里显示的**设备ID**，全程不涉及 authKey |
| EvEmuBuddy 加真机可行吗 | 官方通路对 S4 可行（需合作资格+固件）；手环9 只能走**社区侧载通路**，自动化形态不同（见 §6） |

## 2. 官方真机调试机制拆解（来源：iot.mi.com/vela/quickapp/zh/tools/devicedebug/start.html）

官方流程五步：

1. **设备升级**：联系小米工作人员获取《小米Vela设备真机调试全流程指南》，刷专属 OTA 包，升级到支持真机调试的指定固件（有变砖风险，仅对特定合作方开放）。
2. **环境准备**：手机装**测试版小米运动健康**并连接测试用手表；**电脑与手机在同一局域网**。
3. **真机侧**：手表上打开预装的「真机调试 debug-app」（一个 rpk）→ 点「开启调试」→ 状态变为【等待IDE连接】。
4. **电脑侧**：AIoT-IDE 打开真机调试界面 → 点「连接设备」→ 输入**设备ID**（从 debug-App 界面上读）→ 连接，列表出现设备状态 Connected。
5. **调试**：选设备 → 调试 → 真机自动打开当前应用；可「获取日志」（内核日志缓冲区）、「推送其他 rpk」（替换安装）；**不支持热更新**，改码要重新打包再推。

### 关键技术特征

- **连接载体是网络，不是 adb**：官方流程里没有 `adb devices`、没有 USB。IDE 输入设备ID 即可连上，说明 debug 固件 + 运动健康组成了一条**局域网内的设备发现/握手通道**（手机运动健康大概率承担手环的网络代理——手环本身没有 Wi-Fi 的型号靠 BLE 与手机相连，网络流量经手机中转）。
- **安装链与模拟器不同**：模拟器是我们已打通的 `adb push → mkdir → unzip → vapp`（NuttX nsh）；真机侧走 IDE 私有协议推 rpk，guest 侧是否开放 adb shell **未知**（要拿到 debug 固件才能验证）。
- **无热更新**：每次改码 = 重新打包 → 推送 → 真机冷启动，自动化收益主要在「省掉手动打包传输」这一段。

## 4. 设备ID ≠ authKey（两个完全不同的东西）

| | 设备ID（真机调试用） | authKey（小米 IoT 设备令牌） |
|---|---|---|
| 是什么 | 手环/手表的**唯一标识符**，真机调试时用来让 IDE 找到并连接这台设备 | 小米 IoT 平台的**设备访问密钥**，用于米家/云对设备的控制鉴权（local token / cloud token） |
| 在哪获取 | **真机的 debug-App 界面直接显示**（开启调试后屏幕上就有，官方文档原话：「设备ID从上面的debug-App中的设备ID获取」） | 需要从小米账号体系里提取（micloud 抓取、米家设备 token 提取脚本等），或设备接入 IoT 平台时签发 |
| Vela 真机调试需要吗 | **必须**（IDE 连接的唯一凭据） | **不需要**（官方流程从头到尾没出现） |
| 快应用 API 里的同名物 | `@system.device` 的 `device.getDeviceId()` 运行时也返回 deviceId（需 manifest 声明 `hapjs.permission.DEVICE_INFO`），但那是给应用运行时用的，**与调试连接用的设备ID 是不是同一个值，文档未说明**，不要混淆 | 与快应用开发无关 |

> 顺带澄清：网上「获取小米设备 authKey」的教程全是**米家/IoT 控制类**场景（比如用脚本控制台灯），和 Vela 手环真机调试无关。真机调试只认 debug-App 显示的设备ID。

## 5. 连接必要条件清单（如果走官方通路）

**手环侧**
- 型号 = Watch S4（目前唯一）
- 刷入小米签发的真机调试 OTA 固件
- 预装 debug-app rpk，开启调试处于【等待IDE连接】

**手机侧**
- 测试版小米运动健康，连接测试用手表（承担手环的网络中转/设备注册）
- 手机有可用网络（Wi-Fi 或蜂窝均可，但须与电脑互通）

**Mac 侧**
- 电脑与手机**同一局域网**（不需要蓝牙、不需要 USB——蓝牙只存在于手环↔手机链路）
- 新版 AIoT IDE（本机 0.0.5 扩展不含真机调试，需升级）
- 拿到设备ID（debug-App 屏幕上读）

**EvEmuBuddy 侧（若做同款自动化）**
- 逆向/复用 IDE 的 LAN 发现与握手协议（输入设备ID即连 ⇒ 存在可编程接口，具体协议未公开，需抓包或读新版 IDE 代码）
- rpk 推送通道（IDE 私有协议，或 debug 固件是否开放 adb 待验证）

## 6. EvEmuBuddy 可行的三条路线（按落地难度排序）

### 路线 A：社区侧载通路（手环9 立即可做，形态不同）

米坛社区（bandbbs）的成熟工具链：**表盘自定义工具 / debug 模块安装**——把 debug 版 rpk 通过「运动健康调试入口 + 扫二维码」装进手环9，不需要合作固件（社区大量 rpk 都这么装，我们的课程表 debug 包也验证过这条路）。

- EvEmuBuddy 加一个「真机安装」菜单：选项目 → 出 debug rpk → **自动生成二维码**（运动健康扫码即装）→ 状态落盘与模拟器同款幂等。
- 自动化程度：装包全自动，**但装完后的日志/交互回传没有通路**（这正是 IDE 真机调试的核心价值，社区通路给不了）。
- 工作量：小（1-2 次会话）。真机测试半自动化。

### 路线 B：官方合作通路（完整自动化，前期门槛高）

1. 联系小米申请真机调试合作资格（我们有正式渠道包发行记录，有谈判基础）；
2. 拿测试机：Watch S4（官方唯一支持）；顺带问手环9 的 debug 固件可能性；
3. 按指南刷固件 + 装 debug-app + 测试版运动健康；
4. 升级本机 AIoT IDE 到含真机调试的版本，先用 IDE 人工打通全流程；
5. 抓 IDE 连接过程的局域网包（或读新版扩展代码），把「连接 → 推 rpk → 拉日志」复刻进 emubuddy_core.py——模拟器那套 `deploy_app()` 的幂等/多项目框架可直接复用，只换传输层。

- 自动化程度：目标全量（推包+日志+远程调试）。
- 工作量：合作流程不可控（数周~数月）；拿到环境后 emubuddy 侧 2-4 次会话。

### 路线 C：不做连接，做「半自动验证」

真机测试的痛点其实是「装上之后有没有跑起来、有没有报错」。可以在路线 A 基础上叠加：
- rpk 里埋日志上抛（复用现有追踪链路的 `client-event` 通道，手环应用有网络时经手机上报）——emubuddy 面板直接显示真机侧启动成功/异常。
- 相当于用业务埋点替代调试协议，无固件门槛，但粒度粗（看不到引擎级日志）。

### 推荐组合

**先做 A（本周可落地）+ C（埋点上抛）**，手环9 的真机验证立即半自动化；同时启动 **B 的资格申请**，拿到 S4/合作固件后把 emubuddy 升级成完整真机调试保姆。

---

## 7. 一句话回答原始问题

「AIoT IDE 输个设备ID就能连真机」这件事，对手环9 **现在走不通**——那是 Watch S4 专属 + 合作方专属 + 专属固件的能力；设备ID 来自真机 debug-App（与 authKey 无关、不需要 authKey）；Mac 蓝牙全程用不上（走局域网，蓝牙只管手环↔手机）。EvEmuBuddy 想让真机测试自动化，短期走社区侧载 + 业务埋点（立即可做），长期走小米合作 + IDE 协议复刻（拿到 S4 环境后完全可行）。
