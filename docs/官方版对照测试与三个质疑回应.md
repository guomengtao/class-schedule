# 官方版对照测试（G 项）与三个质疑回应

> 日期：2026-09-25
> 触发：用户提出三个质疑 —— ①官方发布的键盘、几乎所有开发者都在用，会不会是我们改错了？②为什么 10 Pro 好好的？③这次改动会不会影响 10 Pro 用户？
> 结论性质：**无法靠静态阅读定案，必须做 A/B** —— 本文给出已实现好的对照测试（诊断页 G 项）。

## 一、质疑一：官方键盘本身会不会有问题？

### 1.1 实测对比：官方版 vs 我们的版本

官方原版来源：提交 `f549d31`（2026-09-10，*"upgrade Vela input method to latest version"*），即引入上游 Vela_input_method 的那次。

| 特征 | 官方版 `f549d31` | 我们的版本 |
|---|:---:|:---:|
| pill 容器 `height: 305px` | ✅ 有 | ✅ 有 |
| `<progress type="arc">` + `total-angle:-48deg` | ✅ **有** | ❌ 我们移除了（**移除后仍崩**） |
| 3 层绝对定位 + `(screenWidth-192)/2` 居中 | ✅ 有 | ✅ 有 |
| 26 个 `.calbtn66`（60×60 + 3px 描边 + 30px 圆角） | ✅ 有 | ✅ 有 |
| `cvalrow-wrap`（键盘外拼音行） | ✅ 有 | ✅ 有 |
| `onInit` 里调 `adjustScreenWidth()` → `device.getInfo` | ✅ 有 | ✅ 有 |
| `screenWidth: 336` 初值 | ✅ 有 | ✅ 有 |
| 候选行 `scroll-x`（`cvalWaiting`） | ✅ 有 | ✅ 有 |
| 下展面板 `<list>` | ✅ 有 | ❌ 我们移除了 |
| 图片路径 | `./assets/...`（相对） | `/components/InputMethod/assets/...`（绝对） |
| **箭头函数** | **1 处**（`adjustScreenWidth` 里） | 0 处（我们修过） |

**差异总量**：`git diff f549d31 HEAD` → **129 insertions / 141 deletions**。

### 1.2 差异的性质：都是"减法与适配"，没有引入新的重元素

我们相对官方版的改动包括：
- 移除下展面板（`<list>` + `downFlag==='down'` 那一整块）
- 图片路径改为绝对路径
- 去掉 1 处箭头函数（兼容修复）
- 加 `capsule → pill-shaped` 映射
- 移除 pill 的 `arc` 进度条（我做的）
- 加 `$watch("screentype")` 与 `l66DownPanelWidth`

**没有新增任何重元素** —— 反而比官方版更"轻"。

### 1.3 因此有两种可能，必须用 A/B 区分

官方版**同样具备** pill 305px + arc + 绝对定位 + 26 个描边圆角按键 + 8 张 PNG。所以：

> **如果这些特征足以让手环 9 重启，那么官方版也会重启。**

| 可能 | 含义 | 判据 |
|---|---|---|
| **A. 是我们改坏的** | 某个改动引入了问题 | 官方版**不崩** |
| **B. 官方实现对手环 9 性能余量不足** | 不是"bug"，是"边缘场景" | 官方版**也崩** |

### 1.4 一个容易被忽略的视角

上游 Vela_input_method 的主要使用场景是**手表**（屏幕更大、性能更强）。**192px 跑道屏手环属于边缘场景** —— "很多开发者在用"并不等于"在所有机型上都验证过"。

这与我们已知的另一个事实吻合：**10 Pro 正常、手环 9/11 挂**（同一份代码，只有设备不同）。

## 二、质疑二：为什么 10 Pro 好好的？

| 维度 | 手环 9（pill） | 10 Pro（rect） |
|---|:---:|:---:|
| 键盘分支高度 | **305px** + 28px 拼音行 | **255px** |
| 布局方式 | 26 个描边圆角 + 绝对定位层 + 2 个 scroll + 8 张 PNG | `width:100%` + flex 相对布局 |
| 屏幕 | 192×490 | 336×480 |
| CPU/GPU | 弱 | 强 |
| 结果 | **卡很久 → 重启** | 正常 |

**这是"性能余量"差异，不是"某设备专属 bug"**：
- pill 分支的单帧渲染量（200+ 节点 / 8 图片 / 26 个圆角描边）在弱设备上超出可承受范围 → 主线程阻塞 → 看门狗复位；
- 强设备同样的量级扛得住。
- 也解释了为什么**"卡很久"才重启**（耗时问题，而非瞬时崩溃）。

## 三、质疑三：会不会影响 10 Pro？

### 3.1 已回滚的改动

**改法 B（组件根 `position` 按屏型切换）→ 已回滚。**

`position: {{screentype === 'pill-shaped' ? 'relative' : 'absolute'}}` 本意只影响 pill，但 —— **`chinese-input.ux` 的 `screenType` 初始值就是 `'pill-shaped'`**，所以 10 Pro **首帧也会走 `relative`**，等 `device.getInfo` 返回 `rect` 才切回 `absolute`。**你的担心是成立的**，这也是我一确认它无效就立刻回滚的原因。

### 3.2 当前仍保留、且会影响所有设备的改动

| 改动 | 对 10 Pro 的实际影响 |
|---|---|
| 移除 pill 的 `progress type="arc"` | **无影响** —— 10 Pro 走 rect 分支，用的是另一条线性 progress |
| 词典分步分片初始化 | 时序等价，**无感** |
| 键盘延时一帧展开（`keyboardHidden`） | 所有屏型首帧晚一帧出现键盘，**几乎无感**，但严格说不是零影响 ⚠️ |
| `dictlazy` prop | 默认 `false`，**行为不变** |
| 诊断页 / 官方对照组件 | 独立页面，**不影响主流程** |

**若要对 10 Pro 做到"绝对零影响"**：把 `keyboardHidden` 错峰也回滚即可 —— 它已被证明不是崩因（第一轮第 3 步在 `dictlazy=true` 下仍崩，且错峰只影响时序）。
