# 模拟器黑屏排查指南

> 适用对象：Vela / 快应用手环模拟器（Mac 上 EvEmuBuddy 与 vela CLI 两套工具链）
> 编写依据：2026-10-14 真机实测 + 黑屏悬案结案复盘

## 0. 一句话结论

模拟器"黑屏"绝大多数**不是 bug**，而是**帧缓冲（fb0）的物理规律**：

`/dev/fb0` 只有在 app 真正渲染时才有内容，**裸 AVD（没装 / 没拉起快应用）必黑**。
截图工具对裸机输出的是 **353 字节的纯黑 PNG**——这是正常行为，不是工具坏了。

---

## 1. 黑屏根因

- 真身是 `/dev/fb0`（**不是**安卓那套 `/dev/graphics/fb0`）。
- guest 是 NuttX nsh，**没有** Android 的 surfaceflinger 常驻合成；屏幕内容由当前运行的 app 直接写 fb0。
- 没装 rpk / 装了但没拉起 / 实例还没跑到 app 首帧 → fb0 全 0 → 纯黑。

---

## 2. 两条判据（秒辨"真黑"还是"假黑"）

| 判据 | 裸机（黑） | 有 app（有图） |
|---|---|---|
| PNG 文件大小 | **353 字节**（纯黑） | 数千 ～ 上万字节 |
| `vela shot` 采样数 | **0**（非零采样 = 0） | 1387（实测） |

> EvEmuBuddy 与 vela CLI 两条截图链路对裸机**都输出 353B 纯黑 PNG**，行为一致 → 证明是 fb0 规律，
> 不是某条工具链的 bug。所以别再疑神疑鬼"截图工具坏了"。

---

## 3. 五类黑屏场景与解法

| # | 场景 | 解法 |
|---|---|---|
| 1 | **没装 rpk / 没拉起 app** | `vela up <avd> --rpk <rpk> --wait` 装包并等 25s 让首帧起来 |
| 2 | **同一 AVD 被两套系统并行占用** | EvEmuBuddy(13000) 与 vela(11000) 抢同一机型会 `offline`。**严禁并行**，先 `vela down all` 或退出另一管理器 |
| 3 | **管理器退出陪葬** | EvEmuBuddy 退出后 `core.stop_avd` 失效，qemu 进程残留。只能 `pgrep -f qemu` 拿 pid 再 `kill` |
| 4 | **实例池不互通** | EvEmuBuddy 起的实例与 vela 起的实例互相看不到，别指望一套起的实例被另一套截图 |
| 5 | **设备错配** | cfg `defaultDevice` 与实际实例不匹配 → `serial_for_avd` 返回 None。确保 `--repo`/device 指向真实存在的实例 |

---

## 4. 标准排查命令序列（胜利路线）

```bash
# 1) 起一台带窗口、装好课表 rpk、等 25s 让画面起来的实例
vela up xiaomi_band_pro --window --wait --ttl 15m \
  --rpk ~/Documents/guomengtao/ev/class-schedule/dist/com.application.watch.classschedule.release.1.8.319.rpk

# 2) 截首页（实例 id = 机型-端口，单台默认 xiaomi_band_pro-11000）
vela shot xiaomi_band_pro-11000 ~/Desktop/vela-shot-app.png

# 3) 点设置按钮（336×480 屏，按钮约在 168,264）
vela tap xiaomi_band_pro-11000 -x 168 -y 264

# 4) 截设置页
vela shot xiaomi_band_pro-11000 ~/Desktop/vela-shot-settings.png
```

> 进设置页还有 `vela nav`（连点连截）和 `core.launch_app("vapp app/<pkg> &")` 两条路线，见 §6。

---

## 5. 两套工具对照表

| 维度 | EvEmuBuddy（菜单栏 Python） | vela CLI（`~/.local/bin/vela`） |
|---|---|---|
| 实例端口段 | 13000+ | 11000–11099（步长 2） |
| 截图 | `screenshot_frame` | `vela shot <id> out.png` |
| 进设置页 | `navigate_settings` / `launch_app` | `vela tap` / `vela nav` |
| 生命周期 | `core.stop_avd`（退出即失效） | `vela down`（TTL 看门狗自收） |
| 实例互通 | 与 vela 不互通 | 与 EvEmuBuddy 不互通 |
| 黑屏判据 | 353B 纯黑 PNG | 353B / 非零采样数 |

---

## 6. 进设置页的 4 条路线（按实测稳定性）

1. ✅ `vela tap xiaomi_band_pro-11000 -x 168 -y 264` 点按钮 → **最稳**，首选。
2. ✅ `vela nav <id> 168,264@/tmp/a.png 245,452@/tmp/b.png` 连点连截。
3. ✅ `core.launch_app("vapp app/com.application.watch.classschedule &")` 直接拉设置应用。
4. ❌ **input 键路线已死**：NuttX nsh 没有 `input` 命令，`sendevent` / `input tap` 均无效。别再试。

---

## 7. 已排除的错误假设

- ❌ "等一会儿就不黑了" → 裸机等多久都是 353B 纯黑，**等待无效**，必须装 app。
- ❌ "fb 真身是 `/dev/graphics/fb0`" → 这里是 `/dev/fb0`。
- ❌ "input tap 能点点进设置" → nsh 无 input 命令，死路。
- ❌ "截图工具坏了" → 两套工具对裸机都 353B，是规律不是 bug。

---

## 8. 速查命令卡（vela CLI）

```bash
vela ls                     # 看现有实例
vela status <id>            # 探活
vela shot <id> out.png      # 截图（看大小辨真假黑）
vela tap <id> -x 168 -y 264 # 点击
vela down <id>              # 停一台；不给 id = 全停
vela doctor                 # 环境自检
```

## 9. 机型命名陷阱

- vela 的 `xiaomi_band_pro` = **手环 10 Pro（336×480）**，别和 `xiaomi_band_9_pro` 等搞混。
- EvEmuBuddy cfg 里 `9pro` 实际指向 `evc-xiaomi_band_pro-1`，命名不一致；跨系统对照时**以 vela 的 AVD 名为准**。
