# 模拟器分期重启 · 方案

> 立档：2026-10-20 · 起因：用户反馈「每次 AI 重启模拟器，我自己手工用的那台也跟着重启」
> 结论先行：**这不是模拟器瓶颈，是我们自己写的策略在互相踩。** 两台手环 9 在物理上完全可以各跑各的，今天上午已经实测并存成功过。

---

## 一、先给结论

| 问题 | 答案 |
|---|---|
| 多个模拟器必须一同重启吗？ | **不必**。每台是独立 qemu 进程、独立端口、独立磁盘镜像，重启 A 不碰 B。 |
| 为什么现在会一起动？ | 三个自伤设计：**族门闩**教 AI 去停用户那台、**巡检**掐掉后开的那台、**`stop all`** 一键全停。 |
| 是模拟器瓶颈吗？ | **不是主因**。真正瓶颈只有内存（8GB 已用 7554MB，闲置 81MB），它是放大器，不是源头。 |
| 能分期重启吗？ | **能**，前提是把「归属者」这一维度补进规则里，别再只按机型族判断。 |

---

## 二、现场事实（实测，非推断）

### 2.1 两台机器根本不在同一个端口段

```
pid 52152   -avd evc-xiaomi_band-buddy-1   →  emulator-13000   ← 用户手工专用
（已停）     -avd xiaomi_band               →  emulator-5554    ← AI 默认
```

- 用户那台走 **13000 段**，由 EvEmuBuddy（菜单栏管家 / vela CLI）拉起。
- AI 那台走 **5554/5556 段**，由 `emu-start.sh` 直接调 SDK launcher 拉起。
- 两套体系**端口天然错开**，不存在抢端口的问题。

### 2.2 两台并存今天已经成功过

10:18–10:24 实测：

```
pid 992    xiaomi_band              hostfwd 10055  →  emulator-5554
pid 19535  evc-xiaomi_band-buddy-1  hostfwd 10334  →  emulator-5556
两台同时 device 在线，各自 2 个 vapp 独立运行
```

所以「同型号不能多开」这个印象是错的。物理隔离成立，是规则不让。

### 2.3 资源账

```
物理内存        8.0 GB
当前已用        7554 MB（闲置 81 MB，压缩器 2813 MB）
每台 guest      hw.ramSize = 1024 MB，2 核
单台闲置 RSS    约 47 MB（被 compressor 压走）
```

内存确实紧，但**「紧」不等于「必须一起重启」**。一台僵死时重启它，另一台照样活——只要没人去 `pkill`。

## 三、真凶排序（附代码位置）

### 真凶 1：族门闩把「用户的手工机」和「AI 的默认机」归成一族 ★最致命

`scripts/emu-start.sh:74` 的 `avd_family` 把两者都归为 `xiaomi_band`：

```
evc-xiaomi_band-buddy-1  →  族 xiaomi_band
xiaomi_band              →  族 xiaomi_band
```

于是 `emu-start.sh:135` 的门闩直接拒绝 AI 启动，并且提示语**明确教 AI 去停用户那台**：

```
[门闩] 同机型族(xiaomi_band)已有在跑实例：evc-xiaomi_band-buddy-1（pid=52152）
[门闩] 每族整机只许 1 台。先 stop evc-xiaomi_band-buddy-1 再启 xiaomi_band；或 EMU_ONE_PER_FAMILY=0 豁免。
```

**这就是直接因果**：AI 想干活 → 门闩说「先停 buddy-1」→ AI 照做 → 用户那台没了。提示语本身在教错误动作。

### 真凶 2：巡检按「谁先来」保留，用户后开的必然被掐

`scripts/emu-watchdog.sh:94-97`：

```bash
sort -k3,3n -k2,2n     # 按 start_epoch 升序
keep=$(... | head -1)  # 保留启动最早的那台
```

场景：AI 的 `xiaomi_band` 先跑着 → 用户后开 `buddy-1` → 巡检判定「同族 2 台」→ **保留 AI 的，掐掉用户的**。

用户视角就是「我一开就被杀掉」，而 AI 视角是「巡检在正常工作」。两边都没错，规则错了。

### 真凶 3：`stop all` 分支还在

`scripts/emu-start.sh:121`：

```bash
all) for a in $(avd_names_running); do stop_avd "$a"; done ;;
```

早期菜单栏管家的启动流程就是 `clean → stop all → start`，用户 09-30 亲眼见过日志。这套流程在 EvEmuBuddy 里已废除（见该仓库设计文档 §M2.5），但 `emu-start.sh` 这个分支**一直留着**，谁顺手一敲就全停。

### 真凶 4：`adb kill-server` 断开全部连接

`scripts/emu-start.sh:39`（`serial_for_avd` 探测失败后的兜底）：

```bash
"$ADB" kill-server; sleep 2; "$ADB" start-server; sleep 2
```

它不杀模拟器，但会让**所有**设备连接断约 2 秒。用户正在操作时表现为「画面卡死/黑一下/应用闪退」，很容易被当成「被重启了」。

### 真凶 5：内存零余量（放大器，非源头）

8GB 已被 WorkBuddy Helper（2.3GB）、多个 Code Helper（约 2.1GB）、WindowServer（473MB）吃掉大半。此时再启动一台 1GB guest，系统会大量换页，**另一台的 guest 也可能跟着卡死**——看起来像「一起重启」，其实是「一起被拖死」。

这条无法靠改脚本消除，只能靠少开或加内存。

## 四、分期重启：物理上可行，规则上要放行

### 4.1 为什么物理上可行

| 维度 | 是否独立 |
|---|---|
| 进程 | 独立 qemu 进程，pid 不同 |
| 端口 | console 端口 + hostfwd 端口各自分配（已按 AVD 名派生，commit `c6cb456`） |
| 磁盘 | 独立 `~/.vela/vvd/<name>.vvd/`，独立 `vela_data.bin` |
| adb | 独立 serial |
| 生命周期 | `stop <avd>` 只 kill 该 AVD 的 pid |

`stop_avd()` 的实现本身是精确的（按 `-avd <名字>` 匹配 pid），**问题只出在调用它的人**。

### 4.2 分期重启的三条硬前提

1. **禁止 `stop all`**，禁止 `pkill -f qemu-system`（会连 IDE 调试会话一起干掉，EvEmuBuddy 仓库已经踩过一次）
2. **不要重启 adb server**；判活用 `adb devices` + `adb shell echo alive`，不要用 `emu avd name`（它依赖 console，探测失败率高）
3. 重启前先确认**目标之外还有谁在跑**，重启后确认它们没变

### 4.3 正确的分期重启动作

```bash
# ① 看清楚有哪些实例，记下非目标的 pid
bash scripts/emu-start.sh status

# ② 只停目标
bash scripts/emu-start.sh stop xiaomi_band

# ③ 复核：非目标 pid 还在
ps -axo pid=,command= | grep '[q]emu-system'

# ④ 启动目标
bash scripts/emu-start.sh start xiaomi_band

# ⑤ 复核：非目标仍然没变，目标已就绪
adb devices && adb -s <target-serial> shell echo alive
```

## 五、方案：按「归属者」解耦，而不是按「机型族」

核心思想：**机型族**只用于判断「画面对不对、机型参数是否一致」，**不应该用来判断「谁能占资源」**。占资源的判据应该是「这块资源归谁」。

### 档 1（最小改动，当天可落地）：白名单 + 拆掉自伤入口

1. 新增 `~/.vela/devops/user-instances.conf`，一行一个用户专用 AVD 名：

   ```
   evc-xiaomi_band-buddy-1
   ```

2. `emu-start.sh` 门闩改造：
   - 读白名单，命中白名单的实例**不计入同族计数**
   - 提示语改为：「同族已有 AI 实例 X，请先 `stop X`；用户实例 Y 不在管辖范围」
   - **删掉那句「先 stop 用户那台」**

3. `emu-start.sh` 删除 `stop all` 分支，或改名为 `stop-all-dangerous` 并要求二次确认

4. `emu-watchdog.sh` 增加白名单跳过：白名单实例永远不掐，哪怕同族多台

5. `serial_for_avd` 去掉 `kill-server`，改为纯探测 + 失败返回空

**效果**：AI 重启自己的机器时，用户那台不受任何影响。这一档就能解决 90% 的抱怨。

### 档 2（推荐，一到两天）：实例池分离，物理上分家

1. **AI 专用实例**：固定一个新 AVD（如 `ai-xiaomi_band`），只给 AI 用，用户永不碰
2. **端口段分配**：
   - 用户 / EvEmuBuddy：13000 段（现状不变）
   - AI / emu-start：5554 段 + hostfwd 10056-10755（已实现）
3. **门闩判据从「机型族」改为「端口段」**：同一端口段内只许一台，跨段互不干涉
4. **巡检只扫 AI 端口段**，用户段完全不进它的视野

**效果**：两套体系彻底不相交，AI 怎么折腾都碰不到用户那台。这是治本。

### 档 3（长期）：注册表 + 租约

把 `deploy-lock` 的租约心跳思路扩展到实例本身：每个实例在启动时登记 `{avd, pid, port, owner, heartbeat}`，任何"重启/清理"动作先查注册表，只处理 `owner=me` 的条目。

这条最干净，但工作量最大，排在档 2 跑稳之后再考虑。

## 六、落地清单（档 1）

| # | 文件 | 改动 | 风险 |
|---|---|---|---|
| 1 | `scripts/emu-start.sh` | 读 `user-instances.conf`，白名单实例不计入同族 | 低 |
| 2 | `scripts/emu-start.sh` | 门闩提示语去掉「先 stop 用户那台」 | 无 |
| 3 | `scripts/emu-start.sh` | `stop all` 加二次确认或删除 | 低 |
| 4 | `scripts/emu-start.sh` | `serial_for_avd` 去掉 `kill-server` | 低（但需验证探测率） |
| 5 | `scripts/emu-watchdog.sh` | 白名单实例跳过掐杀 | 低 |
| 6 | `scripts/emu-watchdog.sh` | 巡检默认只扫 5554 段，不扫 13000 段 | 中（需确认端口匹配规则） |

### 验收方法（不启第二台也能验）

1. **纯函数验**：`avd_family` + 白名单组合，验证 `xiaomi_band` 计数不含 `buddy-1`
2. **干跑验**：`EMU_PS_FIXTURE` 假进程表放「AI 的 xiaomi_band + 用户的 buddy-1」，`EMU_DRY_RUN=1` 跑巡检 → **必须零动作**
3. **真实验**：用户那台在跑时，AI 执行 `start xiaomi_band` → 应成功启动（不再被门闩拒），且 `buddy-1` 的 pid 前后不变
4. **反向验**：AI 执行 `stop xiaomi_band` → 用户那台 pid 不变、`adb shell echo alive` 仍返回 alive

## 七、明确不做的事

- **不做**「同族多台全杀后重启」这种粗暴恢复（历史 `pkill` 已把 IDE 会话干掉过一次）
- **不做**「为了解决冲突就把用户那台迁走」——用户的实例是既定事实，规则应该迁就它
- **不把内存不足当成借口**：内存不足的代价是慢，不是"必须一起重启"

---

## 八、一句话收尾

今天上午两台并存成功过，说明**技术上不存在「同型号不能多开」**。会互相踩，只因为我们把「机型族」当成了「资源归属」，又在提示语里教 AI 去停用户的机器。

把「归属者」补进规则，分期重启就是默认行为，而不是需要特别争取的例外。

## 八、实施记录

### 档 1 已落地（2026-10-20，commit f17b04b）

| 改动 | 落地方式 |
|---|---|
| 白名单 | `~/.vela/devops/user-instances.conf`，一行一个 AVD 名，当前只含 `evc-xiaomi_band-buddy-1`；两个脚本共用同一份（`EMU_USER_CONF` 可覆盖） |
| 拒绝操作用户实例 | `stop_avd` / `cmd_start` 命中白名单直接返回 1 并打印理由 |
| 门闩提示语 | 删除「先 stop 用户那台」，改为只针对 AI 实例，并附「另有 N 台用户侧实例，不在 AI 管辖范围」 |
| `stop all` | 停用；改 `stop-all-dangerous` + `EMU_CONFIRM_STOP_ALL=1` |
| 巡检 | 白名单实例永不参与决策，打印 `[保护] … 跳过` |
| `kill-server` | 从 `serial_for_avd` 移除（探测失败就重启 adb server 会掐断用户连接 2 秒）；救急用 `EMU_ADB_REPAIR=1` |

**附带修掉的根因**：vela 版 adb 的 `adb -s X emu avd name` 输出是 CRLF，`head -1` 保留的 `\r` 让 `grep -q "^$1$"` 永远匹配失败 →
`serial_for_avd` 恒返回空 → `cmd_start` 判「僵死」→ 杀掉重启。这就是「AI 一重启，用户那台跟着重启」最直接的技术原因，
比白名单问题更早、更隐蔽。修法：管线加 `tr -d '\r'`。修后 `status` 从 `serial=未识别 guest存活=否`
变为 `serial=emulator-13000 guest存活=是`。

`resolve_serial` 的兜底（全机仅一台在线设备）**必须同时要求「反查不到 AVD 名」**才认领，
否则会把用户 13000 段那台认成 AI 的 `xiaomi_band`，等于把包推到用户机器上。

### 档 2 已落地（2026-10-20，commit 见下一节）

判据从「机型族 / 白名单」下沉到**物理事实：端口段**。

| 段 | 端口 | 归属 | AI 权限 |
|---|---|---|---|
| `user` | ≥ `EMU_USER_PORT_MIN`（默认 12000） | 用户 / EvEmuBuddy（实测 buddy-1 = `emulator-13000`） | **完全不进视野**：不计入同族、不进提示语、拒绝 stop/start、巡检跳过 |
| `ai` | < 12000（或进程行无 `-port`） | `emu-start.sh` 起的实例（555x） | 同族只许 1 台，多开后到者被掐 |

- 新增 `port_segment` / `port_of_avd` / `avd_in_user_segment`，两个脚本逻辑一致（`EMU_USER_PORT_MIN` 可调）。
- 拿不到 `-port` 的进程一律按 AI 段处理——AI 从不自己指定 `-port`，这个默认值安全。
- 巡检 `scan` 输出增加第 4 列端口，由 `sweep` 统一分段；`EMU_WATCHDOG_ALL_PORTS=1` 才会把用户段也纳入（危险，默认关）。
- 效果：**即使白名单文件被删或漏配，用户那台因为物理在不同端口段，AI 仍然碰不到**。白名单降级为双保险。
- `status` 每行增加 `段=user|ai`，一眼看出归属。

### 仍存在的边界（未做）

1. 端口段判据依赖进程行里有 `-port`。若某工具起实例时不带 `-port`，会被判为 AI 段——此时只能靠白名单兜底。
2. 硬隔离的最终形态仍是「AI 与用户各占一台固定机器」，档 3 的注册表 + 租约才能给出 owner 级语义。
3. 内存零余量（8G / used 7554M）没有解决，档 2 只保证「不互相踩」，不保证「两台都跑得动」。
