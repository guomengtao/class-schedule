# BUG：激活报「设备ID不匹配」根因定位（V2 · 生产数据实证版）

> 2026-11-05 11:53 +0800 · 现场：设备 ID 设为 `e681`，激活码 `003082815070674773`，一键激活失败
> 本文**替换**同文件 V1 版。V1 的根因方向正确，但「39 天全灭」的结论错误，且没有解释「每天仍有人激活成功」，已按下文修正。

---

## 〇、结论先行

**错误位置已定位：`src/app.ux` 的 `syncHandleActivate`（APK 一键激活）取号分支，与 `syncHandleGetDeviceId`（APK 取号/签发）用了两套不同的设备 ID 解析规则。**

- 取号/签发侧：对 `NA` / `unknown` / `null` / 空串有哨兵判定，**回落本地 UUID** → 得到 `uuid-10128aa4f448d7c564be0cb4bc41e681`，末 4 位 `e681`
- 一键激活校验侧：**裸调 `getDeviceId()` 直接透传，无哨兵、无回落** → 拿到 `"NA"`，末 4 位 `"NA"`

于是同一台手环在同一个进程里返回了两个「设备身份」：
**用 A 签发码（E681），拿 B 去校验（NA）** → 必然「设备ID不匹配」。

11-04 那轮修的是 `toUpperCase()`（大小写），`"NA"` 转大写仍是 `"NA"`，所以「昨天改了一次，今天照旧」。

### 为什么「每天几乎都有人激活成功」并不矛盾（V1 的错误在这里）

这个缺陷**只在 `getDeviceId()` 返回哨兵值的设备上触发**：

| 设备类型 | 签发侧 | 校验侧 | 结果 |
|---|---|---|---|
| 能返回真实 ID 的设备 | 真实串末 4 位 | 同一个真实串末 4 位 | ✅ 一致，激活成功 |
| 取不到真号、走 UUID 兜底的设备（本机就是这类） | UUID 末 4 位 `e681` | `"NA"` | ❌ 永远不匹配 |

所以「39 天全灭」是错的推断：**绝大多数设备一直正常，只有哨兵类设备全灭**。生产库里 204/311 条签发记录是 UUID 兜底，说明这类设备还不少，但它们若走手环端手输页仍能成功（页面侧签发与校验口径自洽），只有走 APK 一键激活才失败。

## 二、代码对照（结构性矛盾）

| 位置 | 取号规则 | 结果 |
|---|---|---|
| `src/app.ux:406-442` `syncHandleGetDeviceId` | 有哨兵判定 + `fallbackUuid()` | `uuid-…e681` |
| `src/app.ux:554-563` `syncHandleActivate` | `success: function(data){ finish(data && data.deviceId) }` 直接透传 | `"NA"` |
| `src/pages/activation/shared/activation-context.js:126` | 有哨兵判定 + `_fallback()` | `uuid-…e681` |
| `src/pages/activation/activation-code.ux:547` 手输校验 | 复用 ctx 的 `deviceId` | `e681` ✅ |

`finish()`（`src/app.ux:515-530`）唯一区分「取不到」与「不匹配」的判据是 `!s`（空串）。`"NA"` 非空，被当成合法设备号继续比对：

```js
var last4 = s.substring(s.length - 4)   // s="NA" → "NA"
if (!s || !decrypted.deviceId ||
    String(decrypted.deviceId).toUpperCase() !== last4.toUpperCase()) {
  reason: !s ? "无法获取设备ID，请到手环端激活" : "设备ID不匹配"
}
```

离线复现四种本机返回值：`"NA"` → `localDeviceId4="NA"` 报不匹配；`uuid-…e681` → 通过；`""` → 报「无法获取设备ID」。现场文案是「设备ID不匹配」，**只能是第一种**（非空但末 4 位 ≠ E681）。

> 回包里已经带了 `codeDeviceId` / `localDeviceId4`，抓一次即可终审：若为 `NA`，本结论 100% 坐实；若为 4 位十六进制但 ≠ `E681`，则是 UUID 被重装重生成、码已失效（第二根因）。目前设备侧失败没有上报通道，这是唯一未闭合的实测缺口。

## 四、修复方案

### P0（根治，一行口径统一）

让 `syncHandleActivate` **复用 `syncHandleGetDeviceId` 的那套 `resolveDeviceId(cb)`（含哨兵判定 + UUID 回落）**，而不是自己再调一次裸 `getDeviceId()`：

```js
// 现在：
success: function (data) { finish(data && data.deviceId) }   // "NA" 照收

// 改为：
resolveDeviceId(function (id) { finish(id) })                 // 回落到 uuid-…e681
```

这样本机校验值也变成 `uuid-…e681` → 末 4 位 `e681` → 与码里的 `E681` 一致 → **真正激活成功**。

⚠️ 只把 `"NA"` 改成 `""` 是不够的：那只会把文案从「设备ID不匹配」换成「无法获取设备ID，请到手环端激活」，用户依旧激活不了。必须复用同一套回落。

### P0.5（补观测）

把 `activate` 失败回包里的 `codeDeviceId` / `localDeviceId4` 上报到服务端（当前 `auth:appfail` 为空、设备侧失败零上报）。没有这条数据，下次同类故障仍只能靠推断。

### P1（防复发）

把 `isSameDevice(codeDeviceId, localId)` 抽成公共函数。同一份比对逻辑目前散落在 `app.ux`、`activation-code.ux`、`activation-code-v2.ux`、`evbox/activation.ux` 四处各自演进 —— 「页面补了、同步没补」正是这个结构造成的。`test/activation-contract.test.js` 应加一条「取号口径一致性」硬断言。
