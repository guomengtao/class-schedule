### 0.3 一处由整改引出的连带修复

统一 padding 到 16px 后，`detail` 胶囊屏内容区由 176px 收窄到 160px，导致第 2 步时间步进器「小时 − 08 +」一行需要 172px 而**重新溢出 12px**。已改为 **`.stepper-row` 换行、标签独占一行**的布局解决：

```
改后单行 = −(44) + 08(56) + +(44) = 144px + padding 8px = 152px ≤ 160px ✓
按钮同时由 40×40 提到 44×48
```

这也说明：**统一 padding 不能只改数值，必须同步核算每个横向多元素行**。

### 0.6 第五轮：把「数据安全性」从 88 推到 100（第三个满分维度）

选它的理由：本维度唯一的结构性缺陷就是「删除无撤销通道」——二次确认只能降低误删概率、无法挽回已发生的误删。补上撤销即可满分，且改动只落在两个删除流程，不碰其它逻辑。

**方案：删除后保留被删数据快照 + 底部浮条「撤销」按钮，5 秒窗口内可原样回滚。**

| # | 位置 | 改动 |
|:--:|:---|:---|
| 1 | `course-manager.ux` 单条删除 | 删除前暂存 `{course, index}`，真正删除并写盘后显示撤销浮条；点「撤销」按时间重排插回并写盘 |
| 2 | `detail.ux` 编辑页删除 | 删除前构造完整课程快照 `{id, day, name, time, location, teacher, notes}`，删除成功显示浮条，**不立即返回首页**；5 秒后自动 `router.back()`，期间点「撤销」用 `database.insertCourse` 原样恢复 |
| 3 | 两页 `onDestroy` 均清理撤销定时器 | 避免离开页面后误触发回滚 |

**关键设计点：**

- 二次确认**保留**（仍是第一道防误删），撤销是第二道「后悔药」，二者互补不冲突；
- `course-manager` 撤销用 `sortByTime` 重排，保证恢复后顺序正确；
- `detail` 撤销直接复用 `database.insertCourse`（按 `day` 分组写入），与现有存储结构一致；
- 浮条用 `position: fixed` 底部浮层，胶囊屏 `bottom: 56px` 避开系统圆角区。

**数据安全性维度现状：二次确认（文案 + 超时反馈）+ 撤销通道双保险，删除即永久丢失的结构性缺陷已消除 → 100 分。**

### 0.7 第六轮：把「数据稳定性」从 78 推到 90（消除 P1 数据丢失硬伤）

选它的理由：本维度 78 分的主要扣分来自 **§4.1 风险点 1「跨星期更新无事务」**——`detail.ux` 原先用 `deleteCourse` + `insertCourse` 两段写盘实现跨星期移动，若插入失败则课程**永久丢失**（§7.2 P1 #3，数据丢失级）。这是比崩溃更严重的稳定性缺陷，优先消除。

**方案：数据库层新增 `updateCourseAcrossDays`，把"原星期删除 + 新星期插入"合并为一次读 + 一次写盘。**

| # | 位置 | 改动 |
|:--:|:---|:---|
| 1 | `database.js` | 新增 `updateCourseAcrossDaysStorage`：读全表 → 内存删除原星期 id → 内存插入目标星期 → **单次 `saveToStorage` 写回**；导出 `updateCourseAcrossDays`（带 `ensureReady` + 缓存失效） |
| 2 | `detail.ux` `updateCourse` | 跨星期分支由「`deleteCourse` → `insertCourse` 两段」改为「`updateCourseAcrossDays` 一段原子」；同星期更新仍走原 `updateCourse`（本就单写盘，安全） |

**为什么能杜绝丢课**：旧逻辑两段写盘之间若断电 / 存储失败，出现"已删未插"；新逻辑要么整段成功、要么原数据不变（读失败或写失败都 callback 错误且不破坏旧数据），不存在中间态。

**未做（留作下轮）**：§7.3 P3-1「`JSON.parse` 未全量 try/catch」仍属低优先级（P3），本次未批量处理；故数据稳定性记为 **90** 而非满分——剩余风险仅限"存储数据已被外部损坏时个别页面可能崩溃"，不影响正常写入路径。

**数据稳定性维度现状**：跨星期更新原子化，P1 数据丢失硬伤已消除 → 90 分。
