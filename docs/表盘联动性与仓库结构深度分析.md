# Ev课程表 表盘联动性与仓库结构深度分析

> 本文是对 `docs/表盘开发可行性分析（讨论稿）.md` 的**深化**，聚焦两个决定"开发能否正常开展"的关键问题：
> 1. **联动性**：表盘与快应用之间，到底有没有数据通信能力？有的话是什么？
> 2. **仓库结构**：包放一起，还是建独立仓库？
>
> 结论先行：**联动性大概率"不可直连"，但"可绕行"；仓库结构因此必须"独立拆分、契约解耦"。** 开发能开展，但要先认清架构边界，避免在一开始就把力气花在错误的方向上。

---

## 零、一句话结论

| 问题 | 结论 |
|---|---|
| 表盘 ↔ 快应用能否直连通信？ | **不能（无公开通道）**。表盘与快应用是两套隔离的运行时，表盘的数据源只有"系统级数据"（时间/步数/心率/天气等），不含自定义业务数据。 |
| 有没有"可供沟通"的能力？ | 快应用自身有通信能力（`@system.storage` / `system.interconnect` / `$emit`），但这些能力**都在"应用侧"或"应用↔手机"之间**，不覆盖"表盘↔快应用"。 |
| 那还有没有办法联动？ | **有，但都是"绕行"**：①表盘工具自带的"课程表小程序"（数据独立维护）；②手机中转（经 Protobuf/BLE 写入手环，需逆向验证）。 |
| 包放一起还是分开？ | **独立仓库**。表盘与快应用在代码层面无耦合（只有数据契约耦合），共用仓库只会带来工具链冲突与历史污染。 |

---

## 一、先建立"运行形态"模型 —— 理解联动性的钥匙

小米手环上，和本项目相关的产物其实是**三种不同的运行形态**，它们之间**没有统一的通信总线**：

| 形态 | 运行时 | 交付格式 | 数据源能力 | 制作方式 |
|---|---|---|---|---|
| **快应用** | Vela JS 运行时（沙箱） | `.rpk` | 可读 `@system.storage`、可跨设备传、可写文件 | 写代码（JS/UX） |
| **表盘** | 表盘引擎（资源渲染） | `.bin` | **仅系统级数据**：时间/日期/步数/心率/天气/电量等 | 米坛工具"选底包 + 配元素" |
| **手机侧工具** | 手机 App（Zepp Life / 小米运动健康 / AstroBox / 表盘工具） | APK | 通过 **BLE + Protobuf** 与手环通信 | 各自技术栈 |

**核心洞察**：表盘能显示什么，是由**表盘引擎内置的数据槽**决定的，而不是由"表盘自己会读什么"决定的。课程数据是**自定义业务数据**，不在表盘引擎的默认数据槽里——这就是联动困难的根因。

## 二、深度分析：数据通信（联动性）

### 2.1 快应用侧"确实有"的通信能力（已核实）

| 能力 | API | 通信对象 | 对本项目的意义 |
|---|---|---|---|
| 本地键值存储 | `@system.storage` | 应用自身沙箱 | 课程数据 `allCourses_N` 就存在这 |
| 跨设备传输 | `system.interconnect` | **手表 ↔ 手机** | 手表可与手机 App 双向通信（需证书一致） |
| 应用内通信 | `$on` / `$emit` / `$off` | 应用内模块 | 只限单个快应用内部 |
| 文件读写 | `@system.file` | 应用沙箱 | 落盘缓存 |

**注意每一行的"通信对象"**：这四个能力，**没有一个指向"表盘"**。

### 2.2 表盘侧"到底是什么"（已核实，附来源）

- 米坛「表盘自定义工具」的核心能力，据公开资料是**"解析并重建官方表盘"**——即逆向小米官方表盘的 `.bin` 格式，让用户替换背景、元素、布局后再打包。
- 它提供的"课程表小程序""电子书小程序"，本质是**表盘层面的一种特殊模板**（米坛社区已有"小米手环 8 Pro 小程序·课程表"示例帖，标注"请使用表盘自定义工具最新版修改"），**不是快应用，也不是可自由编程的环境**。
- 表盘引擎可渲染的数据，来自**系统级传感器/状态**，官方并未开放"自定义数据注入"接口。

### 2.3 关键隔离边界（推断，依据充分）

| 边界 | 状态 | 依据 |
|---|---|---|
| 快应用 ↔ 快应用 | **隔离** | Vela 官方强调"三重隔离机制保障应用安全" |
| 快应用 ↔ 表盘 | **无公开 IPC** | 官方样例、FAQ、组件文档均无"表盘读快应用"的任何条目 |
| 手表 ↔ 手机 | **可通** | `system.interconnect` 官方样例 + "证书需一致"的 FAQ 说明 |
| 手机 ↔ 手环（底层） | **可通（逆向）** | AstroBox 公开描述"通信协议层直接对接小米 Protobuf 与 Vela 设备体系" |

### 2.4 三条路径的可行性**重评估**（比讨论稿更明确）

| 路径 | 做法 | 可行性 | 数据是否与快应用同源 | 代价 |
|---|---|---|---|---|
| **P1 表盘侧课程表小程序** | 用表盘工具自带"课程表小程序"模板，在表盘侧单独录入/展示课程 | **可行**（已有现成示例） | ❌ 否，需用户在表盘工具里**重复维护**一份课程 | 数据双份，体验割裂 |
| **P2 手机中转写入** | 手机 App（同步器/AstroBox 插件）把课程经 Protobuf 写入手环，表盘读取 | **有条件可行**（需逆向验证表盘是否有可写的数据槽） | ✅ 可能同源（手机侧统一管理数据） | 开发量最大、依赖逆向稳定性 |
| **P3 表盘直读快应用 storage** | 表盘直接读 `allCourses_N` | **不可行**（无任何公开证据支撑） | — | — |

### 2.5 结论与"决定性验证动作"

**联动性结论**：
- **表盘与快应用之间，不存在官方开放的直连通信能力**——这是现状，不是没找到。
- 真正有希望的只有 **P1（独立小程序，数据独立）** 和 **P2（手机中转，需逆向）**。

**决定性验证动作（先做这个，再谈投入）**：
1. 下载米坛「表盘自定义工具」，找到"课程表小程序"入口，**确认它的数据是怎么录入的、存在哪**。
2. 判断：它是"表盘内独立数据"，还是"能读到手机 App 同步的数据"。
3. 只有 P2 能被证实（手机写入 → 表盘显示）时，"与快应用联动"才成立；否则表盘只能作为**独立数据源的课程速览**。

> 一句话：**"表盘显示课程" ≠ "表盘联动快应用"。** 前者大概率能做到，后者大概率做不到。

## 三、深度分析：仓库结构

### 3.1 判断原则

仓库怎么分，取决于**产物之间有没有代码级耦合**，以及**构建/发布是否同步**：

| 判断维度 | 表盘 vs 快应用 的实际情况 |
|---|---|
| 代码耦合 | **无**（两套运行时，无共享代码，只有数据契约） |
| 构建工具链 | **不同**（aiot-toolkit vs 表盘工具） |
| 发布节奏 | **不同**（快应用可随时发版；表盘受工具/机型/固件限制） |
| 交付格式 | **不同**（`.rpk` vs `.bin`，`.bin` 为二进制） |
| 共享内容 | **只有数据契约**（JSON 格式 A） |

**结论**：四个维度都不同、唯一共享的是数据契约 → **独立仓库是必然选择**，共用仓库只会增加耦合而没有收益。

### 3.2 三种方案重评

| 方案 | 结论 | 关键理由 |
|---|---|---|
| A. 并入主仓 | ❌ 不推荐 | 工具链混杂；`.bin` 二进制撑大 git 历史；发布节奏不同步；扩大 `git clean` 事故面 |
| B. 并入同步器仓 | ❌ 不推荐 | 同步器是**手机侧**工具，表盘是**设备侧**资源，形态与运行位置都不同 |
| **C. 独立仓库** | ✅ **推荐** | 职责单一、可独立发布、可独立开源/闭源 |

### 3.3 推荐架构（对应 P1/P2 两条可行路径）

```
                    ┌─────────────────────────┐
                    │   Ev课程表（主仓）        │
                    │   .rpk 快应用            │
                    │   数据写入 allCourses_N  │
                    └───────────┬─────────────┘
                                │ 数据契约（JSON 格式 A，文档化 + 版本号）
                                ▼
┌───────────────────────────────┴──────────────────────────────┐
│                                                                │
│   P1 路径（数据独立）              P2 路径（手机中转）            │
│   ┌─────────────────────┐        ┌─────────────────────┐      │
│   │  表盘仓 ev-watchface │        │  EV 同步器（已有仓） │      │
│   │  .bin 课程表小程序   │        │  手机侧数据导入/中转  │      │
│   │  （数据在表盘侧维护） │        │  经 BLE/Protobuf 写入│      │
│   └─────────────────────┘        └──────────┬──────────┘      │
│                                              ▼                 │
│                                       ┌─────────────────────┐ │
│                                       │  表盘仓 ev-watchface │ │
│                                       │  .bin（读手机写入数据）│ │
│                                       └─────────────────────┘ │
└────────────────────────────────────────────────────────────────┘
```

- **P1 下**：三个仓各自独立，仅共享一份"数据契约文档"。
- **P2 下**：中转逻辑**加在同步器仓**（它本来就是手机侧数据工具），表盘仓保持纯资源仓。

### 3.4 数据契约如何跨仓维护（关键操作项）

1. 把 `docs/import-export-json-format-analysis.md` 的**格式 A** 抽成一份**带版本号的契约文档**（如 `data-contract.md`），三仓共同引用。
2. 契约文档变更走**显式版本号**（如 `v1` → `v2`），任何仓改动字段都要 bump 版本并通知其他仓。
3. 用一份**示例 JSON**（含 7 天、含全部字段）作为"测试金标准"，各仓用它做兼容性校验。
4. 禁止任何一仓"悄悄改字段"，否则会破坏联动（这是数据联动项目最常见的翻车点）。

## 四、对"开发结构"和"能否正常开展"的直接回答

**1. 开发能正常开展吗？—— 能，但要按"三个独立产物 + 契约解耦"来组织。**

- 表盘**可以开发**（通过米坛工具做 `.bin`）；
- 但**不能假设**它能与快应用实时通信——**先做 P1/P2 验证，再决定表盘的定位**；
- 仓库**从一开始就分三个**（主仓 / 同步器仓 / 表盘仓），避免后期拆仓返工。

**2. 最大的两个风险点（决定"开展"的节奏）：**

| 风险 | 影响 | 止损点 |
|---|---|---|
| 表盘无法读任何自定义数据 | 表盘沦为"纯装饰"，价值大打折扣 | PoC 阶段 V3 不通过 → 立即降级为 P1"独立课程小程序"或直接放弃 |
| 手机中转依赖逆向协议 | 小米固件一升级就可能失效 | 评估 AstroBox 是否稳定维护，否则不押注 P2 |

**3. 建议的决策树：**

```
是否要做表盘？
 ├─ 是 → 先做 PoC（1~2 天）
 │       ├─ V3 通过（表盘能读数据）→ 走独立仓，正式开发
 │       └─ V3 不通过
 │            ├─ 接受"数据独立"→ 用 P1 做"课程表小程序"（数据在表盘侧单独维护）
 │            └─ 不接受 → 放弃表盘，把精力放回快应用本体
 └─ 否 → 维持现状
```

## 五、下一步行动清单（按优先级）

1. **【最高】验证表盘工具的"课程表小程序"数据来源**：下载米坛「表盘自定义工具」，实测它是"独立录入"还是"可读外部数据"。这一步直接决定联动是否成立。
2. 调研 **AstroBox 插件 SDK**：确认它能否稳定地把手机侧数据写入手环（P2 的前提），并评估其维护活跃度。
3. 建立**数据契约文档**（格式 A + 版本号 + 示例 JSON），作为三仓协作的公共基础。
4. 若决定推进，**新建独立表盘仓**，先只做一个机型的最小表盘跑通全链路。
