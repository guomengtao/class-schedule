## 三、八条教训（根因是方法论，不是分析能力）

| # | 教训 | 本次的具体体现 | 以后怎么做 |
|:--:|---|---|---|
| 1 | **没有可复现环境就盲改** ⭐ 最致命 | 模拟器上一直能复现，却全程靠用户真机试 | **先在模拟器复现，改到模拟器通过，才允许出包** |
| 2 | **症状没问清就开工** | 第一轮按"打不开/看不见"查了 3 轮布局，真症状是"**重启**"——两者根因域完全不同 | 症状必须先落到"**崩溃 / 阻塞 / 内存 / 视觉**"四类之一，再选方向 |
| 3 | **改不动就砍功能** | `698bbe1` 移除下展面板，把需求删了当修好 | 砍功能必须显式记录为"**已放弃的需求**"，不能算修复 |
| 4 | **信任注释/推测而非代码** | `dicUtil.js` 注释写着"由 onInit `setTimeout` 延迟"，实现却是同步直调；布局类结论全靠静态推算的"高度账" | 结论必须来自**实机/实跑证据**（A/B、日志、落盘），注释一律回代码复核 |

## 五、新方案：隔离副本 + 模拟器优先

### 5.1 为什么隔离

- 正式 `InputMethod.ux` / `chinese-input.ux` 服务**所有屏型**，每次改动都会牵扯方屏（10 Pro）、圆屏；
- 历史教训 #3/#6 表明：**在正式组件上边猜边改，既容易引出新 bug，又无法回滚验证**。

### 5.2 结构

| 新增 | 说明 |
|---|---|
| `src/components/InputMethodLab/InputMethodLab.ux` | 正式组件的**完整副本**，专供实验；可任意重写，零回归风险 |
| `src/pages/input-method-lab/input-method-lab.ux` | 实验页，注册到「实验室工具」分组，从工具菜单进入 |

**原则**：修好之前，正式组件的代码**一行都不动**；模拟器全绿后，再把验证过的改动**逐条**搬回正式组件（每条都能独立 A/B）。

### 5.3 模拟器优先工作流（核心）

```
模拟器复现 → 在 Lab 组件上改 → 模拟器看效果 → 迭代到全绿
        → 出包 → 用户真机 1 次最终验收
```

**硬规则**：**没有在模拟器上通过之前，不出包、不打扰用户。**

### 5.4 减少真机测试次数的机制（当确实需要真机时）

| 机制 | 解决什么 |
|---|---|
| **一页多开关**：把待验证假设做成页内开关（每个假设一个），一次装机可跑 N 项 | 告别"一次只验一个假设"的往返 |
| **结果落盘**：每项测试结果写 `storage`，进页面时先读"上次崩在哪一项" | 重启后日志会丢，落盘才能知道崩点 |
| **版本号显示在页面**：顶部显示 `versionName` | 杜绝"测的不是改的" |
| **默认全关**：进页面时所有开关关闭，用户逐个打开 | 避免一进页面就崩、无法继续测 |
