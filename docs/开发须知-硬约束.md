# 开发须知：不可违反的硬约束

> **读这份文档的时机**：任何要改动「购买 / 激活 / 二维码 / URL 参数」的活，动手前先读完本页。
> **写这份文档的原因**：这些约束在代码里看不出来，只有踩过才知道。反复向每个新会话解释一次，
> 成本远高于写下来。完整背景见 `app-auth/docs/下单转化率腰斩-诊断与方案.md`。

## 一、二维码长度：已经到极限，不是随手能加的

### 现状（实测，非估算）

购买二维码里装的是完整 URL：

```
https://app-auth.gudq.com/go/ev-timetable
  ?deviceId=<32位hex>&m=ap&p=Xiaomi%20Smart%20Band%2010%20Pro
  &o=198145&v=1200&t=band&s=pill-shaped&w=212&h=520&a=2&l=zh&c=t-10-r
```

| 指标 | 实测值 |
|---|---|
| 完整长码长度 | **190 字符** |
| 对应 QR 版本 | **Version 10（53×53 点阵）** |
| Version 10 容量上限（字节模式 / 纠错 M） | 213 字符 |
| **剩余可用余量** | **约 23 字符** |
| 失败场景短码 | 96 字符（压力可忽略） |

### 硬规则

1. **213 字符是硬上限，不是 190。** 超过 213 就跳到 Version 11（61×61），
   在 160px 的屏幕上每一格再小 15%，识别率明显下降。
2. **新增参数必须说明占多少字符。** 23 个字符的余量意味着：
   加两个 10 字符的参数就吃光，加三个就跨档。
3. **成功场景的码最贵，失败场景的码几乎免费。**
   任何新标记优先只加在失败路径上（详见第四节）。
4. **不要用"反正还能扫"来判断。** 用户是在手表小屏上扫手机，不是拿手机扫纸面二维码，
   容错空间比想象的小得多。

### 已经验证过、明确不做的优化

| 想法 | 结论 | 原因 |
|---|---|---|
| 删掉 `m` 参数 | ❌ 不做 | `m` 恒为 `"ap"`（2 字符），删了只省 5 个字符，降不了版本 |
| 删掉 `p` 参数 | ❌ **绝对禁止** | `p` 是唯一机型来源（见第三节） |
| 型号名缩写成短码 | ❌ 不做 | 需维护映射表、改语义、违反向下兼容 |
| 缩短 `s=pill-shaped` | ❌ 不做 | 同上，收益 10 字符不值得 |

## 二、向下兼容：发出去的包改不了

已发布的 `.rpk` 无法远程升级，**老用户手机里那份代码的参数是写死的**。

### 四条红线

1. **只追加，不修改。** 绝不改动既有参数名、顺序、含义，也绝不动
   `AFDIAN_BASE` / `REDEEM_BASE` / `APK_BASE` 三个直链常量。
2. **新参数必须可缺失。** 老包不会发新参数，服务端与统计脚本必须在缺失时退化为旧行为。
3. **`deviceId` 缺失时保持空值，绝不写假 ID。**
   `deviceId=none` 这类写法会被服务端当作真实 `device_full` 入库，
   造成**不可逆**的数据污染（唯一设备数、设备↔订单归因全部失真）。
   也不要额外加 `dn=1` 之类的冗余标记——空值本身已经表达了这个状态。
4. **验证方式不是"看起来对"，是逐字对比。** 拿改动前的文件做基线，
   跑 mock 场景，**剥掉新增部分后必须与旧版逐字一致**。

### 兼容性验证的标准做法

```bash
cp <改动前文件> /tmp/before.js   # 改之前先备份
# 改完写 mock 测试：五场景（成功/fail/模块缺失/deviceId空/双失败）
# 每个场景对比：剥掉新标记后 === 旧版输出
```

注意：`Module._load` 劫持必须**全程保持**，不能在 `try/finally` 里恢复，
否则 `@system.device` 的 mock 不生效，测试会给出假结果（本次已踩过）。

## 三、参数语义：平台实际返回与官方规范不一致

这一节是最容易误判的地方。`docs/激活页面参数升级方案.md` 的设计意图是：

| 参数 | 设计含义 | 设计示例 |
|---|---|---|
| `m` | model，人可读型号名 | `Watch S4` |
| `p` | product，产品代号 | `vela_ws4` |

**但 Vela 真机实际返回值与之不符**（全表统计验证）：

| 参数 | 实际取值 | 取值种类 | 用途 |
|---|---|---|---|
| `m` | **恒为 `"ap"`**（模拟器为 `Emulator-Vela`） | 2 种 | 无区分度 |
| `p` | `Xiaomi Smart Band 10` / `11` / `10 Pro` / `9 Pro` / `9`、`REDMI Watch 6`、`Watch S4` / `S5 eSIM` / `S3` | 6 种 | **唯一机型来源** |
| `deviceId` | 32 位 hex | 每机唯一 | 设备归因主键 |

**教训**：不要按快应用规范文档推断字段语义，必须拿真实数据统计取值分布。
本次就是因为按规范推断，误判「m 与 p 重复」，差点删掉唯一有用的字段。

### 其他参数

| 参数 | 来源 | 示例 | 说明 |
|---|---|---|---|
| `o` | osVersionCode | `198145` | 系统版本号 |
| `v` | platformVersionCode | `1200` | 运行时平台版本 |
| `t` | deviceType | `band` / `watch` | 设备类型，判断能否联网靠它 |
| `s` | screenShape | `pill-shaped` / `rect` / `round` | 屏幕形态 |
| `w` `h` | screenWidth/Height | `212` / `520` | 分辨率 |
| `a` | APILevel | `2` | 平台 API 等级 |
| `l` | language | `zh` | 系统语言 |
| `c` | **渠道位（人工配置）** | `t-10-r` | **不是设备来源**，见下 |

### `c` 参数的重大误区

`c` 是**人工配置的投放位编号**，谁带上都会显示这个值，**不能用来判断用户从哪来**。
初版分析曾用 `c` 前缀 `t-*` 判定「手表扫码占 53%」，实际用真实设备维度重算只有 **24.9%**，
虚高了整整一倍。判据必须是「是否携带型号 / 屏幕 / deviceId」，不是 `c`。

## 四、埋点标记策略：只标失败，不标成功

`src/pages/activation/shared/activation-context.js` 的现行策略：

| 场景 | URL 标记 | 长度影响 |
|---|---|---|
| 取参成功 | **不加任何标记** | 190 → 190，零增长 |
| 取参失败（4 个失败分支） | 追加 `i=f` | 96 字符，无压力 |
| deviceId 缺失 | **不加标记**（保持空值） | 无影响 |

### 两态判据（服务端与统计的唯一口径）

| URL 特征 | 含义 |
|---|---|
| 无 `i` | 新包**取参成功**，或**老包**（老包不发该参数） |
| `i=f` | 新包**明确取参失败** |

**为什么不做三态（曾经加过 `i=1`，已删）**：
成功场景的码最长，多 4 个字符虽不跨版本，但没有实际收益就不该占位。

**代价（已知并接受）**：新包的「成功样本量」无法直接计数，失败率只能近似算：

```
失败率 ≈ i=f 条数 ÷ (带 deviceId 且无 i=f 的条数)   ← 会低估，分母含老包成功样本
```

要精确切分，**发布新包时改 `c` 渠道后缀**（如 `t-10-d` → `t-10-v2`），
用渠道位区分包版本，**零字符成本**。这是与老包分期统计的正确做法。

## 五、新增一个 URL 参数前，必须回答四个问题

| # | 问题 | 不通过则 |
|---|---|---|
| 1 | 服务端能否从**已有参数**推导出这个信息？ | 能推导 → 不加 |
| 2 | 能只加在**失败路径**吗？ | 只能加在成功路径 → 需说明为何值 23 字符余量 |
| 3 | 占多少字符？是否会跨过 213 上限？ | 跨档 → 必须给出降档补偿方案 |
| 4 | 老包没有这个参数时，服务端如何退化？ | 无法退化 → 不允许上线 |

四条都过了，才动代码。**任何一条答不上来，先停下来讨论，不要先写再补。**

## 六、已知的平台坑

| 坑 | 表现 | 处置 |
|---|---|---|
| `device.getInfo()` 返回的 `model` 是常量 `"ap"` | 按规范以为它是型号名，实际无信息量 | 只用 `product` 判断机型 |
| `getInfo` 的 `fail` / 模块缺失原本静默置空 | URL 退化成 `?deviceId=&c=xxx`，与「网页点击」无法区分，且**无痕迹** | 已改为标 `i=f`，失败可见 |
| 手环（Band 系列）无网络能力 | 无法独立上报使用数据 | 只有 Watch S4/S5 等有网机型可能做，尚待探针验证 |
| 二维码在手表小屏扫手机 | 容错空间小于纸面二维码 | 长度按 213 上限卡死 |

## 七、改动前检查清单

- [ ] 读过本页

- [ ] 确认新增内容只追加、不改既有参数
- [ ] 确认成功场景字符数未增长（除非有明确理由）
